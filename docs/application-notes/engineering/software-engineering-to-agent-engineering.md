# 从软件工程化到 Agent 工程化

前端工程化组织页面、资源和交互，后端工程化组织业务逻辑、数据访问和服务运行。Agent 工程化在这些基础上，进一步管理模型上下文、工具执行、任务效果和故障恢复。

## 一、前端工程化

随着页面、交互和依赖增多，前端需要通过组件、模块、构建工具、状态管理和路由组织应用，减少重复代码，明确数据流，并生成可发布的资源。

### 1、组件拆分与复用

组件把页面拆成可以分别维护的部分，例如导航栏、文章列表、编辑表单。组件边界需要明确输入数据、输出事件和内部状态。

博客项目中的文章卡片可以接收标题、封面和摘要，由列表页查询数据。修改卡片样式时不必逐个页面调整，切换数据来源也不必重写卡片。

### 2、模块与打包工具

模块通过导入和导出表达代码依赖。打包工具从入口分析依赖，处理 JavaScript、CSS、图片等资源，生成浏览器可加载的产物。构建过程还可以包含语法转换、压缩和代码分割。

前端工具通常运行在 Node.js 环境中，项目通过依赖配置和脚本执行开发、构建等操作。构建配置决定资源如何处理，依赖版本则影响构建结果能否复现。

### 3、状态管理

状态管理处理数据的归属、共享与更新。弹窗开关通常留在组件内部；登录信息、跨页面共享的数据则需要明确统一的管理位置。

列表、详情和编辑页可能依赖同一份文章数据。修改成功后，需要更新相关视图或使旧缓存失效。状态归属不清，容易导致重复维护、数据不同步和组件相互依赖。

### 4、路由与页面组织

路由把 URL 与页面关联起来，管理动态参数、页面嵌套和导航。文章详情通过文章 ID 定位，分页和筛选条件可以放进 URL，使刷新、分享和返回操作保持一致。

路由守卫可以控制前端导航和登录提示，实际的数据访问权限仍由后端校验。

## 二、后端工程化

后端通过分层与模块管理业务代码，通过日志和异常处理统一排查与响应方式，再根据负载和服务边界引入并发处理及中间件。

### 1、项目分层与 Maven 分模块

项目分层区分接口处理、业务逻辑和数据访问。接口层接收请求与校验参数，业务层处理规则，数据访问层负责持久化操作。

Maven 分模块进一步组织代码、构建和依赖，例如将公共类型、业务服务和启动入口放进不同模块。模块之间需要明确依赖方向，避免循环依赖。分模块不等于拆微服务，多个模块仍可以打包成一个应用部署。

### 2、日志与全局异常处理

日志记录请求经过的步骤和失败位置。请求标识、业务标识和异常堆栈帮助关联问题，密码、密钥等敏感信息则应过滤。

全局异常处理统一接口失败时的响应，区分参数错误、业务条件不满足和内部故障。前端按约定展示提示，服务端保留排查细节，各个接口不必重复拼装错误响应。

### 3、微服务与中间件

微服务按业务边界拆分可独立部署的服务。服务拆分后，需要处理服务发现、入口路由、跨服务调用和故障传播等问题。

注册中心管理服务注册与发现；网关集中处理入口路由、认证和限流等逻辑；消息队列用于异步处理、削峰和解耦。消息重复消费需要幂等处理，消息积压需要排查生产与消费速度，服务调用失败则需要超时和重试策略。

中间件的引入应对应具体需求。消息队列、注册中心和网关同样可以用于 AI 应用中的任务调度、服务发现与模型调用管理。

### 4、并发与运行机制

JUC（Java 并发工具包）提供线程池、锁和并发容器等工具；JVM（Java 虚拟机）涉及内存管理与垃圾回收；NIO（非阻塞 I/O 相关 API）与 Netty 网络框架用于组织网络通信。

调用外部模型接口往往有较长的 I/O 等待，异步处理可以减少等待时对线程等资源的占用。实际并发能力还受连接池、供应商限流、队列长度和超时重试影响，需要根据瓶颈调整并发上限、资源配置与处理方式。

## 三、Agent 工程化

Agent 由模型根据上下文选择工具和下一步动作，同一任务可能走出不同路径。系统需要约束模型输入、控制执行边界，并验证任务结果。用户界面、业务服务和数据库等部分仍沿用前后端工程实践。

### 1、上下文与知识组织

每次调用模型前，需要选择指令、对话历史、业务事实和工具说明。内容过多时，通过筛选、摘要或检索控制输入规模，保留当前任务需要的条件。

RAG（检索增强生成）把检索到的资料提供给模型，需要维护文档解析、索引更新、权限过滤和检索效果。Skill 封装可复用的任务说明及配套资源，系统负责加载时机、执行方式和结果验收。

### 2、工具接入与执行边界

工具需要明确参数、返回结果、错误和副作用。MCP（模型上下文协议）统一工具与资源的接入方式，业务权限和执行约束仍由服务端负责。

Agent 调用发布文章的工具时，服务端需要检查用户权限和发布条件。请求超时后，要确认发布是否已成功，避免重试造成重复操作。模型生成的参数必须经过校验。

### 3、状态持久化与故障恢复

长任务可能修改文件、调用外部接口或等待人工处理。中断后恢复，需要知道已完成的步骤及其结果。

Durable Agent（具备持久可恢复执行能力的 Agent）通过保存任务状态，支持进程重启后的继续执行。外部操作成功、状态尚未保存时，需要查询或对账，再决定是否重试。幂等处理用于避免重复操作产生额外副作用。

消息队列可以参与调度与重试，完整的恢复能力还取决于状态保存、执行恢复和副作用确认。需要通过进程中断、工具超时等故障验证这些机制。

### 4、评测与执行记录

评测使用真实任务检查结果、约束遵守情况和重复运行的成功率。例如，资料问答检查依据是否正确，写操作检查结果是否落库、是否重复执行或越权。原有单元测试和集成测试继续覆盖确定的服务逻辑。

执行记录串起模型输入输出、工具调用、状态变化和失败原因。提示词、工具、模型或框架变化后，用同一批任务比较效果、延迟和成本。

### 5、框架与平台职责

LangChain 提供模型与工具适配等抽象，LangGraph 提供状态编排、检查点等机制，Deep Agents 在这些基础上组织更完整的执行能力。Harness 指围绕模型组织工具、上下文和运行控制的配套机制。

平台仍需负责用户、权限、业务数据、任务验收和部署运行。框架选型与更换应对应明确的能力缺口，并评估迁移成本，通过实际任务与故障恢复测试验证效果。

## 四、结语

前端工程化处理组件、资源和交互，后端工程化处理业务、数据与服务运行，Agent 工程化增加上下文管理、工具约束、任务评测和持久恢复。这些能力共同支撑一个可维护、可验证的应用。

AI coding 可以协助生成页面、接口和工具实现。需求边界、权限约束与验收条件仍需明确，生成的代码也需要经过测试和运行验证。

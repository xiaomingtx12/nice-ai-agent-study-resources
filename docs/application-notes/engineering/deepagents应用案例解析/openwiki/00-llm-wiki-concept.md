# 什么是 LLM Wiki——从检索到编译

读 OpenWiki 的源码之前，先把"LLM Wiki"这个概念本身讲清楚。OpenWiki 的每一个设计决定——为什么有页面队列、为什么有 Claims、为什么每次搜索要重建索引——都只有在理解了这个概念之后才显得自然。

## 普通 RAG 是怎么工作的，毛病在哪

最常见的知识问答方案是检索式 RAG：用户提问，系统把问题变成向量或关键词，从原始文档里检索出最相关的几个片段，拼进提示词，让模型基于这些片段回答。

这个方案解决"从大量文档里找到相关内容"的问题，但它有三个绕不开的毛病。

**每次都重新理解。** 今天问"这个项目的重试逻辑在哪"，模型读几个片段、推理一次；明天再问"重试失败之后会发生什么"，它把几乎同一批片段再读一遍、再推理一次。同样的理解工作反复付费，而且两次的理解未必一致。

**知识不累积。** 上次问答里得出的结论（"重试由 `retry.py` 统一管理，上限 3 次"）不会留下来。下次提问不能站在这个结论上继续，只能从原始文档重新爬。时间越长，系统并不变得更聪明。

**跨文档关联弱。** 检索按片段打分，天然偏爱"这段文本和问题像"，而不是"这几个模块共同构成一条链路"。一个行为分散在配置、实现、调用方三处时，检索很可能只捞回其中一处，模型拼不出完整的图。

一句话：普通 RAG 是**临时检索**，每次都从原始材料现场理解。

## LLM Wiki 的另一条路：主动编译

LLM Wiki 把方向反过来：不是提问的时候才去检索，而是**提前把材料读懂、整理好**。

过程很像人做读书笔记或写百科：

1. 通读资料（源码、文档、对话记录……）；
2. 提取关键实体和概念（一个模块、一条工作流、一个配置主题）；
3. 为每个概念写一页结构化的 Markdown——一个概念一页，外加总结页、对比页；
4. 页面之间用链接互相引用，形成网络。

之后提问时，模型主要读这份已经整理好、交叉引用好的 wiki，而不是回到原始材料里翻。理解工作被**前置且只做一次**，后续所有人复用。

这就是"编译"的含义：原始材料是源码，wiki 是编译产物。普通 RAG 每次解释执行，LLM Wiki 提前编译好，查询时直接运行。

## 三层结构：raw、wiki、schema

一个 LLM Wiki 系统里，数据天然分成三层，各层的读写权限不同。

**raw 层：原始数据。** 仓库源码、抓回来的网页、聊天记录。它是事实的唯一来源，LLM 对它**只读**——可以读它来写 wiki，但绝不改写原始材料。

**wiki 层：编译产物。** LLM 按照 schema 层的规则，从 raw 层编译出来的页面网格。这一层**可以反复重写**：新资料进来时更新已有页面、添加链接、修正旧观点，而不是孤立地新增一堆文件。

**schema 层：编译规则。** 由你（系统设计者）制定，告诉编译器按什么格式、什么规则处理数据：页面分哪几类、每页必须有哪些元数据、什么内容值得单独成页、目录怎么组织。它是提示词、校验 schema 和配置的集合，独立于具体数据。

三层分离的意义和编译器一样：源码（raw）变了，重新编译（wiki 更新）；想改变知识的组织方式，改编译规则（schema），而不是逐页手改。

## 两个特殊文件：index.md 与 log.md

wiki 目录里有两个文件由程序自动维护，不需要人手动整理。

**`index.md`：目录导航。** 列出当前 wiki 有哪些页面、每个目录下有什么。页面增删移动后自动重建，读者（人和 Agent）从这里发现入口。

**`log.md`：审计日志。** 可追加的变更记录——什么时候编译过、动了哪些页。它回答"这份知识是怎么变成现在这样的"。

## git 与知识复利

整个 wiki 目录放进 git。这带来三件事：

- **持久**：wiki 是仓库里的普通文件，不会随着一次会话结束而消失；
- **可回滚**：每次编译是一个 commit，改坏了能退回；
- **可审计**：diff 能看清这次更新到底改了什么。

于是知识开始复利：wiki 越大越准，后续任务起步越快；新资料进来时，AI 更新已有页面、添加链接、修正旧观点，而不是每次孤立存放。旧结论错了，下一次编译会被修正——这是"主动编译"和"临时检索"在时间维度上的根本差别。

## 三种操作：Ingest、Query、Lint

一个完整的 LLM Wiki 系统围绕三种操作构建：

**Ingest（导入与编译）。** 读 raw 层材料，产出或更新 wiki 页面。首次是全量编译，之后是增量：判断哪些原料变了、哪些页面受影响、只重做必要的部分。

**Query（查询与推理）。** 面对具体问题，从 wiki 里找到相关页面读进来。查询不生成内容、不改 wiki，越轻越好。

**Lint（维护）。** 保证 wiki 自身健康：链接没有断、格式符合 schema、目录和实际页面一致、图表能渲染、过时的结论被标记出来。

## OpenWiki 对号入座

OpenWiki 是这套概念的完整工程实现。逐条对照：

| 概念 | OpenWiki 里的实现 |
| --- | --- |
| raw 层 | 仓库源码与测试（code 模式）；连接器抓取的原始数据，存于 `~/.openwiki/connectors/<connector>/raw/`（personal 模式） |
| wiki 层 | 仓库内的 `openwiki/` 目录（code 模式），或 `~/.openwiki/wiki`（personal 模式），纯 Markdown，git 管理 |
| schema 层 | 规划与写作提示词（`src/agent/repository-prompts.ts`）、页面与事实的 Zod 校验（`PlanPageSchema`、`ClaimSchema`）、OKF front matter 规范、用户写在 `openwiki/INSTRUCTIONS.md` 里的项目要求 |
| index.md | 真实存在，由 `src/okf/index-sync.ts` 的 `synchronizeWikiIndexes` 在每次运行收尾时确定性生成，模型不手写 |
| log.md | **保留但当前不写**：OKF 规范把 `log.md` 列为保留文件名，源码里它被排除在概念页之外，但当前版本并不生成它。审计职责由别的文件承担——`.last-update.json`（整轮更新记录）、`.page-manifest.json`（逐页基线）、`.claims/`（证据记录），外加 git 历史 |
| Ingest | `openwiki --init` / `--update`（原生 CLI），或宿主 Agent 的 `openwiki_begin → submit_plan → next_page → submit_page → finish` 生命周期 |
| Query | `openwiki_search`（FTS5 搜索）与 `openwiki_read`（读完整章节）两个只读工具 |
| Lint | 收尾时的确定性五步：mermaid 校验、index 同步、链接校验、证据投影、来源戳记（见 [06](./06-finalize-and-okf.md)） |

有一处值得单独点出：概念里说"新资料进来时更新已有页面、修正旧观点"，OpenWiki 把这句话做成了可执行的机制——每条关键事实（Claim）记录它依据的源码位置和版本，代码变化后程序能精确算出**哪句话的依据变了**，只把相关页面排回工作队列。这是 [04：Grounded Claims](./04-claims.md) 的主题，也是这个项目最有特色的部分。

概念与实现也有故意拉开距离的地方：通用概念里的 schema 层是"你为任意数据定规则"，OpenWiki 把它特化为"代码仓库的知识组织"——页面按架构、概念、工作流、运维等域划分，事实必须能指回 `repo://` 源码引用。读后面的实现时，随时可以回到这张对照表。

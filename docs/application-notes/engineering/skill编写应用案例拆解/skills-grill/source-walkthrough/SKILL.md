# source-walkthrough：源码解析与文章改写

把用户指定的实现写成有源码依据、可独立阅读的解析。分析对象可以是程序，也可以是以 Markdown 指令为主体的 skill 工作流。支持新写文章和改进已有文稿；以本次请求与目标项目的约定决定篇幅、格式和交付位置。

本 skill 自包含，不依赖其他 skill、联网能力或子 agent 工具。使用当前环境可用的文件读取、搜索和编辑工具即可开展；外部实现无法读取时保留证据缺口。

## 一、确定分析对象与交付边界

### 1、先读取已有信息

读取用户指定的源码、文稿，以及目标项目适用的 `AGENTS.md`、`CLAUDE.md` 或写作规范。确认以下信息，已有答案不重复询问：

- 要解释的具体行为或问题，以及读者需要理解到什么程度。
- 作为事实依据的源码位置、版本或提交。
- 输出为会话解释、新增文章，还是改写指定文件。

能够从文件和配置确定的事实自行查明。仅当仍有多个实质不同的分析对象，或写入目标无法确定时，提出一个能消除分歧的问题；继续处理不依赖该答案的部分。

用户只要求解释时在会话中交付；要求新增文章但未指定文件名时，参考相邻页面命名和分类。改写已有文章时保留准确且必要的内容、frontmatter、文件名和稳定链接，除非任务本身要求调整。

### 2、固定源码依据

从真实文件读取项目名和版本；Git 仓库可读取 commit 作为快照标识。检查相关源码是否有未提交修改，不能将工作区内容全部称为该 commit 的原文。存在改动时注明分析基于哪一份内容，按实际读取范围给出结论。版本说明只保留影响所分析实现的信息，不列出无关的未跟踪目录或工作区杂项。

用户指定了版本就以该版本为准，不用其他版本的文档补写实现事实。只有明确比较版本时，才分别记录两份依据。无法确认版本时直接说明，不猜测。

文章中的源码定位使用项目相对路径与真实符号；Markdown 指令使用章节或段落入口，顶层脚本使用顶层流程。分析环境的绝对目录不进入正文，交付消息可提供产物的可点击路径。

这一阶段完成时，应能说明“解释什么、依据哪份实现、结果交付到哪里”。

## 二、沿真实执行关系建立解释

### 1、程序：从输入跟到结果及必要副作用

从用户关心的入口读取实现。需要时查调用方、注册位置、配置和测试，弄清输入来源及真正到达该入口的条件。沿着足以回答问题的路径继续读取：

- **输入与分支**：参数、默认值、前置检查，以及改变结果的条件。
- **数据与状态**：谁创建数据，哪一步修改它，修改后谁读取；局部变量、共享状态、持久文件分别承担什么作用。
- **下游与副作用**：返回值、事件、回调、文件写入或外部请求如何被消费。
- **异常与生命周期**：仅对实际涉及的机制，追踪错误传播、取消、重试、清理和恢复；指出条件、次数或结束位置。

动态调用必须回到实际绑定或分派关系。同步返回、异步回调和后台任务分开解释；函数返回不能自动等同于后台工作完成。查不到的下游实现只能描述其可见接口，不推定其内部行为。

不要为了显得完整穷举无关辅助函数。若某一步只是传递已知数据，可以简述其作用，将源码片段留给真正改变结果的分支。

### 2、skill 工作流：区分发现、指令和工具执行

分析 `SKILL.md`、提示词或其他指令文件时，沿实际文本关系追踪：

- 名称、description 和配置负责什么；哪些行为取决于宿主支持。
- 正文要求模型执行什么，引用材料在什么条件下读取。
- 另一个 skill 是被要求使用，还是仅被推荐给用户；调用前是否有已知输入和依赖。
- 哪些信息只留在会话，哪些写入文件或工作项；后续从哪里恢复。
- 哪些步骤等待用户决定，什么条件表示完成，哪些失败分支未定义。

文字中的“必须”“等待”“并行”是执行约定。只有找到对应程序或宿主实现，才描述为强制校验、原子认领、自动调度或可靠重试。配套脚本单独按程序流程解释，不把它们与 Markdown 指令混成一套函数调用。

### 3、逐项判断证据能支持到哪一步

在当前工作记录中维护关键问题与证据的对应关系即可，不为一次分析额外生成调查日志。每项至少能对应到相对路径、入口、相关分支和结论；仍缺材料的项目保留为未确认。

实现支持代码层面的行为；配置说明在什么条件下启用；测试说明它覆盖的场景和预期。读过测试不等于运行过测试，看到配置也不等于该配置已经在某次运行中生效。

README、注释或设计文档与实现冲突时，说明目标版本的实际行为及冲突。工程推断明确以“据此判断”“如果用于……则需要……”等表达与事实区分。

进入写作前，应能用连贯叙述串起入口、关键处理和结果，并指出用户问题中尚不能确认的部分；不要求所有未知都被消除后才交付已确认内容。

## 三、将证据写成独立可读的正文

### 1、让读者先知道机制解决什么问题

开头直接给出核心行为与适用问题。头部用紧凑信息块或表格保留版本基线、源码相对路径、函数或章节入口，方便读者按需核对。

正文沿调用、数据或状态变化展开，不按目录顺序罗列文件职责。首次出现的专属类、函数或概念，用一句话解释它是什么、解决什么问题；稳定术语如 token、agent、worker、hook 可保留。

存在多个状态载体时说明各自的创建、写入、读取和结束条件；没有持久化就明确它只依赖当前会话或进程。读者应能理解一次正常执行怎样走完，以及用户关心的异常会在哪一步改变结果。

### 2、源码片段只承载必要证据

引用原始实现中的最小相关片段，保留非注释代码的真实写法。片段旁标相对路径和入口；跨段拼接或省略内容明确说明。

原有英文注释译成中文。补充中文注释时标明为解释新增，避免让读者误以为是项目原注释。不要将自行编写的简化代码作为项目实现；业务场景或状态表若用于说明，明确标作示例。

每段源码解释它接收什么、为什么进入这个分支、改变什么、下游怎样使用，以及有关的约束和副作用。不要让读者只看英文摘录或跳回源文件才能理解关键行为。极短入口可完整引用，其余文件按关键逻辑截取。

### 3、取舍必须落在当前实现上

说明设计减少了哪些具体成本，又引入哪些限制。例如引用参考文件减少重复，但要求读取条件清楚；将状态保存在会话中减少文件维护，却不能据此保证换会话恢复。

区分源码已有的异常处理、源码留下的缺口，以及建议补充的能力。没有锁、去重、回滚或完成状态更新时，不从“按顺序调用”推导这些保证。也不要把建议补强项写成项目已实现的功能。

保持短段落和必要的小标题。遵循用户与项目的格式约定；没有其他约定时，中文长文二级标题使用“一、二、”，三级使用“1、2、”，每个二级标题下重新编号。源码块内部的原始标题不改编号。

删除重复结论、空泛质量词和作者查证过程。“我搜索到”“经过验证发现”改成直接说明实现、证据和影响；实际运行方法只有在帮助读者理解或复现行为时才进入正文。

## 四、处理缺失材料与范围变化

| 情况 | 处理 | 交付中保留什么 |
| --- | --- | --- |
| 符号不存在或版本不符 | 核对实际版本、改名和调用入口，不换一份实现冒充 | 已确认依据、无法对应的位置 |
| 下游依赖或宿主实现不可读 | 分析可见接口和约定，停止推断隐藏机制 | 可见行为、证据缺口和影响范围 |
| 代码只有占位或未接入 | 指出实际占位内容及是否被调用 | 当前能做什么、尚未实现什么 |
| 用户改变问题或输出范围 | 重新检查旧证据是否仍适用，调整相关段落 | 新范围内有效的结论 |
| 文稿已有他人修改 | 读取当前内容后做针对性编辑 | 保留与请求无关的修改 |

无法完成全部解释时，交付有依据的部分和具体缺口。不要把未知当错误，也不要把推荐答案当作已确认事实。

## 五、按结果验收并交付

交付前逐项检查：

1. 用户关心的每个问题，都有证据支持的回答或明确的未确认说明。
2. 引用的路径、符号、配置与片段对应同一分析基线；实际未实现、未接入和条件限制没有被省略。
3. 正文能连接输入、关键处理、状态变化和输出；读者不依赖额外打开源码才能理解核心机制。
4. 指令约定、程序行为、运行观察和工程建议没有混用；只做静态阅读时如实说明。
5. 文章的 frontmatter、内部链接、标题层级和代码块完整，移除分析环境目录、重复总结与作者工作记录。

检查按任务所需进行。遵守项目对构建、测试和外部操作的约束；不为证明一篇文章完成而主动运行整个站点构建或执行会产生副作用的源码。用户另行要求运行验证时，使用限定场景并记录实际结果。

只写入当前请求涉及的文稿与必要导航。源码解析不自动包含修复被分析的程序、提交代码或发布。交付消息简述产物位置、主要调整及影响理解的剩余缺口；没有剩余缺口时无需额外列警告。

# triage 与 wayfinder：从外部请求到决策地图

:::info 版本基线

本文分析 GitHub 项目 [`mattpocock/skills`](https://github.com/mattpocock/skills) `v1.2.3`。

:::

## 先看两条需求入口流

`triage` 和 `wayfinder` 都处理尚未进入正常实现流程的工作，但入口对象不同：前者处理已经存在于 Issue tracker 的外部请求，后者处理一个规模过大、路线还看不清的想法。

```text
外部 Issue / PR
      │
      ▼
   /triage
      │  category + state
      ▼
验证 / 补充信息 / 澄清
      │
      ├── agent brief → /implement
      ├── human brief → 人工处理
      ├── needs-info → 等待 reporter
      └── wontfix → 关闭或记录 out-of-scope

模糊且过大的想法
      │
      ▼
  /wayfinder
      │  destination + map
      ▼
 decision tickets + blocking edges
      │
      ▼
 frontier：当前可处理的决策
      │
      ▼
 spec / tickets / implement
```

两者的主要区别如下：

| Skill | 输入 | 主要问题 | 产物 | 状态载体 |
| --- | --- | --- | --- | --- |
| `/triage` | Issue、外部 PR、评论和代码 | 这项请求属于什么类别、目前处于什么处理状态？ | 标签、triage notes、agent brief、关闭结果 | Issue tracker |
| `/wayfinder` | 过大且路线不清的 loose idea | 到达目标前还需要作出哪些决定？ | map、child decision tickets、决策记录 | tracker 上的 Issue 图 |

`triage` 把外部请求变成可以判断和分派的状态。`wayfinder` 把未知工作变成一张逐步消除不确定性的决策地图。前者面向请求生命周期，后者面向复杂工作的认知生命周期。

## `triage`：把外部请求变成可判断状态

### 两种 role 组成一个状态机

`triage/SKILL.md` 先定义两种 category role：

```text
bug          something is broken
enhancement  new feature or improvement
```

再定义五种 state role：

```text
needs-triage      maintainer needs to evaluate
needs-info        waiting on reporter for more information
ready-for-agent   fully specified, ready for an AFK agent
ready-for-human   needs human implementation
wontfix           will not be actioned
```

每个已 triaged 的 Issue 必须恰好带一个 category role 和一个 state role。如果 state role 冲突，Skill 要暂停并请求 maintainer 处理。

这里把“请求是什么”和“请求走到哪一步”分成两个维度。`bug` 与 `enhancement` 描述工作的性质，`needs-info` 与 `ready-for-agent` 描述当前处理状态。两个维度组合后，查询可以表达“等待补充信息的 bug”和“已经准备交给 agent 的 enhancement”，不需要把所有组合编码成一组越来越长的单一状态名称。

实际 tracker 使用的 label 字符串可能不同。源码要求由 setup 配置提供映射，Skill 不能根据 canonical role 名称猜测 GitHub、GitLab 或本地 tracker 的真实标签。

### 发现阶段只展示需要维护者判断的请求

当维护者询问“有哪些需要我关注”时，Skill 查询三个桶，并按时间从旧到新展示：

1. 从未打标签的 Issue；
2. 状态为 `needs-triage` 的 Issue；
3. 状态为 `needs-info`，且自上次 triage note 后 reporter 有新活动的 Issue。

每项只给计数和一行摘要，随后让 maintainer 选择具体对象。这个发现入口不自动逐个处理所有 Issue。

如果 tracker 把外部 PR 当作请求面，发现结果会把它们加入这三个桶，并标注 `[PR]` 或 `[issue]`。但 discovery 只包含外部 PR；协作者正在进行的内部 PR 不算 triage 工作。用户明确点名一个 PR 时，作者过滤不再阻止处理。

这条边界同时解决了两个问题：常规查询不会把团队内部正在开发的代码全部拉进 triage，显式请求又不会被发现过滤规则挡住。

### 处理单个 Issue 或 PR 必须先读全上下文

源码规定，处理具体请求时先读取完整 Issue 或 PR：

- 正文；
- 评论；
- labels；
- 作者和日期；
- PR 的 diff。

还要解析过去的 triage notes，避免重复询问已经解决的问题；探索代码库时读取领域 glossary，并遵守相关 ADR。

随后必须做两项代码库检查：

1. **redundancy check（重复能力检查）**：按领域概念搜索已有实现，而不是只搜索 Issue 使用的原词；如果请求已经实现，应判为 already-implemented 的 `wontfix`；
2. **prior rejection check（历史拒绝检查）**：读取 `.out-of-scope/*.md`，找出与请求相似的已拒绝事项。

这两个检查让 triage 先验证请求的事实背景，再决定是否值得进入澄清。只按 Issue 原文搜索容易漏掉已有实现，重复请求也会被错误地送入后续流程。

### 推荐状态后必须等待 maintainer 指示

完成上下文收集后，Skill 要向 maintainer 给出 category 和 state 建议、理由以及与请求相关的代码库摘要。然后等待指示。

```markdown
2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a brief codebase summary relevant to the request — including whether it's already implemented. Wait for direction.
```

推荐阶段不直接修改标签、不关闭 Issue、不启动 grilling。状态改变会影响 tracker 上的其他协作者，maintainer 仍然拥有分类和处理优先级的控制权。

快速 override 是明确例外：如果 maintainer 直接说“把 #42 移到 `ready-for-agent`”，Skill 可以信任这个指令并直接应用 role，但要先确认将要发生的 role 修改、评论和关闭动作。如果没有 grilling 就准备交给 agent，还要询问 maintainer 是否需要写 agent brief。

### 验证决定请求是否真的成立

正常流程在推荐之后进入 verify：

- bug：按照 reporter 的步骤复现；
- PR：检查 diff 是否实现了声称的行为，并运行相关测试或命令；
- 证据不足：报告 failed 或 insufficient detail，这通常支持转入 `needs-info`。

验证结果会改变后续产物的可信度。确认过的 bug 可以写进更强的 agent brief；无法复现的请求不应直接包装成“已确认问题”交给 AFK agent。

如果请求需要补充产品或技术决定，才运行 `/grilling` 和 `/domain-modeling`：逐轮澄清需求，同时更新 `CONTEXT.md` 或 ADR。请求经过验证和必要澄清后，才进入最终状态。

### 每个状态有不同的下游产物

源码把 outcome 细分为四类：

| 结果 | 动作 | 下游 |
| --- | --- | --- |
| `ready-for-agent` | 发布 agent brief | AFK agent 读取 brief 后实现 |
| `ready-for-human` | 发布相同结构的 brief，并写明不能委托的原因 | 人工实现或决策 |
| `needs-info` | 发布 triage notes，列出已确认事实和具体问题 | 等 reporter 回复，再回到 `needs-triage` |
| `wontfix` | 关闭并按原因写评论；被拒绝的 enhancement 记录到 `.out-of-scope/` | 不进入实现 frontier |

`AGENT-BRIEF.md` 负责 durable brief 的结构，`OUT-OF-SCOPE.md` 负责已拒绝需求的知识库。已经实现的请求不写入 `.out-of-scope/`，因为它不是被拒绝的范围，而是当前代码已经覆盖的行为。

无论结果是哪一种，只要 triage 向 Issue tracker 发布评论或 Issue，评论开头都必须带：

```markdown
> *This was generated by AI during triage.*
```

这条声明覆盖 triage 期间的每条 tracker 写入，避免自动生成内容与维护者或 reporter 的原话混淆。

## `wayfinder`：把未知大工作变成 decision map

### 目标先于 ticket

`wayfinder/SKILL.md` 把输入描述成一个“一次 agent session 装不下、路线还被迷雾包住”的 loose idea。它先定义 destination：最终需要找到的是一份 spec、一个待锁定的决定，或者一个原地完成的变更。

```markdown
Wayfinding is about finding that way, not charging at the destination.
```

Wayfinder 默认只做规划。每张 ticket 解决一个决定，地图在路线清楚、没有必须先回答的问题后结束。实现冲动通常表示已经到达地图边缘，应把工作交给后续实现流程；只有 effort 的 Notes 明确允许时，wayfinder 才可以把执行带进地图。

**源码直接证明：**wayfinder 的产物是 decisions，不是 deliverables。它与 `to-tickets` 的 ticket 不同：`to-tickets` 生成可以实现的纵向切片，wayfinder 生成需要先回答的决策问题。

### map 是索引，ticket 保存唯一事实

wayfinder 在 tracker 上创建一个标记为 `wayfinder:map` 的单一 Issue 作为 canonical artifact。它的 child issues 承载具体决定，map 本身只做低分辨率索引：

```markdown
The map is an **index**, not a store. It lists the decisions made and points at the tickets that hold their detail; a decision lives in exactly one place — its ticket, so the map never restates it, only gists it and links.
```

map body 固定包含四个区域：

- `Destination`：到达地图终点的定义；
- `Notes`：领域、每个 session 应查阅的 Skill 和该 effort 的长期偏好；
- `Decisions so far`：已关闭 ticket 的一行摘要和链接；
- `Not yet specified`：属于范围但暂时无法准确写成 ticket 的问题；
- `Out of scope`：已经明确排除的工作。

源码模板实际列出五个二级标题，其中前三个用于路线索引，后两个用于管理未知区域和范围边界。单独保存决定的详细内容，可以避免多个 session 在 map 和 ticket 中同时改写同一条结论。

所有面向人的叙述和 `Decisions so far` 都要引用 ticket name，不使用裸 Issue id、数字或 slug。id 和 URL 仍然保留，但只作为名称内部的链接。这样跨会话阅读地图时，读者先看到决定含义，再看到 tracker 定位信息。

### blocking 和 frontier 让地图可并行推进

每张 child issue 都带一个 `wayfinder:<type>` label，并使用 tracker 原生 dependency relationship 表达阻塞。只有 tracker 没有原生 blocking 能力时，才退回 body convention。

```markdown
A ticket is **unblocked** when every ticket blocking it is closed; the **frontier** is the open, unblocked, unclaimed children — the edge of the known.
```

frontier 同时要求三个条件：ticket 仍然 open、所有 blocker 已关闭、当前没有被其他 session claim。claim 的动作是先把 ticket 分配给正在驱动地图的 dev，再开始任何工作；未分配的 open ticket 才是 unclaimed。

这种 frontier 与前文存在三种同构关系，但对象不同：

- `grilling` frontier：前置决策已经解决、当前可以询问的问题；
- `to-tickets` frontier：前置工作已经完成、当前可以实现的 ticket；
- `wayfinder` frontier：前置决定已经关闭、当前可以由一个 session 认领的决策 ticket。

它们都把依赖关系转换成当前可推进边界，但状态对象分别是问题、交付工作和决定。

### 为什么创建 ticket 后再连 blocker

Chart map 的第四步规定：先创建目前能够明确描述的 child ticket，再在第二遍连接 blocking edges。原因是 Issue 需要先拥有 id，其他 Issue 才能引用它。

```markdown
Create the tickets you can specify now as child issues of the map — then wire blocking edges in a **second pass** (issues need ids before they can reference each other).
```

第二遍完成后，tracker 才能准确显示哪些 ticket 已经进入 frontier，哪些被阻塞。把创建和依赖连接拆成两步，是 tracker 身份生成顺序带来的工程约束，不是额外的流程装饰。

如果某个问题当前还不能写成精确的 question，就放进 `Not yet specified`。源码给出的判断标准是“现在能否清楚表述问题”，不是“现在能否马上回答”。不要把 fog 预先切成 ticket；一个模糊区域在前置决定解决后，可能展开成多张 ticket，也可能不需要 ticket。

`Out of scope` 使用另一条规则：工作已经超出 destination，就不属于 fog。被发现越界的既有 ticket 要关闭，并在 map 的 `Out of scope` 中写下原因；它不会进入 `Decisions so far`，因为后者只记录实际走过的路线。

## 四类 decision ticket

wayfinder 用 `wayfinder:<type>` 区分四类 ticket。每类 ticket 的目的都是解除一个决定的阻塞，只有 `task` 可以做实际操作，但它的完成标准仍是使后续决定可判断。

| 类型 | 参与方式 | 解决什么 | 典型产物 |
| --- | --- | --- | --- |
| `research` | AFK，可由 `/research` subagent 处理 | 外部文档、第三方 API 或本地知识库中的事实问题 | findings，写入临时 `research/<name>` 分支并由 ticket 链接 |
| `prototype` | HITL | 需要具体材料才能讨论的外观或行为问题 | 粗略 outline、stub、UI/logic 原型等 asset |
| `grilling` | HITL | 默认的决策对话 | 经过 `/grilling` 和 `/domain-modeling` 澄清的决定 |
| `task` | HITL 或 AFK | 没有可讨论选择，但需要先完成的手工前置工作 | 访问、迁移、环境事实或操作结果 |

`task` 不能被当作目的地的交付票据。注册账号、准备数据或开通访问权限之所以进入地图，是因为后续决定依赖这些事实；它完成后，后续 ticket 仍需记录决定。

每张 ticket 的 body 只保留一个问题，并控制在一个 fresh agent session 能处理的范围内：

```markdown
## Question

<the decision or investigation this ticket resolves>
```

答案不预先写回 body，而是在 resolution 时记录为评论，关闭 Issue，再把 context pointer 追加到 map 的 `Decisions so far`。过程中产生的 asset 通过链接挂在 Issue 上，不把大段材料复制进地图。

## 两种 wayfinder 运行模式

### Chart the map：一次只负责把路线画出来

用户带着 loose idea 调用 wayfinder 后，流程分六步：

1. 运行 `/grilling` 和 `/domain-modeling`，先确定 destination；
2. 再以 breadth-first 方式探索 frontier，覆盖整个问题空间，而不是沿一个分支深挖；
3. 如果路线已经清楚、规模也能在一个 session 内完成，就不创建 map，停止并询问用户下一步；
4. 创建 `wayfinder:map` Issue，写入 Destination、Notes 和初始 fog；
5. 创建当前能明确描述的 child tickets，第二遍连上 blocking edges；
6. 对刚创建的 `research` tickets 并行启动 `/research` subagent，然后停止，不在 charting session 中解决任何 ticket。

“没有 fog 就不需要地图”的条件很重要。Wayfinder 只为跨上下文的不确定性增加 tracker 状态，简单工作不应为了形式创建一张空 map。

### Work through the map：一次解决一张决定票据

用户可以通过 map URL 或编号进入后续 session，ticket 可选：

1. 只加载 map 的低分辨率索引，不默认读取所有 child ticket；
2. 如果用户指定 ticket，就处理指定对象；否则按 frontier 顺序选择下一张；
3. 先 claim，再读取相关已关闭 ticket 和完整上下文，并调用 Notes 中列出的 Skill；
4. 解决一张 ticket，发布 resolution comment，关闭 Issue，并把一行摘要链接追加到 map；
5. 创建新 ticket、连接依赖、把因当前决定变得清晰的 fog 晋升为新 ticket，或把越界工作移入 Out of scope。

源码规定每个 session 不要解决多于一张 ticket，research ticket 是并行例外。单 ticket 边界让每次会话都能形成可读的决策记录，也减少多 session 同时修改同一张地图时的冲突。

## `triage`、`wayfinder` 与前文工作流的边界

### triage 是外部请求的入口

`triage` 面对的对象已经有 Issue 或 PR 身份。它先判断类别和状态，验证 reporter 的 claim，必要时通过 grilling 补全问题，最终生成 agent brief、human brief、needs-info notes 或关闭结果。

它关注“这个请求现在是否成立、谁可以接手”。它不会把一个已经清楚的 spec 再拆成纵向 tickets，也不会把所有大工作建立成 decision map。

### wayfinder 是未知路线的地图

`wayfinder` 的输入没有稳定的执行路线。它先确定 destination，再探索 fog，创建决定票据，并随着每个决定关闭逐步发现新的问题。

它关注“到达目标前还需要知道什么”。路线清楚后，决策结果可以进入 `to-spec` 或 `to-tickets`；如果某个 ticket 已经变成确定的实现切片，wayfinder 就到了交接边界，不应继续把代码交付藏在地图中。

### to-tickets 是清晰计划的执行拆分

`to-tickets` 面对 spec、plan 或已经讨论清楚的 conversation，生成可独立验证的 tracer-bullet vertical slices。它的 ticket 描述“实现哪一条完整行为路径”，wayfinder ticket 描述“要先解决哪个决定”。

两者都使用 blocking edges 和 frontier，但 ticket 的消费者不同：`to-tickets` 直接服务 `/implement`；wayfinder 先服务未来的规格和计划。把两种 ticket 混写，会让执行者无法判断当前对象是需要回答问题，还是可以开始写代码。

### grilling 与 domain-modeling 提供被调用的能力

wayfinder 不重新实现访谈和领域建模。它通过 `/grilling` 确定 destination 和每张 HITL 决策票据的问题，通过 `/domain-modeling` 维护术语和必要 ADR。`triage` 也只在请求需要澄清时调用这两个 Skill。

这与前文的组合原则一致：入口 Skill 管理状态副作用，通用 Skill 管理能力过程，依赖用 `/skill-name` 表达，不依赖内部文件路径。

## 运行边界与工程代价

| 阶段 | 状态归属 | 主要副作用 | 下游消费者 |
| --- | --- | --- | --- |
| triage discovery | Issue tracker | 查询未分类、待评估和 reporter 新回复的请求 | maintainer |
| triage verify | Issue/PR、代码库和测试环境 | 复现 bug、检查 PR diff、生成证据 | 状态推荐和 brief |
| triage outcome | tracker 和 `.out-of-scope/` | 写评论、改 role、发 brief、关闭 Issue | agent、human 或 reporter |
| wayfinder chart | map Issue 和 child issues | 创建 map、ticket、labels、blocking edges | 后续 wayfinder session |
| wayfinder decision | 已 claim 的 child Issue | 读取关联上下文、执行研究/原型/澄清、写 resolution | map、后续 frontier |
| handoff | spec、tickets 或实现入口 | 把已明确决定交给交付流程 | `/to-spec`、`/to-tickets`、`/implement` |

这套结构减少了三类混乱：

- 外部请求的分类、验证和执行准备混成一次无记录的判断；
- 大型未知工作一开始就按模块或目录预切 ticket；
- 已解决决定、尚未清晰的问题和明确排除的范围混在一个列表。

工程代价也很清楚：

- triage 依赖 tracker 的 role 映射、Issue/PR 查询能力和评论写入权限；
- wayfinder 依赖 child issue、原生 blocking、assignee claim 和跨会话可读的 map；
- 每次决策都需要关闭 ticket、写 resolution 和更新 map，维护成本高于一份聊天记录；
- breadth-first charting 和单 ticket session 会增加交互轮数，但减少大上下文和并行冲突；
- research、prototype 和 HITL task 需要不同的 harness、权限和 artifact 处理方式。

`triage` 的 AI 声明是发布协议的一部分，迁移到不支持评论模板或不允许自动发言的 tracker 时，必须保留同等可见的生成来源标记。`wayfinder` 的 map 是 tracker 上的长期索引，不能只存在当前会话内，否则 frontier 和决定历史无法被其他 session 消费。

## 迁移边界

### 可以采用

- 把请求类别和处理状态拆成两个独立维度；
- 为外部请求定义 needs-triage、needs-info、ready-for-agent、ready-for-human 和 wontfix 等状态语义；
- 在状态改变前先读取完整 Issue/PR、历史 triage notes、代码库和领域上下文；
- 对 bug 做复现，对 PR 检查 diff 和相关测试，再决定是否可交接；
- 用 destination 固定大型工作的 scope，用 map 保存路线摘要，用 child ticket 保存单一决定；
- 用 `Not yet specified` 保存还不能精确成 ticket 的 fog，用 `Out of scope` 保存已经排除的工作；
- 使用原生 blocking、claim 和 frontier 支持跨 session 协作；
- 把 research、prototype、grilling 和 task 区分为不同的决策前置方式。

### 需要改造

- category/state role 必须映射到目标 tracker 的 label 和状态模型；
- 如果 tracker 不支持 PR、child issue、原生 blocking 或 assignee claim，需要设计等价的关系和并发机制；
- Issue/PR 的读取、评论、关闭和附件权限要适配目标系统；
- 没有 `CONTEXT.md`、ADR 或 `/grilling` 的项目，需要提供等价的领域词汇、决策记录和澄清入口；
- 大型工作的 destination、map 和 ticket 可以换成 Linear、GitHub、Markdown 或数据库，但必须保留单一索引、单一决定事实和 frontier 查询；
- research subagent、prototype asset 和 HITL task 要按目标环境的执行能力重新配置。

### 不应照搬

- 不要把所有 Issue 都直接标记为 `ready-for-agent`，跳过复现、重复实现检查和维护者确认；
- 不要让一个 Issue 同时带多个互相冲突的 state role；
- 不要把 `needs-info` 当作永久收件箱，reporter 回复后应重新进入 triage；
- 不要把 wayfinder 的 decision ticket 当成可直接交给实现 agent 的功能 ticket；
- 不要在 destination 尚未确定时预切一整套 ticket；
- 不要把 fog、已决定事项和 out-of-scope 工作放进同一列表；
- 不要让一个 session 自动解决整张地图的多张 ticket，除 research 并行例外；
- 不要把 `task` ticket 当作目的地交付，task 必须服务于解除某个决定的阻塞；
- 不要把 AI 生成的 tracker 评论伪装成维护者原话。

## 编写需求入口与大型规划 Skill 的检查清单

- [ ] 请求类别和处理状态是否使用两个独立维度？
- [ ] 每个请求是否恰好有一个 category role 和一个 state role？
- [ ] discovery 是否只展示真正需要维护者判断的请求，并正确区分外部 PR？
- [ ] 处理具体 Issue/PR 前是否读取正文、评论、labels、作者、日期、diff 和历史 triage notes？
- [ ] 是否按领域概念检查重复实现，并读取历史 out-of-scope 记录？
- [ ] bug 是否先复现，PR 是否检查声称行为和相关测试？
- [ ] 推荐状态后是否等待维护者指示，快速 override 是否明确记录副作用？
- [ ] `ready-for-agent`、`ready-for-human`、`needs-info` 和 `wontfix` 是否分别有清晰产物？
- [ ] 每次 tracker 写入是否带有 AI 生成声明？
- [ ] wayfinder 是否先定义 destination，再固定 scope？
- [ ] map 是否只是索引，具体决定是否只存在于唯一 child ticket？
- [ ] ticket 是否只包含一个现在可以准确表达的决定问题？
- [ ] fog 是否保留在 `Not yet specified`，越界工作是否进入 `Out of scope`？
- [ ] ticket 是否先创建再连接 blocking edges，并使用原生依赖关系？
- [ ] frontier 是否同时检查 open、unblocked 和 unclaimed？
- [ ] claim 是否发生在 ticket 开始处理前？
- [ ] chart map 和 work through map 是否分别限制为“建图不解题”和“一次解决一张 ticket”？
- [ ] research、prototype、grilling、task 是否按 HITL/AFK 和产物差异正确分类？
- [ ] 路线清楚后，是否把决策交给 spec、tickets 和 implement，而不是继续扩张 wayfinder？

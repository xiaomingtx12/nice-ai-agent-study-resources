# 写过 Spring，如何理解 LangChain、LangGraph 和 Deep Agents

如果你用 Spring 写过订单查询、退货申请等业务，接入 Agent 时可以继续复用这些服务。新增的一层负责理解用户的自然语言请求，调用合适的业务能力，再根据返回结果继续处理。

本文用一个假设的售后助手说明这层程序怎样组织：用户询问某笔订单能否退货，确认后提交申请。随着需求增加，再考虑人工审批、失败恢复，以及整理售后材料等长任务。LangChain、LangGraph 和 Deep Agents 会在这些具体问题中逐步出现。

Spring 的接口、组件组合和拦截器经验在这里都有用。下面涉及的 API 来自本系列分析的 Python 实现；Java 业务可以通过 HTTP 等接口提供能力，业务服务与 Agent 程序分别运行。

## 一、已有的 Spring 业务服务怎样供 Agent 使用

### 1、业务规则继续留在 Service 中

假设已有系统提供订单查询、退货条件校验和申请提交三个业务能力。常见的 Spring 实现中，Controller 接收请求，Service 校验订单归属和退货资格，再访问数据库或调用其他服务。

接入售后助手后，可以把这些能力包装成工具。工具需要说明用途、接收哪些参数，以及调用后返回什么结果。例如，订单查询工具接收订单号，在执行时请求已有的订单接口，把查询结果交回 Agent。

这里的工具是 Agent 程序调用业务接口的适配层。订单是否属于当前用户、商品是否允许退货、同一笔申请能否重复提交，仍由业务服务检查。用户身份应来自可信的登录上下文，不能因为模型生成了一个用户 ID 就按该身份执行。

Java 开发者熟悉的业务分层仍然适用：规则在 Service 中维护，工具负责把允许使用的能力接入 Agent。已有 Spring 服务可以继续由原来的容器管理。

### 2、新增的变化是模型参与选择下一步调用

在普通的退货接口中，查询订单、校验资格、写入申请的顺序和条件通常已经写在业务代码里。用户填写表单后，程序沿预定流程执行。

售后助手接收的可能是“上周买的鞋有点小，还能退吗”。模型需要结合当前消息和工具结果提出下一步操作。一条可能的执行路径是：

1. 订单不明确时，助手向用户询问订单号。
2. 模型提出查询订单的工具调用，程序执行工具并返回结果。
3. 模型根据订单信息提出退货条件查询，拿到结果后向用户解释。
4. 用户确认提交后，程序按配置的确认或审批流程放行，再调用申请提交工具。

模型生成的是工具调用请求，实际访问业务系统的仍然是程序。必须执行的权限校验、审批和参数约束，需要由程序保证。工具结果返回后，模型可能继续请求工具，也可能直接回答用户。

LangChain 提供了组织这种“模型提出调用、程序执行工具、结果交回模型”循环的组件与工厂。如果任务只需要固定步骤，原有业务代码或显式编排的流程也可以继续承担它。

## 二、LangChain 怎样把模型和业务工具接起来

### 1、接口经验：统一调用形式，适配不同实现

Java 开发者熟悉面向接口编程：调用方依赖约定，具体实现处理底层差异。Spring 应用依赖数据源接口、通过配置选择连接池实现，就是一个常见例子。

LangChain 的 `langchain-core` 是提供基础抽象的包。其中，`BaseChatModel` 是聊天模型的基础抽象，约定消息输入和模型输出等调用行为；`BaseTool` 是工具的基础抽象，描述工具参数及执行入口。模型集成包适配不同服务商，业务函数可以包装成工具。

在售后助手中，订单接口的地址、HTTP 调用和返回值转换由工具实现处理。上层 Agent 使用工具声明和结果，不必在模型循环里重复编写这些接入逻辑。

这部分可以直接沿用接口与实现的经验。不过，统一接口只减少接入差异。模型的工具选择和参数生成能力仍有区别，更换模型后需要重新验证退货任务的效果。

### 2、组件组合：在入口配置一个可执行的 Agent

LangChain 的 `create_agent()` 是标准 Agent 工厂，接收模型、工具和中间件等配置，构造可执行的 Agent 图。这里的图由模型调用、工具执行等工作单元，以及它们之间的执行关系组成。

放到售后助手里，装配入口需要确定使用哪个模型、开放哪些订单工具、在哪些调用前后加入通用处理。业务工具可以独立维护，装配入口把它们组合起来。

这种组织方式接近你在 Spring 应用配置处集中组合依赖的经验。`create_agent()` 的职责范围较窄：它构造 Agent 执行流程，数据库连接池、HTTP 客户端等资源的创建和关闭仍需应用管理。

还要区分两个时刻：**创建 Agent 时完成装配，调用 Agent 时才开始处理用户任务。** 工厂返回成功，只表示执行结构已经准备好，此时并没有替用户查询订单。

### 3、拦截器经验：在明确的调用位置加入通用处理

Spring MVC 拦截器可以在请求处理前后加入公共逻辑。LangChain 的 Middleware（Agent 中间件）也提供明确的扩展位置，包括生命周期 hook，以及包装模型调用和工具调用的入口。

售后助手可以在这些位置记录工具耗时、调整发给模型的消息，或在提交申请前接入人工审批。这样，订单查询工具可以专注于访问订单服务，模型调用和工具执行中的公共处理由中间件承担。

类比拦截器有助于理解“在哪里介入”。具体能改哪些数据、是否允许重试或改变后续执行，要看 Agent 中间件自身的协议；人工审批还需要下文的状态保存与恢复机制配合。实现细节见 [Agent 工厂装配](./langchain/03-create-agent-assembly.md)和[中间件控制面](./langchain/04-middleware-control-plane.md)。

LangChain 也提供可独立调用的模型、消息和检索等组件。只调用一次模型时，不必先创建 Agent。本文关注的 v1 Agent 工厂则使用 LangGraph 执行模型与工具循环。

## 三、等待审批或执行失败后，LangGraph 怎样接着处理

### 1、一次任务可能跨越多次请求

现在给退货流程增加一个要求：特殊订单提交前，需要人工审核。助手已经查过订单、整理好申请，但审核员可能过一小时才处理。

此时需要保存的是这次任务的进度：已经得到哪些结果、正在等待什么决定、批准后应该继续执行哪一步。Spring 容器管理的对象依赖关系，无法代替这份任务记录。在普通业务系统中，你可能会使用流程表、任务队列或工作流引擎解决类似问题。

LangGraph 为图执行提供状态管理和调度能力。它的 `StateGraph` 是图构造器，用来声明状态、节点和执行关系。节点可以执行模型调用、工具调用或普通业务函数；编译后的图根据执行关系推进任务，并按声明的规则合并状态更新。

使用 LangChain 的标准 Agent 时，工厂已经构造了图。只有在需要自行控制流程结构时，才需要进一步考虑直接使用 LangGraph，例如把固定的资格校验、人工审核和模型分析组织成明确的执行分支。

### 2、检查点保存进度，业务服务保证提交一致性

LangGraph 的 Checkpointer（检查点保存器）用于保存图状态和恢复所需的信息。配置审批中断后，本次图调用可以带着待审核事项返回；审核完成后，应用提交审批结果，再继续这次任务。

这需要应用使用稳定的任务标识，把恢复请求关联到原来的执行历史。LangGraph 使用的 `thread_id` 就承担这一关联作用。若服务重启后还要恢复，检查点必须写入可跨进程读取的持久化存储。

恢复也需要考虑重复执行。例如，退货申请已经在订单系统创建成功，但 Agent 程序还没记下结果就退出了，后续恢复可能再次调用提交接口。业务服务应通过申请标识等方式保证幂等，避免产生两笔申请。

Spring 的数据库事务经验在业务服务内部仍然适用。LangGraph 检查点保存的是图的执行进度，不会自动回滚另一个服务里已经提交的数据库操作。人工中断恢复时，触发中断的节点还可能从入口重新执行，因此放在中断前的外部操作也要考虑重复执行。

对应源码见[检查点与恢复](./langgraph/06-checkpoints-store-and-recovery.md)、[中断与恢复协议](./langgraph/07-interrupts-and-command.md)。阅读时可以带着两个问题：哪些进度已经保存，哪些业务动作可能再次发生。

## 四、任务扩展到整理材料时，Deep Agents 提供什么

### 1、长任务增加了文件、委派和上下文管理需求

如果售后助手只查询订单并提交申请，标准 Agent 配合必要的审批和持久化机制就可以作为起点。现在把任务扩展为“整理这批退货订单的售后材料，核对政策差异，生成处理报告”，需要考虑的事情就更多了。

| 新增需求 | 需要准备的能力 |
| --- | --- |
| 材料较多，需要分步处理 | 记录计划与待办事项，帮助模型跟踪工作 |
| 查询结果和报告草稿需要留存 | 提供文件读写工具，并选择存储方式 |
| 部分订单需要独立分析 | 把子任务委派给子代理，再收集结果 |
| 多轮工具调用使消息历史过长 | 压缩历史或把大段内容移出模型当前输入 |

这些能力可以自行组合。Deep Agents 为这类任务提供现成的工具和策略，减少重复装配工作。围绕模型循环配置的工具、上下文管理和执行约束等配套机制，通常称为 Harness；这里的文件工具、子代理和历史压缩就是其中的具体组成。

### 2、Spring Boot 的经验可以帮助理解“现成组合”

用过 Spring Boot 的开发者，通常熟悉采用框架默认配置、再按应用需求调整的方式。理解 Deep Agents 时，可以借用这一使用经验：先了解默认准备了哪些能力，再决定业务工具、存储方式和执行约束怎样接入。

Deep Agents 的 `create_deep_agent()` 是这套能力的装配入口。它准备工具、提示词和中间件，再调用 LangChain 的 `create_agent()`，底层仍由 LangGraph 执行。各项默认能力及其替换规则由 Deep Agents 的工厂与中间件实现决定。

例如，文件工具提供了读写入口，材料是否能在进程重启后保留仍取决于存储配置；待办工具帮助模型记录计划，计划是否正确、是否全部执行仍需检查。框架提供现成能力之后，业务侧仍要定义报告内容和验收要求。

需要复用领域操作说明时，还可以配置 Skills，即供 Agent 按需读取的任务说明与资源。各项能力的启用条件随版本和配置而变化，具体装配过程见 [Deep Agents 工厂解析](./deepagents/01-create-deep-agent-assembly.md)。

## 五、把生态关系和源码阅读路线放在一起

沿着售后助手的需求，可以把三个框架的职责整理如下：

| 框架 | 在示例中的职责 | 适合从哪里开始使用 |
| --- | --- | --- |
| LangChain | 统一模型和工具的调用方式，构造标准 Agent 循环，接入中间件 | 需要模型根据消息和工具结果继续处理任务时 |
| LangGraph | 推进节点执行、合并状态，配合保存器支持暂停和恢复 | 标准 Agent 已间接使用它；需要自定义流程结构时直接使用 |
| Deep Agents | 在标准 Agent 上组合计划、文件、子代理和上下文管理等能力 | 长任务需要多项配套机制，希望复用现成组合时 |

这三个框架可以按需要组合。Deep Agents 的工厂调用 LangChain，LangChain 的 Agent 工厂构造 LangGraph 图；直接使用 LangGraph 时，也可以在节点中调用 LangChain 的模型或工具组件。

“LangChain”还可能指整个生态，而 `langchain` 和 `langchain-core` 是不同的发布包。LangGraph 复用的是 `langchain-core` 中的基础协议，因此 LangChain Agent 使用 LangGraph、LangGraph 依赖 `langchain-core`，并不构成两个发布包互相依赖的循环。

LangSmith 提供调用追踪、评测等平台能力。例如，排查售后助手为什么选错工具时，可以通过追踪查看模型输入、工具请求和返回结果。使用本地开源框架不要求把 LangSmith 作为执行链中的必经环节。

对刚从 Spring 进入这套生态的读者，建议按 **LangChain → LangGraph → Deep Agents** 入门：从模型怎样使用已有业务能力开始，读到执行与恢复，再看长任务的配套机制。理解分工后，也可以按系列总览从 LangGraph 底层向上追踪封装。

| 栏目入口 | 第一轮阅读主线 | 读完应能解释 |
| --- | --- | --- |
| [LangChain 源码解析](./langchain/index.md) | 00 总览 → 03 工厂装配 → 04 中间件 → 05 消息与状态推进 | 业务工具怎样进入 Agent，一轮模型与工具调用怎样衔接 |
| [LangGraph 源码解析](./langgraph/index.md) | 00 总览 → 01 状态 → 02 编译 → 03 调度 → 04 执行 → 06 检查点 → 07 中断 | 任务执行到哪一步，审批后怎样继续，恢复时哪些操作可能重复 |
| [Deep Agents 源码解析](./deepagents/index.md) | 00 总览 → 01 总装配 → 06 中间件执行，再按需要阅读文件、Skills 和子代理专题 | 默认能力在哪里加入，怎样影响工具、上下文和状态 |

需要补组件基础时，可以阅读[模型、消息与工具](./langchain/02-core-abstractions.md)，以及 [Runnable 与 LCEL](./langchain/01-runnable-and-lcel.md)。Runnable 是统一调用、异步与流式入口的组件接口，LCEL 是组合这些组件的表达方式。

各栏采用独立源码快照：LangChain `1.3.7`、core `1.4.6`，LangGraph `1.2.10`，Deep Agents 声明版本 `0.6.12`。这些版本用于分别分析，不能直接拼成安装组合。具体版本、依赖和证据见 [LangChain 基线](./langchain/source-baseline.md)、[LangGraph 基线](./langgraph/source-baseline.md)、[Deep Agents 基线](./deepagents/source-baseline.md)。

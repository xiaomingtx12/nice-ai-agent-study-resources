# 记忆与上下文：从数据库裁剪到 Store 文件

记忆在总览「共同的功能模块」矩阵的外围四块里，上下文管理是「共同的工程难题」四组之一。这条线的迭代跨度最大：原型里两类记忆都是「拼进提示词的字符串」，现状里短期记忆交给 Checkpointer、长期记忆变成带并发控制和配额的文件系统、上下文进入预算化压缩——三种东西现在有三种完全不同的实现，而它们在原型里是同一种。

> **本篇弧线**
>
> - **初识**：查库加 trim_messages 的短期记忆，拼进提示词的长期记忆
> - **重建**：短期记忆随 Checkpointer 接管，长期记忆重做为 Store 文件
> - **现状**：四类信息分家、前缀稳定、预算化压缩与并发控制

## 一、核心工程问题：四类信息怎么分家

记忆与上下文这条线要回答的工程问题：进入模型上下文的信息有四类（固定规则、本轮输入、压缩摘要、长期记忆），生命周期完全不同——怎么分家管理，让该稳的稳、该新的新、该省的省。三个子问题贯穿全文：

- **前缀稳定与信息新鲜的对冲**。命中供应商提示缓存要求每次输入得到相同前缀，本轮变化的信息又必须进上下文——动静分离（system 固定、本轮选项走用户消息）回答它（第四节）。
- **体积控制**。窗口预算算清楚模型窗口、输出预留与安全余量；超限走自动或主动压缩，媒体归档，摘要本身也计入预算（第四节）。
- **长期记忆是共享资源**。文件式记忆跨会话可读写——乐观锁防并发覆盖、无变化跳过、配额校验，编辑与管理接口在平台手里（第四节）。

暗线是分家本身：原型里两类记忆是同一种东西（拼进提示词的字符串），现状里三种实现对应三种语义——分家的过程就是这条线的全部演进。

## 二、初识：薄记忆层

### 1、短期记忆：查库加裁剪

原型的短期记忆是一个 dataclass（`api/internal/core/memory/token_buffer_memory.py`，节选）：

```python
# 3.调用LangChain继承的trim_messages函数剪切消息列表
return trim_messages(
    messages=prompt_messages,
    max_tokens=max_token_limit,
    token_counter=self.model_instance,
    strategy="last",
    start_on="human",
    end_on="ai",
)
```

每次组装提示词时查 Message 表：取最近若干条（默认 10 条）、过滤掉无答案与异常状态的消息，转成 LangChain 消息后用 `trim_messages` 按 token 上限（默认 2000）从尾部往前裁，保证从人类消息开始、AI 消息结束。会话历史就是数据库里的问答对，没有任何状态机参与。

### 2、长期记忆：拼进系统提示词

长期记忆在 Agent 外围生成：服务层提前产出记忆文本，作为状态字段传入 Agent；`long_term_memory_recall` 节点把它格式化进系统提示词模板的 `long_term_memory` 占位符，并发布一个 LONG_TERM_MEMORY_RECALL 事件供前端展示。记忆的读、写、更新对 Agent 循环完全不可见。

判断：这层设计够课程演示，但两个方向都没有着落——记忆本身没有管理（谁写的、能不能改、并发怎么办），上下文没有预算（裁剪只看条数和 token 上限，不知道模型窗口多大、还剩多少）。

## 三、重建：记忆重做，上下文进入视野

重建与换轨阶段两件事分头演进。短期记忆随 Checkpointer 接管会话状态：LangGraph 的检查点机制保存每步图状态，恢复执行不再依赖重放数据库问答对——短期记忆从「提示词工程」变成了「执行状态管理」。

长期记忆在 DeepAgents 换轨时整个重做：从「一段拼进提示词的文本」改成按账号与应用隔离的文件式记忆，底层用 LangGraph Store（PostgreSQL 后端，`langgraph-checkpoint-postgres==3.0.5`）。上下文预算在模型接入侧成型（第六篇的 `with_context_budget`），本篇看它在记忆与压缩侧的消费。

## 四、现状：文件式记忆与预算化压缩

### 1、四类信息不混用

现状把曾经混在一起的东西拆成四类，各有归属：

| 信息               | 位置                      | 用途                 |
| ------------------ | ------------------------- | -------------------- |
| 固定规则与应用指令 | 构图时生成 system         | 稳定行为             |
| 本轮输入与规划选项 | 用户消息、工具消息        | 当前目标             |
| 当前上下文摘要     | 框架压缩状态与 checkpoint | 用较少上下文延续会话 |
| 长期记忆文件       | 按账号和应用隔离的 Store  | 跨会话按需读取       |

普通总结回答不会自动改变框架上下文，历史摘要也不等于自动写入长期记忆——这四类的边界就是本篇的主线。

规划有两档模式：自动模式由模型按任务复杂度决定是否用 `write_todos` 建立或调整计划；显式模式用提示词要求先建计划再执行主要工作，信息不足时先列澄清事项询问、不编造尚不明确的步骤。显式模式仍是行为约定，不是强制的计划审批流——计划未完成不必然阻止 Agent 自然结束，工具调用过程与计划状态在前端分别展示。

### 2、动静分离：稳定前缀与本轮输入

提示词装配（`build_app_system_prompt`）的固定顺序：

1. 平台规则、任务数据与规划规则；
2. 应用名称、说明与业务指令；
3. 按已启用能力追加的记忆、异步任务、压缩与路径说明。

固定规则置于应用配置之前，能力段按授权追加到末尾——授权集合随应用固定、不随轮次变化，配置不变时同一应用每轮的 system 逐字节相同。工作流里的自动任务是另一种形态：无人工输入、无历史、无记忆的临时执行换用一套精简规则（`ephemeral`），是整体替换而不是参数化拼装。

「避免重复注入」在三个位置各有机制：

- **异步工具说明只进一次**。异步子任务中间件的原生说明只生成一次，提前并入 system（同时纳入压缩计数），中间件自身的追加位置清空——说明不随子任务实例或包装器重复进入请求。
- **本轮选项走用户消息**。新输入复制一条用户消息、在正文前加一个「本轮选项」文本块（只编码规划模式这类任务偏好，刻意不含身份、当前时间等随调用变化的观测字段——它们会把前缀打穿）；公开展示与持久化时剥掉该块保持用户原文；恢复执行不重新装配，旧块不会随恢复二次注入。
- **长期记忆不自动注入**。构图时 `memory=None`，不启用框架的自动文件内容注入，记忆按需读取（第 4 小节）。

缓存命中关心的是最终 token 前缀——每次相同输入得到相同前缀才可能命中供应商提示缓存。这套做法提供的是稳定性条件，不保证命中；排障要看 cached token 实际用量与 system、tools 的指纹。

### 3、体积控制：预算、压缩与归档

预算的算法在模型接入侧（第六篇的 `with_context_budget`：输入限制、总窗口与输出预留取小，再扣约 2% 的安全余量），本节看消费端的三道闸门：

- **调用级快照**。每次模型调用经窗口中间件出一份占用快照：按系统与技能、记忆使用规则、用户消息、助手消息与工具调用、工具返回、工具定义、历史摘要七段估算 token——摘要消息按框架来源标记单独计段；调用前发估算、返回后用供应商真实输入用量与缓存读写回填，估算值不冒充计费事实。
- **固定部分硬门槛**。system 与工具定义合计一旦用尽输入预算，调用直接失败并提示减配或换更大窗口——固定部分每轮都在，超限不能指望压缩历史来救。
- **压缩观测阈值**。按预算的 85% 触发压缩观测（拿不到预算时用 170,000 的缺省观测值）。

压缩分自动与主动两路，共用原生摘要策略与同一套预算，适配层不复制截断算法与消息配对逻辑。自动压缩在构图时启用（有 Checkpointer 才有压缩）；主动 `compact_conversation` 由平台适配层（`ConversationCompactionMiddleware`）补齐三件原生工具没有的事：

1. **同批去重**——检查最近一条 AI 消息的工具调用，同一批多次调用直接拒绝并回错误回执；
2. **媒体卸载**——被压缩区间的内联媒体卸载到后端文件，卸载失败的媒体在摘要里如实声明「需要时请用户重新提供」，不允许声称已读取；
3. **失败收口**——供应商异常翻译成干净的工具错误回执（会话状态保留），不把异常文本与凭证信息带进公开结果。

摘要本身有质检：框架会把摘要生成异常当普通文本返回（如错误提示开头），这类文本被校验拒绝、不替换原上下文；状态里已经存在坏摘要时，下一次调用的快照校验同样会拦下而不是静默继续。有效摘要写回框架状态时带 manual 来源标记。

归档让压缩可回查：被压缩区间的消息原文与媒体卸载到 `/conversation_history/`、`/large_tool_results/` 只读归档，提示词要求按需分段读取、不假设媒体都保存成功——原文不再占上下文，但需要时仍可回查。

「摘要保存了没有」是独立判定：只有已提交的根图 checkpoint 里的摘要状态才算已保存，pending 写入与生成草稿都不算。执行器在每个执行片段首尾各读一次摘要状态，摘要身份（会话、版本、截断点与正文合并的哈希）变化才发「摘要已保存」通知——前端把「摘要生成」（压缩运行）与「摘要保存」（checkpoint 已提交）区分成两个事件，前者完成不代表状态已持久化；摘要响应同时带手动/自动来源与历史是否已归档的标志。

### 4、长期记忆：文件系统而不是提示词插槽

图装配时 `memory=None`，不启用框架的自动文件内容注入；长期记忆通过 `/memories/` 文件路由访问（虚拟路径的路由总表见第九篇），Agent 用 ls、glob、grep 定位、用 read_file 读已知路径，按 preferences、background、experience 三类组织。隔离与配额都有具体数字：Store 命名空间是「平台根前缀 + 账号 + 应用」四段，配额默认单文件 64KB、100 个文件、总量 1MB，条目只存 UTF-8 文本（正文、编码、创建与修改时间）。

Agent 侧的文件读写复用框架原生 Store 后端——文件格式、查找、精确替换都归框架，平台只加业务边界：新建不允许覆盖已有文件；编辑做精确字符串替换，内容未变不落库；写入在同一作用域锁内按最新内容校验配额，并发写不能绕过上限。删除是平台补的工具，运行时从服务端授权的运行上下文解析记忆身份——即使恢复旧 checkpoint，也不能用模型参数或历史状态冒充身份，且只有启用记忆的主 Agent 可用。读取每次只记一条耗时诊断，路径与正文不进日志。

管理接口（编辑、重命名、上传）的核心在并发控制（`internal/core/agent_v2/persistence/agent_memory_repository.py`，节选）：

```python
def operation(base_store: BaseStore) -> AgentMemoryFile:
    """持锁检查冲突和变化，避免无效保存修改时间或覆盖并发编辑。"""
    with memory_file_transaction(base_store, identity.namespace) as store:
        existing = store.get(identity.namespace, old_key)
        self._check_expected(existing, expected_sha256)
        if old_key != key and store.get(identity.namespace, key) is not None:
            raise AgentMemoryConflict("该分类中已有同名记忆，请换一个名称")
        if (
            old_key == key
            and existing is not None
            and existing.value.get("content") == content
        ):
            return self._item_to_entity(existing)
```

顺序是设计过的：先持锁检查冲突（expected_sha256 乐观锁，摘要不符拒绝覆盖，重命名目标重名与原文件已删都拒绝），再判断内容是否相同（相同路径相同正文不重复写 Store、不刷新时间），配额在写入前校验。作用域事务用 PostgreSQL advisory lock 跨进程互斥（锁等待 5 秒上限），内存 Store 用进程锁供本地运行与测试——文件工具与管理接口共享同一把锁、同一套规则，没有旁路。

读取的节奏是按需复用：已知路径直接 read_file，未知位置用 ls、glob、grep 定位；当前上下文里的记忆仍然有效时直接使用，已知发生变化或需要修改时才重读——没有每轮开头的全文注入，也没有自动总结写入。文件保存成功后经 `memory_file_update` 通知页面刷新；通知只在图执行中发布，管理接口走正常响应确认。通知表示文件变了，不代表模型已经用上新内容，文件写入与通知落事件库也不是同一个原子事务。

### 5、去留

记忆存储与压缩策略借框架（LangGraph Store、原生摘要），记忆管理（授权、并发、配额、变更通知）与压缩的触发、观测、回执自持。回看原型，`trim_messages` 那一层并没有被扔掉——它回答的问题「历史放多少进提示词」由 Checkpointer 状态与预算压缩接管；而「长期记忆」这四个字下面长出的东西，是原型时代不存在的完整子系统。

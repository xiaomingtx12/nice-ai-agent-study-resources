# Agent 测评与验收：从没有到证据闭环

这是模块纵线里唯一一个原型完全没有的模块——对象模型新增的五张表里，`agent_evaluation` 是纯平台自建的一张。它的诞生动因写在能力演进里：函数调用时代一轮问答的质量靠人眼就能判断，DeepAgents 任务工作台时代一次执行可能跑几十步、写十几个文件，「执行成功」和「产物做对了」之间的距离大到必须用机制去量。模块对应总览外围的可观测一块，内核则是执行可靠性——验收本质上是给执行结果补一道独立的可信判定。

> **本篇弧线**
>
> - **起点**：原型没有这块，质量观测只有计费口径
> - **定义**：运行成功与验收通过是两个判定，双链分立
> - **机制**：条件认领、Rubric 修订循环、证据约束、候选哈希绑定与终审放行

## 一、核心工程问题：让「验收通过」有哈希背书

测评这条线要回答的工程问题：验收的结论凭什么可信——裁判评的必须是真实发生过的产物，结论必须绑定可回放的证据，而不是模型的一句自我报告。三个子问题贯穿全文：

- **材料真实**。材料从数据库读取、不接受前端提交的答案；候选取自图状态，裁判经无候选参数的 `inspect_candidate` 读取，无法提交更好的答案替换被评对象（第四节）。
- **语义与确定性分离**。程序检查只承担能实际验证的部分（contains、file_exists、json_keys），语义判断交给裁判并受逐字引用与标准全覆盖约束（第四节）。
- **终审门槛**。末轮通过且候选哈希与最终状态一致才放行——图正常结束、裁判说通过、有文件产出，任何一件单独都不够（第四节）。

暗线是这块能力的诞生动因：函数调用时代的问答质量人眼能判，DeepAgents 时代的长任务让「跑完了」与「做对了」的距离必须用机制去量——原型没有这块，正是那条能力边界的证明。

## 二、初识：原型为什么没有这块

原型的质量观测只有计费口径：LLM 节点算 token 与价格，会话页面展示推理轨迹，问答本身没有任何评价机制。课程场景下这不构成缺口——用户自己就是裁判。平台转向任务工作台后缺口出现：长任务的成败不能靠「图正常跑完了」判断，也不该只靠模型的自我报告判断。设计的起点因此定为一条原则：运行成功与验收通过是两个判定，图正常结束、裁判说通过、有文件产出，任何一件单独都不足以放行。

## 三、双链：历史评分与执行验收

测评有两种模式，输入范围与结果依据刻意不同：

| 模式         | 输入与执行范围                                   | 结果依据                                   |
| ------------ | ------------------------------------------------ | ------------------------------------------ |
| 历史回答评分 | 冻结原任务描述、回答与标准；裁判不执行任何工具   | 标准覆盖、原文引用、固定分档               |
| 执行验收     | 冻结草稿模型、提示词与要求；独立图实际执行并修订 | 实际候选、确定性检查、逐项裁判与最终一致性 |

每次重评创建新的 AgentEvaluation 记录，不修改原会话。执行验收使用独立的内存 checkpoint 与状态后端，不接入生产的工具、知识库、Skill、子 Agent、长期记忆或原附件——所以它是受控环境的验收，不是完整生产任务回放，报告必须保留范围说明。

## 四、机制：从认领到放行

### 1、提交与后台生命周期

提交流程（`internal/service/agent_evaluation/agent_evaluation_service.py`）的链路：

1. 校验来源归属与源运行的终态，材料一律从数据库读取，不接受前端提交的答案——裁判评的必须是真实发生过的内容；
2. 幂等身份由账号、应用与 request_id 构成（确定性派生的记录 ID），重复提交时不只看键：已有记录会核对模式、源运行、标准、裁判配置与轮数选项是否全部一致，不一致拒绝——同一幂等键不能悄悄绑定到另一份标准或模型；
3. 提交时即加载并校验裁判连接（执行模式连同冻结的工作模型），配置错误在提交时暴露而不是排队后失败；冻结快照、创建 queued 记录，事务提交之后才向 Celery 投递记录 ID，保证任务不会先跑起来而记录的写入随后失败；投递失败把排队记录收敛为可解释的失败态（记录保留供页面说明原因），队列消息带同一截止时间的过期与软硬超时（执行验收 720/750 秒、历史评分 240/270 秒）；
4. Worker 侧用条件更新争取唯一执行权（`internal/service/agent_evaluation/agent_evaluation_store.py`，节选）：

```python
def claim(self, evaluation_id: UUID) -> AgentEvaluation | None:
    """条件更新争取唯一执行权，重复投递和过期任务都不能再次启动模型。"""
    self.expire_pending(self._query(evaluation_id))
    with self.db.auto_commit():
        claimed = self._active_query(evaluation_id, "queued").update(
            {"status": "running"},
            synchronize_session=False,
        )
    if not claimed:
        return None
```

`UPDATE ... WHERE status='queued'` 的原子性让重复投递自然落空。进度与完成写入都检查运行状态和提交后 15 分钟的截止时间：迟到报告不能覆盖已超时或出错的状态，过期判定不依赖页面轮询。Worker 侧还有一条错误分界：数据库异常原样交回基础设施，不伪装成评分失败；其余执行失败收敛为带说明的 error 状态，已保存的轮次保留。状态语义是刻意的：completed 表示报告生成完毕，不代表内容通过验收。

### 2、历史评分的证据约束

裁判是一次无工具的结构化调用（`agent_evaluation_grader.py`）：系统提示加 Pydantic Schema，任务描述与回答作为用户消息传入，输出经 Pydantic 解析后再与材料核对——结构合法不代表证据真实，两层校验缺一不可。裁判提示词把任务文本与回答定位为待审材料：其中要求改变评分、忽略标准、冒充系统的内容均不构成指令；涉及真实文件、外部事实、代码执行的内容，仅凭回答自称完成不能判通过，必须标记证据不足；suggestion 是给开发者的排查建议，不代表 Agent 已被修改。评分器带版本指纹（evaluator_version），历史报告可追溯到生成它的评分器版本。

解析之后的约束有三层：

- 标准 ID 必须精确覆盖 1 到 N，不能重复、遗漏或自行新增；
- 引用必须是 query 或 answer 中的逐字子串；
- 判定通过的项必须带非空引用。

分档固定：

| 结论                  | 分数         |
| --------------------- | ------------ |
| passed                | 1.0          |
| failed（部分满足）    | 0.5          |
| failed（不满足）      | 0.0          |
| insufficient_evidence | null（弃评） |

弃评存在时总体的 score 与 pass_rate 留空，同时单独给出可评范围的分数、通过率与覆盖率。一条边界同样明确：引用存在只能证明裁判确实引用了材料，不证明回答里关于真实文件、外部事实的自述已经被验证过——那部分交给执行验收。

> 证据不足既不算通过，也不被摊薄成零分。

### 3、隔离执行：一次性图与工具边界

执行验收要回答的问题是「模型实际交付的东西是否达标」。它的隔离不是「换个会话」，是另建一张一次性图（`agent_evaluation_runtime.py`）：工作模型用提交时冻结的草稿模型配置，系统提示词由草稿提示词拼接范围声明与修订指令构成；文件后端是纯内存状态的 StateBackend——临时文件空间只认本次生成的 v2 文本文件，不读历史文件或主机文件；检查点是随任务丢弃的内存实现。Worker 的输入是任务描述加验收要求：标准编号成 C1 到 CN 的 rubric，确定性核验要求以 JSON 附在同一用户消息里。

工具边界是双重约束（`evaluation_tool_middleware.py`）：模型可见的工具列表先被裁剪到白名单（ls、read_file、write_file、edit_file、glob、grep、write_todos），实际工具调用再按名字校验一次——即使模型伪造隐藏工具调用也被拒绝，不能委派默认子 Agent、不能执行命令。执行保护三层限额：模型调用 30、工具调用 50、图递归步数 150，超出按错误终止。

### 4、Rubric 修订循环：取证、核验与放行

修订循环由原生 Rubric 中间件驱动，平台适配层（`internal/core/agent_v2/middleware/evidence_rubric_middleware.py`）只做每轮取证与安全校验，不重写循环本身。一轮的完整节奏：

1. **冻结候选**。工作模型阶段结束（`after_agent` 钩子），适配层从图状态提取本轮候选：回答不能回退到上一轮（遇到当前提问或未完成的工具调用即停），文件格式异常与超限直接报错；候选哈希只覆盖回答与文件内容，不受评分结论或时间戳影响。随后对外报告「评分中」进度。
2. **裁判取证**。裁判提示词规定每轮必须先调用 `inspect_candidate`——该工具不带候选参数，读取的正是本轮冻结的候选，裁判没法提交另一份更好的答案去替换被评材料。程序检查承担能确定验证的部分（contains、file_exists、json_keys，同一候选最多解析一次 JSON），检查结果以 E 编号返回、与裁判的 C 标准编号相互独立；证据对象在构造时就绑定它检查的那个候选。
3. **平台核验**。标准必须精确覆盖 C1 到 CN、本轮证据必须已读取、satisfied 结论不得与程序检查矛盾（检查未全过或回答为空即是矛盾）——任何一条不满足，本轮强制降级为 grader_error 并剥掉修订跳转，既不放行也不再继续修订；裁判失败或框架失败保留原终态，原生错误说明可能含服务端凭证或地址，不落库、换成固定文案，字段超长截断。
4. **记录与下一轮**。EvaluationRound 把裁判的 verdict 与平台核验后的 status 分开保存，报告「修订中」或「已完成」进度；原生循环判定需要修订时，带 gap 的失败项就是给工作模型的修订依据，进入下一轮。进度持久化发生在原生评分回调之外——框架可能吞掉回调异常继续修订，平台不能依赖回调完成落库。

轮数由 max_iterations 限制，第一次评分计入。最终放行是一道复合门槛（`internal/service/agent_evaluation/agent_evaluation_runtime.py`，节选）：

```python
def _execution_result(
    state: dict,
    *,
    rounds: list[EvaluationRound],
    max_iterations: int,
    started_at: float,
) -> dict:
    """只有末轮通过且候选哈希仍与最终状态一致才放行，图正常结束不代表验收通过。"""
    current = candidate_snapshot(state)
    final = rounds[-1] if rounds else None
    accepted = final is not None and final.accepts(current)
    status = final.status if final else "grader_error"
    if status == "satisfied" and not accepted:
        status = "grader_error"
```

`final.accepts(current)` 要求末轮状态为通过、最终回答非空、末轮候选与证据的哈希都等于当前状态的候选哈希、程序检查全过——末轮裁判通过、但产物在裁判之后又变了（修订循环的最后一笔、并发写入），整体降级为 grader_error 而不是放行。报告同时给出 first_pass（一轮即过）与范围声明：验收结论只对冻结配置与临时文件空间成立。

### 5、边界与用量口径

独立执行有硬边界：回答 48,000 字符；最多 50 个文件、合计 96,000 字符，只支持文本文件；file_exists 检查文件存在且非空白，不运行文件内容、不核验程序功能。评分轮数（max_iterations，当前 1 到 5 轮，第一次评分计入）与执行保护（模型调用 30、工具调用 50、图递归步数 150）是三层不同的指标，不能混用。

用量分析独立成服务：从 ConversationTurn 读累计 token、缓存 token、推理 token、调用次数、耗时与价格，概览比较截至当天零点的最近七天与前七天、筛选回答非空的轮次——所以它不是包含失败与空回答的全量成功率，也不是实时仪表；要看供应商单次缓存命中，应看模型调用观测而不是整轮的 cached token 总和。

## 五、去留

测评模块没有原型血统，也没有框架可借——候选取证、证据绑定、条件认领、终审门槛全部自持，借的只有原生 Rubric 的评分修订循环。它身上体现的是平台在 DeepAgents 时代补出的两条工程原则：语义裁判与确定性核验分离，程序只承担能实际验证的部分；每个结论绑定可回放的证据，让「验收通过」这四个字有哈希背书。

原型靠人眼完成的事，最终以证据闭环的形态回到了平台里。

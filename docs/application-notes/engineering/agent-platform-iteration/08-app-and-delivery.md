# 应用与交付：配置版本、多入口与事件流恢复

应用与交付对应总览「共同的功能模块」矩阵里的应用模型与发布多入口两行，外加外围的可观测。这条线是「执行可靠性」那组难题的主战场——流式与断线恢复、幂等与重复执行、暂停与恢复全在这里落地。它也是对照最鲜明的一条：原型的流式是进程内队列加 Redis 停止标志，现状是事件缓冲、快照与水位；变的不是目标（让用户可靠地看到并恢复执行过程），是手段的量级。

> **本篇弧线**
>
> - **初识**：草稿与发布的 App 模型、InvokeFrom 多入口、Redis 停止标志
> - **重建**：配置版本与定义指纹，发布的诚实边界
> - **现状**：四入口统一授权、任务状态机与交互恢复、事件缓冲与快照水位、测评闭环

## 一、核心工程问题：一次执行只有一份可信事实

应用与交付这条线要回答的工程问题：四个入口并发地看同一次执行，怎么保证它有且只有一份可信的事实——不重复启动、暂停后恢复只有一种结果、终态有定论、断线能续上。四个子问题贯穿全文：

- **启动幂等**。会话行锁加部分唯一索引加 `input_message_id` 去重，重复点击与网络重试不产生第二份执行（第四节）。
- **交互恢复幂等**。ask_user 暂停后，答案批次、重复提交与取消请求可能并发到达——表单校验、批次回执与执行权控制保证同一批输入只有一种执行结果、同一执行不被恢复两次、取消与恢复不互相覆盖（第四节）。
- **终态口径**。框架根图结束不等于业务提交成功，终态在结算事务提交后才发布——单次 SSE 推送不是最终事实（第四节）。
- **断线续传**。快照加水位衔接历史与增量，SSE 连接只是观察通道，关闭不等于取消、重连不新建任务（第四节）。

伴生的是入口治理：四个入口身份与凭证各异，但会话管理、重复启动、等待输入、取消与结算必须落在共用的执行服务——只在某个 Handler 禁止重复运行，其他入口就绕过了规则。原型「刷新即丢」是全篇的反面教材。

## 二、初识：草稿、入口与停止标志

### 1、应用模型与入口

原型的对象模型已经把交付形态定齐：App 承载应用配置（草稿与发布分离）、Conversation 与 Message 承载会话、API Key 与 End User 分别服务开放 API 和应用终端用户。入口枚举 `InvokeFrom` 区分调试页、WebApp 与助手调用，并贯穿到执行内部——队列管理器用它判定任务归属（`api/internal/core/agent/agents/agent_queue_manager.py`，节选）：

```python
result = redis_client.get(cls.generate_task_belong_cache_key(task_id))
if not result:
    return
user_prefix = "account" if invoke_from in [
    InvokeFrom.WEB_APP, InvokeFrom.DEBUGGER, InvokeFrom.ASSISTANT_AGENT,
] else "end-user"
if result.decode("utf-8") != f"{user_prefix}-{str(user_id)}":
    return
redis_client.setex(cls.generate_task_stopped_cache_key(task_id), 600, 1)
```

停止一个运行任务的链路是：查 Redis 里的任务归属键，按入口算出请求者前缀，前缀不符直接拒绝——终端用户停不掉账号所有者在调试的任务。归属键在任务启动时写入、1800 秒过期；停止键 600 秒过期，执行侧的监听循环每秒轮询。

### 2、流式的边界

流式输出是线程加进程内队列（第二篇运行时讲过机制），监听循环每 10 秒补 PING 心跳、600 秒超时。这套机制的能力边界就是本篇迭代的起点：事件只存在于当前进程的内存里，页面刷新即丢失，多进程部署下没有恢复手段；「停止」是唯一的跨进程信号，靠的还是 Redis 键而非事件通道。

## 三、重建：配置版本与定义指纹

重建阶段应用模型拆成 AppConfigVersion（草稿与发布历史）与 AppConfig（生产入口引用的配置记录），发布时更新应用指针、重建知识库关联、追加发布历史。发布后的工作流工具化、应用绑定资源的当次校验都在这一层完成。

两个诚实边界值得记录：发布当前由多次独立的 create、update 与 auto_commit 组成，不是一次数据库事务原子完成，中途失败可能留下部分已提交变化；发布配置保存的是能力绑定，不等于对外部 MCP 服务、知识库索引、模型权重做不可变快照。

恢复执行前校验定义指纹——能力配置变了就不盲目接续旧中断，指纹是一致性检查，不是授权的替代品。

## 四、现状：四入口、事件缓冲与测评闭环

### 1、入口统一到一套规则

现状四个入口，身份与配置来源各不相同：

| 入口                 | 身份或凭证                                  | 配置来源               |
| -------------------- | ------------------------------------------- | ---------------------- |
| 平台调试与创建者任务 | 登录 Account                                | 按入口读草稿或相应定义 |
| WebApp               | 发布链接 Token 加应用范围的消费者与会话身份 | 发布配置               |
| 开放 API             | API Key 绑定 Account                        | 发布应用               |
| 内部异步 Protocol    | 绑定账号、父应用与目标应用的短期 HMAC Token | 目标应用发布配置       |

入口先解析可信主体再构造运行身份，浏览器或调用方传来的 account_id、invoke_from 不能覆盖服务端授权结果。会话管理、重复启动、等待输入、取消与结算全部由共用的执行服务处理——只在某个 Handler 禁止重复运行，其他入口就绕过了规则。

内部协议的 Token 载荷含版本、账号、父应用、目标应用与有效期，HMAC-SHA256 签名，传输前移除请求里伪造的内部 Header；签名验证通过后仍要查库确认父子应用与发布状态。

API Key 用密码学随机数生成（`secrets.token_urlsafe(48)`），前缀只作辨识，认证按完整 Key 查库并检查启用状态；当前保存的是可直接匹配的完整值，只存哈希与自动轮换是待改进项而不是现状。

### 2、在线配置：校验、保存与版本

「在线配置模型、规划、工具、Skills、子代理」落到代码是一条固定的保存链（`internal/service/app/app_config_service.py`）：

1. Handler 解析请求并校验字段格式；
2. 查询所有被引用的工具、Workflow、Dataset、Skill 与模型连接；
3. 验证资源属于当前账号、未被禁用、数量在上限内；
4. 对 JSONB 配置补齐默认值并生成规范化结构；
5. 在一个事务中更新草稿与更新时间；
6. 发布时复制配置、更新应用指针与绑定、追加递增的历史版本——这一步当前跨多次事务，不是原子发布。

草稿与发布的分离对应两类读取者：调试用草稿定义，生产入口（WebApp、开放 API、内部协议）用发布定义；运行装配读取当次有效配置，恢复前校验定义指纹。保留版本的理由是可追溯——没有版本快照，就回答不了「这次回答用了哪个提示词、哪个模型、哪一版知识库」，第十篇测评冻结的正是这类依据。

### 3、任务状态机、执行权与终态时序

执行侧的四对象模型（Conversation、ConversationTurn、AgentExecution、executor_id）与 `start_run` 的幂等设计在第二篇运行时已展开，本篇补齐另一半：状态怎么流转、执行权怎么交接、终态什么时候才算数。

状态机只有一条主线：`running` 进入 `completed`、`failed`、`cancelled` 或 `waiting_input`，`waiting_input` 在答案提交后回到 `running`。三个状态集合各司其职：只有 `running` 是活动状态（持有执行租约），`running` 与 `waiting_input` 都是占用状态（等待输入虽无执行进程，但不允许同会话启动新任务），三个终态一经写入不可再变。取消请求不占状态位——`cancel_requested_at` 是独立的时间戳字段，一条 running 记录可以同时是「已请求取消、尚未收敛」。

数据库给幂等兜了两道底：Conversation 行 `SELECT FOR UPDATE` 把同会话的启动串行化；部分唯一索引保证一个会话最多一个占用中的执行（running 与 waiting_input 都算占用）、一条输入消息只创建一次运行——`input_message_id` 的业务去重之外，索引是第二道保险。

执行权（executor_id）回答「谁有资格写这条 Run」：每个执行片段持有一个新的 executor_id，认领要求原值为空——已被接管或已结算的执行不能再认领；新片段同时清掉上一段的取消请求，上一段的取消不能阻止恢复后的正常开始。事件落库、快照更新与结算都在事务内锁定执行行、核对 executor_id 与活动状态，执行权失效即拒绝写入；结算与孤儿收敛在同一事务把 executor_id 置空，迟到线程的写入被行锁校验统一挡下。

每个执行片段持有独立的资源、取消信号与事件写线程，后台链路是 `_execute_run` 到 `_execute_agent` 再到 `AgentExecutor.execute`；结算前必须排空事件尾批，否则结算状态会先于最后几条事件对客户端可见。执行存活的判定依赖进程内 Tracker——它只能证明「本机没有线程」，多进程部署下不能据此断言运行已死亡；启动与取消入口先收敛孤儿（数据库里占用、本进程却不存活的运行按取消或失败结算，终态与事件同事务提交），共享租约是文档里写明的改进项而不是现状。

:::note 终态的口径
框架根图的结束信号不等于业务提交成功。业务终态在结算事务提交后才形成——结算统一写入答案、用量、耗时、状态与快照，终态事件此后才发布。
:::

lifecycle 事件（preparing、running、waiting_input、completed、failed、cancelled）与单调递增的 sequence 是客户端的观察依据，但单次 SSE 推送不是最终事实，最终状态以状态查询与已持久化事件为准；重连以快照水位衔接后续事件，机制在第 5、6 小节展开。

### 4、交互恢复：ask_user、表单批次与取消协调

暂停不占用线程。模型调用 `ask_user` 工具时，工具把表单定义作为中断值交给框架（`interrupt(form)`），图停在检查点上——没有等待表单的线程，进程重启也不影响暂停事实；该工具只注入主图，子代理不继承提问能力。图流退出后执行器收集全部有效中断，ask_user 抛出的中断在事件层按工具调用标识识别为正常暂停，不当作工具错误发给客户端；结果状态按「错误 > 取消 > 等待输入 > 完成」的优先级判定，只有等待输入才保留中断列表。结算事务把中断写入 `pending_inputs`（中断 ID、命名空间、表单定义），并按「状态快照、每张表单一个 input.requested、生命周期」的顺序生成事件——状态先行让客户端拿到渲染表单所需的快照，生命周期放最后避免客户端先结束订阅而漏掉表单。

表单校验两侧同一套规则，服务端保存的表单是最终依据。批次是全集：提交的答案集合必须等于当前待填的中断 ID 集合，部分作答不构成恢复条件；字段层面拒绝未知字段与隐式类型转换，按控件类型校验长度、数值边界与选项值（选项值与展示标签分离，恢复执行用的是值而不是标签），结构化状态（跳过、暂时无法回答、委托、allow_other 自由补充）只是一种回答方式，不构成敏感操作授权。前端执行同一套字段规则先行提示；恢复时答案按中断标识映射传回框架，`interrupt()` 调用点拿到本表单答案后工具内再校验一遍——同一个表单模型，实时提交与框架恢复共用。

提交幂等由批次身份保证：批次 ID 是中断 ID 集合的哈希，答案值与请求键顺序不影响身份；Submission 表以「执行 + 批次」为主键记录答案与接受的序号，重复提交相同答案返回原回执（同一 Run 与原接受的序号），改变已接受的答案被拒绝——同一批输入永远只有一种执行结果；批次按会话范围查重，迟到的重试不会误交给后来创建的 Run。

恢复是原子认领：先锁会话再锁 Run（与启动同一锁序），校验通过后在同一事务保存答案、追加 `input_history`（已确认问答供后续模型调用使用，不依赖恢复已结束的图）、写入 Submission、分配新执行段并沿用 Run 身份与事件序号；本进程仍有未结束的执行段时直接拒绝（「任务正在保存，请稍后重试」），恢复前再校验定义指纹，能力配置变了就不接续旧中断。

取消协调按对手分三种情况。对已结束的执行：行锁内复查占用状态，取消请求覆盖不了已收敛的终态；重复点击不刷新取消时刻，执行线程只认首次请求。对运行中的执行：先在数据库记账（`cancel_requested_at` 是业务事实），再通知本进程执行线程请求图排空——排空期间仍保存根状态但停止交付新事件，阻塞中的工具能否快速停下取决于工具自身实现；启动与恢复侧在事务前后都重读取消信号，数据库取消记录优先于尚未送达的进程内通知。对等待输入的执行：没有执行线程，直接在同一事务内取消——清空表单、消息置停止、追加终态事件一次提交，重连才看得到一致状态。两条规则防止状态悬空：已取消的执行不可恢复，下一条普通提问按新输入启动（框架对新输入丢弃旧中断调度，不把它当成恢复答案）；用户关闭或暂不填写表单与取消执行是两件事。更新式重启先取消前序并等待收敛（数据库终态与本进程线程都确认，10 秒上限），超时不建新记录，调用方可安全重试。

前端按 state 的 `pending_inputs` 与 input.requested 事件渲染表单，答案按中断 ID 打包成 responses 提交到同一命令入口（同一批次一次提交，重复中断 ID 拒绝）；草稿按会话与中断隔离保存在会话存储，表单定义变化或超过时限不恢复旧答案；等待输入的任务没有活动 SSE，停止走取消接口后重新水合状态以清掉已取消的表单。

### 5、事件通道：投影、实时发布与批量落库

框架原生流经三层转换：Core 消费 LangGraph/DeepAgents 的原生流，识别消息、工具、值更新与框架生命周期，产出的规范化事件只有通道、载荷、框架序号与命名空间，不带业务身份；`agent_protocol` 的投影层（`internal/service/agent_protocol/event_projector.py`）绑定业务身份与编号，投影为公开协议；前端经统一适配器按通道消费。投影不是转发，四类内容在入口就被过滤或改写：

- 根图终态直接丢弃——框架根图结束只代表图退出，业务终态由结算事务另行发布，不抢在结算前通知客户端；
- messages 通道的工具参数增量丢弃——工具参数流属于 tools 通道的载荷，恢复读取也在数据库侧排除同类分片，实时与重放共用同一形状；
- custom 通道走白名单——只有登记过的类型（上下文窗口、上下文压缩、模型进度、记忆文件更新）通过校验后包装为 name/payload，其余忽略，历史重放过同一白名单，不直接信任存储里的任意自定义数据；
- 根图的助手消息开始事件补上稳定 ID（`{turn_id}:assistant`），前端才能把后续增量归到本轮回答。

六条公开通道各管一种载荷：

| 通道            | 载荷                                                            |
| --------------- | --------------------------------------------------------------- |
| messages        | 消息开始、文本增量                                              |
| tools           | 工具开始、参数增量、结果、错误                                  |
| values          | 状态快照、待填表单、提交结果                                    |
| lifecycle       | preparing、running、waiting_input、completed、failed、cancelled |
| custom          | 平台自定义事件                                                  |
| input.requested | 用户输入请求                                                    |

`seq` 表示顺序、事件 ID 表示身份、namespace 区分主图与子图——三个坐标合起来才能定位一条增量。序号在投影器里分配：新 Run 接在会话该入口已持久化的最大序号之后，恢复段沿用本 Run 的 `last_event_sequence`，每条事件递增一次；事件 ID 由 `Run ID:序号` 组成。同一会话同一入口的事件序号跨 Run、跨恢复段单调递增，这是快照与增量能够衔接的前提。

缓冲层（`AgentExecutionEventBuffer`）把「发给浏览器」与「写进数据库」拆成两条速度不同的路径，关键数字：待写队列最多 512 条、持续拥塞时对生产者背压；写线程合批最多 128 条、未满批最多等约 250 毫秒；内存实时尾部保留最近 2048 条供正常订阅，不为每条事件查库。收益是首字延迟与单条提交延迟解耦、有界队列限制内存；代价是进程骤停时已实时展示但未提交的尾部可能丢失。

三条顺序规则合起来保证一致性：

- **先发布后落库**。登记待写队列与发布到实时尾部在同一把锁内完成，写线程不能抢先提交一条尚未发布的事件；反过来订阅者会先看到尚未提交的事件，这由「终态在结算提交后才发布」兜住（第 3 小节终态口径）。
- **实时尾部大于写队列**。尾部 2048 大于待写队列 512，被尾部淘汰的事件必定已经提交——订阅者落后到内存覆盖不到时回数据库一定补得到，不存在两边都没有的空洞。
- **提交成功才推进水位**。写线程在锁外执行数据库提交，期间生产者继续实时发布后续事件；只有提交成功才移除队列前缀并推进 `last_event_sequence`，事件按 `(execution_id, sequence)` 主键追加、冲突即忽略，写线程重试不会插入重复行。

批量落库与快照更新同事务：批次内最新的根图 values 事件更新运行快照（迟到批次的快照不回退已提交状态），事务内锁定执行行校验执行权——执行权失效说明运行已被接管或收敛，旧片段不能再向恢复后的执行串入事件。收尾路径同样收口：运行结束先排空尾批，写失败的批按原顺序补写，补写仍失败才把整轮结算为失败；写线程出错会置错误位并唤醒生产者，后续发布直接抛错，不会静默丢事件。

### 6、断线续传：快照、水位与重连

恢复侧三接口分工：state 进会话拿摘要（短只读事务固定同一数据库快照，问答与运行状态不来自不同时刻），snapshot 拿某个执行的恢复投影与配套水位（增量合并由 `recovery_snapshot.py` 完成），stream 订阅实时变化。

SSE 生成器每轮循环做四件事：

1. 先查内存：活动执行的事件中心按游标读最多 256 条；读不到（订阅者落后超出尾部保留范围，或执行已结束、事件中心已关闭）转数据库；
2. 回库补齐先读终态再扫描事件，游标推进到最后一条已扫描的行——被订阅过滤掉的事件同样推进游标，过滤不会卡住续传；
3. 只发送匹配订阅的公开事件；根图 lifecycle 出现终态或等待输入即结束本次流——等待输入也结束当前 SSE，提交答案后开新连接，序号仍在同一空间继续；
4. 其余情况等待事件中心唤醒或 15 秒心跳；响应外壳只在生成器正常结束时补 `: stream-end` 注释，客户端以注释缺失识别异常断开。

快照不是事件的原文分页：先一次查询固定已提交水位（运行行与问答行同读），再取序号不超过水位的全部事件做合并——content-block-delta 拼回它的 block-start 事件并保留原序号，水位之后到达的增量仍能按块继续追加；values 事件的 messages 字段在数据库侧整段剔除，正文从业务表恢复而不是重放重复聊天历史。快照把大量增量压成可恢复记录、水位衔接后续事件，减少的是重复重放，不是响应体积上限。

服务端兼容标准 SSE 的 `Last-Event-ID` 头，与请求体游标取大者作为续传起点；但前端不走这条捷径，`workbench-sse-fetch` 每次重连都重新申请快照：

- 同一取消信号绑定同一订阅，断线重试沿用首次绑定的 Run，不会串进下一轮执行；
- 重连请求强制 `recovery: snapshot` 并删除游标——网络已收到的字节游标不等于页面已应用的状态游标，两者不能混用；
- 连接层只观察结束注释：EOF 没带 `: stream-end` 就把流转成错误交给 SDK 重试，同时把连接状态标记为恢复中。

快照到达先验证再应用：Run 身份、水位一致（运行摘要的 `last_event_sequence` 等于快照水位）、事件严格递增且不超过水位——残缺响应不能跳过后续事件。随后把快照翻译回 SDK 的事件序列：每个命名空间与节点只重放最后一条消息的组装上下文（恢复事件使用独立 ID，不被 SDK 当作已消费的原始事件过滤），先恢复消息、再应用完整状态、待填表单与当前生命周期，此后实时增量继续追加；更早的回合不走事件重放，直接由状态快照进时间线。

连接与订阅在前端分层：SDK 的会话级订阅是不结束的本地队列，HTTP 连接只属于一次执行——命令被接受才绑定 Run 建立连接；终态先释放本次连接再通知 SDK，避免完成回调紧接着发起下一轮时复用旧连接；页面重进或水合时从状态接口恢复 Run 身份（running 与 waiting_input 才重新绑定），连接状态（连接中、已连接、恢复中、失败）由同一适配器单向上报。

这正是原型「刷新即丢失」边界的现状解法：SSE 连接只是观察通道，关闭连接不自动取消执行，重新连接也不创建新任务；执行进程换机或多进程部署下，订阅者从数据库水位照样续得上。

### 7、可观测与测评

用量结算挂在 Turn 上：执行片段的用量累计进当轮问答，主 Agent 与子 Agent 的模型、工具调用数与 token 用量分别统计，恢复不重复计也不覆盖整轮。

测评是独立闭环：支持历史评分与独立执行验收两种模式，材料与配置冻结防止用后续变化评历史任务；任务认领与超时状态用条件更新保护，避免并发双跑；裁判结论用原文引用与确定性检查约束（候选哈希核验），修订由原生 Rubric 驱动。

运行成功与验收通过是两个判定，数据库状态、框架 checkpoint、供应商计费用量是三个不同事实来源，排障时先确认在看哪一个。这一模块的完整证据闭环独立成篇，见[Agent 测评与验收](./10-agent-evaluation.md)。

### 8、去留

入口适配、协议外壳、事件缓冲与快照恢复、测评闭环全部自持；框架在这条线上只提供原生事件流，投影、缓冲、恢复、结算都是平台层。原型留下的 `InvokeFrom` 枚举演化成四入口的身份体系，Redis 停止标志演化成带归属校验的取消与执行资格（executor_id）——第二节的两个机制没有消失，只是各自长成了系统。

# 应用拆解

这里关心的是**一个项目值得拆的到底是哪一点，以及怎么把它拆透**。

## 栏目分工

| 栏目 | 组织方式 | 主要回答 |
| --- | --- | --- |
| 工程化 | 按项目组织，深入关键模块；覆盖框架、平台、完整应用与基础设施 | 一个具体工程问题怎样被解决，哪些设计值得复用？ |
| [开源项目工程对比](./engineering-comparisons/index.md) | 按工程问题组织，对照不同项目的架构、数据流与故障路径 | 不同实现各承担什么责任、代价和运行约束？ |
| [产品业务](./product/index.md) | 按用户任务组织，支持单产品拆解与同场景比较，目前在建 | 用户怎样完成任务，结果怎样交付，业务价值与采用成本是什么？ |

工程对比已建立选题入口：框架方向计划比较 AgentScope 与 Deep Agents，平台方向计划研究 Coze Studio 与 Dify，质量工具方向计划研究 Coze Loop 与 Langfuse。产品业务已建立场景与证据规划。具体对比和产品案例正文待开展。

一级栏目表示分析视角，项目类型只用于筛选研究对象。例如 Coze Studio 可以同时出现在工程解析、工程对比和产品案例中，但各篇回答不同问题，源码细节通过互链复用。单产品与多产品也不是独立的一级分类：工程对比放在工程问题下，产品对比放在共同的用户任务下。

工程化现有项目路径继续保留，新项目有实质内容时再建目录。项目增多后，可以先在索引中按框架、平台、应用、基础设施分组，不必为了分类迁移全部文章。工程对比与产品业务的计划子目录也在首篇内容落地时创建。

## 新选题放在哪里

| 想回答的问题 | 归属 | 示例 |
| --- | --- | --- |
| 一个项目内部怎样工作，设计代价是什么？ | [工程化](./engineering/index.md) | Coze Studio 的草稿怎样发布为运行版本 |
| 两个项目怎样处理同一个工程问题？ | [开源项目工程对比](./engineering-comparisons/index.md) | Coze Studio 与 Dify 怎样保存工作流版本 |
| 用户怎样完成任务，体验和采用成本怎样？ | [产品业务](./product/index.md) | 用 Coze Studio 与 Dify 交付同一个问答助手 |
| 多个案例反复出现的规律是什么？ | 方法与复盘 | 发布态与编辑态分离适用于哪些 Agent 产品 |
| 一个链接或项目只需要介绍和阅读指引 | 资源导航 | 项目定位、入口和推荐阅读顺序 |

同一个研究过程可以产生多篇内容，但每条证据只在最合适的文章中完整展开。其他文章写结论和影响，并链接到原始分析。

拆解不套一个万能模板。一个能套所有项目的固定结构根本不存在，硬套的结果是每篇都在填一样的字段、说一样的正确废话——同质化就是这么来的。真正的分工是：**人先判断这个项目的价值点在哪，定下这次拆的方向；AI 再沿方向把广度铺满；人验真伪，砍掉铺出来的幻觉再定稿。** 方向是人对着具体项目现定的，不是预先写死的。

## 第一步：人判断这个项目值得拆哪一点

打开源码之前，先答一个问题：**这个项目最值得拆的价值点，落在下面哪一类？** 判断维度是跨项目稳定的，所以这层分类固定，是「人定方向」这一步的工具：

- **工程实现做得好** — 架构分层、某个硬问题的解法、一条别人没做对的边界。（Dify 的插件进程隔离、Claude Code 的主循环属于这类）
- **某个功能 / 交互做得绝** — 一个具体功能或交互体验，做出了别人做不出的效果，值得看它怎么实现。
- **商业模式 / AI 的落点** — 这个项目靠什么挣钱、AI 在业务里具体在哪起作用、把什么成本打没了、护城河在哪。

一个项目可能占不止一类，但**每次只沿一个方向拆**——贪多就回到面面俱到的同质化。选哪一类、为什么值得，这一步 AI 替不了：它没有「什么值得」的品味，全交给它就同质化。

## 第二步：按价值点类型，走对应的拆解骨架

方向定了，问的问题就不一样——拆「工程实现」和拆「商业模式」根本不是同一套问法。骨架**按类型复用，不按项目复用**，这样同类之间能对照、能交叉引用，又不会所有项目长一个样。

**拆工程实现，至少答：**

- 我带来的真实问题，在这个项目里是怎么被解决的
- 最值得拆的是哪一层，撑住了系统的什么能力，抽掉它会怎样
- 源码里最容易误读的边界在哪，为什么会误读
- 想复用到自己项目，前置假设是什么，假设不成立时怎么退化

**拆功能 / 交互，至少答：**

- 这个功能做出了什么别人做不出的效果
- 拆到实现层，它靠哪几处关键设计撑住这个效果
- 换一种实现会在哪里塌掉

**拆商业模式 / AI 落点，至少答：**

- 它靠什么挣钱，AI 在这条业务链里具体在哪个环节起作用
- AI 把什么成本 / 什么环节打没了，因此模式和没有 AI 时有什么本质不同
- 护城河是什么，还是只是暂时领先

## 第三步：AI 沿方向深挖，人验真伪

方向和骨架定好后，读源码、查资料、铺广度这些交给 AI。但 AI 是按概率把最像的东西铺出来，越顺越可能在自信地出错——所以铺完必须由人挑真的、砍幻觉，再定稿入库。这一步省掉，「人保留判断」就是空话。

## 三条底线（每篇都守）

- **不抄 README。** README 讲「项目能做什么」，不讲「为什么这样拆」。每篇至少指明 3 处 README 没写、只有源码才看得出的东西：一个隐藏副作用、一个不成文约定、一个说了却是 stub 的功能。
- **不把源码翻成大白话。** 把 `class X { method Y() }` 翻译成「类 X 有方法 Y」是浪费时间。要指出位置（在骨架哪个节点、为什么放这）、约束（上游依赖谁、下游被谁消费）、代价（这么写放弃了什么）。
- **必须给工程判断。** 结尾要答：哪些值得照搬、哪些借思路但换实现、哪些看着漂亮别碰、什么时候整套不适用。做不到这节，就把笔记留在 commit message 里，不必发出来。

# 应用拆解

这里关心的是另一件事：**带着真实问题去开源项目里看人家怎么解决的**。不是无目的拆解——是先有一个你自己实践里撞到的问题，再带着它去看一份代码、一个跑得起来的生产级系统，回答它怎么解决这个问题、为什么这样拆、哪些边界值得借过来、哪些不值得抄。

## 这一栏现在盯住什么

- 带着真实问题进开源项目，看它怎么解决
- 源码与架构文档的拆解与判断
- 那些能复用到下一次自己动手时的边界条件
- 从一份 README 看不到、只有看代码才能识别的隐性约束

## 第一组沉淀：Dify 架构拆解

[./dify/](./dify/index.md) — 基于 Dify v1.15.0 源码的架构拆解。

这是这一栏第一组系统级沉淀。包含 16 篇正文，从六进程拓扑、应用配置层、Agent 运行时、推理策略、上下文记忆、异步事件、工具注册、模型供给与扩展、RAG 索引/检索、Workflow 引擎、MCP 协议、多租户与安全、可观测性、触发器到实战部署，完整覆盖 Dify 整个工程骨架。

## 第二组沉淀：Claude Code CLI 架构拆解

[./claude-code-cli/](./claude-code-cli/index.md) — 基于 Claude Code CLI（Anthropic 官方命令行工具）的架构拆解。

这是这一栏第二组系统级沉淀。包含 18 篇正文，覆盖六层架构、入口生命周期、Agent 主循环、流式渲染、工具管线、权限安全、上下文装配与压缩、Skill 系统、子 Agent 隔离、Plan 模式、Hook 拦截、人在环路、定时任务、MCP 集成、Worktree 隔离、持久化与可观测性。Claude Code 是闭源商业 CLI，所以正文里的 `src/...` 是逆向恢复的内部模块路径，仅标位置、不可点击。

## 写作标准

- 不只写「这个项目有什么」，要写「它为什么这样拆」
- 不只贴源码片段，要指明这段代码在系统里的位置
- 不只说优点，要写边界、代价、什么时候不适用
- 不抄 README，要把 README 没说清的东西补出来

具体方法论见 [怎么带着真实问题拆一份开源项目](./what-i-want-to-write-here.md)。

## 这里不放什么

- 单条资源的收录说明（这属于「资源导航」）
- 抽象方法论（这属于「方法与复盘」）
- 只贴 README 不做判断的搬运
- 没有源码佐证、只有印象流的项目记录

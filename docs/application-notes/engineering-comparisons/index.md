# 开源项目工程对比

同一个工程问题，不同项目把责任放在哪里、承担哪些成本、留下哪些边界？本栏沿源码回答这些问题，帮助判断哪些实现值得复用，哪些需要改造。

现有「工程化」按项目深入解析，新专栏按问题横向对照。例如，单项目文章解释 Deep Agents 怎样装配上下文压缩；对比文章追问 AgentScope 与 Deep Agents 怎样处理同一份超长工具结果，原文保留在哪里，下一轮模型还能读到什么。

> 当前为专栏规划与选题入口，下列题目均待开展。候选项目不代表已经通过工程质量评审。官方资料核对日期：2026-09-21；正式正文另行固定源码 commit 和依赖版本。

## 收录范围与目录组织

本栏覆盖框架、应用构建平台、完整应用和配套基础设施。框架特性与接入方式只是其中一部分；业务对象怎样建模、编辑配置怎样发布、后台任务怎样调度、数据怎样迁移，同样可以成为主问题。

首批项目配对、文章顺序和最小证据要求见[对比专题路线图](./roadmap.md)。

目录按工程问题组织，项目名放在文章或专题名称中。文章积累后按以下方向分组；当前只保留索引，不预建空目录。

| 计划分组 | 比较内容 | 候选题目，均待验证 |
| --- | --- | --- |
| `architecture/`：整体架构与对象模型 | 系统边界、核心业务对象、模块依赖、服务拆分 | Coze Studio × Dify：编辑中的应用怎样成为可执行版本？ |
| `execution/`：执行与编排 | Agent 循环、工作流、调度、并行、事件流 | AgentScope × Deep Agents：一次任务由谁驱动？ |
| `data-state/`：数据与状态 | 会话、记忆、知识索引、版本、存储与恢复 | 两个知识应用如何处理源文档更新与派生内容失效？ |
| `extensions/`：扩展与集成 | 插件、连接器、模型适配、工具协议 | Coze Studio × Dify：外部能力怎样注册、授权和执行？ |
| `delivery/`：交付与运行治理 | 发布、部署、隔离、租户、迁移、升级与资源管理 | 两个应用平台如何处理配置变更对运行中任务的影响？ |
| `quality/`：观测与质量 | 运行记录、评测任务、数据集、实验与回归 | Coze Loop × Langfuse：一次线上失败怎样进入后续评测？ |

按文章的主要结论选择唯一归属。例如，“发布后运行到底引用哪份配置”主要比较版本与执行对象，放在整体架构；“升级部署怎样兼容旧版本配置”主要比较交付流程，放在交付治理。其他主题通过索引和互链进入，不复制正文。

比较双方不必是整体替代品。框架与平台可以对照同一段恢复机制，但需要列出平台承担的额外责任，避免把业务管理代码的多少当成架构优劣。

## Coze 与其他平台怎样进入选题

Coze 需要落实到具体项目、版本和发行形态。官方资料将 [Coze Studio](https://github.com/coze-dev/coze-studio) 定位为 Agent 与应用的可视化开发工具，列出了工作流、知识库和插件等资源；[Coze Loop](https://github.com/coze-dev/coze-loop) 则聚焦提示词开发、评测和运行观测。两者应分别建立工程解析入口。开源版与在线商业产品也要分别核对功能范围。

- **Coze Studio × Dify**：优先研究业务对象关系、编辑态与运行态、工作流执行、资源引用和插件边界。每个题目先追源码，不预设双方采用相同模型或支持相同能力。
- **Coze Loop × Langfuse**：可研究运行数据采集、查询、评测集与实验之间的关系。[Langfuse 官方仓库](https://github.com/langfuse/langfuse)提供观测与评测的研究入口，具体链路需要逐项验证。
- **完整应用之间**：先选共同任务，例如知识维护、代码修改或客服工单处理，再比较数据流、任务状态、人工接管和结果交付。应用名单随具体选题确定。

这些是研究配对建议，不代表已经完成等价功能测试或源码评审。

## 怎样选择值得拆的项目

优先选择在某个工程问题上有代表性、实现可追溯、能找到验证证据的项目。一个模块做得好，不足以证明整个项目适合生产使用。

| 选择依据 | 要找到的证据 | 对选题的影响 |
| --- | --- | --- |
| 问题有实际约束 | 长任务、并发调用、外部副作用、权限或多租户等具体场景 | 能说清设计是在解决谁的问题 |
| 设计具有代表性 | 关键调用链、模块依赖与状态归属 | 值得独立拆解，并能与另一种实现对照 |
| 实现可核验 | 可固定的源码 commit、依赖、配置与关键测试 | 避免把规划、示例和实际行为混在一起 |
| 故障路径可检查 | 超时、重试、取消、重启、部分成功等分支及测试 | 判断正常演示之外的工程代价 |
| 设计可迁移 | 清楚的接口边界、替换点及接入成本 | 给出照搬、改造或不采用的具体依据 |

Star 数、功能数量和 README 中的生产级宣传可以提供线索，不能替代这些证据。业务效果、性能和可靠性若没有实测，只列为待验证问题。

## 对比角度：从具体场景进入

每篇选择一到两个主问题，追完整条执行路径。下表是选题池，不要求每篇逐项填满。

| 角度 | 共同问题或故障场景 | 源码中重点追什么 | 要形成的判断 |
| --- | --- | --- | --- |
| 架构与运行时 | 一次请求经历多轮模型与工具调用，由谁推进和终止？ | 入口、装配、调度、控制流、模块和进程边界 | 改循环策略需要动哪些层，哪些依赖必须一起引入 |
| 状态、持久化与恢复 | 工具已写入外部系统，进程在保存状态前退出 | 状态所有者、提交时机、恢复入口、重复执行与幂等处理 | 能恢复哪些数据，业务侧还要补哪些一致性保障 |
| 工具、权限与隔离 | 模型请求写文件、执行命令或访问外部服务 | 参数校验、授权、人工确认、执行位置、结果回写 | 权限覆盖哪条路径，隔离由哪个组件落实 |
| 上下文与记忆 | 工具返回过大、历史超限、长期记忆发生更新 | 本轮模型输入、持久状态、摘要、原文存储与重新读取 | 哪些信息会丢失，压缩和持久化各承担什么成本 |
| 多 Agent 协作 | 并行委派中一个子任务超时，主任务被取消 | 派发、父子状态、结果合并、错误传播、取消与资源释放 | 适合哪种任务协作，需补什么治理 |
| 扩展机制与可测试性 | 增加工具、替换存储、插入审批 | 扩展接口、hook 顺序、依赖注入、替身与测试边界 | 扩展能否局部完成，是否依赖内部实现 |
| 流式事件与可观测性 | 前端断开连接，任务仍在运行或需要继续展示 | 事件顺序、关联标识、缓冲、重连和运行记录 | 能还原多少执行过程，接入自己的监控需要改哪里 |
| 测试、评测与回归 | 改动提示词、压缩或调度后如何发现退化？ | 确定性测试、故障注入、任务集、断言和评分实现 | 哪些验证协议正确，哪些衡量任务效果，哪些仍靠人工判断 |
| 部署与资源治理 | 多个会话竞争资源，某个任务持续消耗 token | 并发限制、队列、预算、超时、服务与执行环境生命周期 | 成本在哪一层限制，运维和资源回收由谁负责 |

架构总览也要落到执行路径。以“读资料后写报告”为例，画出请求经过的模块、状态由谁保存、工具在哪个进程执行，再解释一种边界划分如何影响重试、扩展和部署。只并排展示两张模块图，还不足以支撑架构判断。

## 先对齐比较层级

同一场景可以跨项目比较，但必须标出能力属于项目自身、底层依赖、可选组件还是业务补充。不能把整个生态的能力都算到一个 SDK 上，也不能把未配置的可选能力写成不支持。

| 比较对象 | 建议范围 | 范围约束 |
| --- | --- | --- |
| AgentScope 与 Deep Agents | Agent 循环、上下文、工具权限、暂停与继续 | 限定 Python SDK 执行路径；Deep Agents 涉及 LangChain、LangGraph 时继续追到对应依赖 |
| AgentScope、LangChain、Pydantic AI | Agent API、工具契约、扩展接口、测试接入 | 每篇选两个项目和一个共同场景，分别标注可选扩展包 |
| Deep Agents 与 OpenHands Software Agent SDK | 文件与命令执行、长任务、运行状态、执行环境 | 固定 SDK 和工作区配置，明确是否纳入远端服务及其他组件 |
| 应用与平台项目 | 请求生命周期、后台任务、租户边界、运行记录 | 先锁定相近业务负载；Dify 等平台与纯 SDK 只做特定机制对照 |

这些范围依据官方入口初筛：[AgentScope](https://github.com/agentscope-ai/agentscope)、[Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview)、[Pydantic AI](https://github.com/pydantic/pydantic-ai)、[OpenHands Software Agent SDK](https://github.com/OpenHands/software-agent-sdk)。它们用于确定研究对象，具体实现优劣仍需正文中的源码与验证支持。

## 框架方向首组：AgentScope 与 Deep Agents

建议用同一个“读取资料 → 多轮工具调用 → 处理大结果 → 写入前人工确认 → 继续执行”的任务，分四篇展开。首篇先对齐模型、工具契约和存储范围，后续沿用这些约束。

| 顺序 | 计划题目 | 核心问题 |
| --- | --- | --- |
| 1 | AgentScope 与 Deep Agents：一次任务由谁驱动 | 从创建对象到执行循环，中间件在哪里介入，终止由谁决定？ |
| 2 | 超长工具结果进入下一轮之前发生了什么 | 什么时候压缩或移出模型输入，原文能否回查，失败后保留什么？ |
| 3 | 一次写入如何经过权限判断与人工确认 | 哪些参数参与判断，批准对应哪次调用，拒绝与部分批准怎样回到循环？ |
| 4 | 暂停后继续与进程重启后恢复有何差别 | 恢复凭据和待处理调用存在哪里，哪些步骤可能重跑，谁防止重复写入？ |

起步时可从 [AgentScope 核心 Agent 实现](https://github.com/agentscope-ai/agentscope/blob/main/src/agentscope/agent/_agent.py) 与 [Deep Agents 装配入口](https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/graph.py) 追调用链。这些是会变化的主分支链接，正式文章应换成固定 commit。

既有 Deep Agents 笔记可复用阅读线索，但[源码版本与路径约定](../engineering/langchain-series/deepagents/source-baseline.md)记录了快照未锁定 commit、不同章节依赖版本不同等限制。首组比较需要重新建立一组可核验的基线，不能直接拼接现有章节作为同一环境下的结论。

## 后续选题与单项目解析衔接

框架方向优先补充 AgentScope 的单项目调用链解析，再写横向对比；已有 Deep Agents 章节可以直接互链。平台方向可从 Coze Studio × Dify 开始，质量工具方向可从 Coze Loop × Langfuse 开始。这几条路线独立推进，无需等框架系列写完。

Deep Agents × OpenHands Software Agent SDK 可聚焦工作区、命令执行与任务生命周期。Pydantic AI 可作为工具契约、类型校验和测试接入的候选对照。

现有工程化内容可作为以下研究的起点：

- [LangChain 系列](../engineering/langchain-series/index.md)：追踪运行时、Agent 框架和 Harness 的分工。Harness 指模型循环周围的工具、状态、上下文和执行策略组合。
- [Dify](../engineering/dify/index.md)：从应用配置、异步任务、插件和多租户相关章节寻找平台层选题，再选择同类项目对照。
- [OpenWiki](../engineering/deepagents应用案例解析/openwiki/index.md)：检查框架进入具体应用后，还需要补哪些输入约束、文件管理和运行记录。

每篇对比至少要让读者核对四件事：共同场景和版本范围、关键调用与数据流、失败路径及验证证据、采用或改造的条件。源码静态阅读、测试断言和实际运行结果分别标注；缺少证据时明确保留结论。

正文结构随问题变化。可迁移的设计判断积累充分后，再提炼到「方法与复盘」；具体项目的源码证据仍保留在本栏与单项目解析中。

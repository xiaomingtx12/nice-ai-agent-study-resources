# 对比专题路线图

工程对比以“共同问题”为主语。每个专题先建立双方的单项目基线，再选择一条可以对齐的任务路径；没有共同输入、输出或验收条件时，不做功能表格式排名。

## 第一阶段：建立四条基线

| 路线 | 单项目基线 | 第一组对比 | 先回答的问题 |
| --- | --- | --- | --- |
| Agent 框架 | AgentScope、Deep Agents | AgentScope × Deep Agents | 循环控制、上下文、权限确认与恢复分别由哪一层负责？ |
| 应用构建平台 | Coze Studio、Dify | Coze Studio × Dify | 编辑对象怎样发布，运行时引用哪份配置，变更怎样影响已有会话？ |
| 质量基础设施 | Coze Loop、Langfuse | Coze Loop × Langfuse | 一次线上失败怎样被定位、加入数据集并进入回归实验？ |
| 软件 Agent | OpenHands、Deep Agents 或 Claude Code CLI | 按可核验范围选择 | 工作区、命令权限、长任务状态与最终变更怎样交付？ |

Claude Code CLI 属于闭源商业工具，现有内容基于逆向恢复的模块路径。涉及它的对比必须单独标明证据等级，不能与可固定 commit 的开源项目写成同等源码证据。

## 平台专题：Coze Studio × Dify

平台包含编辑器、业务对象、执行引擎和运营管理，不能压缩成“谁的工作流节点更多”。建议依次研究：

1. **对象模型**：Agent、App、Workflow、Knowledge、Plugin 等对象怎样引用，哪些对象能独立发布。
2. **编辑态到运行态**：草稿、版本、发布记录和运行快照怎样关联。
3. **工作流执行**：节点如何调度，变量和中间结果保存在哪里，失败后从哪里恢复。
4. **知识链路**：文件上传后经过哪些处理，更新源文档时哪些派生数据失效。
5. **插件边界**：注册、鉴权、参数校验、执行和结果回传分别由什么组件承担。
6. **租户与部署**：资源归属、凭据隔离、异步任务和升级迁移怎样处理。

一篇只选择其中一条链路。对象模型可以作为总览，后续文章引用它，不重复铺开全量模块。

## 质量专题：Coze Loop × Langfuse × Phoenix × Opik

质量基础设施适合采用“一次坏结果的后续生命周期”作为共同场景：

```text
线上运行产生坏结果
  → 找到对应 Trace 和上下文
  → 标注失败原因
  → 加入数据集
  → 配置评测器
  → 运行新版本实验
  → 比较结果并决定是否发布
```

首篇先选 Coze Loop 与 Langfuse，沿这条路径核对数据对象与调用关系。Phoenix、Opik 在出现明确差异问题后加入专题；四个项目同时铺功能表会稀释源码分析。

可拆选题包括：

- Trace、Span、Observation 等运行对象怎样建模和关联。
- 线上样本怎样进入数据集，是否保留原始输入、输出和环境信息。
- 评测器怎样执行，评分结果怎样绑定到实验、样本和运行版本。
- 提示词、模型或应用版本怎样进入对比，能否复现历史结果。
- 自托管部署中的数据量、查询、保留周期与升级成本。

## 完整应用专题

完整应用应按任务闭环配对。例如软件开发 Agent 的共同任务可以是“读取一个仓库、修改一个缺陷、运行验证、生成可审查变更”。对比时观察：

- 用户怎样提供目标和约束。
- Agent 怎样建立仓库上下文并管理长历史。
- 文件和命令在哪个环境执行，权限怎样限制。
- 失败、超时和人工接管怎样回到任务。
- 最终交付代码、补丁、分支还是拉取请求，谁负责验收。

完整应用可以比较产品流程，也可以比较内部工程链路。前者进入产品业务场景目录，后者进入本栏；两篇共享任务定义和实测材料。

## 对比文章的最小证据包

每篇开始前建立一张证据表：

| 证据 | 最低要求 |
| --- | --- |
| 版本 | 双方仓库 commit、依赖和配置；商业产品记录测试日期与版本信息 |
| 场景 | 相同目标、输入、成功标准和故障条件 |
| 源码 | 双方都追到实际调用、状态变化或配置消费位置 |
| 测试 | 引用相关测试；自行运行时记录环境、步骤和结果 |
| 结论 | 分开写源码事实、测试证明、运行观察和工程判断 |

如果只能核验一方源码，题目应改成“方案 A 的实现及方案 B 的可观察行为”，不能写成对称的源码架构比较。

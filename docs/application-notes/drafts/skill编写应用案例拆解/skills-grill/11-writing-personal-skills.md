# 怎样编写个人 skill：从第一版到持续迭代

:::info 案例依据与阅读入口

本文从 `mattpocock/skills` 的设计中提炼个人编写方法。案例基线为 `package.json` 版本 `1.2.3`、commit `84fdeffd12f2ee307994d1eb6feb48173b6e0502`。路径均相对项目根目录；这些文件是模型指令，入口按真实章节或正文定位。

| 相对路径 | 入口 | 本文借鉴的内容 |
| --- | --- | --- |
| `skills/productivity/writing-for-agents/SKILL.md` | `Context pointers`、`Steps and completion criteria`、`Information hierarchy`、`Pruning` | 触发、步骤、资料组织和修剪 |
| `skills/productivity/to-questionnaire/SKILL.md` | 开头第 1–3 步 | 输入如何变成可检查的产物 |
| `skills/engineering/prototype/SKILL.md` | `Pick a branch` | 按任务问题选择参考文件 |
| `skills/productivity/grilling/SKILL.md` | `Finding _facts_`、`The session is done` 开头的正文段 | 事实调查、用户决定和停止条件 |
| `.agents/invocation.md` | `Model-invoked vs user-invoked`、`Dependencies between them` | 入口发现与能力组合 |

标为“源码摘录”的内容来自上述快照；`source-walkthrough` 是本文编写的教学示例，不是原项目已有的 skill，也不是通用标准模板。

:::

个人 skill 可以从一份 `SKILL.md` 开始。先选一个反复发生、每次都要纠正相同偏差的任务，把目标、判断条件和完成标准写清楚；用几次真实任务检验后，再决定是否增加参考文件、脚本或其他 skill 依赖。

例如，经常让 agent 写源码解析，却总得到目录介绍，或者文章引用了函数却没有解释状态变化。值得保存的经验是“沿实际入口追踪调用与数据，关键判断必须有实现依据”，而不是“请扮演资深架构师，全面深入地分析”。前者能改变执行过程，后者很难说明究竟补了什么要求。

本文以这个源码解析任务贯穿编写过程，目标是得到一个可以试用、能够判断哪里出错、方便继续修改的第一版。

需要直接使用时，读取独立的 [source-walkthrough 完整 skill](./source-walkthrough/SKILL.md)。它已补齐版本与工作区差异、程序和指令工作流分支、证据缺失处理及交付验收；下文仍保留较短的教学示例，用于说明第一版怎样组织。

## 一、先找到值得固化的任务

### 1、从重复纠正中提取规则

回看几次同类任务，找出你真正重复强调的内容：是不是每次都要求固定版本、追踪上游输入、说明失败分支、删除只介绍文件作用的段落？这些共同约束适合进入 skill。某次文章恰好分析支付模块、某个文件叫 `worker.ts`，则只是这次任务的输入。

以源码解析为例，可以先做下面这组区分：

| 材料 | 更合适的位置 | 原因 |
| --- | --- | --- |
| 每次都要求区分实现事实与工程推断 | skill 正文 | 决定分析如何开展 |
| 某篇文章要分析哪个项目、哪个机制 | 当次请求 | 随任务改变 |
| 项目规定的文章目录、术语和标题格式 | 项目指令 | 对该项目的其他文章同样有效 |
| 某版本某函数当前在哪个文件 | 读取源码得到 | 写死后容易过期 |
| 在多个任务中重复使用的确定性检查 | 按需要提供脚本 | 无须每次让模型重新编写同一段逻辑 |

这样写出的个人 skill 才能带到其他项目：任务方法留在 skill，仓库约定从目标项目读取，具体对象由这次请求提供。把一次成功会话全文复制进去，会把当时的目录、临时决定和输出形式一起变成默认行为。

### 2、把职责收窄到一个能辨认的结果

“帮助我完成软件开发”无法说明应该何时结束。“把一个指定机制写成可独立阅读的源码解析”就能回答输入是什么、结果是什么，也能与修 bug、做代码审查区分开。

第一版可以用四个问题确定范围：

- 用户会在什么情况下用它？例如要求解释实际执行链，而非只找一个符号的位置。
- 运行前需要哪些材料？例如可读取的源码、目标机制，以及已有文稿或输出要求。
- 完成后新增或改变什么？例如更新指定文章，或者在会话中交付解析。
- 哪些相邻动作不属于这次任务？例如解释实现并不自动包含修改实现、提交代码或发布文章。

边界应针对容易发生的误用。源码解析与修复经常相邻，值得明确两者的区别；没有出现过的远端部署、复杂权限审计等分支，不必预先塞进第一版。

## 二、description 负责选中，正文负责执行

### 1、描述能力和使用场景，不把全部流程塞进头部

`SKILL.md` 开头的 YAML 元数据称为 frontmatter，`name` 标识能力，`description` 说明它做什么、何时适用。详细步骤放在正文。对 `source-walkthrough`，描述可以聚焦“解释或改写源码解析，沿真实调用或指令链说明行为”，无需把读文件、查版本、写段落、检查链接全部列一遍。

在 `mattpocock/skills` 中，允许模型选用的入口会保留触发描述；只由用户选择的入口则用对应配置限制隐式调用。这个区分在[路由篇](./01-ask-matt-router.md)有完整解释。个人编写时要分别决定两件事：模型能否发现这个能力，以及当前任务允许它执行哪些动作。允许自动发现，不等于获得额外的写入或发布授权。

具体调用字段和安装位置由宿主决定。宿主指加载 skill、运行模型并提供工具的环境；不要把某个项目里的 `/skill-name` 写法或某份配置，当成所有环境都支持的接口。先让目标宿主能够加载一份简单指令，再扩展组合关系。

### 2、同时考虑该选中和不该选中的请求

同一个名字可能被用于不同任务，描述需要帮助模型分辨：

| 请求 | `source-walkthrough` 是否适用 | 判断依据 |
| --- | --- | --- |
| “沿调用链解释这个任务如何取消” | 适用 | 要解释真实执行机制 |
| “把这篇源码解析改到不打开源码也能理解” | 适用 | 要用实现补齐文章解释 |
| “帮我定位取消函数在哪” | 通常不需要完整流程 | 只需要一次符号定位 |
| “修复取消后任务仍继续执行的问题” | 不应接管成写文章 | 目标是修复，解析最多是其中一步 |

如果描述写成“分析、理解、学习、开发、维护任何代码”，后两种请求也可能被拉进长篇写作。修正这种误用，应收紧能力描述和结果边界，而不是要求所有调用都先向用户确认一遍。

同样的原则适用于正文中的参考链接。源码位置：`skills/productivity/writing-for-agents/SKILL.md` → `Context pointers`，截取一句：

```markdown
A must-have target behind a weakly worded pointer is a variance bug: sharpen the wording first, and inline the material only if sharpening fails.
```

这里的 context pointer（上下文指针）是“材料说明加读取条件”。如果模型总漏读某份必要规则，先检查是否说清了何时必须读取，而不是立即把全部材料复制到主文件。

## 三、把要求写成动作、依据和完成条件

### 1、每一步结束时，应多出可检查的信息

“充分理解源码”“写得深入”只有质量愿望，没有告诉模型何时可以进入下一步。源码解析可以改成：确认版本后留下版本标识；追踪入口后能说清调用者和输入；分析状态后能指出写入位置、读取者和失败后的处理。

`to-questionnaire` 提供了一个很直接的写法。源码位置：`skills/productivity/to-questionnaire/SKILL.md` → 开头第 3 步，完整摘录：

```markdown
3. **Write the questionnaire.** Draft questions aimed at the gap from steps 1–2, following the Document structure below. Write it to `to-questionnaire-<slug>.md` in the current directory (slug from the topic) and report the path. Done when the file exists and every item the user named in step 2 is covered by a question.
```

这一步有上游输入、生成动作、产物位置和出口条件。文件存在只证明“写了东西”；用户列出的每项信息需求都有对应问题，才证明“覆盖了输入”。

对源码解析也一样：有一篇文章不等于解释完整。完成条件应该落到目标问题是否都有回答、核心判断是否能对应实现，以及未确认的部分有没有被如实标出。条件不要求每篇使用相同小标题，仍允许模型按内容组织叙述。

### 2、事实能查就查，用户决定只在必要处询问

`skills/productivity/grilling/SKILL.md` → `Finding _facts_` 段开头写道：

```markdown
Finding _facts_ is your job, never the user's.
```

用于个人 skill 时，可把它转成清楚的分工：文件位置、现有配置和代码行为由 agent 调查；有多个可能的目标版本、用户希望解释哪个行为、输出是否替换某篇文章等实质选择，才需要结合已有请求判断，缺少决定时再问。

提问条件应与后果相连。例如入口名不唯一时，先查调用方和文件上下文；仍有两种完全不同的业务含义，才请用户选择。没有执行日志时，可以解释代码层面的分支，但不能因此宣称已经观察到某次运行结果。

### 3、写清无法完成时留下什么

一个只写成功路径的 skill，容易在材料不足时补出貌似完整的答案。源码解析至少需要保留几种可辨认的结果：

| 遇到的问题 | 合理的下一步 | 应保留的结果 |
| --- | --- | --- |
| 找不到指定符号 | 检查版本、名称与调用方，再报告差异 | 已确认的版本、未找到的入口 |
| 关键行为在不可读取的依赖中 | 解释可见的调用边界 | 已确认部分与缺失的实现 |
| README 与实现冲突 | 以目标版本的实现描述行为 | 冲突位置及实际分支 |
| 用户改变分析目标 | 重新检查旧结论和片段是否仍适用 | 新范围与需要重做的部分 |

这些分支不必各加一套长流程。把条件写在相关动作旁边，通常比结尾再堆一页“注意事项”更容易遵循。

## 四、把第一版写成一份能直接阅读的 SKILL.md

### 1、一个源码解析 skill 的完整教学示例

下面是本文编写的指令示例，可作为个人版本的起点，**不是 `mattpocock/skills` 源码摘录，也不代表已经通过行为验证**。示例只需要 `source-walkthrough/SKILL.md` 一个文件，没有预设其他 skill、子 agent 或安装脚本。将它放入目标宿主支持的位置后，再按后文的方法试用。

````markdown
---
name: source-walkthrough
description: 编写或改进源码解析文章。用于用户要求解释某个机制的真实调用或指令链、数据流、状态变化和异常分支，或要求文章脱离源码也能独立读懂。
---

# Source Walkthrough

根据用户指定的源码和问题，交付一份有实现依据、能够独立阅读的中文解析。修改已有文章时保留仍然准确且有用的内容。

## 确定范围与依据

读取用户提供的源码、文稿和项目写作约定。确认要解释的行为、目标版本和输出位置，优先使用已经给出的信息。

从项目读取版本标识，并记录源码相对路径与真实入口。没有版本标识时注明依据范围。函数、类和指令文件分别按它们的真实入口定位，不为 Markdown 指令虚构执行函数。

仅当缺失的信息会改变分析对象或写入目标，且无法从现有材料确定时，向用户提问。

## 追踪执行与证据

从用户关心的入口开始，追踪调用者、输入、关键分支、状态写入和下游读取，直到足以回答当前问题。重点保留会改变结果的路径，不穷举无关辅助代码。

对关键结论，找到对应实现或配置依据。按需检查调用方和测试，区分设计说明、代码行为及实际运行观察。

依赖缺失或行为无法确认时，保留未知项并解释证据缺口；不以推测填满链路。

## 组织正文

开头交代该机制解决的问题、版本依据和入口。沿执行或数据变化组织解释，首次出现的专属概念说明用途。

引用支撑判断所需的最小真实片段，标明相对路径和入口；省略部分明确说明，原英文注释译成中文。片段之后解释上游输入、当前处理、下游消费及相关副作用。

将实现事实、说明性例子和工程推断区分开。讨论取舍时说明具体减少的成本、增加的约束，以及不适用的情形。

按项目已有的标题、术语和排版约定成文。删除重复总结和作者查证过程的叙述。

## 交付与核对

用户指定文章文件时，只更新该目标及请求所需的导航；用户只要求解释时，在会话中交付。源码分析本身不包含修改被分析实现、提交或发布。

逐项核对用户关心的问题：每项要么有实现支持的回答，要么明确写出尚不能确认的部分。检查路径、入口、片段和版本是否一致，以及文档内链接、标题层级和代码块是否完整。

遵守项目的执行约束；静态阅读不能表述为运行验证。交付时报告产物位置及确实影响结论的未确认项。
````

这份示例把四段工作串起来：范围决定查什么，证据决定能说什么，正文把证据转成解释，交付核对检查是否回答了原问题。它没有固定每段字数、每篇代码块数量或必须调用多少工具，因为这些数量本身不能证明文章质量。

### 2、完整版本怎样使用

完整版本保存在当前分类的 `source-walkthrough/` 目录中：`SKILL.md` 是执行入口，`agents/openai.yaml` 是可选的界面元数据，`_category_.json` 只供文档站导航使用。执行不依赖配套脚本或其他 skill；迁移时将 `SKILL.md` 与需要的宿主元数据放入目标环境支持的 skill 目录即可。仓库中的文件不会因此自动安装到某个宿主。

也可以直接让 agent 读取这个文件后执行，不必先配置发现机制。例如，向 agent 提供以下请求，并附上实际可读取的源码和文章路径：

```text
读取当前分类下 source-walkthrough/SKILL.md，按其中要求改进我指定的源码解析文章。
源码以我提供的实现为准，目标是读完正文就能理解核心调用链、数据流和状态变化。
更新指定文章，保留版本与入口信息，不执行构建。
```

### 3、为什么第一版没有引入完整工作流

示例没有要求每个问题先经过 `grilling`，因为源码解析的目标通常已经给出；也没有要求并行研究，因为一个入口的上下游可能高度依赖前一步调查。只有任务中出现需要用户选择的设计方向，或确实能独立调查的多条路径时，再考虑这些能力。

它也没有复制当前项目的中文标题编号，而是读取目标项目的写作规则。如果所有项目都适用的个人文风确实需要固化，可以在 skill 中补充；仅适用于一个站点的排版规范则继续由该站点维护。

使用这种第一版仍需要检查实际效果。Markdown 中写了“核对所有问题”，并没有生成一套自动校验器；模型是否读到了规则、怎样理解“关键路径”，还要通过任务表现判断。

## 五、遇到具体需要，再拆资料、状态和脚本

### 1、按分支拆参考文件，让入口说明读取条件

当同一 skill 同时处理程序函数和提示词工作流，两类任务可能需要不同的细节规则。可以把公共过程留在 `SKILL.md`，只将专属分析规则放到参考文件。

`prototype` 的分流方式很清楚。源码位置：`skills/engineering/prototype/SKILL.md` → `Pick a branch`，连续摘录两条分支：

```markdown
- **"Does this logic / state model feel right?"** → [LOGIC.md](LOGIC.md). Build a single shareable HTML file — free-play buttons plus tabbed guided walkthroughs — that pushes the state machine through cases that are hard to reason about on paper, and that a non-developer can drive.
- **"What should this look like?"** → [UI.md](UI.md). Generate several radically different UI variations on a single route, switchable via a URL search param and a floating bottom bar.
```

它同时写明了问题、材料和预期结果。沿用这一组织方式，源码解析的个人版本可以在真正需要时增加 `references/prompt-workflows.md`，并在入口注明“分析以 Markdown 指令为主体的工作流时读取，重点区分模型约定与宿主保证”。这个路径只是扩展示例，第一版不依赖它。

每次任务都需要的“结论要有证据”留在正文；只有某一分支需要的调用策略细节再拆出去。格式模板可以作为参考材料，复制到产物中的样式或图像才适合放入 `assets/`。不要为了凑齐目录结构而创建空文件。

### 2、跨会话状态必须有写入者和读取者

`source-walkthrough` 的一次性执行可以依赖当前会话，不必额外保存调查日志。如果文章很长、要分多次继续，就需要决定哪些中间状态值得留存，例如版本、已解释的问题、证据位置、未确认项，以及下一步要查的入口。

写下这些信息还不够，下一会话必须知道何时读取、是否需要重新核对源码版本、哪些旧结论已经失效。否则文件虽然存在，恢复过程仍会从头开始。

[领域建模篇](./03-grill-with-docs-domain-modeling.md)给出了按内容触发写入的例子：术语明确就更新 `CONTEXT.md`，重要决定满足条件后才提议 ADR。[交接与教学篇](./09-handoff-teach-writing-wait-what.md)则区分交接摘要和持续学习记录。个人 skill 应按后续消费者设计状态，避免把每次执行都变成不断增长的聊天纪要。

多个 skill 组合时，还要检查它们对同一份材料的假设。例如 `implement` 要求提交前审查，但 `code-review` 比较到 `HEAD`，未提交实现不会被包含；这个[真实交接缺口](./05-tdd-diagnosing-bugs-implement.md)说明，仅写“下一步调用审查”并没有定义完整输入。

### 3、确定性的操作适合脚本，判断仍留给模型

源码解析中，“这个分支是否影响用户关心的行为”需要判断；“文章引用的文件是否存在”“某个链接目标是否存在”更适合确定性检查。只有后者反复发生或容易出错时，再考虑提供脚本。

脚本应有明确输入、输出和失败含义。例如检查器接收目标文章，输出不存在的路径及所在位置，出现问题时返回失败；它不能据此宣称“所有解释都正确”。第十篇的[版本同步脚本](./10-release-install-versioning.md)也只保证两个版本字段同步，不保证整个发布过程正确。

脚本一旦涉及写入，需要另外考虑重复执行、覆盖、部分成功和恢复。把同名目录删除后重新建立链接，和发现冲突后停止，是不同的产品行为，不能只在 skill 中用一句“安全处理”带过。

## 六、验证行为，再根据失败修改规则

### 1、格式检查与任务效果分开看

确认 `SKILL.md` 的头部能被宿主识别、名称能被发现、引用文件存在，只能证明入口和资源基本可用。真正需要验证的是：在相同任务下，加入 skill 后是否少了你原本反复纠正的问题。

对 `source-walkthrough`，可以使用熟悉的小模块，在独立会话中分别观察普通请求和启用 skill 的结果。尽量保持模型、工具、任务材料和项目约定相近；否则结果差异可能来自环境变化。不要把预期答案和已经定位的缺陷一并告诉执行者，否则看不出它能否自己找到依据。

### 2、选择少量能暴露不同问题的任务

不需要为第一版建立庞大评测平台，但样例应覆盖不同失败方式：

| 试用任务 | 重点观察什么 |
| --- | --- |
| 一个调用链很短的同步函数 | 能否简洁解释，不人为扩成架构长文 |
| 有取消、重试或异步回调的任务 | 是否追踪状态何时改变、由谁继续消费 |
| 一份以 Markdown 指令为主的 skill | 是否区分行为约定与程序保证 |
| 文档与源码版本不一致 | 是否固定依据并指出差异 |
| 关键依赖不可读取 | 是否保留未知，而非编造完整链路 |
| 仅要求定位符号或修复问题 | 是否避免把任务接管成长篇解析 |

每次观察产物，也看关键过程：是否读取了必要实现、是否追到了下游、是否把调查失败藏进了肯定语气。某次结果很好，只说明它在这次输入上有效；对于你最在意的高频偏差，应换一份材料再次观察。

### 3、先判断失效在哪一层，再改对应位置

| 观察到的偏差 | 优先检查 | 可能的改法 |
| --- | --- | --- |
| 合适的请求没有选中 skill | 入口是否可用，description 是否匹配实际用语 | 修正发现条件，不先扩写正文 |
| 选中了却漏读专属规则 | 参考链接是否给出读取条件 | 在相关分支明确指向材料 |
| 写了长文却没解释状态变化 | 分析步骤的出口是否只要求“理解” | 要求指出写入位置和读取者 |
| 交付后无法继续 | 中间产物是否足够，恢复入口是否存在 | 补上最小状态与读取条件 |
| 重复执行产生重复产物 | 写入规则或脚本是否识别既有结果 | 明确复用、更新和冲突处理 |

修正应针对已经观察到的失效。一篇异步文章漏了取消路径，可以补“涉及异步任务时检查取消与后续回调”；不必把它扩大成“所有文章必须包含取消、超时和重试三节”。后者会让同步函数解析也被迫编造不存在的机制。

## 七、维护个人 skill 时，保留能改变行为的部分

一条新规则加入后，用原失败任务判断偏差是否减轻，再挑一个正常任务看它有没有增加无用工作。任务表现没有变化的句子，未必值得长期保留；重复表达同一个意思，也会让真正重要的约束更难找到。

修改时保留简短的变更理由即可，例如“异步链路遗漏回调读取，所以补充状态消费者要求”。这类维护记录不必塞进每次都会加载的正文，也不需要在每篇产物里复述。

只有当一种行为需要独立被发现，或多个 skill 确实重复使用它时，才值得拆出新的 skill。`grill-me` 与 `grill-with-docs` 共用 `grilling`，是因为同一种访谈规则服务了不同入口；个人只有一个源码解析入口时，普通参考文件通常已经足够。

最终留下的个人版本应能回答具体问题：它帮你避免了哪种重复错误，输入不足时怎样处理，产物由谁继续使用，以及什么证据说明这次已经完成。每增加一个文件或一条限制，都用这些问题检查其作用，skill 才不会随着使用逐渐变成一份难以执行的经验杂烩。

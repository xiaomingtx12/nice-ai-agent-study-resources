# 产品案例路线图

产品案例从一个可完成、可验收的用户任务开始。产品名用于选择样本，功能形态和商业模式用于解释结果。单产品拆解与多产品比较放在同一场景下，避免形成两套重复目录。

## 首批场景与候选案例

| 场景 | 共同任务 | 候选产品 | 重点观察 |
| --- | --- | --- | --- |
| 应用构建与交付 | 用给定资料搭建一个可发布的问答助手 | Coze Studio、Dify、FastGPT | 上手准备、调试反馈、知识更新、发布、交接维护 |
| 软件开发与协作 | 在陌生仓库修复一个有测试标准的缺陷 | OpenHands、Claude Code、其他可获得同等测试条件的工具 | 任务表达、计划、权限确认、验证、变更审查 |
| 知识工作与研究 | 从多份资料产出带证据的持续更新文档 | OpenWiki、研究类 Agent 或知识产品 | 来源追溯、冲突处理、更新成本和交付格式 |
| Agent 调试与质量运营 | 从一个线上坏结果建立回归用例并比较修复版本 | Coze Loop、Langfuse、Phoenix、Opik | 问题定位、数据集、评测器、实验比较和发布判断 |
| 业务流程与运营 | 从客户输入到完成一次可验收的业务动作 | 待真实案例确定 | 人工接管、系统写入、责任边界、单位任务成本 |

业务流程方向暂不先列产品名单。没有真实流程、验收标准和使用证据时，只凭产品宣传容易把能力清单写成业务价值。

## 应用构建方向先做两篇

第一篇做 **Coze Studio 单产品任务走查**：从新建项目到发布一个问答助手，记录用户必须理解的对象、配置和错误反馈。工程源码引用对应单项目解析，不在产品文重复解释内部调用链。

第二篇做 **Coze Studio × Dify 同任务比较**：使用相同资料、模型能力范围和成功标准，比较搭建、调试、发布及后续更新。无法统一的条件单列，例如在线版与自托管版、内置模型供应商和商业功能差异。

建议记录：

- 从空项目到第一次有效回答所需的操作和前置配置。
- 错误发生时，用户能否定位到知识、提示词、工作流或模型配置。
- 发布产物是什么，分享、嵌入、API 调用和权限由谁配置。
- 更新资料或流程后，已有发布版本和会话受到什么影响。
- 将项目交给另一位维护者时，对方需要补哪些隐性知识。

## 产品文章如何处理商业问题

商业模式不单独作为所有产品都要填写的章节。只有当计费、部署或采购方式改变用户决策时，才深入分析。

| 情况 | 应回答的问题 |
| --- | --- |
| 开源自托管 | 谁承担部署、升级、模型、存储和运维成本？哪些能力依赖商业版？ |
| SaaS 按量计费 | 计费单位是否与用户获得的结果一致？失败、重试和长任务怎样计费？ |
| 面向企业采购 | 采购者、使用者和维护者是否是同一角色？安全、权限和服务承诺怎样影响采用？ |
| 平台生态 | 插件、模板、模型渠道或分发能力是否形成采用优势？迁移成本来自数据还是配置？ |

价格和产品能力会变化，正文必须写明核对日期。收入、利润、留存和市场份额需要可靠数据；没有数据时只保留待验证假设。

## 与方法与复盘的边界

产品案例保存具体任务、版本、操作和证据。多个案例重复出现的判断，再沉淀到方法与复盘：

- 同类产品中反复出现的交互结构，进入 Agent 产品形态图谱。
- 多个案例都需要的人机协作原则，进入 Agent 产品设计方法。
- 某个市场阶段、厂商路线或商业变化，进入市场观察。
- 某个项目自己的体验和限制，继续留在产品案例中。

一条判断至少经过两个独立案例支持，再考虑提炼为跨项目方法。单个案例可以提出假设，但不直接写成普遍规律。

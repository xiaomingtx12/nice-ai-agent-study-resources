# 创投研究 Agent：从筛选公司到可追问的投资研究

Scout 是服务投资机构的**创投研究 Agent**。它帮助用户寻找符合投资主题的创业公司、研究创始团队、准备投资会面，交付候选公司表、研究报告和图表，并支持围绕这些结果继续提问。

这篇案例的起点是：旧版已经能把自然语言变成精确的公司筛选条件，但用户开始要求综合研究、会面准备和个性化联系草稿。团队需要让模型组合数据工具开展研究，也要让它始终知道用户正在看哪份结果。

> 主来源为 2026 年 6 月 3 日的 [LangChain 客户案例](https://www.langchain.com/blog/how-harmonic-rebuilt-scout-on-deep-agents-and-4xd-retention-with-langsmith)。业务背景补充自 Harmonic 2026 年 5 月 6 日的[创投业务介绍](https://harmonic.ai/blog/how-harmonic-serves-venture-capital-firms)；产品入口、分享与计费依据[官方使用说明](https://support.harmonic.ai/en/articles/11047921-scout-your-ai-research-agent)，页面标注更新于 2026 年 7 月 8 日。下文先讲来源内容，再说明证据边界与实施建议。

## 一、最初的挑战：能找到公司，还不能完成开放式研究

**本节说明为什么重建 Scout：投资者需要把多种资料综合成判断依据，旧版的预设查询流程难以覆盖这些新任务。**

### 1、研究需求：从公司名单走到会面准备

投资团队要了解谁在创业、团队怎样变化、哪些公司符合自己的投资主题。Harmonic 的业务介绍强调，人员流动、公司成立和招聘变化可能早于融资公告；只有融资历史和联系人名单，还不足以解释一家公司正在做什么。

LangChain 原文用两类请求说明 Scout V2 的任务范围：

| 用户提出的目标 | 需要开展的研究 | 交付物 |
| --- | --- | --- |
| 按投资主题挑出五家公司 | 将抽象主题落实到公司条件，查询并比较候选对象 | 候选名单及选择依据 |
| 十分钟后见创始人，整理应该知道的情况 | 综合团队背景、公司资料、CRM 笔记、历史邮件和人脉关系 | 会面准备材料 |

CRM 是记录客户或潜在合作对象及接触过程的关系管理系统。对投资机构来说，公司公开资料回答“它在做什么”，内部笔记、邮件和 LinkedIn 关系则补充“我们是否接触过、谁认识对方”。研究结果进入团队自己的判断与接触过程。

### 2、工程瓶颈：每种新意图都要扩展一条执行路径

Scout V1 已是基于 LangGraph 的 Agent。LangGraph 是组织有状态执行步骤的框架；团队用多个子图拆分查询解析，并在各节点设置评测。

例如，“找旧金山或纽约、过去一年获得知名投资人融资、与本团队有人脉联系的 AI 公司”，可以转成 Harmonic 数据索引中的精确过滤条件。用户省去了手工配置与保存筛选器的工作。

但个性化联系草稿、抽象投资主题研究等请求超出既有流程后容易失败。新增能力往往需要新子图，维护工作也包括数百项评测。团队希望模型能随着任务和底层能力变化选择做法，减少逐个节点调整。

![Scout 原文架构对照：V1 用多个预设节点解析查询，V2 使用模型与工具循环，工具包括搜索、资料补全和列表操作](/img/blog-cases/harmonic-scout-architecture.png)

## 二、解决方式：让一个研究 Agent 组合全局数据与机构资料

**本节解释新版怎样处理同一项研究目标：模型选择工具、综合证据并继续查询，数据访问由工具承担。**

Scout V2 使用 Deep Agents，即提供长任务执行、工具使用和上下文管理能力的 Agent 运行框架。原文描述的核心结构是一个前沿模型，加上两组经过设计的数据工具。

~~~mermaid
flowchart TD
    A["研究目标<br/>筛选公司或准备会面"] --> B["Scout 研究 Agent<br/>决定查什么、怎样比较"]
    B --> C["全局数据工具<br/>公司、人物、投资人"]
    B --> D["机构资料工具<br/>列表、CRM、邮件与关系"]
    C --> E["综合研究结果<br/>候选名单、报告与图表"]
    D --> E
    E --> F["用户检查结果并追问"]
    F --> B
    classDef agent fill:#e8f2ff,stroke:#426a9b,color:#172b4d
    classDef data fill:#eaf5ec,stroke:#477655,color:#193e25
    class A,B,F agent

~~~

*图 2：根据原文整理的研究关系，不是固定工具调用顺序。不同请求使用不同资料，也可以在追问后继续调查。*

全局资料用于了解公司的领域、团队、融资与市场背景；机构资料补足历史接触、内部判断和人脉关系。

6 月案例给出的全局数据规模约为四千万家公司、两亿人物和二十三万投资人。原文的会面准备示例会从公司档案与机构记录中取材，再综合成一份材料，用户无需分别查询后手工拼接。

Harmonic 的业务介绍还补充了联系人资料、Affinity CRM 集成和已有引荐关系查询。发现值得接触的公司之后，团队可以继续寻找联系人与引荐路径。这里披露的是研究与接触准备能力，没有展示 Scout 自动作出投资决定的过程。

## 三、交互关键：用户看见的列表和图表，Agent 必须能重新读取

**本节解释本案例最具体的产品设计：研究产物要同时服务界面展示和模型回读，否则用户一追问，会话就断开了。**

### 1、图表展示：把技术输出变成会话中的研究产物

测试时，用户要求画一张市场图谱。模型返回了 SVG，即描述矢量图形的代码格式，但当时前端无法直接展示。

团队将可视化改成会话中的正式产物：模型在消息内生成，前端原地渲染，双方围绕同一份内容继续讨论。会面准备、研究报告、市场图谱和团队时间线因此可以复用同一种交互方式。

![Scout 生成的团队增长时间线，按部门展示累计入职人数，并标注部分人员来源与融资事件](/img/blog-cases/harmonic-scout-team-timeline.png)

*图 3：原文中的团队时间线。横轴是时间，不同颜色对应部门，人员背景与融资事件放在同一张图中，便于研究团队扩张过程；这里不单独核验图中的人物与融资事实。来源：[LangChain 原文](https://www.langchain.com/blog/how-harmonic-rebuilt-scout-on-deep-agents-and-4xd-retention-with-langsmith)。*

用户追问某段时间的团队变化时，模型仍能找到会话中的这份产物，继续讨论。

### 2、搜索回读：完整结果留在共享文件，模型按需分页查看

公司搜索可能返回数千条记录，聊天消息无法承载整个结果集。早期设计把结果交给侧栏展示，模型继续执行；等用户问“为什么这三家排在前面”，模型却没读过那份结果。

Scout 将结果写入 Agent 可访问的共享文件系统，前端按行展示，同时提供分页工具，让模型按需回读同一份数据。

~~~mermaid
flowchart TD
    A["公司搜索<br/>返回大量记录"] --> B["共享文件系统<br/>保存完整结果集"]
    B --> C["前端按行展示<br/>用户看见公司列表"]
    C --> D["用户追问<br/>为什么这三家排在前面？"]
    D --> E["Agent 调用分页工具"]
    B -->|读取同一份结果| E
    E --> F["根据记录比较与解释<br/>继续筛选或研究"]
    classDef data fill:#e8f2ff,stroke:#426a9b,color:#172b4d
    classDef use fill:#fff3d6,stroke:#946b17,color:#513a0c
    class A,B,E,F data
    class C,D use
~~~

*图 4：根据原文整理的结果回读机制。共享文件保存完整数据，分页工具让模型只读取当前问题需要的部分。*

![Scout 公司搜索表：包含公司描述、融资阶段、融资额、成立时间与地点，顶部显示已评估数量](/img/blog-cases/harmonic-scout-search-results.png)

*图 5：原文的搜索界面。顶部显示已评估 250 家、共 1,410 家；表格展示候选集合与处理进度，不代表 Agent 已完整评估全部记录。来源：[LangChain 原文](https://www.langchain.com/blog/how-harmonic-rebuilt-scout-on-deep-agents-and-4xd-retention-with-langsmith)。*

团队不必为每一种追问单独设计流程，还能从用户怎样继续研究中发现新用例。

## 四、生产迭代：把运行轨迹、用户看到的产物和代码修改连起来

**本节说明团队怎样改进研究体验，以及原文报告了哪些产品变化。**

LangSmith 是支持 Agent 轨迹记录、评测与部署的平台。团队使用 LangSmith Deployment 承担持久会话执行与部署管理，把主要精力放在数据工具和产品交互上。

内部看板会重现完整会话和生成的产物，让工程师同时看到工具执行过程与用户实际看见的内容。团队还通过 LangSmith 的 MCP 接口把轨迹接入编程工具；MCP 是供 AI 应用发现和调用外部能力的协议。

~~~mermaid
flowchart LR
    A["运行研究任务"] --> B["记录会话轨迹<br/>重现列表与图表"]
    B --> C["定位问题<br/>总结重复失败模式"]
    C --> D["修改代码与评测<br/>重新运行验证"]
    D --> A
    classDef work fill:#e8f2ff,stroke:#426a9b,color:#172b4d
    class A,B,C,D work
~~~

*图 6：根据原文整理的工程迭代过程。工程师依据真实运行修改产品；原文没有说这些修改会未经审核自动发布。*

长任务的轨迹可能有数十至数百轮，逐条检查很费时。原文称，团队早期使用的 LangSmith Engine 会聚类失败模式，并建议评测和代码改动，帮助减少人工查找。

| 原文报告的变化 | 应如何理解 |
| --- | --- |
| 产品迭代从按月推进缩短到按天推进 | 团队对研发节奏的描述 |
| 第一周到第四周的用户留存达到 V1 的四倍 | 相对旧版的留存变化，不是绝对留存率 |
| 平均会话时长达到十倍 | 团队观察到用户从单次查询转向多步研究 |
| 不再持续讨论原来的“80% 良好结果率”目标 | 属于团队的质量感受，未披露新版对应准确率 |

原文还报告，使用场景扩展到企业创新、企业发展、招聘，以及向创业公司销售的团队。其共同需求是研究创业公司与相关人员，而非都在作投资决策。

## 五、产品与证据边界：研究可以保存和计费，效果不能直接换算成投资收益

**本节补充官方使用说明，并区分已披露的产品功能、客户自报结果与尚未公开的实现。**

### 1、使用方式：入口、保存和分享范围各有规则

官方使用说明标注更新于 2026 年 7 月 8 日，列出以下产品行为：

| 产品环节 | 官方说明 |
| --- | --- |
| 发起研究 | 从 Scout 页面、公司档案页或 Chrome 扩展进入 |
| 保存结果 | 会话进入研究历史，公司档案中的研究保留在对应档案上 |
| 分享范围 | Scout Reports 在团队内共享，个人研究问题保持私有 |
| 复用工作方式 | 保存个人背景与偏好，将常用提示词存为 Skill，并通过命令复用 |
| 周期研究 | 安排重复任务，将新发现发送到收件箱 |
| 使用计费 | Console 工作台许可证含一定额度，超出后可启用按使用量收费 |

这里的 Skill 是产品内可复用的工作指令，文档没有说明它是否采用某种框架的文件格式。定时执行增加了触发方式，运行中的研究仍可能由 Agent 根据结果选择下一步。

### 2、核验范围：来源支持什么，还缺什么

这些资料支持 Scout 已进入产品的保存、分享与用量计费体系，但没有公开生产源码。共享文件与分页来自客户架构叙述，不能据此声称已核验租户隔离、文件生命周期、授权或失败恢复的实现。

留存与会话时长也只有相对变化，缺少公开的绝对值、样本量、用户分组和实验控制条件。使用说明未给出具体单价或合同条款，现有资料不足以计算收入、利润或投资回报。

数据规模应保留来源口径：6 月案例写约四千万公司、两亿人物；7 月使用说明写三千五百万公司、一亿九千五百万人物。本文不将其拼成增长或下降趋势，也不当作当前精确规模。

## 六、整篇总结：让研究路径保持灵活，让数据与产物始终可定位

**本节总结同类研究 Agent 的搭建方法：模型组织调查，工具控制资料访问，产物存储支持展示与回读，权限和评测补齐可靠性。以下为本站实施建议。**

### 1、架构总图：界面与 Agent 使用同一份研究结果

按本站的[控制权判断口径](../index.md#四架构方式与执行控制)，Scout V2 属于 **Agent 主导的研究应用**：模型决定查什么、怎样比较和生成产物，工具承担数据访问。变化的是研究路径的组织方式，并非 V1 完全没有 Agent。

同类系统可以按下图组织。共享结果应当同时支持用户查看和模型读取，而资料来源、访问范围与结果版本需要明确记录。

~~~mermaid
flowchart TD
    A["研究入口<br/>对话、公司档案<br/>定时任务"] --> B["研究 Agent<br/>选择资料、比较与综合"]
    B --> C["授权数据工具<br/>全局公司数据<br/>机构 CRM、邮件与关系"]
    C --> D["研究结果存储<br/>记录、来源、顺序与版本<br/>用户和团队访问范围"]
    D --> E["用户界面<br/>列表、报告与图表"]
    D --> F["分页与产物读取工具"]
    F --> B
    E -->|继续追问| B
    B -->|生成研究材料| D
    B -.-> O["可观测与评测<br/>关联任务、工具和产物"]
    D -.-> O
    classDef agent fill:#e8f2ff,stroke:#426a9b,color:#172b4d
    classDef data fill:#eaf5ec,stroke:#477655,color:#193e25
    classDef observe fill:#fff3d6,stroke:#946b17,color:#513a0c
    class A,B,E agent
    class C,D,F data
    class O observe
~~~

*图 7：同类研究系统的建议架构。共享结果与回读依据原文；结果版本、访问范围和关联记录是本站建议明确的工程职责，不代表已公开的 Scout 内部实现。*

例如，用户问“第三家公司为什么合适”，后端应能找到当时展示的记录、顺序与筛选条件，再交给 Agent 读取。只存聊天回答，或重新搜索后返回另一版列表，都不能保证解释对应用户眼前的结果。

### 2、实施顺序：从一项研究任务开始，把展示和回读一起验收

| 实施阶段 | 具体工程工作 | 验收重点 |
| --- | --- | --- |
| 1. 选定研究任务 | 从主题筛选或会面准备起步，定义需要的资料与交付物 | 名单是否符合条件，报告是否回答了实际问题 |
| 2. 封装资料工具 | 分开全局与机构资料，传递账户身份和访问范围，保留来源 | 能否读到必要证据，是否误用其他用户或机构资料 |
| 3. 保存并回读结果 | 为结果集与产物设置稳定标识，保存查询条件、顺序和版本，提供分页读取 | 追问某一行时，模型读到的是否正是用户所见记录 |
| 4. 接入报告与图表 | 统一产物引用和渲染入口，明确私有与团队共享范围 | 图表能否展示、引用和继续讨论，分享是否越权 |
| 5. 建立反馈再扩展 | 在轨迹中关联任务、工具与产物，将真实失败整理成评测，再扩展周期研究 | 能否复现问题、验证修复，并控制单次任务成本 |

模型生成的 SVG、HTML 等内容还需要明确支持的格式与受限渲染方式；图能显示出来，只完成了展示这一部分。机构邮件与个人研究进入团队报告前，也应检查来源权限，不能因为报告可分享就默认其中所有材料都可分享。

### 3、适用边界：用可检查的研究交付衡量价值

最值得复用的是**结果可回读**：名单和图表成为后续研究的材料，用户不必重新解释对象。资料权限、结果版本、文件保留期限、失败恢复与成本控制，则需要实施方逐项补齐。

如果任务始终只是固定条件筛选，原有查询流程仍能完成工作。需要跨资料综合、比较和追问时，Agent 才承担了本例新增的研究职责。

验收应检查候选匹配度、判断能否追溯、报告返工情况，以及是否帮助团队完成有效接触。长会话可能包含深入研究，也可能包含反复纠错。Scout 案例展示了研究过程怎样进入产品，真正的投资决策仍涉及这些公开材料没有覆盖的尽调、条款和投资委员会判断。

# 用户会话分析 Agent：从还款诉求发现到理财助手的功能迭代

> 来源：Credit Genie 工程团队的 [How Credit Genie used Insights Agent to improve their AI financial assistant](https://www.langchain.com/blog/credit-genie-insights-agent-financial-assistant)，作者 David Li、Jeffrey Ngai、Goyo Lozano Palacio、Charles Yuan，发布于 2026 年 4 月 20 日。前三节讲原文及配图，后两节补充官方文档核验与本站判断。

AskGenie 是 Credit Genie 手机应用里的理财助手，面向需要了解个人财务和预支款情况的用户。本文要讲的 Insights Agent 是另一套供团队分析会话的 Agent：它读 AskGenie 的运行轨迹，找出用户实际在求助什么，再把发现交给产品团队。原文讲的是一次“会话反馈 → 产品改动”的过程。

## 一、用户在理财应用里办事，团队在后台观察需求

### 1、AskGenie 承接个人财务与预支款问题

Credit Genie 是移动端个人财务平台。AskGenie 嵌在它的应用里，最初用于帮助用户理解自己的财务状况。预支款是文中另一类具体业务对象：用户关心申请、获批金额、到账、余额和计划还款日，而这些问题会随着一笔预支款的进展连续出现。

AskGenie 用 LangGraph 构建。LangGraph 是用图组织执行步骤与状态的框架，在本例中用于承载前台理财助手。上线后，团队需要从真实对话中了解用户到底拿它处理哪些事务，不能只根据最初设计的“财务洞察”用途判断需求。

这一点在 Credit Genie 特别明显：应用里已经有独立的客服聊天入口，团队原以为 AskGenie 的会话会更多围绕财务解释。实际轨迹里却出现了不少账户与还款问题。用户并不按产品划定的入口提问，他们会在眼前能对话的助手里直接问“能否改预支款的还款日期”。

### 2、Insights Agent 把会话交给产品团队继续处理

Insights Agent 的使用者是 Credit Genie 团队。它是 LangSmith 提供的轨迹分析能力；LangSmith 是记录 Agent 运行过程、支持观测和评测的平台。Credit Genie 配置 Insights 分析其中保存的 AskGenie 对话轨迹，按主题和子主题整理用户诉求，再把结果交给产品团队。它交付的是需求线索，不替用户办理预支款。

原文介绍的产品改进过程由两段组成：用户在 AskGenie 中提问，后台分析发现反复出现却接不住的事务；产品团队给 AskGenie 补查询、修改日期和请求支持的入口，再通过每周会话分析观察新的需求变化。后文的两种分类实验，就是这条改进过程中的需求发现环节。

## 二、两种分类方法怎样找到具体问题

### 1、保留同一提示词，改变类别约束

团队让 Insights Agent 对 AskGenie 轨迹运行两种配置。V1 给它四个预设类别：客户支持、财务洞察、产品与功能、政策与合规。V2 使用相同提示词，但不提供类别，让 Agent 从对话中生成分类。两种配置都用 Sonnet 4.5 作为思考模型、Haiku 4.5 作为摘要模型；这里比较的是类别约束，而非两个模型的效果，也不是 AskGenie 改版前后的线上对照实验。

V2 最终也产生了四个大类，但类别数相同不代表分析视角相同。V1 从团队事先定义的产品用途出发，V2 则把还款管理和预支款申请这样的具体业务事务提到了大类层级。

### 2、大类分布说明用户没有按产品预设的用途提问

原文列出的主题分布如下。左右两列各自构成一套分类，同行并不表示同一类问题的前后变化。

| 预设分类 V1 | 会话占比 | 自动归纳 V2 | 会话占比 |
| --- | ---: | --- | ---: |
| 客户支持 | 36% | 还款管理 | 33% |
| 财务洞察 | 30% | 财务洞察 | 30% |
| 产品与功能 | 25% | 预支款申请 | 27% |
| 政策与合规 | 9% | 使用障碍 | 10% |

V1 的“客户支持”说明有大量问题超出原先设想，却太宽泛，不足以决定补哪项功能。V2 的“还款管理”让团队进一步看到，这些会话有具体的业务对象：已经获得的预支款，以及它的到账、余额和还款安排。

### 3、原文两张图把宽泛主题拆成了可改的功能

*原文图 1：V1 的“客户支持”分类展开结果，保留英文原图。来源为本文开头链接的 Credit Genie 客座文章。*

这张图把“客户支持”拆成五类具体诉求：资格与访问问题（9.0%）、账户状态查询（7.0%）、还款日期修改（7.0%）、预支款到账问题（6.5%）、还款过程排障（6.0%）。对产品团队而言，“修改还款日期”已经能对应到一项业务操作；“客户支持”这个大标签本身还做不到这一点。

![Credit Genie 的 V2 分析：还款管理占 33.2%，下分预支款状态追踪、还款日期修改请求、余额与费用问题、还款流程咨询和付款处理问题](/img/blog-cases/credit-genie-v2-repayment-subclusters.png)

*原文图 2：V2 自动归纳的“还款管理”分类展开结果，保留英文原图，来源同上。*

V2 的子类分别是预支款状态与进度追踪（11.1%）、还款日期修改请求（6.5%）、余额与费用问题（5.5%）、还款流程咨询（5.5%）、付款处理问题（4.5%）。它把原本笼统的支持需求放回预支款的使用过程：用户既想知道钱和还款安排处于什么状态，也希望直接改变某些安排。

以上百分比按截图原样转录。截图的大类占比分别为 35.7% 和 33.2%，正文汇总表使用了约数 36% 和 33%；子类数值也不应当被读成各自父类内部重新归一化的占比。

继续查看子类，V1 找到“修改还款日期”，V2 也归纳出相近的“还款日期修改请求”。另有用户查询预支款状态、到账进度、余额和费用。团队由此确认两个缺口：AskGenie 要能读到用户自己的预支款事实，还要能处理修改还款日期的请求。

预设分类显示了偏离产品预期的会话，自动归纳则把还款事务直接列为大类；两边的子类又指向相近的产品动作。原文用这些发现决定补什么功能，没有给出分类准确率来判定 V1、V2 谁胜出。

## 三、发现怎样进入产品，而不只留在分析报告里

### 1、把需求落到查询、业务操作和支持入口

团队给 AskGenie 增加查询工具，让它能取回用户已获批的预支款金额、预计到账日、计划还款日和预支款历史。用户问“我的钱什么时候到账”，助手因此有了个人账户事实可查。

修改还款日期、申请新预支款也被接进聊天界面。团队还在当前聊天内加入支持请求弹窗，用户不用离开 AskGenie 再找另一个客服机器人。

把上述改动按用户任务组织，可以看出它们处理的是不同的缺口：

| 用户想完成什么 | 团队披露的产品改动 | 聊天入口交付什么 |
| --- | --- | --- |
| 了解自己的预支款情况 | 新增读取个人预支款资料的工具 | 基于获批金额、预计到账日、计划还款日和历史记录的回答 |
| 改变还款安排 | 支持在聊天界面修改还款日期 | 办理还款日期修改的能力 |
| 发起下一笔申请 | 支持从聊天界面申请新预支款 | 进入申请事务的入口 |
| 继续寻求支持 | 在当前聊天内弹出支持请求窗口 | 提交支持请求，无须切换到另一个机器人 |

查询工具让助手能回答“我的这笔预支款怎样了”，日期修改和申请入口承接后续操作，支持窗口保留继续求助的出口。原文直接由分析结果推导出的两项缺口是预支款查询和还款日期修改；申请入口与支持窗口属于团队一并披露的产品扩展。

### 2、每周分析继续寻找新的能力缺口

Insights Agent 现在每周运行一次。团队观察用户话题是否变化、有没有新的集中诉求，再把发现交给产品团队，用于下一轮设计、实验和修订。

这次迭代中，分析结果促成了查询、修改和支持请求等出口。后续周报继续检查真实会话，而非沿用最初“用户主要需要财务洞察”的产品假设。

据原文整理，这条产品反馈链是：**用户提出真实诉求 → AskGenie 留下会话轨迹 → Insights 按主题与子主题分析 → 团队识别功能缺口并开发 → AskGenie 接入新能力 → 后续会话再进入每周分析。**

链条中的自动化承担会话分析，产品和工程团队承担功能设计与改动。它的闭环对象是“发现需求后改进助手”，不能把这一过程写成后台 Agent 自行修改业务系统。

## 四、架构核验：前台处理事务，后台批量分析，团队连接两端

### 1、原文能确认的组件与职责

这套应用需要分开看在线服务与事后分析。AskGenie 在用户会话中提供回答和业务入口；Insights 分析积累下来的运行轨迹；产品团队把分析结果转成前台能力。下表是根据原文整理的职责关系，原文没有提供系统架构图或生产源码。

| 组件或参与者 | 接收什么 | 负责什么 |
| --- | --- | --- |
| AskGenie，基于 LangGraph | 用户的理财与预支款问题 | 在聊天中查询个人预支款资料，并承接修改、申请和支持请求入口 |
| LangSmith 轨迹记录 | AskGenie 的运行过程与会话 | 保存供团队分析用户行为的材料 |
| LangSmith Insights Agent | 轨迹、提示词、可选的预设类别及模型配置 | 生成主题与子主题分析；Credit Genie 每周运行 |
| 产品与工程团队 | 主题报告和发现的能力缺口 | 决定产品改动，开发并交付 AskGenie 新能力 |

这里没有证据表明 AskGenie 在每次回答时都调用 Insights，也没有证据表明 Insights 能直接修改还款日。两者通过运行数据和团队的产品改动发生联系。

### 2、官方文档补充了“摘要后分类”的处理方式

原文链接的 [LangSmith Insights 官方文档](https://docs.langchain.com/langsmith/insights)补充说明：摘要模型先生成逐条轨迹摘要，思考模型再对摘要分类；结果可以从大类、子类下钻到原始轨迹。预设大类时，子类仍可自动生成。这解释了为什么 V1 虽然只给出四个大类，仍能发现“修改还款日期”这样的细分诉求。

这部分核验依据是 2026 年 10 月 3 日的文档，不是 Credit Genie 在 4 月发布案例时的部署快照。案例确认使用 Sonnet 4.5 与 Haiku 4.5 分担思考和摘要，但没有公布完整提示词、采样配置或内部调用轨迹。

### 3、怎样判断这套系统的架构方式

按[控制权的判断口径](../index.md#四架构方式与执行控制)，更有依据的描述是：**前台对话助手与后台定时批量分析配合，由人推动产品迭代。** 当前官方文档可以确认 Insights 的摘要与分层分类阶段，原文可以确认 Credit Genie 的每周运行方式；完整内部控制流仍未公开。

V2 放开的是分类内容，让模型生成类别，并不直接证明模型能自主改变处理阶段、反复追加查询或选择新的分析工具。因此，既不应把全部内部执行写成已核验的固定 workflow（工作流），也不应把它写成会自主调查、改产品并上线的 Agent。

AskGenie 使用 LangGraph、拥有查询工具和聊天内业务入口，但文章没有展开它的图节点、路由方式或审批机制。不能用前台框架的名称替后台分析补出执行架构，也不能把同一个案例中的两套系统视为一个 Agent。

## 五、本站判断：需求反馈已接上产品迭代，任务结果还需验证

### 1、功能已经扩展，不等于业务结果已经量化

原文没有报告改动上线后的还款修改成功率、客服工单减少量或财务结果。36% 和 33% 是两套分类中的主题占比，不能相减成“客服问题下降三个百分点”。

这里有两种需要分别验证的闭环。**产品迭代闭环**已经有“会话分析促成功能交付、随后按周继续观察”的团队自述；**单次用户事务闭环**还需要看到查询、修改或支持请求的最终结果。只出现了一个修改日期的入口，不足以证明用户完成了修改。

自己复用这种方式时，可以在主题之外核对任务终态：查询是否对应正确账户、日期是否写入成功、支持请求是否已受理并解决。这些是本站建议的验收项，原文没有报告相应数据。

金融交易还涉及身份、账户归属、可选还款日期和执行后的状态确认。原文未公开这些生产校验的代码，也没有公布逐条会话或交易结果；“聊天中可以修改日期”是团队对产品能力的描述，不能据此推断完整风控实现。轨迹若无法与业务终态关联，团队最多知道需求出现了，仍不知道它是否办成。

申请新预支款的资格、审批、定价与放款过程也不在这篇文章的披露范围内。因此，本例能说明聊天入口怎样接入既有业务，以及会话分析怎样推动改版，不能作为一套完整信贷产品流程来复用。

### 2、复用两种分类视角，同时保留原始会话与统计口径

这个案例适合借鉴的是同时使用预设类和自动归纳类：前者方便观察团队已知的问题，后者可能把过宽的“客服”拆成还款、到账、余额等业务任务。两种视角指向相近需求后，还应回到原始会话确认用户实际要做什么，避免仅凭标签命名决定产品需求。

若要比较不同周的趋势，需要记录抽样时间、样本量和分类配置。标签变了、采样范围变了，主题占比也可能变化；原文没有给出足以复算全部结果的样本与配置，不能把两次分类的比例差异当成产品改版效果。

当前官方文档还说明：未预设大类的配置首次生成类别后，会保存并供后续定时运行复用。因此，“每周运行”不必然表示每周重新发现一套大类。这是当前产品行为，案例没有披露当时怎样管理分类配置。若要持续发现新主题，应单独检查探索配置与固定趋势配置是否满足各自目的。

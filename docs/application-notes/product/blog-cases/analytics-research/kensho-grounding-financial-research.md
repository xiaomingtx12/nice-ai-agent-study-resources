# 金融数据检索 Agent：如何联合查询财务、评级与市场数据

> 主来源：[Kensho 在 LangChain 发布的客户案例](https://www.langchain.com/blog/customers-kensho)，发布于 2026 年 3 月 26 日，作者为 Ilya Yudkovich 和 Nick Roshdieh。产品落地补充来自 2026 年 7 月 21 日的 [AI Data Portal 公告](https://kensho.com/news/sp-global-launches-adaptive-retrieval-and-ai-data-portal-enabling-data-across-ai-agentic-workflows)与 2026 年 9 月 10 日的 [RBC Capital Markets 客户案例](https://kensho.com/news/rbc-capital-markets-trusted-ai-bankers-sp-global-kensho)。

Kensho Grounding 是面向金融研究的多 Agent 数据访问系统。它帮助分析师及金融 AI 产品，从标普全球分散的财务、市场、商品、评级和文本资料中取得答案，并保留引用。客户可以提出一个跨领域研究问题，由系统拆分查询、调用相关数据 Agent，再合并结果。

它参与的商业业务是专业数据与研究服务：让客户在自己的 AI 工作环境里使用标普全球的数据。本文先解释一项研究怎样完成，再介绍这套能力如何进入具体产品和客户部署。

## 一、比较一组能源公司，为什么需要多个专业数据源

### 1、用户提出的是研究问题，不是数据库查询

原文架构图的例子是：找出全球液化天然气（LNG）出口行业中的主要公司，并从财务表现、估值、商品价格风险、信用实力和管理层展望等方面比较。

对分析师而言，这是同一个研究任务。但营业收入和市值、天然气价格、信用评级、业绩会上的管理层发言，分属不同的数据系统，字段与查询方式也不同。原文所述的旧痛点，是研究人员耗费时间寻找和核对数据，或者先学习数据库结构与专用查询语言。

![Kensho 将液化天然气出口企业比较问题拆成财务市场、商品价格、信用评级和业绩会文本查询，再汇总带引用的结果](/img/blog-cases/kensho-grounding-research.png)

*原文图中的查询涉及四类数据：财务与市场数据、商品价格、信用评级、业绩会文本。右侧输出示意包含数字、引文和来源。图里的占位公司及价格不是本文提供的市场数据。图片来源：[LangChain 原文](https://www.langchain.com/blog/customers-kensho)。*

### 2、交付内容要能支持后续分析

Grounding 提供自然语言查询入口，将结果连接到经过验证的标普全球来源。上面的例子最终需要返回相互关联的财务数据、市场数据、评级和文本引文，用户据此继续研究。

主文还列出两类上层应用：帮助分析师比较行业表现的股票研究助手，以及跟踪可持续发展指标的 ESG 合规 Agent。ESG 指环境、社会与公司治理。这些应用可以共享底层的数据访问能力，不必分别重建所有数据管道。

## 二、路由负责拆问题，数据团队负责专业查询

### 1、一个入口协调多个领域

Kensho 将系统分为路由层和数据检索 Agent。后者在原文中简称 DRA，每个 DRA 面向一个专业数据领域，由相应数据团队维护，例如股票研究、固定收益或宏观经济。

路由层使用 LangGraph 组织执行。LangGraph 是用于管理有状态任务步骤及其衔接的框架；这里负责判断问题需要哪些领域、生成各领域的子问题，并汇总返回内容。

在 LNG 例子里，财务查询不必承担解释全部商品数据的职责，评级查询也不必理解整个研究产品界面。领域 Agent 处理自己的数据，路由再把这些结果组合成面向用户的回答。原文将这种分发再聚合的方式称为 map-reduce。

### 2、统一协议让结果可以合并和复用

多个团队分别提供 Agent 时，返回格式容易不一致：有的输出表格，有的返回文字，有的附带不同形式的来源信息。每个上层应用都去兼容这些差异，会重复承担集成工作。

Kensho 在早期试验后设计了统一的 DRA 协议，用共同的数据格式承载结构化与非结构化结果，并携带跨 Agent 追踪需要的信息。它既供模型理解，也供程序继续处理。

协议与路由共同形成上层产品的数据基础。新增股票研究功能或 ESG 应用时，可以接入既有数据能力，而不是重新连接每一套数据库。原文强调，这也让路由团队与专业数据团队能够并行维护各自负责的部分。

## 三、系统怎样判断是选错数据源，还是查错了内容

质量检查需要沿查询过程展开。原文介绍了三类持续工作：

- **跨 Agent 追踪**：通过调用轨迹及明确要求的元数据，定位请求到过哪些组件、在哪里出错。统一协议也负责在分布式系统中传递相关信息。

- **分阶段评测**：将测试查询送入基于 LangGraph 的路由执行图，检查选择的 Agent、取得的数据和答案完整性。既比较是否选对 Agent 且返回预期内容，也单独检查工具选择是否正确。

- **协议优化**：观察用户与 Agent 的交互，持续调整输出，使同一结果同时便于模型阅读和程序消费。

原文将路由执行图称为 RouterGraph。它是案例中的组件名称；公开文章没有提供其类定义，本文不把它当作读者需要直接导入的 LangGraph 通用接口。

## 四、2026 年的产品公告补上了哪些商业使用证据

### 1、同一个数据产品提供两种查询方式

7 月 21 日，标普全球宣布推出 Adaptive Retrieval，即按任务自适应地组织数据检索的服务。它允许客户的 Agent 通过自然语言，从多个授权数据集提取并组合资料，适合多步研究与报告生成。

这项能力与已有的 Deterministic Retrieval 一起进入 S&P Global AI Data Portal。后者通过直接、结构化的查询获取数据，更适合问题和所需返回内容较明确的任务。客户可以按自己的工作流使用其中一种或组合使用。

公告还提到金融 Skill、插件和 MCP 应用，把数据带入客户已有工具，并支持在对话中查看图表与表格。MCP 是让 AI 应用调用外部工具与数据能力的协议。商业产品的交付物包括授权数据访问与可追溯结果，客户不必自行重建所有查询连接。

### 2、RBC 银行员工怎样用数据准备客户工作

9 月 10 日的案例介绍了 RBC Capital Markets 的 Aiden 平台：银行员工需要快速取得有来源的财务答案，用于会面准备与客户工作。因为问题较结构化，团队选用的是 Deterministic Retrieval。

Kensho Labs 工程师与 RBC 团队每周多次协作，按银行安全与合规要求定制接入，调整响应时间及输出质量，修复边界问题，并进行规模化负载测试。官方报告部署覆盖八千名员工，实施一个月后查询准确率超过 98%，会面准备从数小时缩短到数分钟。

这段实施过程见 [RBC 客户原文](https://kensho.com/news/rbc-capital-markets-trusted-ai-bankers-sp-global-kensho)。

## 五、核验与本站判断：数据服务的专业性在哪里

### 1、公开材料支持到产品接入，没有支持到盈利结果

3 月原文来自 Kensho 作者在 LangChain 发布的架构介绍；后续公告说明了正式数据产品与银行部署。它们没有给出 Grounding 独立收入、计费单价、付费客户数量或客户投资收益。

RBC 使用的是确定性检索，不能把它的八千人覆盖规模或超过 98% 的查询准确率移植到 3 月的多 Agent 架构上。该数字也没有附完整评测集与统计口径；覆盖员工人数不等于活跃使用人数。7 月公告未逐项说明新服务与原 Grounding 组件的对应关系，内部 DRA 协议也不能直接当作对外 MCP 接口。

本次材料没有公开完整 DRA 协议、生产路由源码、评测集和访问控制实现。文中的股票研究、ESG 与银行研究也不能被进一步扩写成自动交易、自动合规签核或自动授信。

### 2、可借鉴的是领域分工，真正的难点是数据能否比较

**领域 DRA 适合由不同团队维护、查询规则各异的数据产品。** 财务团队维护财务数据的定义与查询，评级团队维护评级对象和更新方式；路由负责组合问题，可以减少上层产品重复集成。

**自己实现时还要补足结果的可比性约束。** 例如，两家公司的收入若分别来自不同财年、不同币种，直接并排会误导研究。返回结果应携带实体标识、期间、单位、口径和来源，聚合前检查能否比较。这些字段是本站建议，原文没有公布完整协议来证明它们已经逐项实现。

**引用与权限需要一同验证。** 对专业数据产品，客户能看到来源名称，不代表拥有查看全文或向外部系统转发的许可。接入新的聊天入口时，应验证数据授权如何随身份传递，避免在汇总答案中扩大可见范围。

若只有单一数据库、固定查询和清晰的字段映射，不必先建设多 Agent 系统。先保证实体、时间和计算口径正确，等跨团队、跨数据域的组合需求真实出现后，再引入这里的分工方式。

### 3、架构方式：能确认查询编排，不能推定每个 DRA 都自主规划

按[控制权的判断口径](../index.md#四架构方式与执行控制)，原文足以确认 **问题拆解、领域路由和结果聚合组成的多 Agent 查询编排**，但不足以将每个组件都判定为能够自主反复调查的 Agent。

在 LNG 公司比较中，路由选择相关数据领域，形成子查询，再把财务、商品、评级和文本结果汇总。统一协议规定了跨团队的数据交换方式。这些信息说明组件怎样协作，却没有完整说明某个 DRA 收到问题后，会动态选择并反复调用工具，还是执行较固定的查询与整理步骤。

因此，这个案例不宜硬分成“纯 Agent”或“纯 workflow（工作流）”。路由、并行和聚合也可以用工作流实现；原文采用多 Agent 的命名，仍需要实际调用轨迹或源码才能确定各层的自主范围。

后续产品材料中的 Adaptive Retrieval 和 Deterministic Retrieval 也不能替代这项核验。RBC 的确定性查询说明一个客户选择了怎样的数据服务，并不说明 Grounding 的所有组件都按同样流程工作；自适应产品名称同样不是开放规划能力的充分证据。

资料核对日期：2026-09-26。主文对应原文的数据碎片化、多 Agent 设计、自定义协议与实践经验四部分；商业使用补充限定为上面列出的 2026 年公告。

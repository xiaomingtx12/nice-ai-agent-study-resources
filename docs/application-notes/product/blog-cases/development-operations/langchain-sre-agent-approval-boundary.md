# 集群运维 Agent：从集群巡检、故障诊断到修复审批

> 来源：LangChain 团队的[工程文章](https://www.langchain.com/blog/how-we-build-an-autonomous-sre-agent-for-kubernetes-deployments)，发布于 2026 年 8 月 5 日；[公开示例仓库](https://github.com/langchain-samples/sre-agent)，本文核对提交 eee1cf02。

SRE Agent 是面向 Kubernetes 运维人员的集群巡检与故障调查 Agent。它定时汇总健康状态，在按需调查中调用专业子 Agent 诊断，提出变更后等人审批。原文围绕一个现实负担展开：值班工程师必须不断阅读 Pod、节点、扩缩容和部署状态，却常常只得到“一切正常”的结论。

## 一、运维人员怎样从集群信号走到处理决定

### 1、部署工程师需要持续照看已经运行的服务

作者负责 LangChain 内部自托管集群，也协助客户搭建和升级自托管环境。集群既承载正在运行的服务，也用于团队先行验证新的自托管功能。SRE Agent 要减少的，是持续查看基础设施、判断故障和准备处理办法的工作负担。

SRE 指站点可靠性工程；这里的直接使用者是值班或部署工程师。业务目标是更快完成故障分诊和修复准备，让服务可靠运行，而不是单纯生成一份技术报告。

### 2、巡检给出优先级，调查给出处置建议

Kubernetes 会产生大量底层信号：Pod 重启、内存耗尽、HPA（水平自动扩缩容配置）达到上限、节点异常、部署没有就绪实例等。值班人员最终要回答三件事：现在坏了什么，哪些情况快要出问题，应该怎么处理。把全部信号每隔几分钟交给完整 Agent 调查，既贵又容易把人淹没在重复报告里。

日常巡检把这些状态整理成按严重程度排序的 Slack 健康报告。需要解释异常时，再发起按需调查，汇总故障发现与修复建议。若建议涉及扩缩容、重启或修改配置，工程师在 Slack 中批准、编辑或拒绝，获批动作才交给执行工具。

这几种输出承担不同业务责任：报告帮助值班人员分配注意力，调查帮助判断原因，变更提案让负责人决定是否动集群。下文的读写拆分，是为了把这三段工作接起来。

### 3、常规检查足够便宜，才适合持续运行

团队原先每次正常巡检也运行整套编排，约需 20 次模型调用。改造后，定时器先用 Kubernetes Python 客户端取原始状态，这一步不消耗模型 token；再调用一次较轻的 Haiku 模型，要求它按工具参数格式返回结构化健康报告，按严重程度排序后发到 Slack。

真正需要解释异常时，主 Agent 才启动完整调查。原文报告，每次定时检查成本下降约 95%–99%，同时保持问题发现能力。

## 二、深入调查和变更各由谁执行

![SRE 总体架构：快速巡检与 Agent 调查分别执行，写工具集中在变更执行子 Agent 并逐次审批](/img/blog-cases/sre-monitoring-investigation-architecture.png)

*图 1：原文的运行入口、快速巡检、专业调查与变更审批结构。来源：[SRE Agent 原文](https://www.langchain.com/blog/how-we-build-an-autonomous-sre-agent-for-kubernetes-deployments)。*

下方 Fast path（快速路径）由定时器或健康检查请求进入：直接采集集群数据，做一次 Haiku 调用，生成结构化报告送到 Slack。上方 Agent path（调查路径）由主 Agent 规划、委派只读专家；需要变更时交给唯一持有写工具的 `change-executor`，每次写调用先经过人工批准。图中两条路径并列，没有画出“发现任意异常便自动启动完整调查”的连接。

右侧 Kubernetes 客户端承接工具执行，Slack 同时接收报告和审批请求。图上还把提示词缓存、递归与调用次数限制放在调查路径旁，说明开放式调查需要额外控制执行成本。44 个读工具、11 个写工具是原图列出的规模，不是部署时应固定照搬的数量。

### 1、只读专家分别检查集群的一面

按需调查时，主 Agent 并行委派 Pod、日志、扩缩容、性能、安全和可靠性等只读子 Agent。各自检查同一集群的不同切面，再由主 Agent 汇成按优先级排序的报告。主 Agent 用 Sonnet 作汇总，只读子 Agent 和定时巡检用 Haiku 控制成本。

团队选择 Deep Agents，是为了复用规划、子 Agent 委派和执行前暂停等运行能力。每个专家只接触与自己职责有关的工具和资料，主 Agent 负责把局部发现组合成值班人员可用的处理顺序。

### 2、变更集中在可供人审阅的窄工具

原文的边界是“可自主读、不可自主改”。主 Agent 不拿写工具；扩缩容、重启部署、修改 HPA 等动作集中到变更执行子 Agent。写工具调用前 LangGraph 暂停，在 Slack 上让人批准、拒绝或编辑提案。

团队故意不给它大范围 Helm 升级工具：审批人能看懂“把某个部署扩到 3 个副本”，却难以从一张卡片判断一次 Helm 升级会同时改动多少资源。

### 3、部署环境也按读写和网络入口划分

文章还描述了集群侧的 RBAC（基于角色的访问控制）：全局只读能力和受限写能力分开配置，与代码里的工具拆分对应。

Slack 用向外建立 WebSocket 连接的 Socket Mode 接收审批，无需为此开放入站地址。Kubernetes Python 客户端自动识别本地或集群内环境，镜像不必安装 kubectl；容器以非 root 身份、只读根文件系统运行。

## 三、轨迹怎样把误报变成下一轮检查

### 1、追踪成本、误判和人工修改

LangSmith 记录定时检查、每个子 Agent 的调查、读操作及变更提案。团队先从运行成本轨迹发现正常巡检也耗费约 20 次模型调用，才改成一次 Haiku 调用。另一条轨迹显示子 Agent 把故意只部署单副本的服务持续报成严重故障；保存当时的集群快照和判断过程后，团队修改提示词，并把该问题变成回归样本。

定时器直接调用模型的部分也补上追踪，使它与 Agent 调查一样可检查。团队还曾看到另一套 Agent 在文件搜索和读取之间反复循环，发现前已耗费约 5 美元，因此为运维 Agent 加上递归深度、模型调用次数和单工具调用次数的硬限制，并配合提示词缓存控制成本。

有人将建议的十个副本改为四个，编辑动作也会附到运行轨迹，成为“建议与人工决定不同”的标注。误判 Pod、漏掉内存耗尽等案例可加入数据集；提示词或模型变更时，再用模型评审和代码检查一起运行回归。

原文还介绍 LangSmith Engine：一套读取运行轨迹、发现问题并提出修复的辅助工程系统。它把相似失败归为问题，生成代码或提示词变更请求，再建议线上评测规则和回归样本。维护者审阅后决定是否采用。

其中一次问题是定时巡检报告反复要求人检查容量，但采集器根本没有提供 CPU、内存用量。

### 2、修复采集器后才可能回答容量问题

定时分支只看 Python 采集器交给模型的快照，生成报告的调用没有额外工具可用，无法自己补查遗漏的用量。原文说交互式 Agent 已有读取 Pod 和节点指标的能力，却没有接进定时分支。

Engine 将重复疑问归为同一问题，提出把已有指标读取和单位解析能力接入采集器。修改范围留在采集侧，不改分析提示词，也不增加采集阶段的模型调用。团队审核代码、加入回归样本并确认通过后才合入。

团队称会继续内部使用，并已向部分 LangSmith 客户推出；让审批状态更持久、让巡检记住近期事故仍是下一步工作。

## 四、公开示例怎样实现暂停，哪里还需核对身份

以上是团队对自身工作流的描述。公开仓库可核验部分边界：主 Agent 的 [agent.py](https://github.com/langchain-samples/sre-agent/blob/eee1cf02c14cf5579a1177f174c95d74c956c33f/agent.py) 只接只读工具，写工具集中在 change-executor 子 Agent；[change_executor.py](https://github.com/langchain-samples/sre-agent/blob/eee1cf02c14cf5579a1177f174c95d74c956c33f/subagents/change_executor.py) 给写工具配置执行前中断。

但“图暂停”与“审批人经过身份校验”是两个条件。Slack 入口可用 SLACK_APPROVER_IDS 限制人员；同一提交的 [api.py](https://github.com/langchain-samples/sre-agent/blob/eee1cf02c14cf5579a1177f174c95d74c956c33f/api.py#L990-L1003) 中，HTTP 审批端点没有身份校验。以下仅节选审批记录部分，省略函数其他逻辑；原代码的英文注释译为中文：

```python
# 注意：此端点未鉴权，审计只能把审批人记录为 "api-user"。
_audit(session, "approve", actor="api-user")
session.pending_hitl_actor = "api-user"
session.pending_hitl_approved = True
```

示例中的 [role-writer.yaml](https://github.com/langchain-samples/sre-agent/blob/eee1cf02c14cf5579a1177f174c95d74c956c33f/k8s/role-writer.yaml) 使用集群级 ClusterRole（Kubernetes 的集群权限角色）；部分自定义资源规则包含通配的 API 组与资源，并通过 ClusterRoleBinding 绑定服务账号。这不能证明内部生产环境也如此部署，却说明照示例接入自己集群前需要单独审查 HTTP 审批身份和实际权限范围。

## 五、本站判断：一次批准之后还要看集群终态

博客报告了成本下降和问题发现能力，但没有提供可独立复算的生产账单或漏报测试集。公开示例的实现检查与内部运行效果应分别看待。

作者说团队已开始向部分客户推出这套能力，但没有披露完整的客户交付套餐或收费方式。文章也没有给出事故升级、交接班、回滚和恢复验收的全套制度，不能把这套助手的流程当作完整运维服务流程。

这一案例可借鉴低成本常规采集、按需深入调查、窄写工具待审批和轨迹进入回归的分工。验收不能只看发现了故障和有人点击批准；还要看审批人是否有权、批准时目标状态是否变化、写入失败时是否停止，以及修改后集群是否达到预期状态。

公开示例的未鉴权入口和集群级写权限是具体部署风险，不宜外推为 LangChain 内部生产配置。95%–99% 的成本降幅属于团队报告，也不能替代故障漏报率和误改风险的测试。

### 1、架构方式：日常巡检是固定流程，深入调查交给 Agent

按[控制权的判断口径](../index.md#四架构方式与执行控制)，SRE 是分层很清楚的 **混合架构**。以下三部分不能因为共用“SRE Agent”这个名称，就全部理解为自主调查。

| 运行部分 | 实际执行方式 | 架构判断 |
| --- | --- | --- |
| 日常巡检 | 定时取集群状态，单次模型调用整理结构化报告，再发送 Slack | 固定 workflow（工作流）中包含模型步骤 |
| 按需调查 | 主 Agent 委派只读专家，使用诊断工具并汇总局部发现 | 有分工和工具使用的 Agent 调查 |
| 集群变更 | 窄写工具执行前暂停，经批准、编辑或拒绝后继续处理 | Agent 提出行动，审批流程限制执行 |

第一部分即使使用模型，也没有因此变成开放探索：取数和生成报告的外层步骤已经确定。第二部分才把调查交给主 Agent 与专业子 Agent。原文将定时巡检和按需调查分别描述，不能补推每一条异常报告都会自动启动完整调查。

固定并行分发本身不是自主性的充分证据；这里还要结合原文说明的 Deep Agents 规划、专家工具使用和调查汇总来判断。修复审批的暂停机制有前文公开示例支持，但示例的身份校验缺口也仍然存在。更准确的理解是按任务深度切换执行方式，而不是让一个无限循环的 Agent 持续检查整个集群。

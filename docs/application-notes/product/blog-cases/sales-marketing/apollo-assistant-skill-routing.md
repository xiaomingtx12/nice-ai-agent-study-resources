# 销售拓客 Agent：用一个目标串起找潜客、补资料与安排触达

Apollo AI Assistant 是服务销售平台客户的**销售拓客 Agent**。用户用自然语言提出获客目标，它组织寻找潜客、补全资料、研究公司与联系人、创建触达序列和分析效果等工作。

这个案例面对两种协调成本：客户要在多个产品模块之间来回操作，研发团队则要为每个新用例增加专门 Agent 和连接逻辑。Apollo 改为让助手按目标选择 Skill、发现工具并组织执行，同时用运行轨迹和评测控制质量。

> 来源：LangChain 客户案例 [How Apollo Rebuilt Its AI Assistant on Deep Agents to Power the Full GTM Loop](https://www.langchain.com/blog/how-apollo-rebuilt-its-ai-assistant-on-deep-agents-to-power-the-full-gtm-loop)，作者 Sofia Sulikowski，发布于 2026 年 7 月 21 日。前五节讲原文，后两节说明证据边界与实施建议；中文图解按图注区分来源。

## 一、业务挑战：同一个获客目标，需要用户手动连接多个模块

**本节说明助手要替用户省掉什么工作：把散落在各处的产品能力组织成一项销售任务。**

Apollo 覆盖潜客发现、联系人资料补全、外联、交易管理和效果分析。产品积累近十年后，客户调研反而发现，能力丰富带来了操作负担。

发起一轮潜客触达，需要到一个模块找线索，换到另一个模块补资料、起草联系步骤，再去分析界面看结果。用户想完成的是一次获客任务，却必须自己决定先后顺序、切换界面并衔接中间结果。

| 谁遇到了问题 | 原来的负担 | 希望改变什么 |
| --- | --- | --- |
| 销售用户 | 找人、研究、安排联系和看效果分散在不同模块 | 说明目标，由助手组织相关工作 |
| 助手研发团队 | 新用例需要新增子 Agent、接入主管并反复评测 | 复用任务指导和业务工具，减少逐条连接 |
| 线上排错人员 | 工具顺序、耗时和失败点分散在多处日志 | 按一次会话追踪完整执行过程 |

原文把业务范围称为 GTM（Go-to-Market，围绕获客与销售开展的工作）闭环。它的起点是让用户更容易调用平台已有能力，而非要求客户先学会所有模块的操作方式。

*图 1：根据原文整理的业务关系。箭头表示各环节怎样衔接，不是一条公开的客户执行记录，也不要求每次请求都运行全部环节。*

找潜客把宽泛目标落到具体公司和人员；补全资料与研究背景，为后续联系提供事实依据；触达序列把联系步骤与内容组织起来；分析能力帮助团队理解本轮外联表现。

“触达序列”是一组按安排推进的联系步骤，不只是某一封邮件的正文。销售语境中的“账户”指目标客户公司或组织，“联系人”则是其中的个人。

Skill 是完成某类任务的执行指导。原文列出的能力可以按用途理解：

| 用户要解决的问题 | 相关 Skill |
| --- | --- |
| 找谁、优先关注谁 | 潜客发现、账户评分、意向信号检测 |
| 对方是什么情况 | 账户研究、联系人研究 |
| 怎样安排联系 | 序列创建、邮件可送达性 |
| 这轮工作效果如何 | 分析 |

Assistant 根据本次目标选择适用的 Skill 并形成计划。例如，研究与序列创建可以为同一项外联任务服务；只问某家公司的背景时，不必把后续能力都执行一遍。效果分析为下一轮决策提供依据，原文没有展示它自动修改下一轮策略的过程。

## 三、架构变化：从固定连接专门 Agent，改为按目标获取指导与工具

**本节解释新版的扩展方式：任务方法、实际操作和临时并行工作分开组织，由编排 Agent 选择怎样组合。**

### 1、旧版代价：新增用例，需要新增子 Agent 并接入主管

第一版使用 LangGraph，即组织执行步骤与状态的图框架。Apollo 当时让主管 Agent 分发任务，每个专门子 Agent 负责一部分工作。

这套方案能够运行，但新用例需要写新子 Agent、连接主管，再验证是否沿规定路径执行。原文还报告，用户频繁遇到确认意图的提示。

![Apollo 原文架构图：左侧主管连接多个专门子 Agent；右侧编排 Agent 获取 Skill 指导、检索工具，并可委派临时并行 worker](/img/blog-cases/apollo-skill-architecture.png)

*图 2：原文的架构对照。左下角写明新增业务领域需要新增 Agent 类并重新连接主管；右侧把工具发现与任务指导单独列出。左侧 A–F 没有具体业务名称。*

团队比较了 Deep Agents 与 Claude Agent SDK，选择前者的一个理由是保留多模型供应商选择。这是 Apollo 对当时选型的说明。Deep Agents 在本例中是承载新版助手的 Agent 框架，让模型围绕目标选择能力、形成计划并执行。

### 2、新版分工：Skill 说明怎么做，工具完成业务操作

原图中的 DeepAgent Orchestrator 是负责组织任务的编排 Agent。它连接两类入口，并保留临时并行 worker：

*图 3：根据原文正文与架构图重绘。指导获取与工具检索没有固定先后，worker 也不是每项任务的必经步骤。英文名称是原图标记，并非本文核验过的函数接口。*

`get_skill_guidance` 提供某类任务的执行指导；`retrieve_tools` 查找可用业务工具，连接图中的 `@apollo_tool Registry`，即工具注册表。例如，账户研究需要指导说明研究哪些信息、怎样组织结果，还需要查询公司资料的工具提供事实。

原文所称的“扁平 Skill 架构”，改变的是能力扩展方式：工程师维护可组合的指导与工具，模型按当前目标组织路径。原图仍保留临时 worker，因此新版并没有取消所有委派。

### 3、研发流程：Agent 准备方案，资深工程师审核后再构建

Apollo 还开发了内部 meta-skill，即帮助研发团队规划和构建新能力的指导。流程是“问题描述 → Agent 生成架构方案 → 资深工程师审核 → 另一个 Agent 执行构建”。这是内部开发过程，与客户使用 Assistant 查潜客、建序列的运行过程不同。

旧方式下，新用例初版准确率约为 20%–30%，要经过较长评测才能达到团队设定的 80% 上线门槛。采用新架构及研发方式后，团队称从开发到上线的工作量下降约 80%–85%，响应延迟改善、确认意图的提示也明显减少。原文没有给出后两项的具体数字。

## 四、质量反馈：上线前设标准，线上沿会话轨迹定位问题

**本节说明 Apollo 怎样发现和修复失败：固定场景拦住已知问题，线上趋势与用户反馈发现新问题，运行轨迹帮助查明原因。**

### 1、排错入口：用会话 ID 找到哪一步出错

旧系统很难看清一次会话调用了什么工具、按什么顺序执行、在哪里超时。工程师需要交叉检查 GCS 日志、Mongo 数据和多个下游系统。

LangSmith 是记录 Agent 运行轨迹、支持评测与观测的平台。接入后，它成为 Apollo AI 团队默认的排错入口。工程师用会话 ID 查询提示词、上下文、工具调用、输出与延迟，定位失败步骤。

### 2、六层检查：让版本回归、线上趋势与客户反馈相互补充

Apollo 把这套质量体系称为 AI Watchtower。六层不是一次请求必须依次经过的六个节点，而是覆盖不同阶段的检查方式。

| 检查层 | 原文中的具体做法 |
| --- | --- |
| 质量标准 | 写代码前定义 3–5 个维度，如准确性、语气、相关性；每项按 1–5 分评分并配例子；上线前由两名独立评审者检查 50–200 条输出 |
| 端到端测试 | 保存必须通过的典型场景；每次涉及提示词或模型配置的代码变更、每次部署都执行 |
| 实时轨迹 | 新产品从第一天起接入；信号触发时，记录请求的完整提示词、上下文、工具调用、输出和延迟 |
| 线上趋势 | 对抽样流量做模型评审，观察质量、拒答率和延迟；明显下降时按类别、子类、用户分组下钻，并临时把采样率提高到 50%–100% |
| 每周汇总 | 综合各层信号，按套餐、公司规模和行业分组，检查问题是否集中在某类客户 |
| 客户反馈 | 反馈入口与功能一起上线；差评几分钟内进入每日分流队列；滚动七天窗口中差评率持续高于 8%，按 P1 级严重事故处理 |

这里要分清两种“效果”：销售分析关心潜客触达表现，Watchtower 关心助手回答是否正确、是否拒答以及响应多慢。两者需要各自的指标，不能用助手质量评分代替销售业务结果。

## 五、入口与结果：同一助手走出产品页面，持续运行仍在扩展中

**本节说明架构调整带来的使用方式变化，并交代原文报告的数据及未来方向。**

Assistant 起初依赖用户所在的 Apollo 页面获取上下文。改为按目标执行后，同一助手可以通过 API、MCP 和 CLI 使用；原文称之为 headless，即不依赖产品图形界面的运行方式。

MCP（模型上下文协议）让外部 AI 应用接入 Apollo 能力，原文列举了 Claude、ChatGPT 和 Perplexity 集成。CLI 是命令行入口，团队也用它减少 MCP 交互带来的上下文开销。客户可以从已有工具发起销售目标，无须先打开 Apollo 的某个模块。

| 原文报告项 | 数字或变化 | 对应的范围 |
| --- | --- | --- |
| 开发到上线的工作量 | 下降约 80%–85% | 团队对架构与研发方式调整的自述 |
| 响应与交互体验 | 延迟改善，确认提示减少 | 未给出量化对照 |
| Apollo MCP 采用情况 | 超过四万团队 | 通过 MCP 构建应用的团队 |
| Apollo API 采用情况 | 超过五十万团队，月调用超过 2.3 亿次 | 平台 API 的采用与调用规模 |

这些是文章发布时的数据。团队认为，外部入口的采用情况说明客户比预期更愿意自己组合技术工具。

后续投入包括提高现有 Skill 的准确性、覆盖新任务，以及发展定时和持续运行的 Agent。原文用“每天早上通过 Slack 等已连接工具交付符合 ICP 的前 50 条线索”说明方向；ICP（Ideal Customer Profile）指理想客户画像。这个例子出现在展望部分，并非文中展示过的完整生产运行记录。

## 六、证据边界：能确认能力组织方式，尚不能复原生产系统

**本节区分客户自述、架构图能支持的结论，以及公开资料仍未说明的执行细节。**

原文与配图足以支持：新版由 Agent 按目标选择 Skill、组织计划，结合工具完成任务，并可委派临时 worker。它没有提供 Apollo 生产源码或某个客户任务的完整运行记录。

| 需要进一步确认的问题 | 现有证据能到哪里 |
| --- | --- |
| 序列创建是否等于真正发送 | 披露了序列创建与触达能力，未展开启用、发信和人工确认的关系 |
| 收到回复后是否继续推进成交 | 未展开回复处理、预约、转交销售人员及后续交易推进 |
| 分析后是否自动优化下一轮 | 有分析能力，未展示自动修改筛选条件、内容或策略的机制 |
| Skill、工具和 worker 如何运行 | 未公开检索算法、加载方式、worker 生命周期、结果合并、持久化与重试实现 |
| 效果数字能否换算成业务收益 | 未披露可复算的完整比较方法、成交归因或 Assistant 独立商业化数据 |

按本站的[控制权判断口径](../index.md#四架构方式与执行控制)，新版属于 **Agent 主导的任务编排**。Skill 可以指导“先研究，再创建序列”，但这不足以证明服务端会拒绝跳过研究的调用。需要强制保证的条件，还得有业务执行约束。

旧版也有主管与专门 Agent，不能简单归为纯工作流，更不能从 Apollo 当时的连接方式推断 LangGraph 只能运行固定流程。原文减少的是确认意图的提示，不足以证明发送审批也已取消。

数字同样要保留口径：20%–30% 是旧方式的初版准确率，80% 是上线目标，都不是新版线上准确率；API 和 MCP 的团队数不等于 Assistant 的付费客户数，更不能直接换算成销售收入。

## 七、整篇总结：把销售能力做成可组合服务，再补齐执行约束与质量反馈

**本节总结同类助手怎么建设：Agent 负责组织变化中的任务，Skill 提供方法，工具承接业务操作，权限与评测保证结果可检查。以下为本站实施建议。**

### 1、架构总图：复用同一套能力，在业务服务中控制真实动作

可以借鉴 Apollo 的能力组织方式，让产品对话、API、MCP 和 CLI 接入同一个任务入口。入口传入用户目标、账户身份和必要上下文；Agent 获取相关指导与工具，决定本次工作怎样展开。

~~~mermaid
flowchart TD
    A["产品对话与外部入口<br/>API、MCP、CLI"] --> B["统一任务入口<br/>目标、身份与上下文"]
    B --> C["编排 Agent<br/>获取指导、查找工具<br/>组织本次任务"]
    S["Skill 指导库<br/>研究方法、序列编排方法"] --> C
    C --> T["授权业务工具<br/>查潜客、补资料<br/>准备触达草稿"]
    C -.->|需要并行时| W["临时 worker<br/>限定输入与工具<br/>约定返回结果"]
    C --> P["受控写入服务<br/>启用或发送前<br/>校验权限与必要审批"]
    T --> R["保存并交付结果"]
    P --> R
    C -.-> O["运行轨迹与质量反馈<br/>会话定位、输出评测<br/>版本回归"]
    T -.-> O
    P -.-> O
    R -.-> O

    classDef service fill:#eaf5ec,stroke:#477655,color:#193e25
    classDef guard fill:#fff3d6,stroke:#946b17,color:#513a0c
    class A,B,C,S,W agent
~~~

*图 5：同类销售助手的建议架构。身份传递、写入约束和结果记录是本站建议补齐的工程职责，不代表原文披露了 Apollo 的具体实现；worker 分支省略了结果回收过程。*

例如，研究 Skill 说明应了解什么，查询工具返回公司资料；序列 Skill 说明如何安排联系，创建工具保存草稿。启用序列和真正发送属于另外的业务动作，应由服务端检查身份、权限和必要审批。这样，即使入口或模型计划变化，发信条件仍由业务服务执行。

### 2、落地顺序：先跑通一项销售任务，再扩展组合与入口

| 实施阶段 | 具体工程工作 | 验收时检查什么 |
| --- | --- | --- |
| 1. 选定任务与交付物 | 从找潜客、研究并准备序列草稿等有限范围起步，定义质量维度和代表性场景 | 交付是否满足销售目标，资料与内容是否有依据 |
| 2. 分开方法与操作 | 把研究和编排方法写成 Skill，为查询、补全和创建记录提供清楚的工具定义 | 工具结果能否支持下一步，指导是否能复用 |
| 3. 接入动态编排 | 让 Agent 获取相关指导与工具，记录选择、执行结果和中间产物 | 能否组合完成任务，工具不足时是否明确报告 |
| 4. 补齐执行状态与权限 | 传递账户身份，区分查询、草稿、启用和发送；处理超时、重试与重复提交 | 跨入口权限是否一致，失败恢复是否造成重复动作 |
| 5. 建立质量反馈后扩展 | 接入轨迹、固定场景回归、线上抽样和差评分流，再按需求增加 worker 与外部入口 | 是否能定位失败并验证修复，质量是否因用户群不同而变化 |

并行 worker 应有明确的输入范围、工具权限、返回格式和失败处理，再由编排层汇总。原文只画出了这项能力，文件隔离、状态管理和回收机制需要实施方另行设计。

### 3、复用边界：动态目标适合 Agent，固定约束保留在程序中

目标经常变化、底层业务工具已经成熟的产品，可以复用“指导库＋工具发现＋目标编排”的方式。步骤固定、审批严格的任务，则应保留明确的流程控制。新增 Skill 不会自动解决工具缺失、权限校验或失败恢复。

这套方案的维护工作会落到 Skill 质量、工具契约、账户权限和评测场景上。Apollo 的六层体系值得参考，但 8% 差评阈值、抽样率和评审规模应按自己的流量与业务要求确定。

回到用户最初的困难，助手应让一次销售目标的中间结果能够继续被使用：潜客名单用于研究，研究依据用于序列草稿，执行结果用于效果分析。工程上的验收也要沿这条链检查任务完成情况，同时保留对真实业务动作的权限控制和排错依据。

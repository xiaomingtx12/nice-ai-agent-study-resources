# 出行客服 Agent：业务专家配置流程，平台承接路由与评测

> 来源：Lyft 团队的 [LangChain 客座文章](https://www.langchain.com/blog/lyft-built-a-self-serve-ai-agent-platform-for-customer-support-with-langgraph-and-langsmith)，发布于 2026 年 5 月 27 日。

Lyft 的 AI Assist 是为乘客和司机处理账户、车费、收入等问题的客服 Agent 系统。原文解释当客服问题快速增加时，如何让最懂业务的运营、用户反馈和产品人员配置常规 Agent，同时让工程平台继续负责路由、工具执行、状态和评测。

## 一、客服业务与内部配置平台怎样配合

### 1、乘客和司机来解决不同的出行问题

AI Assist 承接 Lyft 的乘客和司机客服请求。乘客会问遗失物品、收费争议和行程问题；司机会问收入、账户访问、车辆损坏理赔或税务事项。产品需要识别当前诉求，将它送入相应服务流程，并在对话中调用所需业务工具。

司机从收入问题转而询问损坏理赔时，服务流程也要跟着变化。原文中的路由、对话状态和转交能力，都围绕“同一个人可能在一次客服会话中处理多个问题”展开。

### 2、客服专家维护流程，工程团队提供执行能力

原文重点介绍的自助平台，面向内部运营、用户反馈负责人和产品经理。他们知道某类问题应问什么、按什么政策处理、什么时候转交；平台让这些人员直接写提示词和配置，更新常规客服流程。乘客和司机使用的是配置完成后的 AI Assist。

Lyft 从 2023 年起建设乘客和司机 Agent。新增一个问题类型，通常由领域专家描述流程，机器学习工程师再把规则翻译成提示词和工具配置；上线后双方反复查轨迹、改代码。一只 Agent 就可能花数月。到了 2026 年，新用户群、新问题和自动驾驶车辆支持扩大了需求，这种跨团队往返成为瓶颈。

团队没有把所有客服问题都交给低代码配置。车辆损坏理赔可能涉及图像处理、欺诈识别、多段分类和自动化动作，仍由工程师编写专用 Agent。较稳定的常规问题，则让业务人员通过结构化提示词和 JSON 配置建立可配置 Agent。这样缩短的是业务流程迭代的距离，不是取消底层工程。

业务作者提交一个明确的问题范围和处理流程，平台接上工具与运行保障，再用小流量真实会话检查表现。日常维护由此分成两类：业务专家修订政策表达和服务分支，工程师维护工具、复杂理赔流程和运行基础。

## 二、一条客服消息怎样找到处理者

### 1、路由负责识别，专门 Agent 负责处理

Lyft 用 LangGraph 组织路由。乘客和司机各有入口；元 Agent（负责识别请求并分派任务的主 Agent）把消息交给适合的子 Agent。假如司机先问收入，聊到一半转为车辆损坏索赔，原子 Agent 可以把控制权交回元 Agent，重新路由到理赔 Agent，而不是硬沿收入流程回答。

![Lyft 客服路由：乘客和司机请求经元 Agent 分流，专门 Agent 与配置型 Agent 均可交回控制权重新路由](/img/blog-cases/lyft-router.png)

*图 1：Lyft 的客服请求总路由。来源：[Lyft 团队原文](https://www.langchain.com/blog/lyft-built-a-self-serve-ai-agent-platform-for-customer-support-with-langgraph-and-langsmith)。*

图中的 Rider、Driver 分别是乘客和司机；Meta agent 是保存路由状态的主 Agent。标为 specialized 的节点由工程师编写，标为 configurable 的节点由业务配置生成。虚线 Reroute 表示交回控制权、重新分派；右侧 finalize 是各条路径共用的收尾步骤。

### 2、对话状态和安全检查由平台承接

每个子 Agent 是独立的 LangGraph 子图。原文流程图中，每轮先清理状态，再并行检查恶意意图与安全问题，经过路由后才进入模型推理。模型需要工具时进入工具节点，读取执行结果后继续判断；完成本轮则进入结束节点。

![Lyft 子 Agent 单轮流程：清理状态后并行检测恶意意图和安全问题，再进入模型与工具执行循环](/img/blog-cases/lyft-subagent-turn.png)

*图 2：各类子 Agent 共用的单轮执行结构。来源：[Lyft 团队原文](https://www.langchain.com/blog/lyft-built-a-self-serve-ai-agent-platform-for-customer-support-with-langgraph-and-langsmith)。*

左侧两个 detector 分别检测恶意意图和安全问题。右侧 tool call 与 observation 的往返箭头表示“调用工具—读取结果—继续判断”，done 分支则结束当前轮次。

跨轮对话由 Lyft 自建的 DynamoDBSaver 保存。它是 LangGraph 检查点存储的实现，记录完整图状态、执行元数据和前一个检查点的关联，供会话回放、排错和状态检查使用。业务专家不用自己处理这些执行细节。

### 3、配置型 Agent 复用底层能力

配置型 Agent 从内部服务读取 JSON 配置，从 LangSmith Prompt Hub 读取提示词。Prompt Hub 是团队保存和复用提示词的地方；平台中的 ConfigurableAgent 是根据配置组装 Agent 的类，负责图构建、工具绑定、安全关口和状态管理。

启动时，平台按配置的意图名称把这些 Agent 注册为主图的子节点，并连接统一的收尾节点。产品经理因而可以通过提示词和配置增加司机税务问答，在平台已有能力上扩展一个常规话题。

原文的 “Specialized vs. Configurable Agents” 小节给出了这段注册代码。以下保留代码，只将两条英文注释译成中文；文章没有披露所在文件、外层函数或提交版本，不能把它当作可独立运行的完整实现。

```python
# 配置型 Agent 在启动时动态加载。
for configurable_agent in load_configurable_agents():
    self.configurable_subagents[configurable_agent.config.intent] = configurable_agent

# 每个配置型 Agent 都作为子图注册到元 Agent 中。
for configurable_subagent in self.configurable_subagents.values():
    graph_builder.add_node(
        configurable_subagent.config.intent,
        configurable_subagent.get_state_graph()
    )
    graph_builder.add_edge(configurable_subagent.config.intent, "finalize")
```

第一段以 `intent`（客服问题类型）为键保存加载结果；第二段取出各实例的执行图，注册为同名节点，再把出口连接到共用的 `finalize`。因此，业务人员新增的是平台已有能力能够承接的一种问题配置，图构建、工具绑定和状态管理仍由公共实现提供。

注册解决“有哪些处理者”，对话中的转交还需要控制流。原文另用 `Command(goto=...)` 指定下一节点；`Command` 是 LangGraph 用来表达状态更新和跳转的对象。子图需要交回主图时，使用带 `graph=Command.PARENT` 的跳转，由父图继续处理重新路由。启动时加载配置与运行中换话题是两个不同环节。

## 三、为什么“会配置”仍可能处理错问题

### 1、业务经验必须写成有出口的分支

平台开放后，团队发现最难的是把业务经验写成 Agent 能执行的流程。原文举过司机讨论车费时中途换话题的例子：提示词只写了顺利处理车费争议的步骤，没说明何时停止和改派，就会继续回答过时的问题。“保持同理心”这样的抽象话术也无法稳定约束具体措辞。

Lyft 为此要求提示词写清五部分：

- **身份**：服务哪类用户，负责哪类问题。

- **目标**：用具体动作描述要完成什么，避免只写“帮助用户”。

- **范围**：哪些问题可以处理，哪些不能处理，越界后交给谁。

- **阶段流程**：各阶段的进入条件、分支、退出条件和结束动作。

- **话术规则**：明确该说什么、避免什么，并给具体措辞例子。

审核清单还会检查每阶段是否有出口、工具不可用时如何继续。原文将提示词当作可检查的产品规格：业务专家要把平时靠经验判断的分支写出来，平台才能稳定执行。

### 2、自动提示词检查还在建设

文章还描述了一个尚在建设的 Git 提示词校验流水线：作者在界面写好提示词后，配置仓库生成变更请求，静态检查抓格式错误的模板变量、重复意图和拼写问题；模型检查提示词注入风险、互相矛盾的规则和走不出的分支。

计划中的流程会阻止有问题的配置合入，并把行内反馈交回编写界面，让业务作者直接修订。它与已经使用的模板和人工审核清单处于不同建设阶段。

## 四、上线后怎样判断配置是否可靠

### 1、小流量取真实多轮样本

![Lyft 新 Agent 通过小流量采样、模型评审与提示词修订后逐步扩大流量](/img/blog-cases/lyft-evaluation-rollout.png)

*图 3：新 Agent 全量上线前的评测与迭代路径。来源：[Lyft 团队原文](https://www.langchain.com/blog/lyft-built-a-self-serve-ai-agent-platform-for-customer-support-with-langgraph-and-langsmith)。*

图中从 5%–10% shadow（影子流量）开始，抽取轨迹形成 LangSmith 数据集，再让模型评审幻觉、简洁性和领域指标。通过后逐步扩大到全量，未通过则修订提示词、重新运行。它把业务配置的反馈出口接回作者，让“上线一个话题”包含持续校正；图没有给出每项评分的具体放量阈值。

新 Agent 先拿约 5%–10% 的真实流量。团队从 LangSmith 轨迹抽取多轮对话，使用共同的模型评审模板，再补上具体业务指标。原文表格列出三项基础标准：

| 基础标准 | 检查的问题 |
| --- | --- |
| 幻觉 | 是否编造数据不支持的政策、行程详情或功能 |
| 简洁性 | 回答是否过长，是否适合司机快速阅读 |
| 矛盾 | 前后陈述是否冲突，是否与自动化执行结果相抵触 |

司机收入 Agent 还要检查是否遵守收入政策、推理是否自洽。原文建议尽量使用通过／不通过等二元结果，便于行动。生产评测按会话过滤并抽样运行；初期采样较高，信心增加后再调整。

每个 Agent 还跟踪运行量、错误率、p50/p95 延迟、token、工具调用成功率和模型评测分数。若 15 分钟内错误率超过 5%，或 p95 延迟超过 10 秒，PagerDuty 通知值班工程师。轨迹携带用户类型、Agent 名、意图和会话 ID；有人报告错答时，工程师可以检查是意图分类、工具调用还是最终回答出了问题。

### 2、运行指标与业务解决率分开看

Lyft 报告首个司机 Agent 约花六个月，新配置型 Agent 约两周；所有生产 Agent 均接入自动评测，幻觉和矛盾率下降 20%，AI 解决率上升 16%。越来越多非工程成员可以自行迭代常规 Agent。

后续工作包括完成提示词校验流水线、用模拟对话和工具响应提前测试、让人工成对比较提示词版本，以及从抽样评测走向更连续的生产评分。团队还计划把平台扩展到欧洲 Freenow 客户和自动驾驶支持场景。

## 五、本站判断：把业务配置和执行权限分开验收

这篇文章披露的是客服业务的承接方式和内部配置平台，没有逐项公开退款、赔付资格、金额计算、申诉或结案规则。图中的 Agent 能处理某类问题，不足以证明该类问题已从申请到业务结案完全自动化。

这个架构适合工具和业务边界已由平台确定、问题类型持续增加的客服团队。业务专家能改车费争议的阶段说明，不意味着可以凭提示词新增赔付工具或扩大账户修改权限。原文没有公开逐工具授权实现；涉及赔付资格或跨账户动作时，仍需在实际业务服务核对身份、参数与操作结果。

复用时可以固定四类多轮回归题：正常完成、半途换话题、工具失败、必须转人工。每题同时检查路由去向、所用工具、配置版本和最终客服任务是否完成。“六个月到两周”衡量的是不同阶段的开发任务，16% 与 20% 也缺少完整口径；这些结果支持关注平台方式，却不能直接当成自己团队的收益预测。

### 1、架构方式：固定执行结构中运行对话 Agent

这个案例属于 **workflow（工作流）与 Agent 结合的架构**。按[控制权的判断口径](../index.md#四架构方式与执行控制)，判断依据是子图中的实际步骤：状态清理、安全检测和收尾有预设位置；进入模型与工具循环后，模型根据当前对话及工具结果决定继续调用还是结束当前轮次。

司机先询问收入、随后转为车辆损坏索赔时，系统还可以交回控制权重新路由。这里既有程序提供的交接结构，也有依据对话选择处理能力的行为。因而不能因为它画成了 LangGraph 图，就把模型与工具之间的往返理解为一条固定问答流水线。

业务专家配置的阶段、进入条件和退出条件，又需要区分提示词规则与代码约束。原文说明了结构化配置、审核清单和共用运行结构，但没有逐项证明业务规则都由代码强制执行。模型负责理解和处理请求，平台提供工具与执行结构；具体退款、赔付等业务条件怎样被硬性校验，仍需单独核对。

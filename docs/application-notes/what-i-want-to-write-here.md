# 怎么带着真实问题拆一份开源项目

这一栏的主题是「带着真实问题去开源项目里看是怎么解决的」。

## 先回答：你带着什么真实问题来的

在打开一份源码之前，先把这个答清楚：**你这次来，是带着哪个真实会遇到的问题？** 是一个具体的、实践里撞到的问题——比如“我的 Agent 多轮调用时上下文怎么不爆”、“工具并发执行怎么不互相污染”、“长任务怎么做可中断可恢复”。

问题定下来之后，再补三个辅助判断：

1. 我打算从它身上**借走什么**——是某个抽象、某个分层、某条边界、某个失败模式？
2. 我打算**避开它什么**——是某条看起来先进但有隐性代价的设计？
3. 我打算**用它在什么场景下**——是自己手搓一个类似系统时做参考？还是只是想把一种实现看明白？

## 我会强迫自己守住的三条底线

### 1. 不抄 README

README 是写给“还没看过这个项目”的人看的。它讲的是「这个项目能做什么」，不是「它为什么这样拆」。

如果我的拆解文档只是把 README 翻译成另一种语言、加几张图，那它对读者毫无增量——读者看原文比翻译得快。

**强约束**：每一篇必须至少指明 3 处 README 没写、只有源码才看得出的东西。可能是：

- 一个隐藏的副作用（比如某段代码在某个分支下会跳过校验）
- 一个不成文的约定（比如团队在某处写了注释「don't touch this」）
- 一个 README 提到的功能，但实际实现是 stub 或 TODO

### 2. 不把源码翻成大白话

源码本身不是教学材料。把 `class X { method Y() { ... } }` 翻译成「类 X 有方法 Y 做了 ...」是浪费读者时间。

真正有价值的拆解是：

- **指出位置**：这段代码在系统骨架的哪个节点上？为什么放这里而不是别处？
- **指出约束**：它的上游依赖什么、下游被谁消费、哪条边界由它守着？
- **指出代价**：选这种写法放弃了什么？换一种写法会出什么问题？

如果一段源码讲不清这三件事，再多也是噪音。

### 3. 必须给工程判断

文档末尾必须有「我的判断是什么」一节，至少回答：

- 哪些设计**值得照搬**到自己的项目
- 哪些设计**值得借鉴思路，但实现要换**（比如 Dify 的 Plugin Daemon 用 Go 写，自己手搓时 Python + 独立进程可能更现实）
- 哪些设计**看着漂亮但别碰**（比如某个看起来简洁的抽象，背后是三个隐式假设）
- 这套设计**什么时候不适用**（比如 RAG 索引管线在文档量 1k 以下完全是过度工程）

如果做不到这一节，就别硬撑——把读源码的笔记留在仓库 commit message 里就行，不一定要发出来。

## 一篇合格的拆解，至少要回答这 6 个问题

1. **我带来的真实问题，在这个项目里是怎么被解决的**——这是入口，答不出这条整篇就跑题。
2. 这个项目**最值得拆开看的是哪一层**——为什么不是别的层？
3. 这一层**撑住了系统的什么能力**——如果抽掉它会发生什么？
4. 这一层的**源码里最容易误读的边界**是哪一处——为什么会误读？
5. 如果我打算在自己项目里复用这部分，**前置假设是什么**——假设不成立时怎么退化？
6. 它的**README 没写、但源码里写得最坦诚**的一行注释或一段说明是什么？

第一题保证文档对得上你带来的问题，中间四题保证文档不空、有用，最后一题保证文档有温度。

## 我会主动避开的写法

- 把官方架构文档换个说法再写一遍
- 用「这个项目有 100 个特性」掩盖自己其实没看代码
- 只讲优点、避开失败模式 / 已弃用代码 / 已知 issue
- 拿一个 50 万行代码的项目，挑 5 行源码讲「你看它写得多好」

## 一句自查

如果把项目名字抹掉，这篇文档还能成立，那说明我大概率还没抓住它真正的特征。

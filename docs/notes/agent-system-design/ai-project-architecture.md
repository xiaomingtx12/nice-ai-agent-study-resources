# AI 工程项目架构：从 I/O 密集型编排到并发治理

调用远程模型和工具的 Agent Loop，编排进程通常有较多时间在等待网络返回，适合按 **I/O 密集型（I/O-bound）负载**设计。但文档解析、本地检索和模型推理可能受 CPU、GPU 或内存限制，需要分层判断。

本文讨论多用户 AI 应用的服务端架构：识别负载，估算容量，再决定执行方式与资源边界。小项目可以从模块化单体起步；并发上限、超时和过载出口应从上线时就有。文中数字均为演算假设。

## 1. Agent Loop 的负载特征

Agent Loop 是反复调用模型、执行工具、收集结果并决定是否继续的运行流程。采用远程模型与工具时，一轮任务通常经历下面的等待路径：

```text
组装上下文 → 等模型响应 → 执行工具并等待结果 → 更新状态 → 下一轮
               网络 I/O          网络 / 文件 / 计算
```

### I/O 密集型指等待占主导，不代表数据量大

一次模型调用可能只传输少量文本，却长时间等待远端生成。对编排进程而言，这段时间主要是网络 I/O 等待；对模型服务器而言，可能是推理计算、显存访问或排队。同一次调用，在不同服务上有不同瓶颈。

因此，“高 I/O”容易混淆两件事：大量时间在等 I/O，与每秒传输大量数据。Agent 编排常需要处理前一种压力。异步 I/O 允许执行线程在等待期间处理其他任务，适合这种工作方式。[1][2]

| 运行位置 | 典型工作 | 需要观察的瓶颈 | 执行方式 |
| --- | --- | --- | --- |
| Agent 编排层 | 等模型、搜索、数据库和远程工具返回 | 连接池等待、请求时延、活跃连接、下游配额 | 异步 I/O 或虚拟线程，限制在途请求数 |
| 本地工具层 | 文档解析、数据转换、图像处理 | CPU、内存、文件读写；按具体工具测量 | 重计算移到独立进程或 worker |
| 模型推理层 | 自部署模型生成 | GPU 计算、显存容量与带宽、推理排队 | 独立推理服务，按实际输入输出长度规划容量 |
| 状态与事件层 | 检查点、日志、进度事件 | 数据库连接、写入延迟、事件缓冲 | 短事务、有界缓冲，必要时合并事件写入 |

检查点是用于恢复任务的进度快照。确认瓶颈时应分别记录各阶段耗时和资源占用。低 CPU 利用率也可能来自配额等待或锁竞争，不能单凭 CPU 空闲就认定网络 I/O 是瓶颈。vLLM 是用于部署和调度模型推理的服务引擎，可通过其排队、KV Cache（推理键值缓存）与生成延迟指标观察推理层瓶颈。[10]

### 长等待与多轮调用共同放大并发压力

任务耗时增加后，相同到达速率下会有更多任务同时未完成；一次任务中的模型调用、子 Agent 和工具调用又会增加下游工作量。系统需要同时处理三个不同问题：

- **多任务并发**：用户 A 等模型时，执行用户 B 的任务。
- **单任务并行**：对没有依赖、允许同时执行的工具或子任务做并行调度。
- **循环依赖**：下一轮模型需要上一轮工具结果时，必须等待，不能直接并行。

异步调度能利用等待间隙，提高服务承载能力；它不会自动缩短一次模型生成，也不会消除循环中的数据依赖。[1][2] 把一个任务拆成更多子 Agent，还需要评估额外调用对总吞吐和其他用户的影响。

## 2. 容量估算：同时有多少任务、多少调用

假设系统稳定接纳每秒 20 个任务；每个任务从开始执行到结束平均用时 30 秒，平均调用模型 4 次，每次模型调用平均用时 5 秒。

| 容量指标 | 估算结果 | 对应约束 |
| --- | --- | --- |
| 平均执行中任务数 | `20 × 30 = 600` | 活跃任务、上下文内存和执行资源 |
| 模型调用到达率 | `20 × 4 = 80 次/秒` | 模型请求速率配额 |
| 平均在途模型调用数 | `80 × 5 = 400` | 调用并发、连接池和超时管理 |
| 每分钟输入 token | 每次平均 3,000 token，则为 `80 × 60 × 3,000 = 1,440 万` | 输入 token 配额 |

这里使用“平均数量 = 平均到达率 × 平均停留时间”的关系。统计边界必须一致：若 30 秒包含排队，600 就是排队与执行中的任务总数。平均值用于容量规划，还需通过突发流量和长任务分布验证余量。

假设可用输入配额只有每分钟 200 万 token，则按上述平均输入长度，模型调用吞吐上界约为 `200 万 ÷ 3,000 ÷ 60 ≈ 11.1 次/秒`，折合约 `2.8 个任务/秒`。增加编排 worker 无法突破这个限制。实际还要同时满足输出 token、请求数等约束；Claude API 就分别设置了这些速率限制。[3]

容量规划应区分新任务提交、进度查询、执行中任务和实际模型调用。一个批量导入接口可能只有一次提交，却产生数千个子任务；等待人工审批的任务则应释放执行资源，不计入活跃模型调用。

## 3. C 端与 B 端的架构差异

C 端直接面向个人用户，B 端面向企业或组织。两者主要影响资源分配和交付要求，不能仅凭用户数量判断并发压力。下表列出典型设计侧重点。

| 维度 | C 端场景 | B 端场景 |
| --- | --- | --- |
| 负载来源 | 对话、创作与活动带来的集中访问 | 员工交互、业务 API、批量导入与定时任务并存 |
| 响应目标 | 聊天关注首段反馈；长生成展示排队与进度 | 在线助手同样需要低延迟；批处理按完成期限保障吞吐 |
| 配额分配 | 按账号、套餐和任务类型限制使用量 | 按租户、部门与应用分配容量，保护其他租户 |
| 成本约束 | 单用户、单任务预算和套餐用量 | 租户成本归集、批次预算、预留容量的利用率 |
| 状态与权限 | 用户会话、文件权限、取消与重连 | 企业内外的数据权限、工具凭据、业务写入审计与恢复 |

**C 端例子：聊天与深度研究。** 给聊天保留模型调用预算；研究任务进入后台，限制活跃任务数、子 Agent 数和总调用量。如果只分开队列，却仍无差别争抢同一份模型配额，聊天仍可能被研究任务挤占。

**B 端例子：批量文档与在线助手。** 一个租户提交 3,000 份文档时，拆成可恢复的子任务，限制该租户的执行数，并给其他租户的在线任务保留容量。批次截止时间决定所需吞吐，提交接口的请求数不能代表后台负载。

数据隔离与容量隔离需要分别设计：租户之间不能互读数据，也应避免耗尽彼此共享的资源。共享或专属部署的取舍可参考 Azure 的多租户 AI 架构说明。[9] 专属 worker 若仍共用已耗尽的模型配额，也无法保障端到端吞吐。

企业采购的客服系统还可能承接消费者的集中咨询，兼具两类压力。调度应按实时性、工作量、共享资源和交付期限分类，而非只按 C/B 端划分。

## 4. 执行架构：并发编排与计算隔离

面向长任务和多租户的参考部署如下。短问答可在 API 内有界执行；需要跨请求、跨重启继续的任务进入后台 worker。

```text
客户端：提交 / 查询 / 订阅事件 / 取消
  ↓
API 层：鉴权、提交幂等、租户准入
  ├── 短交互 → 有界并发执行
  └── 长任务 → 持久化任务 → 有界队列 → 并发编排 worker
                                           ├── 模型调用 → 共享配额 → 模型 API
                                           ├── 远程工具 → 各自的连接池与限额
                                           └── 重计算 → 进程 / 沙箱 / 专用 worker

执行结果 → 任务状态与事件 → 查询或推送给客户端
```

### 使用事件循环时，异步必须落实到实际调用链

事件循环负责调度就绪任务。在协程里直接调用同步 HTTP SDK、同步数据库客户端或耗时计算，会阻塞该事件循环所在的线程，其他协程也会被拖住。给函数加上 `async def` 不会改变这些调用的阻塞性质。[2]

| 调用类型 | 处理方式 | 边界 |
| --- | --- | --- |
| 原生异步网络客户端 | 使用异步 API，复用客户端和连接池 | 设置连接、读写和连接池等待超时 |
| 只有同步接口的 I/O SDK | 放入有界线程池 | 控制提交量；超时不保证后台线程已经停止 |
| CPU 密集的本地工具 | 独立进程或计算 worker | 按 CPU、内存限制执行数，避免占用事件循环 |

HTTPX 是支持同步与异步调用的 Python HTTP 客户端库。其文档明确建议复用异步客户端，避免在高频循环中反复创建客户端而失去连接池收益。[5] 连接池大小也应与调用并发匹配，不能让大量任务在池内无期限等待。

并行工具还需检查读写冲突。同一任务中的两次搜索可以独立执行；读取工具结果后再调用模型必须等待；同时修改同一业务对象则需要串行或冲突控制。不要先创建无限数量的协程，再依赖执行时的信号量兜底，待执行对象本身也会占用内存。

### 异步执行与持久化执行分开设计

进程内协程会随进程退出而消失。需要恢复的长任务先持久化，再返回 HTTP 202 和任务标识，由 worker 推进；客户端独立查询或订阅进度。[4]

要避免“任务已入库、消息未入队”的空档，可在同一数据库事务中保存任务和 outbox（待投递记录），由投递器重试发送。消息可能重复，worker 仍需按任务标识和执行版本控制领取与提交。

小规模阶段可以共用一个代码仓库，分别启动 API 与 worker。拆分依据是资源占用和恢复要求；仅仅使用异步 I/O，不要求引入消息队列或微服务。

## 5. Java、Python、TypeScript 的框架支持

三种语言都能承载 I/O 密集型 Agent 编排，但执行模型不同。下表比较如何利用等待时间；实际吞吐仍受模型配额、连接池和工具容量约束。TypeScript 部分以 Node.js 服务端运行时为例。

| 技术路线 | 框架与运行机制 | 阻塞调用如何处理 | CPU 密集工具放哪里 |
| --- | --- | --- | --- |
| Java：同步写法 | Spring Boot 组织应用，Spring MVC 提供 Web 接口；可结合 Java 21+ 虚拟线程承载 I/O 等待 | 在虚拟线程执行，核对依赖库和实际执行器；限制下游并发 | 有界计算线程池或独立 worker |
| Java：非阻塞写法 | Spring WebFlux 提供基于响应式流的 Web 栈，用少量线程调度 I/O | 使用非阻塞客户端；遗留阻塞代码移到有界执行器 | 独立计算池或 worker，避开事件循环 |
| Python | FastAPI 提供 Web 接口，`asyncio` 负责协程调度，HTTPX 提供异步 HTTP 调用 | 原生异步客户端优先；同步 SDK 移到有界线程池 | 纯 Python 重计算通常交给独立进程或 worker |
| TypeScript / Node.js | NestJS 组织服务端模块，可用 Fastify 作为 HTTP 底层；事件循环调度异步 I/O | 使用异步 API；阻塞库移出请求事件循环 | `worker_threads` 工作线程池或独立进程 |

上述执行机制分别见 Java、Spring、FastAPI、NestJS 与 Node.js 官方文档。[1][2][11][12][13][14][15]

### Java：根据现有依赖选择虚拟线程或 WebFlux

虚拟线程是 JVM（Java 虚拟机）调度的轻量线程，在许多阻塞 I/O 等待期间可以释放承载它的操作系统线程。已有同步业务代码、同步数据库驱动和工具 SDK 时，可以评估 Spring MVC 配合虚拟线程，保留顺序调用的写法。Spring Boot 提供 `spring.threads.virtual.enabled` 开关，但自定义执行器不会因此全部变成虚拟线程，需检查实际调用路径。[11][12]

虚拟线程不会增加 CPU 算力，也不会扩大数据库连接池。调用模型前仍需获取并发许可；不要用固定大小的虚拟线程池模拟配额控制，应该按受限资源限制并发，并给等待许可的任务设置数量与时间上限。部分阻塞路径仍可能占住底层线程，具体行为取决于 JDK 版本和依赖，应使用实际调用链压测。[11]

WebFlux 适合依赖链能够保持非阻塞的服务。它通过响应式流组织异步处理，并支持消费者反馈处理速度的背压机制；`WebClient` 是其中用于调用远程 HTTP 服务的非阻塞客户端。在事件循环中直接执行阻塞 SDK，仍会拖住其他请求。若主要依赖都是同步接口，为了使用 WebFlux 而到处切换线程，通常不如沿用 MVC 容易维护。[13]

### Python：区分异步路由、线程池与后台任务

FastAPI 的 `async def` 路由适合配合异步模型和工具客户端。普通 `def` 路由由框架放在线程池执行，但在异步路由里直接调用的普通辅助函数不会自动进入线程池。比如把同步搜索 SDK 包装成普通函数后直接调用，依旧会阻塞事件循环。[1]

线程池适合承接无法改造的同步 I/O；重计算应隔离到进程或专用 worker。[2] `BackgroundTasks` 是 FastAPI 在响应后运行进程内工作的机制，不能承担重启后必须恢复的长任务。需要独立执行和重试时，可以接入 Celery 等任务队列；队列任务内部是否采用异步编排，还要单独设计。[16]

### TypeScript：异步 I/O 与计算并行分开处理

NestJS 和 Fastify 不会改变 Node.js 的执行边界：网络等待可以异步调度，大型 JSON 处理、同步文件操作和长时间计算仍可能阻塞事件循环。`worker_threads` 是 Node.js 用于并行执行 JavaScript 的工作线程模块，适合计算任务；普通网络请求优先使用原生异步 I/O，无需每个请求创建一个工作线程。[14][15][17]

批量调用要在启动时控制并发。`Promise.all` 用于汇总多个异步结果，本身不提供限流；把整个批次的请求一次性启动后再等待，仍可能耗尽连接或模型额度。长任务可以交给 BullMQ 这类基于 Redis 的任务队列，由独立 worker 执行，并配置重试与并发。消息重投后仍需保证业务幂等。[18]

### AI 框架负责哪一层

Spring AI 为 Java 应用提供模型集成；其中 `ChatClient` 是构造请求并获取同步或流式模型响应的客户端。LangGraph 是编排有状态 Agent 流程的框架，提供 Python 与 JavaScript/TypeScript 版本，可组织循环、检查点和人工介入。[19][20][21]

选择这些框架后，仍需逐项确认工具的执行方式、持久化后端和部署调度。例如，LangGraph 的内存检查点无法跨进程重启保留状态；接上数据库检查点后，也还要落实本文的租户准入和每次模型调用配额。[22] 对已有项目，优先沿用熟悉的语言与业务框架，再按瓶颈拆出计算或编排 worker；仅凭 I/O 密集型这一点，无需先引入跨语言服务。

## 6. 并发控制：限制正在执行和等待的工作

**异步解决等待期间如何调度，限流和背压决定接纳多少工作。** 背压是下游处理不过来时，限制上游继续提交。三处控制共同保护系统：

| 控制位置 | 限制什么 | 达到上限后的行为 |
| --- | --- | --- |
| 接入层 | 租户提交速率、未完成任务数、预算 | 拒绝新任务，或在明确等待上限内接纳 |
| 调度层 | 活跃任务、每租户执行数、工具与沙箱槽位 | 在有界队列等待；超过截止时间则终止 |
| 每次模型调用前 | 在途调用数、请求速率、输入输出 token 配额 | 在剩余时限内等待额度，或结束任务 |

并发数与速率要分别限制：同时允许 20 个调用，不能保证每分钟请求数合规；每分钟允许 1,000 次，也不能阻止慢调用不断累积。多副本共享模型账号时，必须在供应商实际配额范围内协调总量。[3]

### 源码例子：worker 的本地限流不能代替共享配额

Celery 是后台任务队列框架。以下片段来自 **v5.5.3，commit `088c39c0f78b23a9cdf8d1c9e265ea64d02cfd86`** 的 `celery/worker/consumer/consumer.py`，方法为 `Consumer.bucket_for_task`。[6]

`Consumer` 接收并调度 worker 消息；`TokenBucket` 是按速率补充执行许可的令牌桶，与模型文本 token 无关。仅摘录该方法，中文注释为本文补充。

```python
def bucket_for_task(self, type):
    # 读取任务类型的限速配置，并换算为执行速率。
    limit = rate(getattr(type, 'rate_limit', None))
    # 为当前 Consumer 创建令牌桶；未配置限速时返回 None。
    return TokenBucket(limit, capacity=1) if limit else None
```

初始化路径中，`Consumer.__init__` 创建实例内的 `task_buckets`，再经 `reset_rate_limits` 为任务类型调用此方法。返回的桶控制当前 Consumer 何时放行任务，这段路径没有跨 worker 共享配额。

因此，各 worker 分别配置每分钟 60 次，不能把共同使用的模型账号限制为总共每分钟 60 次。一个任务内部调用模型 5 次，也不能只在任务开始时扣一次额度。共享配额检查应发生在每次实际模型调用之前。

### 队列只吸收有限的波峰

若每秒接纳 20 个任务、只能完成 12 个，队列每分钟增加约 480 个任务。持续超载时需要减少接纳量、增加有效处理能力，或按产品规则降级。[7]

队列应有数量或工作量上限、最长等待时间与租户公平策略。观察最老任务的等待时间，并统计 worker 已领取但尚未执行的任务。扩容前确认下游模型、数据库和工具仍有余量。

## 7. 任务恢复：管理长等待和重复执行

长任务需要保存状态版本、执行尝试、截止时间和取消标记。以下规则决定多个 worker 接管任务时是否还能保持正确结果：

| 场景 | 必要规则 |
| --- | --- |
| 客户端重复提交 | 同租户、同幂等键返回原任务；同键不同参数报冲突 |
| 消息重复投递或 worker 接管 | 原子领取执行权，用版本校验阻止旧执行者覆盖新状态 |
| 外部写入成功，但本地未记录结果 | 使用业务幂等键或查询对账，不直接重做写入 |
| 等待人工审批 | 保存检查点，释放执行资源；收到回复后重新调度 |
| 模型或工具暂时失败 | 明确重试负责层，共享总时限与重试预算，采用带随机扰动的退避 |
| 取消或客户端断线 | 区分停止订阅与取消任务，按产品语义传播取消 |

执行租约到期，不代表旧 worker 已经停止。递增执行版本只能保护会检查版本的存储；外部工具仍需自己的幂等或对账机制。多层叠加重试和非幂等操作的风险可参考 Azure 的 Retry 模式说明。[8]

模型等待期间不要长期持有数据库事务或借出的数据库连接。使用 SSE（服务端事件推送）时，限制慢客户端的发送缓冲；后台任务重连按事件序号恢复订阅，不能重新创建任务。取消本地等待，也不能直接认定远端模型、同步线程或业务写入已经停止。

更完整的状态设计见[任务状态与恢复](./02-state/agent-state-architecture.md)。

## 8. 验收与扩容依据

按排队、模型、工具和状态提交分别记录耗时，观察 P95/P99（95%/99% 样本不超过的值）、完成吞吐、成功率和单任务成本。指标需要按租户与任务类型拆分。

| 验证场景 | 应观察的结果 |
| --- | --- |
| 模型延迟增加，入口速率保持不变 | 在途调用与队列有界，超载时按规则拒绝，内存不持续增长 |
| 异步路径混入阻塞 SDK 或重计算 | 能观察事件循环延迟，并通过线程池或计算 worker 隔离 |
| 聊天与研究任务同时增长 | 聊天的模型预算有效，研究子任务数受控 |
| 大租户批量导入 | 其他租户仍获得容量，在线任务与批次分别满足时限 |
| worker 在外部写入后退出 | 接管后不重复产生业务副作用 |
| 单副本扩为多副本 | 共享模型配额保持约束，状态竞争可控 |
| 断线、重连与取消 | 不重复创建任务，缓冲和执行资源按规则释放 |

压测应包含实际输入长度、输出长度和工具耗时分布，并按设定速率产生到达流量。如果客户端总等前一请求结束才发下一请求，服务变慢时发送量也会下降，容易掩盖积压。模拟慢模型可验证调度，真实模型测试另行验证配额、延迟和结果质量。

扩容针对已确认的瓶颈：编排层按执行模型观察事件循环延迟或线程执行情况，以及连接与内存；计算 worker 观察 CPU 和内存；自部署推理观察 GPU、显存与排队；外部模型受配额限制时，增加应用副本无效。

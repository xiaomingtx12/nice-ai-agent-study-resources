# Skill：用渐进式披露给模型提供工作方法

> Skill 的核心本质，是把任务方法拆成不同详细程度的内容，让模型先发现“是否需要这套方法”，再按需读取“如何执行这套方法”。

Skill 解决的不是模型完全不知道某个知识，而是模型在不同任务中需要不同深度的工作方法。如果所有方法都提前放进提示词，输入会变长，规则会互相干扰，模型也很难判断当前哪些内容真正相关。Skill 将方法放在可发现、可加载的外部文档中，只在任务需要时逐层展开。

## 渐进式披露的四层内容

一个 Skill 通常可以拆成四层。越靠前的内容越短、越稳定、越适合用于筛选；越靠后的内容越具体，只在执行分支需要时加载。

| 层级 | 模型看到的内容 | 作用 | 加载时机 |
| --- | --- | --- | --- |
| 发现层 | 名称、用途、适用任务、关键词或实体 | 判断是否可能相关 | 候选检索时 |
| 入口层 | 核心流程、前置条件、关键约束、输出要求 | 让模型开始执行 | 确认适用后 |
| 参考层 | 分支规则、领域说明、示例、异常处理 | 支撑具体判断 | 执行到对应分支时 |
| 资源层 | 脚本、模板、配置、校验工具 | 完成实际操作 | 需要调用时 |

发现层不应该塞进完整教程，入口层也不应该复制所有参考资料。每一层只承担当前阶段需要承担的认知负担。

## 第一层：让模型知道什么时候使用

发现层的目标是提高召回准确度，而不是教模型执行。它只需要回答：

- 这套 Skill 处理什么任务；
- 什么信号出现时应该考虑它；
- 它能提供什么结果；
- 是否有明显的使用限制。

触发条件要写成可观察的任务特征，例如“需要修改数据库结构”“需要审查对外发布内容”“需要执行具有破坏性的批量操作”。“适用于复杂任务”这类描述不能帮助模型做出路由判断。

发现层越短，越容易被大量 Skill 同时索引；描述越具体，越不容易把无关 Skill 带入当前任务。

## 第二层：给出可执行的入口

Skill 被选中后，模型先读取入口内容。入口只保留完成主流程所需的信息：

1. 执行前要确认的输入、环境和权限；
2. 主流程的步骤顺序；
3. 必须遵守的约束；
4. 需要产出的中间结果；
5. 完成和暂停的条件；
6. 继续深入时应该读取哪些参考资料。

入口层的作用是把模型从“知道有这个方法”带到“可以开始按这个方法工作”。步骤应该写成动作和判断，不要只列概念。例如“检查兼容性”需要说明检查对象、判断依据以及不通过时的处理方式。

## 第三层：按分支加载参考内容

任务执行到具体分支时，再读取对应参考内容：

- 处理某种文件格式时加载该格式的规则；
- 遇到特定错误时加载诊断和修复说明；
- 进入某个行业场景时加载该场景的判断标准；
- 需要生成特定产物时加载模板和示例。

参考内容应通过明确的主题和加载条件组织。模型不需要在任务开始时阅读所有异常处理、所有格式说明和所有案例，只有进入相应分支才需要这些信息。

## 第四层：需要时才调用资源

脚本、模板、校验器和配置文件是 Skill 的可执行资源。入口层告诉模型资源解决什么问题、使用前要满足什么条件，具体调用发生在任务确实需要时。

资源层要让模型知道三件事：

- 输入和输出是什么；
- 调用会产生什么副作用；
- 结果如何验证。

这样可以避免模型为了“熟悉 Skill”而提前执行命令，也能把高风险动作留到前置检查完成之后。

## Skill 的实际工作路径

渐进式披露可以表示为：

```text
任务输入
→ 读取 Skill 发现信息
→ 判断是否相关
→ 加载入口说明
→ 根据执行分支读取参考内容
→ 按需调用脚本、模板或工具
→ 使用 Skill 中的验收条件检查结果
```

模型每次只获得当前决策所需的下一层内容。任务结束后，系统可以根据执行结果和用户修正更新 Skill，但不需要把所有运行轨迹永久塞回入口文档。

## Skill 在模型上下文中的位置

Skill 的内容进入模型上下文时，也需要区分发现信息、活动指令和深入资料：

```text
Skill 目录元数据
→ 当前任务命中的 Skill 入口
→ 当前分支需要的参考内容
→ 需要调用时才暴露脚本、模板和工具
```

目录元数据可以由路由层或能力目录管理，不必每轮完整注入。命中的 Skill 入口通常放在稳定规则之后、当前任务和动态证据之前，让模型先知道工作方法，再结合本轮事实执行。分支资料放在动态区域，随阶段和任务变化加载。

系统级安全规则、权限和终态要求优先于 Skill。Skill 可以规定“如何完成任务”，不能通过提示文本扩大能力范围、覆盖运行时约束或把候选事实变成已确认事实。

Skill 与工具定义同时进入能力视图时，二者承担不同角色：Skill 规定操作方法和检查顺序，工具定义说明可以请求的具体动作。入口 Skill 只引用当前任务需要的工具，不把全部工具说明复制进文档。

## Skill 文档的组织方式

一个入口 Skill 文档可以按下面的顺序编排：

### 用途和适用条件

用一两段话说明任务范围和触发信号，方便发现和路由。

### 前置条件

列出必需的文件、工具、权限、版本和用户确认项。缺少条件时明确暂停或补充信息的路径。

### 主流程

只写通用且稳定的步骤。每一步说明动作、输入和产出，复杂分支链接到参考内容。

### 约束和验收

说明禁止动作、风险边界、完成条件和证据要求。没有证据时，模型应保持未完成状态。

### 参考与资源索引

按任务分支列出下一层文档和资源，并说明各自何时加载。索引本身不重复参考文档的正文。

## 设计渐进式披露时的几个判断

### 入口内容是否足够短

如果模型每次加载入口都要阅读大量背景知识，说明发现层和参考层没有拆开。

### 每一层是否都有独立价值

发现层应该帮助路由，入口层应该帮助启动执行，参考层应该帮助解决分支，资源层应该帮助完成操作。某一层只是重复上一层内容，就应当合并或删减。

### 深入加载是否有明确条件

“需要时参考”不够具体。应说明什么任务信号、错误类型或执行阶段会触发下一层内容。

### 内容是否改变了模型行为

加载 Skill 后，模型的步骤顺序、工具选择、检查动作或输出结构应该出现可观察变化。只有增加背景知识、没有改变执行路径的内容，不适合放在 Skill 中。

## 常见错误

| 错误 | 结果 | 调整方式 |
| --- | --- | --- |
| 把完整教程都放在发现层 | 所有任务都付出高输入成本 | 只保留用途和触发信号 |
| 一个 Skill 文件包含所有分支 | 模型难以定位当前需要的规则 | 将分支说明拆到参考层 |
| 入口层重复参考文档 | 内容更新后出现多处不一致 | 入口只保留流程和索引 |
| 参考文档没有加载条件 | 模型不知道何时继续深入 | 为每份参考内容写明适用信号 |
| 资源没有副作用说明 | 模型可能提前或误用工具 | 标出权限、风险和验证方式 |
| Skill 只讲知识不讲动作 | 模型复述内容却没有执行变化 | 改写成步骤、判断和验收 |
| Skill 之间互相复制 | 规则冲突且难以维护 | 为每条规则保留唯一来源 |

## 如何判断渐进式披露是否有效

关注三组结果：

- **发现效率**：相关任务能召回，入口层不会被无关任务频繁加载；
- **加载效率**：模型只读取当前阶段需要的内容，深入层级与任务分支相匹配；
- **执行效果**：加载后模型确实按照 Skill 的步骤、约束和验收要求完成任务。

可以记录入口加载量、参考内容的按需命中率、无关 Skill 激活率、工具误用率、跳过验收的比例和任务返工率。Skill 的价值不在于文档越长，而在于模型能在正确的时机获得正确深度的方法。

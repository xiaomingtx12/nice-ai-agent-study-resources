# Skill：用渐进式披露给模型提供工作方法

> **模块本质：** 将可复用的任务方法封装成按需加载的操作说明，让模型在适用时获得步骤、约束和验收方法，并通过验证与版本管理维护这些经验。

发现时判断是否适用，执行时读取流程，遇到分支再补充资料和工具。经验更新也应保留这种结构，避免每次遇到问题就往入口文档追加一条永久规则。

Skill 解决的不是模型完全不知道某个知识，而是模型在不同任务中需要不同深度的工作方法。如果所有方法都提前放进提示词，输入会变长，规则会互相干扰，模型也很难判断当前哪些内容真正相关。Skill 将方法放在可发现、可加载的外部文档中，只在任务需要时逐层展开。

## 一、渐进式披露的四层内容 {/* #渐进式披露的四层内容 */}

一个 Skill 通常可以拆成四层。越靠前的内容越短、越稳定、越适合用于筛选；越靠后的内容越具体，只在执行分支需要时加载。

| 层级 | 模型看到的内容 | 作用 | 加载时机 |
| --- | --- | --- | --- |
| 发现层 | 名称、用途、适用任务、关键词或实体 | 判断是否可能相关 | 候选检索时 |
| 入口层 | 核心流程、前置条件、关键约束、输出要求 | 让模型开始执行 | 确认适用后 |
| 参考层 | 分支规则、领域说明、示例、异常处理 | 支撑具体判断 | 执行到对应分支时 |
| 资源层 | 脚本、模板、配置、校验工具 | 完成实际操作 | 需要调用时 |

发现层不应该塞进完整教程，入口层也不应该复制所有参考资料。每一层只承担当前阶段需要承担的认知负担。

## 二、发现层：让模型知道什么时候使用 {/* #第一层让模型知道什么时候使用 */}

发现层的目标是提高召回准确度，而不是教模型执行。它只需要回答：

- 这套 Skill 处理什么任务；
- 什么信号出现时应该考虑它；
- 它能提供什么结果；
- 是否有明显的使用限制。

触发条件要写成可观察的任务特征，例如“需要修改数据库结构”“需要审查对外发布内容”“需要执行具有破坏性的批量操作”。“适用于复杂任务”这类描述不能帮助模型做出路由判断。

发现层越短，越容易被大量 Skill 同时索引；描述越具体，越不容易把无关 Skill 带入当前任务。

## 三、入口层：给出可执行的入口 {/* #第二层给出可执行的入口 */}

Skill 被选中后，模型先读取入口内容。入口只保留完成主流程所需的信息：

1. 执行前要确认的输入、环境和权限；
2. 主流程的步骤顺序；
3. 必须遵守的约束；
4. 需要产出的中间结果；
5. 完成和暂停的条件；
6. 继续深入时应该读取哪些参考资料。

入口层的作用是把模型从“知道有这个方法”带到“可以开始按这个方法工作”。步骤应该写成动作和判断，不要只列概念。例如“检查兼容性”需要说明检查对象、判断依据以及不通过时的处理方式。

## 四、参考层：按分支加载参考内容 {/* #第三层按分支加载参考内容 */}

任务执行到具体分支时，再读取对应参考内容：

- 处理某种文件格式时加载该格式的规则；
- 遇到特定错误时加载诊断和修复说明；
- 进入某个行业场景时加载该场景的判断标准；
- 需要生成特定产物时加载模板和示例。

参考内容应通过明确的主题和加载条件组织。模型不需要在任务开始时阅读所有异常处理、所有格式说明和所有案例，只有进入相应分支才需要这些信息。

## 五、资源层：需要时才调用资源 {/* #第四层需要时才调用资源 */}

脚本、模板、校验器和配置文件是 Skill 的可执行资源。入口层告诉模型资源解决什么问题、使用前要满足什么条件，具体调用发生在任务确实需要时。

资源层要让模型知道三件事：

- 输入和输出是什么；
- 调用会产生什么副作用；
- 结果如何验证。

这样可以避免模型为了“熟悉 Skill”而提前执行命令，也能把高风险动作留到前置检查完成之后。

## 六、Skill 的实际工作路径 {/* #skill-的实际工作路径 */}

渐进式披露可以表示为：

```text
任务输入
→ 读取 Skill 发现信息
→ 判断是否相关
→ 加载入口说明
→ 根据执行分支读取参考内容
→ 按需调用脚本、模板或工具
→ 使用 Skill 中的验收条件检查结果
```

模型每次只获得当前决策所需的下一层内容。任务结束后，系统可以根据执行结果和用户修正更新 Skill，但不需要把所有运行轨迹永久塞回入口文档。

## 七、Skill 在模型上下文中的位置 {/* #skill-在模型上下文中的位置 */}

Skill 的内容进入模型上下文时，也需要区分发现信息、活动指令和深入资料：

```text
Skill 目录元数据
→ 当前任务命中的 Skill 入口
→ 当前分支需要的参考内容
→ 需要调用时才暴露脚本、模板和工具
```

目录元数据可以由路由层或能力目录管理，不必每轮完整注入。命中的 Skill 入口通常放在稳定规则之后、当前任务和动态证据之前，让模型先知道工作方法，再结合本轮事实执行。分支资料放在动态区域，随阶段和任务变化加载。

系统级安全规则、权限和终态要求优先于 Skill。Skill 可以规定“如何完成任务”，不能通过提示文本扩大能力范围、覆盖运行时约束或把候选事实变成已确认事实。

Skill 与工具定义同时进入能力视图时，二者承担不同角色：Skill 规定操作方法和检查顺序，工具定义说明可以请求的具体动作。入口 Skill 只引用当前任务需要的工具，不把全部工具说明复制进文档。

## 八、Skill 文档的组织方式 {/* #skill-文档的组织方式 */}

一个入口 Skill 文档可以按下面的顺序编排：

### 1. 用途和适用条件 {/* #用途和适用条件 */}

用一两段话说明任务范围和触发信号，方便发现和路由。

### 2. 前置条件 {/* #前置条件 */}

列出必需的文件、工具、权限、版本和用户确认项。缺少条件时明确暂停或补充信息的路径。

### 3. 主流程 {/* #主流程 */}

只写通用且稳定的步骤。每一步说明动作、输入和产出，复杂分支链接到参考内容。

### 4. 约束和验收 {/* #约束和验收 */}

说明禁止动作、风险边界、完成条件和证据要求。没有证据时，模型应保持未完成状态。

### 5. 参考与资源索引 {/* #参考与资源索引 */}

按任务分支列出下一层文档和资源，并说明各自何时加载。索引本身不重复参考文档的正文。

## 九、设计渐进式披露时的几个判断 {/* #设计渐进式披露时的几个判断 */}

### 1. 入口内容是否足够短 {/* #入口内容是否足够短 */}

如果模型每次加载入口都要阅读大量背景知识，说明发现层和参考层没有拆开。

### 2. 每一层是否都有独立价值 {/* #每一层是否都有独立价值 */}

发现层应该帮助路由，入口层应该帮助启动执行，参考层应该帮助解决分支，资源层应该帮助完成操作。某一层只是重复上一层内容，就应当合并或删减。

### 3. 深入加载是否有明确条件 {/* #深入加载是否有明确条件 */}

“需要时参考”不够具体。应说明什么任务信号、错误类型或执行阶段会触发下一层内容。

### 4. 内容是否改变了模型行为 {/* #内容是否改变了模型行为 */}

加载 Skill 后，模型的步骤顺序、工具选择、检查动作或输出结构应该出现可观察变化。只有增加背景知识、没有改变执行路径的内容，不适合放在 Skill 中。

## 十、从运行案例生成候选方法 {/* #从运行案例生成候选方法 */}

成功、失败和人工纠正都可以提供改进线索，但先要判断问题归属。权限门失效需要修执行器，外部服务不可用需要修恢复路径；把它们都写成“模型下次要小心”，不能修复系统。只有可复用的任务判断、步骤和验收经验，才适合进入 Skill。

如需建设经验回灌，可以保留任务前提、有效版本、关键动作、验证结果、纠正依据和适用范围，再生成候选修改。模型自报成功不足以作为正例；人工纠正也需要核实其权限与依据。

一次失败可以支持一个窄范围修正，不能直接推出所有任务都要增加同一步骤。候选记录应能回答：它修复哪个样本，适用于什么条件，会影响哪些现有分支，怎样证明没有损坏其他任务。

### 1、从案例中分离方法与旧答案 {/* #从案例中分离方法与旧答案 */}

一次成功调查至少混合了两类信息：帮助下一次取得证据的方法，以及只属于这次任务的现场和结论。提炼 Skill 时，先对每项内容确定去向，再组织步骤。

| 案例内容 | 适合提炼的部分 | 留在旧任务中的部分 |
| --- | --- | --- |
| 模块背景 | 系统边界、依赖关系与适用条件 | 当时的临时拓扑或实例分布 |
| 查询过程 | 日志、发布、配置的查询入口及输入要求 | 本次请求编号、实例名和查询返回值 |
| 指标分析 | 指标定义、单位与关联方式 | 当时的数值和已过期阈值 |
| 调查顺序 | 怎样获取样本、交叉核对和修正假设 | 沿着上次根因固定查找证据 |
| 最终结论 | 证据要求与停止判断的条件 | 上次事故的根因与处置参数 |

例如上次故障是连接没有归还，方法中应保留“关联异常请求、核对依赖调用与连接指标”，并要求重新读取当前现场。如果写成“支付超时优先确认连接泄漏”，就把旧答案变成了新任务的默认方向。

可以把 Skill 的每一步写清楚为：需要哪些输入，执行什么查询，如何理解结果，结果不足时怎样继续，以及什么条件下结束或转交。第一版只需要完成主流程的说明；确实出现复杂分支、重复计算或固定产物后，再增加参考文档、脚本和模板。分层能力不要求从开始就建齐所有目录。

### 2、结构合格、方法可靠与有效采用分别验证

文件存在、元数据可解析、名称和描述齐全，只能证明基础结构合格。它们不能证明查询入口真实可用、方法适合当前模块，也不能发现一段语法正确的旧根因正在影响所有新任务。

内容审阅后，应在不继承原调查历史的新会话中试用。显式指定 Skill 可以检查加载后的执行方法；不指定名称、只给任务则可以检查发现条件。两类试验分别记录，不能用显式调用成功证明自动选择准确。

为调查方法准备“同模块、相似症状、不同根因”的独立材料，再补充证据不足和范围外任务。检查它是否获取当前版本与配置、跟随新证据改变方向、保留未知，并在不适用时不激活。旧任务记录继续作为方法来源保存，日常使用不应再要求每次复制整段历史。

## 十一、冲突需要补条件，不靠不断叠加规则 {/* #冲突需要补条件不靠不断叠加规则 */}

假设旧方法要求“先读取本地配置”，新案例要求“先查询远端配置”。应检查二者分别适用于哪种部署和权限条件，再决定替换或条件化；不能只因为新文本更新，就把旧方法整体覆盖。

| 冲突类型 | 建议处理 |
| --- | --- |
| 同一规则的重复表达 | 合并为一处，其他位置引用 |
| 前提不同、步骤各自有效 | 写清可观察的分支条件 |
| 同一前提下建议相反 | 保留证据，进入复核，不直接发布 |
| 上游规则已经变化 | 更新适用版本，废弃不再有效的分支 |
| 多个候选同时修改同一版本 | 检测版本冲突，重新合并和评测 |

模型可以辅助找冲突，但发布判断还需要程序校验与回归样本。系统级权限和业务规则优先；Skill 的版本更新不能扩大授权，也不能让低可信案例中的指令进入全局规则。

## 十二、候选、发布与回滚分别管理 {/* #候选发布与回滚分别管理 */}

经验回灌可以采用以下生命周期：

```text
案例审核 → 候选修改 → 差异与冲突检查 → 离线评测
→ 隔离或影子验证 → 启用版本 → 监控与回滚
```

候选生成可以异步运行，生成完成不代表立即可用。回归集除了触发本次修改的失败样本，还需要已有成功任务、相邻任务和不该激活该 Skill 的负例。指标覆盖触发准确性、任务完成、必要检查与成功交付成本。评测方法见 [Agent 评测](../06-observation/agent-evaluation.md)。

Skill 可以继续以 Markdown 保存，不必为了测试把所有方法都改成工作流。适用范围、版本、依赖和验收依据可以由配套元数据维护；真正需要强制执行的检查放在运行时。

发布时保存不可变版本和当前启用版本引用，新任务读取已启用版本。正在运行的任务固定所用版本，或在明确的阶段边界迁移，避免执行中途一半使用旧方法、一半使用新方法。多实例环境还需要处理缓存失效与版本确认。

回滚只影响后续加载的方法，不能撤销新版本已经产生的外部效果。发现权限风险时，还要停止相关任务并处理副作用；不能只切回文件版本就宣布故障解除。尚未建立案例审核与发布门禁时，先采用人工维护，不宜直接开放自动热更新。

### 1、验证资格绑定具体版本与适用环境

技能已经保存、技能通过验证、当前任务获准调用，是三个独立条件。能力发布流程决定哪版方法可以进入正式候选集；运行时仍要检查它是否匹配当前任务、环境、权限和工具依赖。

验证记录应绑定技能内容摘要、依赖版本、适用范围、评测集和结果，以及失效条件。路由先排除资格失效或范围不符的技能，再比较相关性。没有合适技能时，明确回退到通用方法、补证或人工处理，不能为了命中而选择一个不适用的技能。

工具接口、规则或运行环境发生变化，且原验证已不能支持当前使用时，应暂停受影响资格，再完成复验。例行复验是否阻断旧版，可以按风险决定；部署候选新版本时，也可以继续使用资格有效的旧版。不能把“正在测试”当成新版本已经合格。

复用记录分别保存技能版本、验证资格、实际采用的任务与外部结果。新旧版本不混算成功率；任务成功也不能直接证明技能有效，需要结合采用证据和无技能或旧版对照。验证至少覆盖结果、激活、异常流程、相对收益和依赖变化后的失效处理。

稳定前置条件可以进一步转成运行时检查，尚未确定的教训先留在[经验回放](../02-state/agent-progress-and-failure-records.md)中接受验证。

## 十三、把 Skill 接到框架的发现与读取流程 {/* #框架中的-skill-接入 */}

### 1. 同时配置目录、存储和读取权限 {/* #1-同时配置目录存储和读取权限 */}

Deep Agents 的 `create_deep_agent(skills=[...], backend=...)` 用于指定 Skill 来源与文件存储。`SkillsMiddleware` 是扫描入口文件、提取名称描述并向模型提供索引的中间件；模型选择某个 Skill 后，再通过文件工具读取正文与参考材料。

按本文核对的 0.6.12 源码快照，`skills` 中的路径使用正斜杠，并相对于 Backend 的根目录。采用 `FilesystemBackend` 时，文件来自配置的根目录；采用 `StateBackend` 时，需要先将 Skill 文件放进对应状态文件空间。指定一个宿主机目录字符串，不会让任意后端自动看见磁盘文件。

文档维护场景可以发布一个只读的 `docs-maintenance` Skill：入口说明何时整理旧文、何时补充来源、何时请求澄清；参考文件保存标题规范和引用要求；脚本只做确定性的链接检查。正文不重复解释工具权限，也不让模型通过修改当前 Skill 绕开发布流程。

### 2. 同名覆盖和子代理技能要显式管理 {/* #2-同名覆盖和子代理技能要显式管理 */}

`graph.py` → `create_deep_agent()` 的来源约定是：后面的来源覆盖前面同名 Skill。若平台规范与项目扩展恰好同名，实际生效的可能只剩项目版本。因此要固定来源顺序，记录解析后的入口路径和内容版本，发布前检查重名。需要组合两套方法时，应在 Skill 入口中明确引用关系，而不是假设系统会自动合并正文。

自定义子代理应在自己的 `skills` 字段中声明所需来源，并核对组装后的工具与 Backend。主代理能发现某个 Skill，不足以证明审校子代理也能读取它。通用子代理与自定义子代理的默认装配存在差异，升级时应检查实际配置。

### 3. 将必须执行的检查移到确定性节点 {/* #3-将必须执行的检查移到确定性节点 */}

Skill 中的 `allowed-tools` 是建议性元数据，不自动注册或限制工具；目录中存在脚本也不代表后端支持执行。工具权限由运行时控制，脚本执行还受实际执行环境约束。

如果发布前必须检查失效链接，应让业务发布流程或 LangGraph 节点调用检查器，并以检查结果决定是否继续；Skill 负责提示何时提前检查、如何修复。验证 Skill 时分别记录发现、读取、采用方法和产物通过检查的比例，避免只验证“目录扫描成功”。加载机制与源码范围见[SkillsMiddleware](../../../application-notes/engineering/langchain-series/deepagents/07-skills-middleware.md)。

## 十四、常见错误 {/* #常见错误 */}

| 错误 | 结果 | 调整方式 |
| --- | --- | --- |
| 把完整教程都放在发现层 | 所有任务都付出高输入成本 | 只保留用途和触发信号 |
| 一个 Skill 文件包含所有分支 | 模型难以定位当前需要的规则 | 将分支说明拆到参考层 |
| 入口层重复参考文档 | 内容更新后出现多处不一致 | 入口只保留流程和索引 |
| 参考文档没有加载条件 | 模型不知道何时继续深入 | 为每份参考内容写明适用信号 |
| 资源没有副作用说明 | 模型可能提前或误用工具 | 标出权限、风险和验证方式 |
| Skill 只讲知识不讲动作 | 模型复述内容却没有执行变化 | 改写成步骤、判断和验收 |
| Skill 之间互相复制 | 规则冲突且难以维护 | 为每条规则保留唯一来源 |

## 十五、如何判断渐进式披露是否有效 {/* #如何判断渐进式披露是否有效 */}

关注三组结果：

- **发现效率**：相关任务能召回，入口层不会被无关任务频繁加载；
- **加载效率**：模型只读取当前阶段需要的内容，深入层级与任务分支相匹配；
- **执行效果**：加载后模型确实按照 Skill 的步骤、约束和验收要求完成任务。

可以记录入口加载量、参考内容的按需命中率、无关 Skill 激活率、工具误用率、跳过验收的比例和任务返工率。Skill 的价值不在于文档越长，而在于模型能在正确的时机获得正确深度的方法。

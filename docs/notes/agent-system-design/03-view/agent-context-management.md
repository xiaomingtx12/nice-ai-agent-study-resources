# 上下文装配：为每轮模型调用编译输入

> **模块本质：** 从系统保存的全部信息中，生成足以支持本轮决策的有限视图。选择会损失信息，因此必须明确哪些事实不能省略、哪些材料可以稍后读取，以及何时应停止调用模型并补齐证据。

任务 `T17` 正在把页面 `doc-42` 从 `v7` 更新为草稿 `r18`。编辑时，模型需要旧正文、引用与修改范围；发布动作 `A903` 超时后，下一轮需要知道“可能已经发布，必须查询结果”。如果继续提供旧编辑输入，或把超时压成一句“发布失败”，即使输入远未超限，也会把下一步引向错误方向。

这是贯穿本文的设计案例，工具和状态两篇分别讨论[执行协议](../05-action/agent-tool-calling.md)与[恢复依据](../02-state/agent-state-architecture.md)。本文负责从这些事实派生输入，不让装配器自行裁定发布成功或修改审批状态；实际框架行为以引用的源码为准。

输入窗口限制了每次能携带的材料，但装配的目标不能只设成缩短输入。删掉未完成动作会导致重复执行，沿用旧版本会导致错误编辑。应先确定本轮决策依赖，再选择材料：

```text
收集来源
→ 筛选内容
→ 排定优先级
→ 分配预算
→ 渲染输入
→ 校验可见内容
```

## 一、模型需要什么输入 {/* #一模型需要什么输入 */}

一次模型调用通常需要五类材料：

| 材料 | 作用 | 变化方式 |
|---|---|---|
| 稳定规则 | 身份、输出要求、运行约束 | 版本化管理，变化较少 |
| 当前任务 | 目标、参数、约束、成功条件 | 随任务推进变化 |
| 当前事实 | 已确认结果、进度和待处理事项 | 随运行持续更新 |
| 相关证据 | 文件片段、知识内容、外部查询结果 | 按当前问题动态选择 |
| 可用能力 | 工具、操作说明和结果格式 | 按阶段和权限变化 |

本轮输入可以抽象为：

```text
ContextView =
  stable_rules
  + current_task
  + current_facts
  + selected_evidence
  + available_capabilities
```

记忆、RAG、Skill、文件和外部查询都是输入来源。它们进入模型输入前，都要经过相同的选择、排序和预算处理。

### 1. 模型实际收到的上下文 {/* #模型实际收到的上下文 */}

从模型 API 的角度看，一次请求通常由两部分组成：

| 部分 | 承载内容 |
|---|---|
| 消息序列 | 系统规则、用户任务、模型历史决策和工具结果 |
| 能力定义 | 当前可用工具的名称、用途、输入 Schema 和限制 |

消息序列中的工具调用和工具结果需要成组保留，并通过调用 ID 关联。裁剪历史时不能只保留工具结果而删除对应的模型调用，也不能把一次并行调用拆成无法对应的几条结果。

能力定义位于消息序列之外，但同样属于模型本轮可见输入。工具描述发生变化、权限发生变化或当前阶段发生变化时，能力定义需要重新筛选和装配。

不同模型接口可能由客户端传入历史，也可能通过服务端会话引用续接；无论历史由谁保存，应用仍要确认本次调用实际使用的任务版本、证据和工具。不能用“会话里曾经出现过”替代当前输入的有效性检查。

### 2. 上下文溢出和上下文腐化 {/* #上下文溢出和上下文腐化 */}

上下文问题有两种表现：

- **溢出**：输入超过模型窗口或预算，调用无法完成；
- **腐化**：输入仍然装得下，但无关历史、重复证据和过期内容分散了注意力，模型找不到真正需要的信息。

阶段切换、证据失效或模型反复使用旧结论时，应检查当前视图，再决定是否裁剪或压缩。不能看到答错就直接缩短历史：缺少必要事实时，正确动作可能是补充输入。是否改善，需要用同一任务集合比较，不能把输入变短本身当作质量提升。

### 3. 按实际问题逐步增加装配能力 {/* #按实际问题选择装配策略 */}

| 当前场景 | 起步做法 | 值得升级的信号 | 需要承担的代价 |
| --- | --- | --- | --- |
| 少量工具、短任务、输入稳定 | 固定系统说明、明确任务字段和有限历史 | 出现明显阶段差异或旧事实被误用 | 增加视图版本与阶段测试 |
| 编辑、校验、对账需要不同信息 | 根据可信任务状态筛选消息和工具 | 不同阶段仍有大量无关材料 | 维护阶段与材料的映射 |
| 工具与资料数量增长 | 在授权范围内召回，再装配完整定义或片段 | 固定候选经常漏掉能力或证据 | 增加检索延迟与召回评测 |
| 长结果持续挤占输入 | 外部化结果，保留关键状态和读取引用 | 后续决策仍需跨多轮历史 | 增加摘要、原文保留与重新读取成本 |

不要为少量稳定工具预先建立复杂检索目录，也不要为了少一次读取，把整份文档永久放在每轮输入中。选择依据应是任务效果、完整运行成本与维护负担。

### 4、材料可访问，不代表模型已经看见 {/* #材料可访问不代表模型已经看见 */}

工作区、任务历史、本轮上下文与事件日志需要分别检查。工作区保存可查找的材料；任务历史保存此前发生的过程；上下文是当前模型调用实际采用的输入；事件日志帮助观察运行过程，但未必完整记录了输入装配结果。

例如，一份详细变更记录已经放进工作目录，Agent 却只引用部署工具返回的摘要。应沿着材料进入输入的路径排查：

| 检查位置 | 要确认什么 | 常见修正 |
| --- | --- | --- |
| 发现入口 | 是否知道有这份材料及其用途 | 提供目录索引或明确的查找线索 |
| 工具读取 | 是否读取正文，是否被截断或只返回路径 | 分段读取必要内容，保留版本和位置 |
| 输入装配 | 工具结果是否在关键判断前进入调用 | 检查历史筛选、阶段过滤与结果关联 |
| 决策采用 | 模型是否理解材料支持或削弱什么判断 | 对照证据检查结论，保留尚未确认的部分 |

不能因为读取命令成功，就断言完整正文始终在后续输入中。结果可能被截断、外部化或在压缩后退出当前工作集；重新读取也可能得到更新后的文件。因此，需要同时确认读取时间、材料版本和发生判断的调用位置。

一个小型对照练习是：先让 Agent 仅根据告警列出事实，再要求读取变更记录并重新判断。检查新增事实是否出现在读取之后、是否带有来源，以及模型有没有把时间相邻直接当成因果。这里检验的是证据进入判断的路径，不是回答篇幅有没有变长。

## 二、上下文装配流程 {/* #二上下文装配流程 */}

### 1. 收集来源 {/* #1-收集来源 */}

先读取当前任务、已确认事实和运行阶段，再按需要获取证据与能力描述。案例中的最小输入依赖包括 `doc-42`、期望版本 `v7`、草稿 `r18`、允许修改的范围，以及当前是否有未确认的发布动作。它们来自状态或权威服务，不依赖相似度检索恰好命中：

```text
任务目标
→ 当前阶段
→ 已确认事实
→ 相关证据
→ 阶段可用能力
```

来源读取需要绑定当前任务和阶段，避免把所有历史、所有工具和所有知识一次性加载。

### 2. 筛选内容 {/* #2-筛选内容 */}

每段内容进入本轮前，至少检查：

- 与当前目标的相关性；
- 是否适用于当前阶段；
- 是否仍然有效；
- 当前运行是否有权访问；
- 是否已经重复出现。

相关度高但已经过期或超出权限范围的内容排除出当前决策依据。历史版本若是比较或审计对象，可以保留，但要标为历史材料，不能冒充当前事实。

### 3. 排定优先级 {/* #3-排定优先级 */}

模型输入优先保留：

```text
任务约束
→ 已确认事实
→ 当前步骤
→ 验收条件
→ 直接证据
→ 补充背景
```

这个顺序表达保留优先级，不是所有模型都适用的最佳消息排列。未确认动作、修改范围与目标版本属于必需字段，参考背景可以被替换或延后读取；实际排列需结合模型接口和评测结果确定。

### 4. 渲染输入 {/* #4-渲染输入 */}

不同材料使用稳定区域和标签，保持来源边界：

```text
<rules>...</rules>
<task>...</task>
<facts>...</facts>
<evidence>...</evidence>
<capabilities>...</capabilities>
```

这些标签是材料分区的表达示意，不是框架 API，也不提供安全隔离保证。可以采用结构化消息或清晰的自然语言分区，重点是让事实、用户要求和外部证据的来源可区分。来源、版本和选择理由由系统保留，只向模型展示完成当前判断需要的部分。

### 5. 校验可见内容 {/* #5-校验可见内容 */}

模型调用前检查：

- 必需字段是否齐全；
- 过期和越权内容是否已移除；
- 当前阶段是否暴露了不必要的能力；
- 预算是否足够；
- 每段动态材料是否可以追溯来源。

必需信息缺失时，返回可定位的装配失败，例如“`A903` 的结果待查询”或“无法读取 `r18`”。运行时安排查询或暂停；不要悄悄删掉字段，再让模型猜测当前版本。可选背景缺失则可以降级继续，并记录遗漏范围。

## 三、阶段可见性 {/* #三阶段可见性 */}

同一个任务在不同阶段需要不同输入：

| 本例阶段 | 本轮必需事实与证据 | 可用能力 | 本轮可不展开的材料 |
| --- | --- | --- | --- |
| 编辑 `r18` | 页面 `v7`、修改范围、有效来源、草稿位置 | 读取来源、编辑草稿 | 旧任务的全文记录 |
| 校验 `r18` | 草稿、差异、引用依据与验收要求 | 读取、比对、运行确定性检查 | 与本次变更无关的检索结果 |
| 等待批准 | 待批准草稿版本、差异与影响范围 | 人工决定入口 | 等待期间通常不必反复调用模型 |
| 对账 `A903` | 原目标与草稿版本、动作 ID、已尝试发送、结果未知 | 查询发布记录与结果版本 | 已完成编辑过程的长对话、新的发布入口 |
| 确认结果 | `A903` 对应的 `v8`、验收证据、剩余问题 | 读取结果、向用户报告 | 过时的失败猜测 |

从编辑转入对账时，视图发生的关键变化是：草稿编辑历史可以收起，但动作 `A903` 及“结果未知”必须保留；发布工具退出本轮目录，查询入口保留。若查询证明已经生成 `v8`，由业务处理更新状态，再装配确认结果的视图。业务阶段变化不能只由模型在回复里自称“进入下一阶段”。

## 四、能力视图：工具如何进入上下文 {/* #四能力视图工具如何进入上下文 */}

工具同时存在于 View 和 Action 两个边界中：

- View 暴露当前模型可以使用的能力说明；
- Decision 根据说明提出工具调用；
- Action 校验并执行真实工具；
- Observation 把执行结果返回给下一轮。

进入 View 的是工具描述，不是执行句柄。模型可以看到：

| 工具描述 | 作用 |
|---|---|
| 名称和用途 | 帮助模型判断是否相关 |
| 输入 Schema | 约束模型生成调用参数 |
| 输出和错误格式 | 让模型知道如何消费结果 |
| 使用限制 | 说明阶段、权限、风险和调用条件 |
| 成本和时效 | 帮助模型在多个能力之间取舍 |

凭据、数据库连接和文件句柄留在运行时执行边界内。模型确需知道项目名称或业务范围时，可以提供经过筛选的非敏感信息；可信身份与权限判断仍以服务端上下文为准，不采用模型返回的租户字段。

工具描述也适合渐进式披露：

```text
工具目录
→ 当前任务相关工具摘要
→ 入选工具的 Schema
→ 分支需要时加载详细说明
→ 模型提出调用
```

能力筛选至少结合任务目标、当前阶段、权限范围、风险等级、预算和工具可用性。所有工具常驻会增加输入成本，也会让模型在相似能力之间更容易选错。

### 1. 工具目录分层，保留找回能力的入口 {/* #工具目录分层保留找回能力的入口 */}

可以将工具分成常驻入口、阶段工具和按需检索工具。常驻入口负责发现能力与补充信息；阶段工具服务于当前任务；长尾能力在需要时再加载完整定义。层级数量由实际工具规模决定，不必为少量工具增加检索服务。

工具描述优先说明触发条件、输入前提、输出结果和相近工具的边界。例如“读取文档当前版本”和“读取历史版本”应清楚区分，不能只写成两个都能“查询文档”的工具。名称、用途和完整 schema 使用同一版本。

候选没有覆盖任务时，应允许在权限范围内扩展检索或请求澄清，不能直接把“本轮未入选”解释成“系统没有这个能力”。同时记录候选召回、最终选择和调用结果，分别定位找不到工具、选错工具与执行失败。

工具选择优化需要同时看描述 token、额外检索延迟、目标工具召回率与任务完成率。候选集很小但漏掉必要能力，同样不合格。工具熔断后还要更新可用性，避免向下一轮继续提供必然失败的入口。

Skill 和工具在能力视图中可以同时出现：Skill 提供完成一类任务的方法，工具提供可以执行的操作。Skill 可以引用工具的使用顺序和验收方式，但不能替代工具的参数校验、权限检查和执行结果。

能力视图负责减少无关选择，执行授权由[工具入口与权限门](../05-action/agent-permission-and-postconditions.md)检查。验收时既要捕获本轮模型请求，确认发布工具已移除，也要验证旧调用仍无法绕过执行门；两项分别证明视图与执行控制。

## 五、预算、取舍与缓存 {/* #五预算取舍与缓存 */}

### 1. 预算分配 {/* #预算分配 */}

```text
总窗口
− 稳定规则
− 当前任务和事实
− 能力描述
− 输出预留
= 动态材料预算
```

动态预算再分配给证据、历史和补充背景：

```text
保留任务约束
→ 保留已确认事实
→ 保留当前步骤
→ 保留必要证据
→ 释放补充背景
```

这是一种输入预算核算方式，实际窗口计费和 token 计算需按模型接口核对。必需字段、完整工具调用配对和输出预留扣除后，再给证据片段与历史分配空间。

裁剪、摘要、外部化和重新获取都属于预算策略。外部化长文档可减少重复输入，但下一轮查原文会增加工具调用与延迟；摘要还会产生额外模型调用，并可能丢失条件。比较时计算整个任务的成本，记录释放对象、理由及重新获取方式。

### 2. 必须出现的约束不参加普通相关性竞争 {/* #必须出现的约束不参加普通相关性竞争 */}

用户已经明确的目标范围、当前审批状态和执行所需的关键限制，应从任务状态或权威配置按标识读取。它们可以占用单独的必需字段预算；普通知识材料再按相关性竞争剩余空间。

如果必需字段本身装不下，应缩小任务、拆分阶段或暂停，而不是把它们悄悄放入待裁剪区域。规则进入上下文只能帮助模型决策，涉及权限和不可逆效果的限制仍由 [Action 执行门](../05-action/agent-permission-and-postconditions.md)落实。

### 3. 缓存类型 {/* #缓存类型 */}

| 缓存类型 | 主要作用 |
|---|---|
| Provider Prompt Cache | 缓存稳定输入前缀，降低重复输入成本 |
| `ContextView` 缓存 | 缓存已经渲染的本轮输入，减少重复装配 |
| 模型响应缓存 | 在输入与复用条件一致时复用已有输出 |
| KV Cache | 加速模型当前推理过程 |

Prompt Cache 适合保存稳定规则、固定输出协议和稳定能力描述。任务目标、动态事实、临时证据和阶段能力放在可变化区域。

前缀缓存依赖实际供应商协议。应检查哪些消息、工具定义和缓存标记参与匹配，并用返回的缓存用量验证效果。把每轮变化的时间戳放在稳定前缀前部，可能使后续内容无法复用；反过来，为了缓存保留过期状态，也会让模型使用错误依据。

历史追加、工具动态加载和阶段摘要会产生不同的缓存变化。比较策略时，计算整个任务的输入、压缩调用和重新读取成本，不能只追求某一轮的缓存命中率。下面的版本维度主要用于应用自己管理的视图与响应缓存；供应商缓存未必允许调用方定义相同的键。

缓存键至少考虑：

```text
prompt_version
state_version
stage
tool_schema_version
permission_scope
evidence_version
```

规则、事实、阶段、工具权限或证据版本发生变化后，相关缓存需要失效。缓存保存装配结果，失效后根据当前有效信息重新生成输入。

例如 `T17` 从编辑进入对账，即使用户文本未变，也必须使旧阶段视图失效。对于带工具提案的响应缓存，命中后仍要重新检查当前执行条件，不能将旧提案连同旧授权一起重放。

## 六、来源、时效与可见性 {/* #六来源时效与可见性 */}

动态材料至少保留：

```text
source_id
version
freshness
permission_scope
selected_reason
```

这些字段支持三类判断：

- 内容从哪里来；
- 内容是否仍然有效；
- 内容为什么进入本轮。

系统保留完整元数据，模型只接收当前决策需要的部分。来源不明、已经过期、超出权限范围或无法解释选择原因的内容，不进入当前输入。

来源标签还应跨摘要和子任务交接保留。检索文档中的指令性内容仍然属于材料，不能在摘要后变成系统规则。必须引用可疑原文时，将其作为待分析证据隔离展示，并由运行时继续限制工具与外发权限。

## 七、在模型调用入口定制上下文 {/* #框架中的上下文装配 */}

### 1. 区分改请求与改状态 {/* #1-区分改请求与改状态 */}

LangChain 的 `dynamic_prompt` 用于按本轮状态和运行上下文生成系统提示；`wrap_model_call` 是包裹模型调用的中间件入口，可修改本轮请求或控制是否调用模型。`ModelRequest` 是该入口收到的请求对象，`request.override()` 返回带有指定字段替换的新请求。

| 需求 | 适合的扩展位置 | 需要保留的边界 |
| --- | --- | --- |
| 按项目和阶段装配系统说明 | `dynamic_prompt` | 明确返回的完整系统说明，不能无意丢掉固定规则 |
| 本轮只提供相关消息、材料和工具 | `wrap_model_call` + `request.override()` | 只改变输入视图，保留可恢复的原始事实 |
| 将新证据或阶段推进写入后续状态 | 图节点返回状态更新，或状态更新 hook | 明确更新者和版本，避免请求裁剪顺便删除长期事实 |

动态工具需要同时接入模型目录与执行分发。下面节选 LangChain 1.3.7 的真实测试 `libs/langchain_v1/tests/unit_tests/agents/middleware/core/test_dynamic_tools.py` → `DynamicToolMiddleware`；省略类型标注、异步方法和测试工具定义，代码中的 `dynamic_tool` 是测试预先定义的工具。

```python
def wrap_model_call(self, request, handler):
    # 将工具加入本轮模型能看到的目录。
    updated = request.override(tools=[*request.tools, dynamic_tool])
    return handler(updated)

def wrap_tool_call(self, request, handler):
    # 模型选中工具后，还要提供实际执行对象。
    if request.tool_call["name"] == "dynamic_tool":
        return handler(request.override(tool=dynamic_tool))
    return handler(request)
```

这个测试验证注册与分发，没有实现业务鉴权。本例的读取、编辑和查询工具可以预先注册，按阶段筛选本轮 `request.tools` 即可；不必为了动态显示工具而再建立动态执行对象。只有工具实例确实在运行时创建时，才需要补齐后一段分发逻辑。

### 2. 按业务阶段装配，不靠提示词隐藏权限 {/* #2-按业务阶段装配不靠提示词隐藏权限 */}

在 `wrap_model_call` 中读取已确认的阶段与版本，选择必需事实和候选工具，校验完整性后通过 `request.override()` 生成本轮请求，再交给 `handler` 调用模型。材料检索可以提前在节点或服务中完成，避免包装器每次重试都重复下载整份资料。

装配器不应顺便把 `A903` 标成失败或清除历史动作。查询结果进入图状态的路径负责事实更新，模型调用中间件只派生视图。请求视图裁剪后，还要确认持久状态中的动作 ID、原始来源引用和审批版本没有被删除。

若存在多个修改请求的中间件，应在尽可能靠近模型适配器的位置检查最终消息和工具目录，确认后续中间件没有重新加入被移除的工具。同步与异步调用使用各自的包装入口，验收应覆盖业务实际使用的路径。

接口基线为 LangChain 1.3.7。进一步的中间件顺序与动态工具实现见[中间件控制面](../../../application-notes/engineering/langchain-series/langchain/04-middleware-control-plane.md)和[动态工具](../../../application-notes/engineering/langchain-series/langchain/11-tool-dynamics.md)。

### 真实项目：上下文计量不能代替事实选择

本地 `my-dify` 源码提交 `4e21eae6006c719a560a0b2f1af0aeba58d9b9ed` 中，`ContextWindowMiddleware` 是包住模型调用的上下文观测中间件：调用前按系统规则、历史摘要、用户消息、工具返回和工具定义分类估算，调用后补上供应商给出的实际用量。源码：`internal/core/agent_v2/middleware/context_window_middleware.py` → `build_context_snapshot()`（第 62–133 行，节选）。

```python
budget = request_input_budget(request.model)
counted = ([request.system_message] if request.system_message else []) + list(request.messages)
compaction_count = count_tokens_approximately(counted, tools=request.tools)
fixed_count = count_tokens_approximately([request.system_message] if request.system_message else [], tools=request.tools)
if budget and fixed_count >= budget:
    raise ValueError("系统提示与工具定义已用尽模型输入预算，请减少固定配置或提高可用窗口")
```

检查固定部分是否吃光预算，可以及早暴露“工具定义太多”这种无法靠裁剪聊天历史解决的问题。多模态输入没有按 Base64 长度伪算媒体 token；真实用量要等供应商响应后补齐（同文件第 89–95、137 行以后）。主动压缩由 `ConversationCompactionMiddleware` 适配 Deep Agents 的摘要实现，并校验摘要及媒体归档结果（`internal/core/agent_v2/middleware/conversation_compaction.py` 第 19–57 行）。

这些机制能说明**输入占用在哪里**，却不能独自判断客户字段、记录 ID 或逾期规则是否是本轮必需事实。后者要回到客户跟进的业务上下文定义，再用本篇的信息充分性和业务结果两层指标对照验证。

## 八、常见装配失败 {/* #七常见装配失败 */}

| 失败现象 | 主要原因 | 调整方式 |
|---|---|---|
| 全量拼接历史 | 缺少任务和阶段筛选 | 按目标、阶段和优先级选择 |
| 动态内容覆盖规则 | 稳定区和动态区混用 | 固定规则区域，动态内容独立注入 |
| 所有工具常驻 | 能力可见范围过大 | 按阶段和权限注入 |
| 过期证据继续使用 | 缺少版本和时效判断 | 记录版本，失效后重新获取 |
| 超预算直接截断 | 没有明确释放顺序 | 按优先级裁剪、摘要或外部化 |
| 阶段内容泄漏 | 一份输入贯穿全流程 | 每次阶段变化后重新装配 |

## 九、上下文装配的验收 {/* #八上下文装配的验收 */}

### 1. 信息充分性 {/* #信息充分性 */}

移除无关背景后，模型仍能获得完成任务所需的事实、约束和证据。

### 2. 信息隔离 {/* #信息隔离 */}

不属于当前任务、权限或阶段的内容不会进入输入。

### 3. 阶段一致性 {/* #阶段一致性 */}

不同阶段的模型调用只看到对应阶段需要的材料和能力。

### 4. 预算稳定性 {/* #预算稳定性 */}

输入长度、输出预留和动态材料数量处于预期范围，超预算时按既定策略释放内容。

### 5. 用同一批任务比较装配策略 {/* #用同一批任务比较装配策略 */}

以下是待执行的验收设计，不包含虚构的性能数据。固定任务输入、来源快照和框架配置，用原有策略作为基线，再比较阶段装配策略。捕获最终模型请求能验证输入控制；真实模型运行才能观察它是否改善任务结果。

| 输入变化或故障 | 请求层应满足的条件 | 业务层应观察的结果 |
| --- | --- | --- |
| 在编辑历史中加入大量无关旧材料 | 必需版本、范围与引用仍存在 | 不因干扰遗漏修改要求 |
| 发布超时后进入对账阶段 | 保留 `A903` 与未知状态，提供查询能力 | 查询结果后再决定后续动作，不盲目重发 |
| 新版与旧版说明都被召回 | 当前版本明确，历史材料有标签 | 依据有效版本回答，并说明必要差异 |
| 必需草稿暂时无法读取 | 阻止依赖该草稿的生成，或转入补取 | 不编造草稿内容或声称完成审校 |
| 权限范围或阶段变化，但旧视图已缓存 | 缓存失效，最终请求不含越权材料与旧阶段工具 | 旧提案仍被执行端重新校验 |
| 裁剪请求视图后恢复执行 | 持久状态仍保留动作和来源记录 | 恢复能继续对账与重新读取 |

必需事实遗漏率可以按“未满足必需字段约束的请求数 / 被检查请求数”统计；它验证的是装配完整性，不代表模型已经正确使用这些事实。另行统计任务通过率、重复发布提案、实际越权执行和过期证据使用，避免把不同失败混成一个分数。

收益比较同时看整项任务的输入用量、摘要与检索调用、重新读取次数、装配延迟和完成耗时。输入减少但任务完成率下降，或频繁重读抵消了节省，都需要重新调整策略；没有完成对照评测前，只描述预期收益。

# 项目规则：让一次纠正持续影响后续任务

一条纠正留在当前会话中，通常只能影响这项工作的后续判断。希望新任务继续遵守，就需要把其中稳定、已确认的要求放到可发现、可维护的项目规则里，并验证它确实进入了新任务。

例如，Agent 把“发布后出现告警”直接写成“发布造成故障”。纠正当前报告时，需要补查证据；沉淀长期规则时，要保留的是因果判断的证据要求，而不是某次发布和某台机器的细节。

## 一、先判断信息应该留在哪里

Thread 是保存任务过程的会话记录；Memory 是跨任务复用的事实或经验；项目规则表达团队已确认的要求；Skill 则提供完成某类任务的方法。它们可能都以文本保存，但维护责任和使用条件不同。

| 内容 | 合适的位置 | 后续任务如何使用 |
| --- | --- | --- |
| 本次请求编号、异常实例、临时处置 | 当前任务记录 | 回查本次事故 |
| 某模块日志已迁移到新入口 | 有来源和有效期的记忆或模块文档 | 查询前核对入口是否仍有效 |
| 报告必须区分事实、推断和未决问题 | 项目规则 | 适用任务默认遵守 |
| 关联日志、发布和指标的调查步骤 | Skill | 命中任务后加载执行 |
| 禁止修改生产配置 | 运行时权限策略，并在规则中说明 | 执行端阻止越权动作 |

放在哪里，应由信息的职责决定。同一句要求可以先作为记忆候选，经过确认后成为项目规则；正式规则生效后，应同步处理旧记忆，避免两处长期维护互相冲突的版本。

## 二、从纠正中提取稳定要求

一次纠正可以分成现场信息、判断原则和执行要求。只有离开当前样本仍成立的部分，才适合扩大作用范围。

以事故报告为例，“这次先别认定发布是根因”仍然依赖当前现场。进一步提取后，可以形成三条可检查的要求：

- 将已确认事实、原因假设和仍缺少的证据分开表达。
- 时间相邻只能支持调查顺序，确认因果还需要机制或验证证据。
- 关键判断附上日志、指标、代码或变更记录的位置。

这三条要求能指导另一场事故，也能在产物中检查。相反，“遇到支付超时就先查连接池”可能只是一次成功路径，未经更多样本验证，不宜成为所有任务的默认步骤。

审核候选规则时，可以做两次替换：换一个对象，它还成立吗；换一种原因，它还会帮助判断吗。若必须限定为某个模块或任务类型，就把这个条件写进规则，放到相应范围。

规则还应说明缺少证据时怎样继续。例如无法确认根因时，输出已有事实、候选原因和下一步验证方式，而不是要求模型无论如何都给出一个明确结论。

## 三、规则的生效范围取决于加载机制

`AGENTS.md`、`CLAUDE.md` 等文件可用于保存项目要求，但文件名只是入口。规则能否生效，还取决于运行时从哪里查找、何时读取，以及怎样组合不同范围的内容。

组织规则时，可以将全项目共同要求放在公共入口，将某个模块的日志路径、输出格式和特殊约束放在模块入口。但不要仅凭目录结构推断加载行为：有的实现启动时沿目录链加载，有的会在读取文件或进入模块时再发现局部规则。

接入具体工具时，应核对以下问题：

| 问题 | 为什么会影响行为 |
| --- | --- |
| 从当前目录、仓库根目录还是指定路径开始查找 | 决定哪些规则有机会被发现 |
| 子目录规则何时读取 | 决定根目录启动的任务能否及时拿到局部要求 |
| 同层多个文件和上下层规则怎样组合 | 决定冲突、覆盖与遗漏 |
| 是否存在大小限制或截断 | 决定文件存在时是否仍有内容未被读取 |
| 修改后何时重新加载 | 决定当前任务还是后续任务采用新版本 |

因此，规则更新的交付物不应只有一个修改过的文件，还应包括适用范围、版本和新任务中的加载证据。未经验证，不要把“已保存”报告成“所有活跃任务已经采用”。

## 四、用规则表达方法，用执行器限制动作

项目规则影响模型的判断和提案，权限系统限制提案能否真正执行。事故调查中，“不要修改日志”可以写在规则里，让模型理解任务边界；日志目录的只读权限和工具写入限制，负责在执行时守住这一要求。

同样，“发布前运行检查”若是业务必须满足的条件，就应由发布流程核对结果。只在规则文件里要求检查，无法证明每条发布路径都会经过它。

规则改进也不能替代故障修复。工具错误地允许越权写入，应修改授权逻辑；只有报告组织不清、证据引用遗漏等工作方法问题，才优先考虑通过规则调整。

## 五、用新任务检验规则，而不是让旧会话复述它

旧会话已经收到人工纠正，即使没有加载项目规则，也可能答对。验证跨任务生效时，需要另开一个不含该纠正的新任务。

一个最小验证过程是：

1. 保存规则修改前的版本，并准备不同于触发修改的任务材料。
2. 明确新任务应加载的项目和模块范围，确认读取到了目标版本。
3. 检查新报告是否按要求区分事实和假设，并核对引用。
4. 再用规则范围以外的任务检查误用，例如普通代码格式修改不应被强制写成事故调查报告。

如果需要比较前后收益，让旧规则和新规则分别在相同的新任务材料上运行；两边都从干净会话开始。除了结果是否正确，也观察是否增加不必要的查询、交互和输出。

## 六、规则增长时，合并条件与移出细节

持续追加补丁会让项目规则逐渐变成事故流水账。维护时应处理重复、冲突和已经失效的要求，并给复杂方法找到更合适的位置。

例如公共入口保留“关键结论需要证据”，具体模块的指标口径放在参考文档，完整调查步骤放入 Skill。这样调整调查命令时，不必连带修改所有任务默认加载的规则。

每次改动应能说明触发问题、适用范围、验证结果和撤回方式。规则文件可以很短，但它影响后续任务的路径必须可追查。如何把更完整的操作经验整理成方法，见 [Skill 激活与经验封装](./agent-skill-design.md)。

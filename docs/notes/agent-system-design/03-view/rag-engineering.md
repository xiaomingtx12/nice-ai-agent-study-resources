# RAG 工程：从资料到在线证据

完整 RAG 是一条数据链：资料被解析、切分、索引、召回、过滤、重排，再以带来源的证据进入模型；上线后还要处理权限、更新、缓存、延迟和失败回退。

```text
source
  → ingest
  → parse / normalize
  → chunk / enrich metadata
  → index
  → query understanding
  → retrieve
  → filter / rerank
  → context assembly
  → grounded generation
  → citation / verification
```

## 先决定是否需要 RAG

不要把“知识库”当作默认架构。先比较三种方案：

| 场景 | 更合适的方案 |
|---|---|
| 资料少、稳定、每次都要看 | 固定上下文或摘要 |
| 资料多、更新频繁、问题可定位到片段 | 普通 RAG |
| 需要实体关系、多跳路径或全局主题 | RAG + GraphRAG |

引入 RAG 的信号是：上下文无法常驻、知识更新不能靠重新发版、回答需要引用、权限和来源必须可追溯。若只是几十段稳定规则，复杂检索链可能比直接注入更不可靠。

## 一、离线构建链路

### 1. 接入与版本

为每个来源建立稳定身份、版本和同步状态：

```text
source_id / source_type / version / updated_at / owner / access_scope
```

同步要区分新增、修改、删除和暂时不可用。删除事件必须能让旧片段失效，否则在线检索会返回已经不存在的事实。

### 2. 解析与质量检查

解析过程处理表格、代码、标题层级、图片 OCR、附件和链接，这些结构都可能影响答案。解析后要保留：

- 原文或原始文件引用；
- 标题路径和页码/段落位置；
- 文档类型和结构；
- 解析警告与失败原因。

解析质量没有通过时，不要继续切分和入库；错误会被索引放大。

### 3. 切分与元数据

切分目标是让一个片段足够独立地支撑一个事实，同时保留必要上下文。每个 chunk 至少包含：

```text
chunk_id
document_id
content
section_path
source_ref
version
permission_scope
updated_at
```

切分策略按文档类型选择：标题/段落、代码块、表格行、问答对和父子片段使用不同规则。`overlap` 根据边界补偿需求设置。

### 4. 索引

向量索引擅长语义相似，关键词索引擅长错误码、专有名词、编号和精确匹配。生产系统通常需要按查询类型组合：

```text
lexical search + vector search
        → merge / deduplicate
        → rerank
```

索引版本必须和 embedding 模型、切分版本、过滤规则绑定。升级 embedding 或切分规则时，不能把新旧向量静默混用。

## 二、在线 RAG

### 1. 查询理解

在线请求先保留原始 query，再视需要做：

- 指代消解；
- 时间、租户、项目和权限条件提取；
- 查询改写或多查询扩展；
- 是否需要检索的路由判断。

改写结果不能覆盖原始 query。改写可能把用户范围、否定条件或实体名称改错，检索时要保留原始查询兜底。

### 2. 召回与过滤顺序

推荐先做硬过滤，再做相关性排序：

```text
query
→ tenant / permission / version / freshness filter
→ lexical + vector recall
→ deduplicate
→ rerank
→ evidence budget
```

权限过滤不能只放在生成前；不允许看到的片段不应先进入候选集。过滤条件要可审计，结果要记录被过滤的原因。

### 3. 证据预算与上下文注入

召回数量按证据预算控制。最终上下文需要关注：

- 证据片段数量；
- 每片段长度；
- 来源多样性，避免同一文档占满窗口；
- 证据之间的冲突；
- 输出预留和引用格式。

交给模型的内容组织成带编号、来源和版本的证据包：

```text
[E1] title / source / version
content...

[E2] title / source / version
content...
```

生成合同要求：事实性陈述必须能指向证据；证据不足时拒答或澄清；证据冲突时显式说明冲突。

### 4. 生成后校验

生成后的最小校验链：

1. 引用 ID 是否存在；
2. 引用来源是否真的包含对应事实；
3. 答案是否超出证据范围；
4. 是否触发拒答或敏感信息规则；
5. 引用和答案是否使用同一版本的证据。

模型自报“根据资料”不能作为验证结果。

## 三、在线系统的工程问题

### 新鲜度

资料更新到用户可见之间存在延迟。需要定义：

```text
source updated → ingestion → index publish → cache invalidate
```

高时效数据可以走实时查询或短缓存；稳定文档可以批量索引。不能用一个全局 TTL 解决所有来源。

### 延迟

在线延迟通常来自查询改写、向量召回、重排和模型生成。优化顺序应由 trace 决定：

- 重复 query：缓存召回或最终答案；
- 召回慢：批量、连接池、索引参数；
- 重排慢：减少候选、并行化或使用轻量模型；
- 首 token 慢：流式输出，但不能绕过证据校验。

缓存键必须包含租户、权限、知识版本和查询策略；否则会造成跨用户或跨版本泄漏。

### 失败回退

在线 RAG 至少需要这些出口：

- 检索服务不可用：返回明确降级，不伪装成有依据的答案；
- 召回为空：拒答、追问或转人工；
- 证据冲突：展示冲突并要求确认；
- 证据过期：标记时间或走实时源；
- 重排超时：使用已过滤的基础召回并降低置信表达。

## 四、评测和观测

离线评测要把检索和生成拆开：

| 评测段 | 问题 |
|---|---|
| 索引/召回 | 支撑答案的证据是否被找到 |
| 重排/过滤 | 正确证据是否排在可用位置，权限是否正确 |
| 生成/引用 | 答案是否忠实、相关、可引用 |
| 在线运行 | 延迟、新鲜度、成本和失败回退是否可接受 |

每次线上事故都应保留 query、知识版本、召回候选、过滤原因、最终证据、模型版本和引用校验结果，才能判断问题来自资料、检索还是生成。

## 五、何时引入 GraphRAG

只有当问题需要稳定实体关系、多跳路径或全局主题摘要时，才在普通 RAG 上增加图结构。图构建、别名合并、社区摘要和路径搜索见 [GraphRAG：什么时候值得建图](./graph-rag-engineering.md)。

## 六、与其他组件的边界

- [上下文装配](./agent-context-management.md)决定证据如何进入当前模型视图；
- [Agent 评测](../06-observation/agent-evaluation.md)验证召回和生成是否正确；
- [知识编译：LLM-Wiki](./llm-wiki-knowledge-compilation.md)处理知识资产持续整理，不等同于在线检索；
- Memory 保存主体或任务的长期事实，RAG 保存外部资料。

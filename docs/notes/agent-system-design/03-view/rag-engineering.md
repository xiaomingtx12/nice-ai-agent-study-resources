# RAG 工程：从资料到在线证据

> **模块本质：** 将外部资料转换成当前任务可检索、可验证、可追溯的证据，用权限范围内的有效信息支撑模型回答，并在证据不足或冲突时明确限制结论。

完整 RAG 是一条数据链：资料被解析、切分、索引、召回、过滤、重排，再以带来源的证据进入模型；上线后还要处理权限、更新、缓存、延迟和失败回退。

```text
source
  → ingest
  → parse / normalize
  → chunk / enrich metadata
  → index
  → query understanding
  → retrieve
  → filter / rerank
  → context assembly
  → grounded generation
  → citation / verification
```

## 一、先决定是否需要 RAG {/* #先决定是否需要-rag */}

不要把“知识库”当作默认架构。先比较三种方案：

| 场景 | 更合适的方案 |
|---|---|
| 资料少、稳定、每次都要看 | 固定上下文或摘要 |
| 资料多、更新频繁、问题可定位到片段 | 普通 RAG |
| 需要实体关系、多跳路径或全局主题 | RAG + GraphRAG |

引入 RAG 的信号是：上下文无法常驻、知识更新不能靠重新发版、回答需要引用、权限和来源必须可追溯。若只是几十段稳定规则，复杂检索链可能比直接注入更不可靠。

## 二、离线构建链路 {/* #一离线构建链路 */}

### 1. 接入与版本 {/* #1-接入与版本 */}

为每个来源建立稳定身份、版本和同步状态：

```text
source_id / source_type / version / updated_at / owner / access_scope
```

同步要区分新增、修改、删除和暂时不可用。删除事件必须能让旧片段失效，否则在线检索会返回已经不存在的事实。

### 2. 解析与质量检查 {/* #2-解析与质量检查 */}

解析过程处理表格、代码、标题层级、图片 OCR、附件和链接，这些结构都可能影响答案。解析后要保留：

- 原文或原始文件引用；
- 标题路径和页码/段落位置；
- 文档类型和结构；
- 解析警告与失败原因。

解析质量没有通过时，不要继续切分和入库；错误会被索引放大。

### 3. 切分与元数据 {/* #3-切分与元数据 */}

切分目标是让一个片段足够独立地支撑一个事实，同时保留必要上下文。每个 chunk 至少包含：

```text
chunk_id
document_id
content
section_path
source_ref
version
permission_scope
updated_at
```

切分策略按文档类型选择：标题/段落、代码块、表格行、问答对和父子片段使用不同规则。`overlap` 根据边界补偿需求设置。

### 4. 索引 {/* #4-索引 */}

向量索引擅长语义相似，关键词索引擅长错误码、专有名词、编号和精确匹配。生产系统通常需要按查询类型组合：

```text
lexical search + vector search
        → merge / deduplicate
        → rerank
```

索引版本必须和 embedding 模型、切分版本、过滤规则绑定。升级 embedding 或切分规则时，不能把新旧向量静默混用。

### 5、把建库结果作为可发布、可回退的制品

每次构建保留一份清单，记录来源及内容摘要、解析器版本、切分规则、embedding 模型与维度、索引版本、构建时间和验证结果。仅有“昨天重建成功”的日志，无法解释某条证据为什么发生变化。

新构建先进入候选索引，用独立问题验证证据覆盖、引用位置、权限过滤和删除传播。通过后再切换在线入口，保留前一版本供必要时回退。切换时保证查询向量与候选索引使用兼容的模型和维度，避免入口已经更新，检索配置仍停在旧版本。

回退只恢复检索制品，不能恢复已经撤销的权限或已删除的资料。删除标记、租户权限与禁止访问规则需要在当前访问层继续生效；旧索引中残留的片段也应被过滤并清理。验收时专门安排“删源后回退索引”和“权限收紧后回退”，确认旧内容不会重新出现。

输入包含表格、扫描页或图像时，先验证转换是否保留行列、单位和来源坐标，再进入建库流程，见[渐进发现与多模态核验](./agent-evidence-intake.md)。

## 三、在线 RAG {/* #二在线-rag */}

### 1. 查询理解 {/* #1-查询理解 */}

在线请求先保留原始 query，再视需要做：

- 指代消解；
- 时间、租户、项目和权限条件提取；
- 查询改写或多查询扩展；
- 是否需要检索的路由判断。

改写结果不能覆盖原始 query。改写可能把用户范围、否定条件或实体名称改错，检索时要保留原始查询兜底。

### 2. 召回与过滤顺序 {/* #2-召回与过滤顺序 */}

推荐先做硬过滤，再做相关性排序：

```text
query
→ tenant / permission / version / freshness filter
→ lexical + vector recall
→ deduplicate
→ rerank
→ evidence budget
```

权限过滤不能只放在生成前；不允许看到的片段不应先进入候选集。过滤条件要可审计，结果要记录被过滤的原因。

### 3. 约束读取与知识召回分开 {/* #约束读取与知识召回分开 */}

与问题语义相关的材料，和本次任务必须遵守的限制，需要不同的获取方式。假设用户要求“只处理草稿”，这条限制即使与检索问题的相似度很低，也必须在后续写操作中生效。

| 信息类型 | 获取方式 | 缺失时的处理 |
| --- | --- | --- |
| 任务目标、用户明确限制 | 按任务 ID 从有效状态读取 | 澄清或暂停依赖该字段的动作 |
| 租户策略、资源权限 | 按执行身份和资源从权威策略源读取 | 无法确认授权时拒绝相关执行 |
| 领域知识、历史案例 | 权限过滤后的关键词、向量或混合召回 | 扩展查询、说明证据不足或拒答 |

两路结果可以共同进入模型视图，但不能混用排序规则。必需限制不参加普通 top-k 竞争；它们是否允许某个动作，仍由执行门确定。向量召回只为知识证据选候选，不承担授权判断。

规则也需要生命周期。记录适用范围、生效时间、版本和失效条件；规则冲突时按既定优先级或人工处理，不让模型仅凭措辞强弱选择。规则内容过多时按任务阶段筛选适用集合，不能把全部组织规定永久塞入每次调用。

### 4. 证据预算与上下文注入 {/* #3-证据预算与上下文注入 */}

召回数量按证据预算控制。最终上下文需要关注：

- 证据片段数量；
- 每片段长度；
- 来源多样性，避免同一文档占满窗口；
- 证据之间的冲突；
- 输出预留和引用格式。

交给模型的内容组织成带编号、来源和版本的证据包：

```text
[E1] title / source / version
content...

[E2] title / source / version
content...
```

生成合同要求：事实性陈述必须能指向证据；证据不足时拒答或澄清；证据冲突时显式说明冲突。

生成摘要时保留否定条件、适用范围和证据来源。引用中的操作建议仍是待判断材料，不能变成新增权限。例如一篇迁移文档建议清空旧数据，不代表当前只读诊断任务可以执行删除。

### 5. 生成后校验 {/* #4-生成后校验 */}

生成后的最小校验链：

1. 引用 ID 是否存在；
2. 引用来源是否真的包含对应事实；
3. 答案是否超出证据范围；
4. 是否触发拒答或敏感信息规则；
5. 引用和答案是否使用同一版本的证据。

模型自报“根据资料”不能作为验证结果。

## 四、在线系统的工程问题 {/* #三在线系统的工程问题 */}

### 1. 新鲜度 {/* #新鲜度 */}

资料更新到用户可见之间存在延迟。需要定义：

```text
source updated → ingestion → index publish → cache invalidate
```

高时效数据可以走实时查询或短缓存；稳定文档可以批量索引。不能用一个全局 TTL 解决所有来源。

### 2. 延迟 {/* #延迟 */}

在线延迟通常来自查询改写、向量召回、重排和模型生成。优化顺序应由 trace 决定：

- 重复 query：缓存召回或最终答案；
- 召回慢：批量、连接池、索引参数；
- 重排慢：减少候选、并行化或使用轻量模型；
- 首 token 慢：流式输出，但不能绕过证据校验。

缓存键必须包含租户、权限、知识版本和查询策略；否则会造成跨用户或跨版本泄漏。

### 3. 失败回退 {/* #失败回退 */}

在线 RAG 至少需要这些出口：

- 检索服务不可用：返回明确降级，不伪装成有依据的答案；
- 召回为空：拒答、追问或转人工；
- 证据冲突：展示冲突并要求确认；
- 证据过期：标记时间或走实时源；
- 重排超时：使用已过滤的基础召回并降低置信表达。

## 五、用检索组件定制业务证据链 {/* #框架中的检索接入 */}

### 1. 先选固定检索流程，再决定是否开放为工具 {/* #1-先选固定检索流程再决定是否开放为工具 */}

LangChain 的 Retriever 是接收查询并返回文档的检索接口；`VectorStore.as_retriever()` 将向量存储包装成该接口，`invoke()` 执行一次查询。固定流程适合“回答前必须检查知识库”的业务；将检索注册为 Agent 工具，适合模型需要判断是否检索、改写问题或补充证据的开放任务。

两种方式可以组合：入口节点强制检索当前文档版本和项目规则，Agent 再按缺口调用补充检索。不要把必须获得的依据完全交给模型自行决定是否读取。

### 2. 将召回策略与访问范围分开传入 {/* #2-将召回策略与访问范围分开传入 */}

LangChain Core 1.4.6 的 `libs/core/langchain_core/vectorstores/base.py` → `VectorStore.as_retriever()` 文档包含以下真实用法。`docsearch` 是已初始化的向量存储；这里节选配置表达式，不包含索引构建。

```python
docsearch.as_retriever(search_type="mmr", search_kwargs={"k": 5, "fetch_k": 50})
```

MMR（最大边际相关性）在相关性之外考虑结果差异度，适合减少多个相似片段占满候选集。`fetch_k` 和 `k` 的数值来自源码示例，不是通用最佳参数；支持程度和实际行为还需核对所用向量存储。调整后应比较证据覆盖率与无关片段比例。

| 定制点 | 放置位置 | 业务要求 |
| --- | --- | --- |
| 查询改写和领域词扩展 | 检索前节点或专用服务 | 保留原始问题与改写结果，避免改变实体和约束 |
| 租户、项目与版本过滤 | 检索服务依据可信身份生成过滤条件 | 核对底层是否支持并实际执行；不能让模型自由填写租户范围 |
| 关键词与向量混合召回 | 组合多个检索通道 | 保留来源并去重，用固定样本决定融合权重 |
| 重排与证据裁剪 | 召回后、模型生成前 | 返回来源 ID、版本和片段位置，保留相互冲突的证据 |

`search_kwargs` 是向底层检索方法传参的入口，不是跨数据库统一的权限协议。未授权内容应在进入重排服务和模型前排除；服务端还应验证返回记录的归属，发现过滤失效时拒绝继续回答。

### 3. 用业务问题验证整条链路 {/* #3-用业务问题验证整条链路 */}

文档问答可以同时放入旧版部署说明、新版迁移说明和另一项目的相似页面。检查系统能否选择当前项目的有效版本，回答中能否定位依据，以及证据冲突时是否继续补查。只验证 Retriever 返回了五个文档，无法证明检索有效。

组件调用、参数透传与扩展实现见[检索组件与调用路径](../../../application-notes/engineering/langchain-series/langchain/12-rag-components-and-retrieval.md)和[高级检索](../../../application-notes/engineering/langchain-series/langchain/13-advanced-retrieval-techniques.md)。

## 六、评测和观测 {/* #四评测和观测 */}

离线评测要把检索和生成拆开：

| 评测段 | 问题 |
|---|---|
| 索引/召回 | 支撑答案的证据是否被找到 |
| 重排/过滤 | 正确证据是否排在可用位置，权限是否正确 |
| 生成/引用 | 答案是否忠实、相关、可引用 |
| 在线运行 | 延迟、新鲜度、成本和失败回退是否可接受 |

每次线上事故都应保留 query、知识版本、召回候选、过滤原因、最终证据、模型版本和引用校验结果，才能判断问题来自资料、检索还是生成。

## 七、何时引入 GraphRAG {/* #五何时引入-graphrag */}

只有当问题需要稳定实体关系、多跳路径或全局主题摘要时，才在普通 RAG 上增加图结构。图构建、别名合并、社区摘要和路径搜索见 [GraphRAG：什么时候值得建图](./graph-rag-engineering.md)。

## 八、与其他组件的边界 {/* #六与其他组件的边界 */}

- [上下文装配](./agent-context-management.md)决定证据如何进入当前模型视图；
- [Agent 评测](../06-observation/agent-evaluation.md)验证召回和生成是否正确；
- [知识编译：LLM-Wiki](./llm-wiki-knowledge-compilation.md)处理知识资产持续整理，不等同于在线检索；
- Memory 保存主体或任务的长期事实，RAG 保存外部资料。

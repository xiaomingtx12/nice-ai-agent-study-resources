# GraphRAG：什么时候值得建图

GraphRAG 适合问题依赖实体、关系、路径或集合结构的场景。它增加抽取、归一化、增量更新和查询成本，只有当这些结构会改变答案时才值得建图。

## 先做路线选择

| 问题形态 | 默认路线 | 升级信号 |
|---|---|---|
| 单个事实、局部段落 | 普通 RAG | 召回段落经常缺少关系上下文 |
| 两到三跳关系 | 向量召回 + 邻居扩展 | 关系类型稳定，路径可解释 |
| 跨文档比较 | 混合检索 | 需要实体归一化和证据合并 |
| “整个领域有哪些主题” | 社区/主题摘要 | 有稳定语料、允许离线编译 |
| 高频变化、强实时数据 | 数据库或 API | 不应把最新状态滞后写进图 |

先用评测样本证明普通 RAG 的失败来自“结构缺失”，再引入 GraphRAG。否则建图只是把召回链路变长。

## 图数据需要服务查询

最小图模型需要同时保存结构和证据：

```text
Entity {
  id, type, canonical_name, aliases,
  source_refs, valid_from, valid_until, version
}

Relation {
  source, type, target,
  confidence, source_refs, valid_from, valid_until
}
```

`source_refs` 必须能定位到原始文档、版本和片段。实体或关系无法回溯来源时，只能作为待审核候选，不能直接进入正式答案。

## 构建链路

```mermaid
flowchart LR
    S[来源文档] --> P[解析与切片]
    P --> E[实体/关系候选]
    E --> N[实体归一化]
    N --> C[冲突与置信度检查]
    C --> G[版本化图存储]
    G --> I[向量/邻居/社区索引]
    I --> Q[查询规划]
    Q --> R[路径与段落混合召回]
    R --> V[证据校验]
```

抽取、归一化和写入要分开。模型把“北京”“北京市”和某个项目简称识别成同一实体，仍然需要规则、别名表或人工确认；不能让一次抽取调用直接覆盖图数据。

增量更新至少记录三类变更：

- 新实体或新关系；
- 原关系的置信度、有效期或来源变化；
- 来源删除或版本失效导致的反向删除。

删除来源时只删文本索引、不删图关系，会留下无法解释的“幽灵事实”。

## 查询时控制路径

一次查询先判断要找的是节点、邻居、路径还是全局主题，再决定检索算子：

```text
query
→ entity linking
→ seed nodes
→ bounded traversal
→ evidence join
→ rerank / contradiction check
→ answer
```

工程上要显式限制：

- 最大跳数；
- 每个节点的展开数；
- 总路径数和 token 预算；
- 允许的关系类型；
- 证据必须覆盖的来源数。

路径结果不能直接当答案。应把路径节点、关系来源和原文片段一起交给生成阶段；社区摘要只能帮助定位主题，不能替代原始证据。

## 关系冲突怎么处理

同一关系出现不同值时，不要用最后写入覆盖前值。保留候选及其来源，按时间、来源权威性和任务有效期决定当前视图；无法判定时显式返回冲突或请求澄清。

实体归一化也需要可回滚。合并两个实体后，如果后续发现别名判断错误，必须能拆分并重建受影响的邻居索引。

## 失败样本矩阵

| 样本 | 需要看到的失败 | 保护措施 |
|---|---|---|
| 同名实体 | 路径串到错误主体 | 租户/类型/时间约束 + 人工候选 |
| 过期关系 | 旧政策覆盖新政策 | 有效期和来源版本过滤 |
| 路径过长 | 生成编造中间结论 | 跳数、路径和证据预算 |
| 图无结果 | 系统硬凑答案 | 退回普通 RAG 或拒答 |
| 社区摘要失真 | 全局总结掩盖例外 | 摘要只做导航，答案引用原文 |

评测至少拆开看：实体链接准确率、关系/路径准确率、来源覆盖率、答案忠实度、索引更新延迟和尾延迟。只看最终回答分数，定位不了到底是抽取错、图错还是生成错。

## 与普通 RAG 的边界

普通 RAG 擅长找到相关段落，GraphRAG 擅长沿结构找证据。二者应共享来源、权限、版本和评测合同；查询时可以混合，不能互相替代。

# 证据与反馈

> **模块本质：** 将模型可见依据、执行决策、外部结果和状态变化记录为能够关联的证据，支持运行时反馈、故障定位、成本归因与后续评测。

Agent 的观测需要回答三个问题：模型当时获得了什么依据，运行时实际允许并执行了什么，外部世界是否达到任务要求。请求成功率只能覆盖其中一部分；工具返回成功而产物缺失、任务停了而子任务仍在计费，都需要额外证据。

Observation 在运行时还承担反馈职责。工具的成功、拒绝、部分完成和未知结果，要转换成下一轮能消费的事实；不能只写进日志，然后仍向模型返回一个“成功”。

## 一、用稳定身份关联一次任务 {/* #用稳定身份关联一次任务 */}

Trace（调用链）关联一组执行活动，Span（操作区间）记录一次模型调用、工具执行或等待，Event（事件）记录审批通过、状态提交等瞬时变化。跨队列或跨进程后仍需保留业务身份，才能把恢复后的运行与原任务连接起来。

| 身份 | 用途 | 重试与恢复时的规则 |
| --- | --- | --- |
| 任务 ID | 标识用户要完成的工作 | 同一任务持续使用 |
| 运行 ID、父运行 ID | 区分执行尝试和子任务 | 新运行有新身份，并关联原任务 |
| 业务动作 ID | 标识一次已确定的外部效果意图 | 同一动作重试复用，不能靠当前轮数重建 |
| 调用尝试 ID | 区分一次动作的多次网络尝试 | 每次尝试单独记录 |
| 事件 ID、状态版本 | 去重并定位状态变化 | 重复投递按事件身份去重，更新检查版本 |

模型协议里的工具调用 ID 用来配对调用消息与结果，不能默认代替持久化的业务动作 ID。模型重新生成一次调用时，协议 ID 可能已经不同。

并发分支、异步子任务和恢复运行需要记录关联关系。单纯按时间排序无法可靠重建因果；同一状态流可使用版本或序号，跨流用父运行和前置事件引用连接。

## 二、记录决策现场，避免事后猜测 {/* #记录决策现场避免事后猜测 */}

看到“模型选错工具”之后，应该能继续追问：正确工具当时是否可见，描述是否使用旧版本，关键证据是否被裁剪，动作参数是否经过运行时改写。只保存最终输出回答不了这些问题。

| 边界 | 至少保留的证据 | 能定位的问题 |
| --- | --- | --- |
| 输入装配 | 状态版本、提示词版本、可见工具版本、证据引用及裁剪原因 | 依据缺失、旧信息混入、工具不在候选中 |
| 模型调用 | 模型配置、实际请求引用、响应、用量和结束原因 | 输出截断、无效参数、调用成本异常 |
| 执行门 | 动作身份、参数摘要、授权结论、策略和审批版本 | 未授权请求、审批失效、参数变化 |
| 工具与外部系统 | 请求身份、外部任务 ID、执行状态与业务确认 | 重复创建、结果未知、部分生效 |
| 状态更新 | 更新前后版本、变更原因、持久化确认 | 写入冲突、恢复丢进度、结果未归并 |
| 退出 | 退出原因、未完成项、已验证产物、仍在运行的子任务 | 假成功、提前停止、后台任务遗漏 |

内容哈希只能帮助判断两份内容是否相同，不能还原原文。需要回放时，应保存有权限控制和保留期的内容快照或不可变引用；只有摘要的记录要明确标为诊断材料，不能宣称可以精确回放。

记录模型实际提供的动作、说明和依据即可，不以获取隐藏的内部思考过程作为可观测性的前提。凭据、会话令牌和不必要的个人信息不进入观测载荷。

## 三、调用成功、业务完成、状态提交分别记录 {/* #调用成功业务完成状态提交分别记录 */}

一次远端操作可能经过以下时点：

```text
动作获准 → 远端接受 → 远端执行 → 业务验收 → 本地状态持久化
```

每个时点都可能失败。建议分别记录传输结果、业务结果和状态提交结果，保留“尚未确认”的空间。例如服务端接受异步任务，只能记为已受理；直到产物可读取且通过验收，才能更新业务完成状态。

Deep Agents 声明版本 0.6.12 的源码快照提供了一个具体故障窗口，commit 未锁定，见[源码版本与路径约定](../../../application-notes/engineering/langchain-series/deepagents/source-baseline.md)。`start_async_task` 是启动远端子任务的工具；`Command` 是交给图运行时合并的状态更新指令。

源码：`libs/deepagents/deepagents/middleware/async_subagents.py` → `_build_start_tool()` 内的 `start_async_task()`（第 297–302、319–324 行节选；省略其他处理与局部变量构造，中文注释为阅读说明）。

```python
# 远端已经可能创建任务，本地索引尚未更新。
thread = client.threads.create()
run = client.runs.create(
    thread_id=thread["thread_id"],
    assistant_id=spec["graph_id"],
    input={"messages": [{"role": "user", "content": description}]},
)
# ……省略错误处理、task 和 msg 的构造……
return Command(
    update={
        "messages": [ToolMessage(msg, tool_call_id=runtime.tool_call_id)],
        "async_tasks": {task_id: task},
    }
)
```

源码顺序表明，远端创建发生在本地更新指令返回之前。若远端已经接受请求，但客户端没收到响应，本地可能缺少可查询的任务索引。观测端需要业务动作身份与远端记录的关联，不能只统计工具异常次数；恢复处理见[状态架构](../02-state/agent-state-architecture.md)。这段代码不构成对远端服务幂等能力的判断。

## 四、以任务和成功交付为单位看成本 {/* #以任务和成功交付为单位看成本 */}

费用记录应落在实际产生消耗的调用上，包括主模型、子 Agent、摘要、检索改写、评分器、重试和外部工具。父任务展示汇总费用时，底层消费记录仍保留唯一身份，避免把子任务费用既加到父级又再次加进全局总额。

建议同时保留三种口径：

| 口径 | 计算范围 | 用途 |
| --- | --- | --- |
| 单任务成本 | 一项任务及其子任务的全部消耗 | 定位异常任务与昂贵阶段 |
| 单位成功交付成本 | 同一批任务总消耗除以其中成功交付数 | 看见失败尝试和返工带来的浪费 |
| 成本分布 | 按任务类型统计中位数、尾部和超预算比例 | 避免少数长任务被平均值掩盖 |

没有成功交付时，单位成功交付成本标为不可计算，并单列已消耗费用。不能只统计成功任务花费，漏掉失败任务已经产生的成本。

用量、计价版本与估算状态分开记录。超时或流式中断未收到用量时，费用保持待核对；供应商账单回来后再对账。观察报表只能解释费用，执行时的预算预留与停止规则见 [Agent Loop](../04-decision/agent-brain.md)。

延迟也要拆开队列等待、模型响应、工具执行、人工等待和恢复等待。并行 Span 耗时相加得到的是累计操作时间，不能当成用户等待时间。

## 五、监控业务漂移，而不只监控异常码 {/* #监控业务漂移而不只监控异常码 */}

业务漂移指系统仍能返回结果，但行为开始偏离任务要求。例如不断换关键词搜索、计划多次重写却没有新证据，或者绕过验收提前宣称完成。

| 信号 | 应联合检查的证据 | 合理的处理方向 |
| --- | --- | --- |
| 无进展循环增加 | 已确认事实、产物版本和待办是否变化 | 调整停止条件或计划策略 |
| 工具结果未知比例上升 | 服务端请求身份、超时位置、对账积压 | 检查外部服务和恢复流程 |
| 任务成功但验收失败 | 完成提案、独立后置检查和返回用户的状态 | 修正终态判定 |
| 子任务成本占比突增 | 派生深度、重试、重复工作与汇合等待 | 收窄拆分和共享预算 |
| 上下文成本突增 | 输入分区大小、工具目录、缓存用量 | 检查装配变化与缓存失效 |

按任务类型和版本建立基线，并设最小样本量、持续时间和告警冷却。一次复杂任务花费高，不足以证明策略退化；频繁拒绝危险请求，也可能说明执行门正常工作。告警应附上代表轨迹与影响范围，便于负责人采取行动。

## 六、观测数据与恢复数据分开承担责任 {/* #观测数据与恢复数据分开承担责任 */}

诊断日志可以异步导出、采样和过期删除。恢复所需的动作登记、审批记录、账本与状态提交则需要满足业务持久化要求，不能只保存在一个可能丢事件的 Trace 后端中。

正常只读任务可以抽样保存详细内容；失败、未知副作用、审批变更和预算终止应优先保留关键证据。异步缓冲区要有上限，并记录丢弃数量。高风险动作若要求执行前审计落盘，应单独设计持久审计通道，而不是让普通遥测导出器承担这一保证。

证据快照需要租户隔离、访问控制和到期清理。删除源材料时，还要考虑观测副本与派生摘要，避免业务库已经删除、诊断记录仍可读取。

## 七、用框架事件拼出业务执行证据 {/* #框架中的观测接入 */}

### 1. 为不同消费者选择事件类型 {/* #1-为不同消费者选择事件类型 */}

LangGraph 的 `stream()` 和 `astream()` 分别提供同步与异步事件流，`stream_mode` 决定输出哪些事件。节点或工具中的 `get_stream_writer()` 可取得自定义事件写入器，用于报告业务进展。下表按 LangGraph 1.2.10 的 `libs/langgraph/langgraph/pregel/main.py` → `Pregel.stream()` 核对。

| 模式 | 输出内容 | 适合用途 |
| --- | --- | --- |
| `messages` | 模型消息片段及元数据 | 展示生成过程，按节点区分输出 |
| `updates` | 节点或任务返回的状态增量 | 展示阶段变化，定位哪一步更新了什么 |
| `values` | 每步之后的状态值 | 调试状态流转，需控制敏感内容暴露 |
| `custom` | 节点主动写出的自定义数据 | 显示已检查的文档数量、产物引用等业务进度 |
| `tasks` / `checkpoints` | 任务开始结束、检查点事件 | 分析执行顺序与恢复位置 |

界面通常只需要消息片段、阶段进展和终态，不应把完整 State 原样转发。多个模式与子图同时启用时，输出封装会变化；本快照还区分 `version`。消费者应锁定版本与输出契约，不要把所有事件都按纯文本 token 解析。

### 2. 在模型和工具边界关联业务身份 {/* #2-在模型和工具边界关联业务身份 */}

LangChain 的调用配置可携带 `metadata`、`tags` 与 callbacks；callbacks 是接收调用生命周期事件的回调接口，可对接 Trace 采集。把任务 ID、策略版本和阶段等非敏感标识关联到运行，工具中再记录动作 ID、资源版本与外部请求 ID。异步子任务跨服务后，需要显式传递父任务身份并核对回传关联。

框架的 run ID、图的 thread ID 和业务动作 ID 用途不同：一次业务任务可能多次恢复，一次动作可能经历多次请求尝试。用一个 ID 覆盖所有层，会无法区分重试与重复业务动作。

### 3. 将“正在发布”与“已发布”分别建模 {/* #3-将正在发布与已发布分别建模 */}

文档发布节点可以通过 `custom` 事件报告“正在校验”，但只有业务服务返回结果并完成独立读取后，才记录发布确认。UI 事件丢失时，用户应能重新查询任务状态和产物；不能因为连接断开就把写操作当成未发生。

普通流事件和诊断回调没有替业务提供持久审计事务。动作登记、批准记录和费用账本仍需可靠存储；状态增量到达客户端也不代表检查点已经满足当前部署的持久化要求。

接入验收可在子任务执行和主流断连时检查三件事：是否能从父任务追到子任务；重新连接后能否查到终态；每次真实写入是否都能对应授权、尝试记录和产物。流式封装与恢复机制见[LangGraph 流式系统](../../../application-notes/engineering/langchain-series/langgraph/09-stream-system.md)和[Deep Agents 流式输出](../../../application-notes/engineering/langchain-series/deepagents/18-streaming-output.md)。两篇的依赖基线不同，使用时按各自版本核对，不混用返回结构。

## 八、将事故证据交给能修复它的人 {/* #将事故证据交给能修复它的人 */}

一次异常应整理成可复核的问题记录：任务与版本、触发输入、首次偏离预期的事件、已产生的副作用、缺少的证据，以及建议修改的组件。模型可以辅助归类，最终归因仍要回到请求、状态变化和外部事实。

修复后将事故转成[回归用例](./agent-evaluation.md)，在同样故障条件下检查原问题是否被阻断，再用真实模型样本检查正常任务是否受损。经验适合长期复用时，可以进入 [Skill 候选更新](../03-view/agent-skill-design.md)；不应直接把一次异常摘要写成所有任务永久遵循的规则。

验收观测链时，选择一次包含子任务、重试和中断的隔离运行：应能找到每次调用的输入版本，分清提案与实际执行，解释费用归属，并定位恢复从哪个状态继续。缺失的记录也要可见，否则一条看似完整的轨迹可能只是没有记录失败分支。

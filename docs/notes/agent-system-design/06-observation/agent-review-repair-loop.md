# Agent 评审与自愈：绑定版本、独立验收、有界修复

Agent 生成结果以后，需要对照可复核的标准发现偏差。有效反馈应说明检查了哪个版本、依据什么事实、发现什么问题，以及这个问题会怎样改变后续执行。只让模型再看一遍，无法保证它取得了新的信息。

评审主要裁决一份产物是否满足要求，自愈则进一步改变代码、配置或运行状态，并验证改变是否修复问题。两者可以组合，但持续时间、权限和失败出口需要分别设计。

## 一、把生成、举证和裁决分开

生成者和修订者提出候选内容，评审者报告问题与证据，策略闸门或授权裁决者决定退回、通过、补证或升级。生成者不能靠修改自己的状态字段获得通过；评审者的自然语言“建议通过”也不能绕过发布入口。

一条可处理的意见应包含被审对象、问题位置、违反的规则、严重程度、证据及检查器身份。无法复核的意见仍可保留，但应与已经证实的问题分开。

发现偏差不要求先知道完整根因。例如报表中的已处理数量与业务快照不一致，已经足以阻止发布。数据延迟、状态映射或汇总错误需要继续调查，不能为了写完整评语而编一个原因。

证据不足的意见也不能简单删掉后自动放行。若它涉及必需风险且对应检查尚未完成，当前状态应为待补证或待审；只有必需检查齐全，才有资格按策略判断通过。

## 二、评审回执只属于被检查的那个版本

评审 v1 后生成 v2，v2 的状态应为未评审。它可能修好了旧问题，也可能引入新问题。最终交付必须绑定最终版本自己的检查结果。

| 回执信息 | 作用 |
| --- | --- |
| 工件身份、版本和内容摘要 | 明确实际检查的对象 |
| 来源与依赖快照 | 说明判断基于哪版事实 |
| 检查器与策略版本 | 说明使用哪套尺度 |
| 检查覆盖、问题与证据 | 区分检查通过、未检查和阻断 |
| 裁决、时间与适用条件 | 支持放行时重新校验 |

发布入口核对当前工件是否匹配回执，阻断项是否解决，必需检查是否覆盖，证据是否仍适用。正文或依赖变化后，由失效规则决定重查范围，不能直接沿用整份旧回执。

对抗评审进一步强调职责独立：专门的评审者主动寻找足以阻止当前版本的失败条件，异议进入实际状态转换。若评审意见只显示在界面上，而发布函数不检查，它还没有产生控制作用。

## 三、独立性要落实到事实和覆盖面

换模型可以增加判断视角，但多个模型都只读同一份错误摘要，仍可能共享盲区。评审者应能访问原始资料、权威业务快照、实际差异或独立测试结果。干净的上下文帮助减少先入结论，独立事实帮助检验结论。

先列风险，再指定检查器：

| 失败面 | 检查方法 | 放行条件 |
| --- | --- | --- |
| 数量或金额汇总错误 | 独立查询与确定性计算 | 口径一致且结果相符 |
| 总量正确但对象错配 | 按主键逐项比较 | 对象、值与来源关系成立 |
| 引用失效或超出证据 | 打开对应材料并核对范围 | 结论有适用证据 |
| 修改超出任务范围 | 检查实际差异与允许集合 | 无越界变更 |
| 表达含糊或遗漏解释 | 量表、模型辅助与人工抽查 | 达到当前内容要求 |

检查器本身也可能有错。评测集、业务规则和模型评分需要定期校准，保留人工改判与漏检案例。单看通过率会奖励宽松检查；单看退回率也可能把误拦当成严格。

## 四、自愈循环围绕明确失败建立

### 1、固定目标、基线和故障身份

修复开始前保存任务目标、验收条件、代码或配置基线、允许修改范围、原始失败证据和预算。修复器只能在这个范围内提出补丁，不能为追求绿灯自行降低验收标准。

给故障建立稳定身份，例如错误码、业务对象、验证器版本和证据位置。同一个错误只因时间戳变化而被当成新故障，会导致循环不断重开；归一化过度，又可能把不同原因合并。身份设计需要保留能区分故障的关键条件。

### 2、跟踪补丁与新增信息

补丁指纹可绑定修改内容、基线与依赖变化。相同故障、相同补丁、相同环境再次出现时，检查本轮是否取得了新信息。若没有，就不应机械重复已经失败的尝试。

修复前校验变更范围，应用后运行原验收及受影响的必要检查。修改实现与修改验收规则属于不同决定；需求确实变化时，应明确更新任务与标准，保留依据，不能把降低标准藏在修复里。

### 3、设置成功、停止与升级出口

当原始问题解决、业务约束仍成立且相关检查通过，可以结束修复。出现以下情况应停止自动推进：预算耗尽、重复无进展、影响范围扩大、原基线不再适用，或者下一步涉及尚未授权的效果。

修复退出时交付已尝试的补丁、每轮结果、当前现场、未决风险和可继续调查的入口。失败现场保留清楚，比留下一个无法解释的“修复失败”更有利于接手。

## 五、回滚后要重新核对现实状态

回滚命令执行成功，只能证明恢复操作返回。代码恢复需要检查文件、版本与依赖；部署恢复需要核对实际运行制品；业务恢复则可能需要外部回执、补偿或人工确认。

| 修改对象 | 可采用的恢复方式 | 仍需核实 |
| --- | --- | --- |
| 隔离工作区内的代码 | 撤回本次补丁或恢复指定基线 | 文件内容、测试结果和用户已有改动 |
| 配置与部署制品 | 切回已知版本 | 运行实例、兼容性与健康状态 |
| 已写入的业务状态 | 受控修正或补偿事务 | 外部终态、幂等与未结清影响 |
| 已外发的通知 | 纠正、说明或其他业务处置 | 原消息仍可能被接收，无法假设撤销 |

恢复操作自身失败时，应停止依赖它的新动作，保留现场并升级处理。不能在记录里标成“已回滚”，让后续任务基于不存在的基线继续执行。

## 六、将反馈送到合适的改进对象

同一份失败证据可能导致不同改变：修正当前稿件、更新一个技能候选、保存一条经验，或修改实现。应先确定改变对象，再选择验证与发布路径。

当前稿件走版本评审；跨任务做法走 [Skill 候选验证](../03-view/agent-skill-design.md)；尚未确定有效性的教训进入[经验回放](../02-state/agent-progress-and-failure-records.md)；代码与配置修改走有界修复。一次成功不能自动授予长期调用资格或更宽权限。

可以用四项故障检验反馈机制：评审后修改产物、遗漏关键检查器、重复提交失败补丁、恢复命令成功但现场未恢复。应分别得到复审、待补证、无进展停止和恢复失败状态。结果观察包含错误放行、误拦、未评审版本外流、修复成功与恢复失败，并保留对应样本。

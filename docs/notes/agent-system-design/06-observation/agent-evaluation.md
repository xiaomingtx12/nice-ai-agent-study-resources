# Agent 评测

> **模块本质：** 用独立、可重复的判据检查 Agent 是否完成任务、遵守执行边界并合理消耗资源，再通过可比较的实验判断策略变更是否有效、失败发生在哪里。

最终回复相同，两次运行也可能有完全不同的质量：一次先核对资源再修改，另一次跳过检查但碰巧改对。只比较答案，会漏掉执行中的越权、重复副作用和恢复错误。

可以用“生成并保存一份报告”说明验收范围。文件存在、引用可追溯、写入目录正确、用户取消后没有继续发布，分别需要不同证据。模型说“已经完成”只能作为待核验的输出。

## 一、将运行时测试与模型效果评估分开 {/* #将运行时测试与模型效果评估分开 */}

先确定被测对象，再决定是否调用真实模型。

| 被测对象 | 控制哪些输入 | 主要判断 |
| --- | --- | --- |
| 运行时控制逻辑 | 固定模型响应、工具响应和故障时点 | 校验、路由、重试、取消、恢复是否按规则执行 |
| 模型与策略效果 | 固定任务、工具版本和环境，调用真实模型 | 能否选择正确动作、完成任务、控制成本 |
| 完整交付链 | 在隔离环境接入必要的真实依赖 | 凭据、资源、状态与最终产物能否共同满足要求 |

固定响应测试可以稳定构造“模型请求不存在的工具”“审批拒绝后仍然请求执行”等情况。它验证系统能否挡住给定错误，不能证明真实模型犯错的频率。真实模型评测衡量效果分布，也不能替代确定性的授权和状态机测试。

只读问答可以从答案、引用和拒答评测起步。包含写操作、长任务或多 Agent 时，再加入副作用、恢复和任务树的检查，不必一开始搭建完整平台。

## 二、一条用例需要输入现场和独立判据 {/* #一条用例需要输入现场和独立判据 */}

用例不能只有用户问题与参考答案。它至少需要说明运行从什么状态开始、怎样才算完成，以及哪些行为不能发生。

| 内容 | 建议保留的信息 | 缺少时的后果 |
| --- | --- | --- |
| 输入现场 | 任务、初始状态、必要历史、允许访问的资源 | 同一道题实际运行条件不同 |
| 环境版本 | 模型配置、提示词、工具定义、策略与数据快照 | 无法区分代码变化与环境变化 |
| 判定依据 | 业务终态、必要前置检查、允许的副作用范围 | 只剩文本相似度或模型主观评分 |
| 故障条件 | 超时、重复投递、取消、状态变化发生在哪一步 | 无法稳定覆盖危险分支 |
| 样本来源 | 来源记录、审核状态、适用业务版本 | 错误轨迹被当成标准答案 |

生产轨迹是“发生过什么”的证据，必须经过审核才能成为“应该怎样做”的判据。一次错误发布应保存为失败输入和禁止条件，不能把当时的工具顺序直接设成期望路径。

数据集、判定规则和评测器分别版本化。业务规则改变后，先标记受影响用例待复审，再决定更新或归档；不要为了让新版通过而静默改掉旧答案。用于生成策略的案例与最终检验策略的保留集也应分开，避免只测到对已见题目的适应。

## 三、用固定模型响应覆盖危险分支 {/* #用固定模型响应覆盖危险分支 */}

Fake Model（固定响应的模型替身）按预设顺序返回模型消息，让测试聚焦运行时对消息的处理。工具也需要受控替身，避免测试真的发送消息、修改线上数据或启动付费任务。

| 构造的输入或故障 | 应检查的运行时行为 |
| --- | --- |
| 模型请求未注册工具 | 执行器没有被调用，错误返回后续决策 |
| JSON 合法，但资源属于另一租户 | 业务校验拒绝，受影响记录数为零 |
| 同一动作被重复投递 | 沿用业务动作身份，不重复产生效果 |
| 外部操作已提交，响应丢失 | 保持结果未知，进入查询或对账 |
| 审批后参数改变 | 旧审批不能用于新动作 |
| 用户取消时子任务仍在运行 | 停止派发，跟踪子任务取消与剩余副作用 |
| 重启后继续执行 | 已用预算、重试计数和待处理动作仍然有效 |

断言应检查外部记录、执行器调用次数和状态转移，不能只检查返回文本是否含有“拒绝”或“成功”。故障注入也要区分执行前失败和提交后丢响应，两者允许的恢复动作不同。

## 四、事故回放需要匹配请求，不能只顺序发答案 {/* #事故回放需要匹配请求不能只顺序发答案 */}

回放应保存事故当时的模型请求与响应、工具请求与结果、状态版本，以及必要的时钟和外部数据。缺失原始现场时，重新调用模型得到的是新样本；即使问题相同，也不能标为精确复现。

回放客户端每次发出录制响应前，都要检查当前请求与记录是否兼容，包括工具名、关键参数、轮次关联和协议版本。新版多了一次调用，却继续拿旧记录的下一项作为答案，会制造虚假的通过结果。遇到不匹配应停止回放并报告差异。

两种回放用途需要分开：

- **复现控制逻辑**：使用原始模型响应和工具结果，检查修复后的运行时能否阻断原故障。
- **比较新策略**：允许模型重新决策，在相同的隔离环境中执行，再检查同一组业务判据。

固定旧响应无法评估新提示词是否更好；重新采样也无法保证走到同一个罕见故障。两类测试各自保存结果，不合并成一个含义模糊的通过率。

## 五、轨迹约束与业务终态一起验收 {/* #轨迹约束与业务终态一起验收 */}

轨迹是模型提案、授权、执行、结果和状态变化组成的运行记录。记录时必须区分“请求了危险动作”和“危险动作实际执行”：前者被成功拦截，恰好可能是安全测试通过的证据。

以报告任务为例，可以检查这些条件：

| 约束 | 应检查的证据 |
| --- | --- |
| 写入前确认目标工作区 | 授权事件先于该动作的执行事件，且绑定同一资源 |
| 只修改约定产物 | 实际变更清单落在允许范围，不能只靠工具名黑名单 |
| 引用来自已读取材料 | 引用与来源版本可对应，必要时校验支持关系 |
| 完成后文件可读取 | 文件系统或对象存储的独立读取结果 |
| 重试不会重复发布 | 业务动作身份与外部发布记录对应 |

只有协议要求唯一顺序时才使用精确轨迹匹配。通常应检查必要步骤之间的先后关系、参数范围和终态；互不依赖的资料读取可以换序，多一次合理的验证也不应自动判错。并行任务的先后关系以依赖和事件关联为准，不能只把不同机器的时间戳排成一条线。

硬边界失败单独判定。表达质量再高，也不能抵消越权写入；同时，“没有越权”也不代表任务完成。

## 六、让模型裁判只承担适合它的判断 {/* #让模型裁判只承担适合它的判断 */}

能用程序验证的文件、实体归属、金额范围、版本和执行顺序，优先用程序验证。模型裁判适合判断说明是否清楚、回答是否覆盖问题、引用是否支持结论等语义质量，并接受人工抽检校准。

裁判输入应包括任务、约束、可见证据、实际结果和评分标准。要求它给出可核对的理由与证据位置，证据不足时输出“不确定”。不要要求提供不可获得的模型内部思考过程，也不要把模型自报的置信度直接当作正确概率。

更换裁判模型可以作为偏差检查，但不能替代校准。可以用人工标注样本检查一致性，交换候选答案顺序检查位置偏差，并单独复核裁判与程序判据冲突的样本。裁判失败、超时或无法读取证据时，记录评测异常，不能默认给满分。

## 七、比较版本时保留逐题差异 {/* #比较版本时保留逐题差异 */}

基线与候选应使用相同的数据集、外部环境和判定规则。逐题记录“都通过、都失败、新增失败、修复成功”，再按任务类型和风险分组。整体均分上涨时，仍要能看见高风险组是否退化。

真实模型存在运行波动。对关键样本重复运行，记录次数、通过比例和不确定范围；不要把同一任务的多次运行当成完全不同的业务覆盖。比较方法需要匹配实验设计，同题配对结果、独立样本和长尾延迟不能套用同一个检验。样本不足时报告证据不足，不用“不显著”宣称两版等效。

发布标准应预先定义业务允许的退化幅度。安全违规、完成率、成功任务成本与尾延迟分别设置条件，统计结果只帮助判断变化是否可信。严重事故用例失败可以直接阻断，无需等待总分或统计显著性。

## 八、发布门禁必须读取实际评测结果 {/* #发布门禁必须读取实际评测结果 */}

评测程序成功退出，可能只代表报告生成成功。需要检查报告是否存在、是否对应当前版本、实际运行数是否符合预期，以及阻断项是否通过。零用例、全部跳过和报告缺失都不能被当成通过。

一个具体例子来自 Deep Agents 声明版本 0.6.12 的源码快照，评测包为 `deepagents-evals` 0.0.1；commit 未锁定，版本边界见[源码版本与路径约定](../../../application-notes/engineering/langchain-series/deepagents/source-baseline.md)。`pytest_sessionfinish` 是测试会话结束时执行的 hook，这里的实现为后续汇总保留了继续运行的机会。

源码：`libs/evals/tests/evals/pytest_reporter.py` → `pytest_sessionfinish()`（第 342–354 行；后续报告逻辑省略，原注释翻译如下）。

```python
def pytest_sessionfinish(session: pytest.Session, exitstatus: int) -> None:
    _ = exitstatus
    # 单独的测试失败不应阻断 CI 步骤，评测退化时也需要继续汇总和报告。
    # 没有测试运行时保留非零退出码，以暴露配置错误或收集前崩溃。
    # total 仅在 call 阶段增加；只有 setup 阶段的跳过也算没有运行测试。
    # 中断、内部错误、用法错误、未收集到测试等非 1 退出码不会被改写。
    if session.exitstatus == 1 and _RESULTS["total"] > 0:
        session.exitstatus = 0
```

这段代码直接证明特定条件下退出码会被改写，不证明整个项目缺少发布检查。接入这类报告器时，调用方应增加读取报告的独立门禁；不能只照搬运行命令，再把进程退出码当作质量结论。

影子验证让候选策略在真实输入上产生提案，但不执行真实写操作。需要验证写后状态时，使用隔离环境或受控模拟；同一请求同时交给两个版本真实执行，会引入重复副作用。

## 九、围绕框架扩展点组织业务评测 {/* #框架接入后的评测方法 */}

### 1. 配置测试、执行测试与模型评测分开维护 {/* #1-配置测试执行测试与模型评测分开维护 */}

修改中间件、工具、检索器或子代理配置后，先确定这次改动需要证明什么。框架能正常创建实例，只能证明部分装配条件成立，不能证明业务策略已经生效。

| 改动 | 可控测试重点 | 真实模型评测重点 |
| --- | --- | --- |
| 动态上下文或工具筛选 | 捕获模型请求，检查可见字段与执行拒绝 | 是否减少错误选择、是否遗漏必要能力 |
| 摘要或记忆策略 | 检查状态更新、来源和范围过滤 | 压缩后是否仍遵守约束、是否使用过期事实 |
| 工具重试或审批 | 注入超时、拒绝、重复恢复，检查实际副作用 | 能否根据失败类型修正或合理停止 |
| 子代理协作 | 固定交接数据，检查汇合和失败传播 | 拆分是否有效、结果是否重复或缺项 |

LangChain 的 `GenericFakeChatModel` 是按给定消息序列返回结果的测试模型，可用来稳定复现指定工具提案。它适合验证执行控制，不能证明真实模型会在自然输入下作出相同选择。Deep Agents 的测试也使用了本地辅助实现，复制用例前需核对导入路径，不能把测试辅助类当成 SDK 的公开接口。

### 2. 让断言越过模型回复，检查真实状态 {/* #2-让断言越过模型回复检查真实状态 */}

文档发布的控制测试可固定一次发布提案，再让服务模拟“写入成功但响应超时”。恢复后检查实际发布记录只有一条、页面版本正确、任务终态能解释是否已对账。另一个用例固定越权提案，检查权限门拒绝且页面没有变化。固定模型只控制提案，发布服务与存储仍需可检查的执行记录。

源码中的具体范例包括 Deep Agents 0.6.12 快照的 `tests/unit_tests/test_permissions.py`：它不只匹配错误文本，还读取文件状态证明拒绝没有产生部分删除。LangChain 1.3.7 的 `tests/unit_tests/agents/middleware/implementations/test_human_in_the_loop.py` 则检查编辑决定如何修改动作并保留工具调用 ID。这两类断言可以分别对应业务后置条件和协议连续性。

### 3. 将真实模型结果接入独立发布门禁 {/* #3-将真实模型结果接入独立发布门禁 */}

真实模型评测记录模型、框架、提示词、Skill、工具 schema、数据集和环境版本；将一次运行的轨迹与产物交给程序判据和语义评分器。模型评测关注能否完成任务，可控测试关注约束是否必然生效，两类失败分别展示。

采用 Deep Agents Evals 报告链时，独立读取报告中的通过数、失败数、运行错误与证据，而不只检查进程退出码。必需用例未运行、结果缺失或硬边界失败时，应阻止候选发布；评分提高不能抵消这些失败。报告字段与运行行为要跟随评测包版本一起核对。

已有实现入口见[Deep Agents Evals](../../../application-notes/engineering/langchain-series/deepagents/16-deepagents-evals.md)与[故障路径验证](../../../application-notes/engineering/langchain-series/deepagents/21-production-failure-validation.md)。这些实现提供测试和报告机制，业务仍需维护自己的任务样本、通过标准与发布门禁。

## 十、从小规模用例集开始维护 {/* #从小规模用例集开始维护 */}

初期挑选有明确业务终态的正常任务，再补缺参数、权限拒绝、未知结果、取消、恢复和部分成功。每个已修复事故至少保留一个能触发原故障的回归用例，并标明它验证到哪一层。

评测结果应回到具体修改位置：错误输入路由归 Task，旧事实与恢复错误归 State，证据遗漏归 View，循环与重排归 Decision，越权或重复执行归 Action，结果丢失与误报归 Observation。归因需要事件证据支持，不能只让模型选择一个标签。

[证据与反馈](./agent-observability.md)负责保存可回放现场；[权限与后置条件](../05-action/agent-permission-and-postconditions.md)定义运行时边界。本篇的用例和门禁用于验证这些边界是否按预期工作。

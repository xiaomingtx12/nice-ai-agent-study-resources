# Agent 评测题从哪里来：共享规格、单题规格与运行校准

> 来源：LangChain 的 [How We Build Agent Environments & Tasks](https://www.langchain.com/blog/building-agent-environments-and-tasks)，发布于 2026 年 8 月 25 日。本文依据公开文章，未取得其内部题库、生产轨迹或任务环境。

Agent 评测既要有代表性问题，也要有可运行的现场和独立评分。LangChain 文章讨论的是这些题目怎样被生产出来。

团队用真实轨迹、代码和人的判断写规格，再把规格变成可运行的任务。它为本站已有的[Agent 评测](./agent-evaluation.md)补上了“用例从哪里来”的过程。

## 一、原文为什么要把评测题拆成规格和环境

LangChain 想持续改进 Agent，需要一组能反复运行的任务，才能发现回归、比较提示词或工具的改动。原文中的一条任务由用户输入、Agent 工作的环境和评分脚本组成。

以 GTM 研究为例，只问“研究这家公司”，却不准备可访问的数据、缺失记录和成功判据，就无法检验 Agent 是否真的找对了公司及联系人。

原文还列出提示词优化、根据已合并 PR 进行代码审查，以及从大量轨迹中找少数异常等内部任务。它们需要的输入、环境和评分方式各不相同，不能只靠一套“问题—标准答案”模板。

一条代表性任务要接近真实用户请求，环境要接近 Agent 实际能碰到的系统，评分标准还要与业务目标对齐。造一条这样的题已经耗费人工判断；扩成题库更难。文章因此把“确定题目是什么”和“实现可运行题目”分开。

## 二、做第一道题时，逐步形成共享规格

### 1、World Spec 保存多道题共用的造题知识

World Spec（共享环境规格）保存一组任务共同需要的项目知识、脚本、辅助函数和重要定义。它不局限于实体关系表，也可能包含解析轨迹的脚本、生成测试数据的方法、统一评分函数，以及需要模拟的外部 API 和数据结构。

只有这道题才成立的客户、初始状态和评分条件，应留给单题规格。两种规格的区别在于知识是否能被同一题库里的其他题目复用。

原文用两组内部题库解释共享知识的差别：

| 题库 | World Spec 可复用的内容 |
| --- | --- |
| 提示词优化 | 每道题先收集哪些领域、输入和输出信息；如何生成数据；共用的评分函数 |
| GTM Agent | 需要模拟的 Salesforce、Notion 等服务的 API 与数据结构；从历史轨迹归纳的常见请求 |

有了这些材料，第二道、第三道题不必重新发现同一套系统约束。

LangChain 建议先与 Coding Agent 合作做第一道题，再把过程中弄清的通用知识反写成 World Spec；第二、第三道题继续检验它是否遗漏关键条件。

为完成首题，Agent 会查看仓库里的提示词、工具和 Skill，聚合轨迹中的用户请求，列出所需凭证、外部服务及数据关系。遇到在线搜索等真实 API，还要决定评测时调用服务还是模拟行为。人根据真实业务继续纠正这些材料。

### 2、Task Spec 让人先审题，再实现题目

Task Spec（单题规格）是描述具体任务的 Markdown 文件，通常交代三个问题：

- Agent 将进入怎样的环境？
- 它会收到什么输入？
- 输出或环境终态怎样评分？

若某项内容对整组题完全相同，可放在 World Spec，而不在每题重复。例如，普通问答题可能共用环境；GTM 研究任务则可能输入形式相同，环境数据和评分条件随题变化。

这种分层让领域人员在审阅代码和假数据之前，就能检查题目是否代表真实工作、成功条件是否合理。规格可以像代码一样审阅、版本化和修改。经过人工对齐后，多份单题规格再并行转成任务，减少“模型造完题才发现目标不对”的返工。

## 三、Spec2Task 怎样把文字变成可运行评测

Spec2Task 是“从规格生成任务”的步骤：Coding Agent 读取 Task Spec、项目专属的 World Spec 和通用 eval-engineering Skill，把输入、环境及评分器实现成 Harbor 格式的任务。Harbor 是定义和运行 Agent 任务集的评测框架。

博客描述了这一工作流，没有公开这些内部题目的完整代码与数据。

任务生成后还要运行真实 Agent 并看轨迹。原文举了一个坏环境的细节：表里竟有“Answer placeholder”这样的占位值，可能向 Agent 泄露题意或引出取巧路径。

运行不同能力档次的模型，可以检查任务是过易、过难，还是让更强模型发现了评分漏洞。轨迹还可能暴露工具缺失、说明过于具体等环境问题。

造假数据也要匹配类型。原文建议，自由文本可以让模型生成并用标准审查；结构化表格则用明确 schema 和脚本生成，例如 SQLite 数据。让造题 Agent 不分数据类型自行选择方法，容易产生看似丰富、实际不合业务的记录。

文章给出的完整路径有明确先后：

1. 从轨迹与仓库做第一题，形成初版 World Spec，并由人审阅。
2. 用第二、第三道题检验这份共享规格，按新发现继续修改。
3. 从近期轨迹生成多份 Task Spec，交人审核任务是否真实、判据是否合理。
4. 把审核过的单题规格批量转为可运行任务，再根据执行轨迹排除坏题。

这不是一次性由模型生成整套题库。

## 四、原文交代的人工边界与结果边界

LangChain 说，人仍需判断规格是否符合真实领域、用户行为和任务要求。Agent 自行造的题常常过简单。让一道题成功运行，只说明环境基本可用，不说明它足以区分 Agent 能力。

难度还要通过多次运行、阅读轨迹和人工反馈校准。题库用于提示词优化、Harness 调整或后训练后，也要检查任务是否仍代表当前用户工作。

原文报告的是团队迭代出的造题方法，未给出该方法生成了多少经过审阅的任务、评测构造耗时下降多少，或新题库与生产表现的一致性数据。用户请求与模型能力变化后，环境也需要持续更新。

## 五、本站判断：把“发生过”与“应该怎样做”分开

本站[Agent 评测](./agent-evaluation.md)说明了用例的输入现场、环境版本和独立判据。LangChain 文章提供了生产这些材料的具体流程。站内[Deep Agents Evals 源码解析](../../../application-notes/engineering/langchain-series/deepagents/16-deepagents-evals.md)讨论任务定义之后，怎样运行、记录轨迹和汇总分数。

可借鉴的是“首题校准共享知识，再批量造题”。例如，用一次真实的商机研究任务，核对客户记录缺字段时 Agent 能访问什么、联系人如何验证、什么结果算可用。把 Salesforce schema 和通用验证方法放入共享规格，再让下一道题检验这份规格。

历史轨迹只能告诉团队用户问过什么，不能自动成为标准操作路径。错误轨迹更适合保留为失败现场和禁止条件。

把造题和评分都交给同一套未经校准的模型，可能让它奖励自己的捷径。字段归属、数据修改和权限边界应由可运行环境的真实状态检查；解释质量才适合经人工校准的语义评分。

题库扩充后，还应保留未参与策略调整的题目，检查 Agent 是否只适应了已经看过的样本。外部系统持续变化时，数据快照、工具、凭证和评分规则也需随版本保存。

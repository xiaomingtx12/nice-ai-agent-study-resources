# RAG 评测篇

评测这一刀切的目的是回答"我上的这个 RAG 是不是真的能上"。**用户没投诉不等于检索质量高**——投诉率低可能是用户懒得反馈，也可能是问题被错误答案"看上去合理"地糊弄过去了。

读这篇之前你应该已经读过 [RAG 工程篇](./rag-engineering.md)（知道切分 / 检索 / 重排怎么搭）和 [可观测性（横切）](./index.md#可观测性--横切)（知道运行时怎么埋点）。本篇聚焦"判对错"那一段——离线评估集的搭建、指标的选取、排查顺序、上线后监控。

## 一、动机

RAG 工程化最容易踩的坑不是搭不起来，而是**搭起来之后不知道怎么判断它好不好**。RAG 的失败模式有两层：检索层（喂错料）、生成层（喂对料但答歪）。两层都得有指标照着，没有指标等于盲调。

评测的产出反过来调上游：检索段 Recall 低 → 回去调切分 / embedding；Faithfulness 低 → 回去调 Prompt 硬约束。所以评测节点有**回流箭头**，不是单方向的"上线前体检"。

## 二、关键判断速览

- **最小评估集 30 条起步**：从真实用户 query 中抽（脱敏），覆盖简单问法 / 复杂问法 / 边缘 case / 错误 query；不要用 LLM 生成的合成 query，分布偏理想
- **Ground truth 标到 chunk 级**：不只标参考答案，还要标出支撑它的 `chunk_id`，检索段和生成段评估才有共同地基
- **四项核心指标**：Context Precision / Context Recall / Faithfulness / Answer Relevancy
- **排查铁律**：先看检索段 Recall，再排查生成；顺序反了白折腾
- **五个维度一个不能漏**：准确 / 可信 / 速度 / 扩展 / 体验；只盯准确率不看 P95/P99 必翻车
- **别用"用户没投诉"当评估**：投诉率低不等于检索质量高

## 三、离线评估集怎么搭

### 从哪里抽 query

- **首选真实用户 query**（脱敏），分布最贴近真实使用
- 公开基准（HotpotQA / TriviaQA / NQ）可参考但**不能当裁判**——自家业务的评估集才是
- 让 LLM 出题、人工筛的混合做法：自动出的题偏"阅读理解"味，要筛掉"答案太明显 / 不像真用户问法"的样本

### 标注到 chunk 级

每道题标注两样：

- **参考答案**：理想输出长什么样
- **支撑 chunk_id**：答案涉及的所有 chunk（用切分阶段的 `section_path` 元数据反查）

chunk 级 ground truth 的价值是**双重评估**：

- 检索段评估：候选池里有没有这些 chunk → Context Recall
- 生成段评估：答案内容能不能溯源到这些 chunk → Faithfulness

### 难度分层

评估集要覆盖三种难度，按比例分配：

- **事实题**（占比 40-50%）：单段就能答上
- **多跳题**（占比 30-40%）：跨 2-3 段整合才能答
- **边缘 case + 错误 query**（占比 10-20%）：超纲 / 拼写错 / 指代不清

### 自动评估工具

RAGAS 用 LLM 给 Faithfulness / Answer Relevancy 打分，能省人工标注初筛。**但 LLM 打分只能做初筛，最终裁判还得是人工标注的 30-50 条**——LLM 打分和真实用户满意度相关性不总是 1。

## 四、四项核心指标

| 指标 | 度量对象 | 计算方式 | 何时重点盯 |
|---|---|---|---|
| **Context Precision** | 检索精度 | top-K 中相关段占比 | 喂的料太多太杂，模型分心 |
| **Context Recall** | 检索召回率 | 标准答案涉及的段被召回的比例 | 召回不足、漏料 |
| **Faithfulness** | 答案忠实度 | 答案中有多少能被引用段落支撑 | 模型"看了料还瞎编" |
| **Answer Relevancy** | 答案相关性 | 答案是否回答了用户问题（与 query 语义相似度） | 模型答非所问 |

四项指标不能只看一项：Recall 高但 Faithfulness 低 = 喂对料了但模型瞎编；Precision 高但 Recall 低 = 喂得太精但漏了真料。

## 五、上线的五个维度（不只是"准"）

只盯准确率就上线必翻车——够准但 P99 5 秒、一上量就崩、或答得对但用户看不懂，一样不能用。

| 维度 | 关键指标 | 监控方式 |
|---|---|---|
| **准确** | Recall@k / MRR | 离线评估集 |
| **可信** | 证据覆盖率（Faithfulness） | 离线 + 在线抽样人工评 |
| **速度** | P95 / P99 延迟 | 在线监控，**别只盯平均延迟** |
| **扩展** | QPS / 并发承载 | 压测 |
| **体验** | 人工满意度 / 跳出率 | 用户反馈 + 行为埋点 |

平均 0.2s 但 P99 5s，那批用户就是崩的——P95 / P99 尾延迟比平均值重要得多。

## 六、排查铁律：先看检索段 Recall

| 现象 | 真问题在哪 |
|---|---|
| 检索段 Recall 低 | 切分 / embedding / 检索配置（召回率是天花板） |
| 检索段 Recall 高，答案还差 | Prompt / 模型的生成问题（喂对料但答歪） |

**顺序反了白折腾**——召回不足时去调 Prompt，调一年也调不出标准答案。

---

## 七、线上优化顺序

按这个顺序省力：

1. **缓存先行**：FAQ 类问题答案缓存直接零延迟
2. ANN 调参（HNSW efSearch / IVF nprobe）
3. 提并发（连接池 / 批量推理）
4. 流式输出改善体感（用户感知延迟下降）

持续监控可以用 `DocumentSegment.hit_count` 作为"热门问题"代理指标，索引侧靠 `DocumentSegment.status` 做读时过滤。

---

## 八、反模式

- 用"用户没投诉"当评估：投诉率低不等于检索质量高
- 用 LLM 生成的合成 query 评测：分布偏理想，真实 query 噪声多
- 只看平均延迟不看 P95 / P99：尾部用户实际在崩
- 检索段 Recall 没查就去调 Prompt：方向反了白折腾
- 不上线前评估直接上生产：没有 4 项指标的最小评估集是赌博
- Ground truth 只标到答案级不标到 chunk：检索段和生成段评估没法做共同地基
- LLM 自动打分当最终裁判：初筛可以，裁判不行

---

## 九、何时不该用 RAG 评测

- **知识 < 50 段且静态**：直接 Prompt 直塞，连 RAG 都不上，更不需要 RAG 评测
- **MVP 早期**：评估集搭建是重投入，业务没稳之前先把功能跑通
- **没有 ground truth 标注能力**：评估集不可信，比没有评估更误导——这时候不如先做可观测性 + 用户反馈闭环

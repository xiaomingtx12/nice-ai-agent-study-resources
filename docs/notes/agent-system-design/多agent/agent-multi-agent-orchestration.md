# 多 Agent 编排篇

读这篇之前你应该已经掌握 Agent 大脑（详见 [Agent 大脑篇](./agent-brain.md)）——本篇聚焦什么时候该拆、怎么拆、怎么协作、失败怎么处理。

正文按两个观察面展开：

- **编排机制侧**——运行时怎么执行：Fork-Join 模型、上下文继承策略、物理隔离 vs Prompt 警告、并发模型、Handoff 层次、失败处理、Token 预算。这一面是 Agent 视角。
- **编排图编写与维护侧**——作者怎么画图：图类型选型（DAG/Swarm/Hybrid）、状态外部化、节点配置、可观测性、可重放性、图的迭代。这一面是图作者视角。

这两面是同一张图在不同时刻被两个角色同时看到的——运行时关心"它怎么协作"，作者关心"它怎么定义"。两面约束叠加生效，单面看不全。

贯穿全文的内在张力正交于这两面：**并行收益 ↔ 协调开销**。拆任务获得 wall-clock 节省，但引入路由、Handoff、状态外部化、失败传播的工程问题。CLAUDE.md 是"完全不拆"那一极端、单 Agent 串行是"拆到最小"那一极端，多 Agent 是这条权衡曲线上的工程化折中点。本篇解释这条曲线怎么被工程化出来。

## 一、动机

多 Agent 编排处在单 Agent 与业务系统之间——它把这两种形态合成一种复合工程层：

- **控制流借用单 Agent**——每个子 Agent 就是一个普通的循环层实例，仍按"决定调不调 → 调什么 → 收什么"的循环跑
- **失败处理借用业务系统**——失败跨子图传播、根因定位、告警 / 重试 / 降级这些语义，是借业务系统的事务经验
- **拓扑调度独立**——这是多 Agent 独有的设计：DAG / Swarm / Hybrid 三种范式让作者在不画图也能让多个循环协作

这三条合起来才是多 Agent 真正的工程身份——**不是"几个 Agent 加起来"那么简单，也不是"业务流程引擎套个 LLM"那么包装**。类比：Kubernetes 仍然跑的是容器（每个 Pod 就是单 Agent），但调度 / 容灾 / 拓扑这些工程化封装让它成为独立的工程层。多 Agent 同理——"编排层"指的是它夹在单 Agent 与业务系统之间，不是等级居中。

工程化的核心拉扯：**并行收益 ↔ 协调开销**。拆任务获得 wall-clock 节省，但引入路由、Handoff、状态外部化、失败传播的工程问题。协调开销 > 并行收益时，拆比不拆更糟。

### 多 Agent vs 单 Agent + 工具

多 Agent **不是**"单 Agent 加上一堆工具"。单 Agent 是循环层一个实例，靠工具改变环境；多 Agent 是循环层多个实例，靠 Handoff 改变"谁在循环"。区别见：Tool 篇 §三 注册与执行层 与 本篇 §三 编排机制侧。

| 维度 | 单 Agent + 工具 | 多 Agent 编排 |
|---|---|---|
| 形态 | 一个循环 + N 个工具 | N 个循环 + Handoff 协议 |
| 状态归属 | 主对话消息历史 | 子 Agent 隔离上下文 + 外部状态 |
| 并发方式 | 工具调用的同轮并行 | 子 Agent 实例的并发生命周期 |
| 失败处理 | 注入错误回主循环 | 跨子图传播 + Lead 决策 |
| 数量上限 | 60+ 工具（Tool 篇 §一）| 50+ Agent 边际协调成本陡升 |

### 多 Agent vs Workflow / DAG 引擎

多 Agent **也不是**纯 Workflow / DAG 引擎。Workflow 引擎（Temporal / Airflow）强调确定性重放、状态外部化、失败恢复——这些经验可被多 Agent 借用，但多 Agent 的每个节点自身就是非确定的（LLM 输出）。区别在于节点的不可重放性。

| 机制 | 适用场景 | 代价 |
|---|---|---|
| 单 Agent + 工具 | 单循环能搞定的任务 | 上下文累积 / 无并行 |
| 单 Agent + 工具 + 异步 | 工具调用后等异步回调 | 单 Agent 串行 / 无并行 |
| 多 Agent + Handoff | 任务需要并行 / 协商 / 中途改变路径 | 协调开销 / 失败传播 |
| Workflow / DAG 引擎 | 强事务 / 重放 / SLA 兜底 | 节点得是确定函数 / 接 LLM 失去"通用智能" |

cc-10 子 Agent 隔离实现样本：Fork-Join 子 Agent 作为 `tool_use` 跑，主 Agent 等待同轮所有 tool_use 返回后再继续——这是"多 Agent 用 Tool 的形态包装"的物理实现。

## 二、关键判断速览

### 编排机制侧

- 拆多 Agent 的硬指标：并行收益 > 协调开销，子任务边界清晰才拆
- Fork-Join 是基本模型：主 Agent 跑 query()，子 Agent 作为 tool_use 跑独立 query()，只回传结论
- 上下文继承默认剥离，Fork 路径才继承（worker 需要延续父决策）
- 物理隔离（工具白名单）比 prompt 警告更可靠，prompt 是软约束
- 并发模型是同轮并行 + 跨轮串行，不要全局异步任务池
- Handoff 选最浅够用的层次，链式依赖用前序注入而非共享工作区
- 失败处理是检测 + 重试 + 告警，不靠重试掩盖根因
- Token 预算按复杂度分配，简单任务和复杂任务同等预算是反模式
- 结果综合必须 LLM 整合，不直接拼接子 Agent 输出

### 编排图编写与维护侧

- 图类型按依赖清晰度选：DAG 优先、Swarm 用于运行时路径未定、Hybrid 取两者
- 状态外部化按共享范围选：in-memory（短跑）→ Redis（多进程）→ 数据库（带持久）
- 节点配置三件套：工具白名单（防越权）+ 角色 prompt（定职责）+ 退出条件（end_turn / maxTurns / abort）
- 可观测性分三层：节点级（trace）→ 整图级（边、并发度）→ 跨图级（跨任务重放）
- 可重放性看任务 SLA：长跑任务上 Temporal 类引擎、短跑任务靠 trace 日志
- 图的迭代靠评测驱动：拆 / 合并 / 废弃节点必须有评测用例回归

## 三、多 Agent 的编排机制（运行时怎么协作）

### Fork-Join 模型

多 Agent 的入口是 Fork-Join，不是"拆分任务"。

主 Agent 需要让子 Agent 跑一段重活（探索 / 计划 / 实现），结果再回到主上下文继续推理。如果把子任务当成普通消息塞进主上下文（不隔离），主 Agent 会被中间过程淹没。

cc-10 明示"子 Agent 把『过程』隔离在独立上下文中执行，只把『结论』回传给主 Agent"——这是 fork-join：

```
主 Agent：query()
  ↓ 工具调用（子 Agent）
子 Agent：query()（独立上下文）
  ↓
子 Agent 结论 → tool_result 回流到主 Agent
  ↓
主 Agent：继续推理
```

子 Agent 的过程是否需要从主上下文完全消失？如果是，必须 fork-join。如果过程本身是结论的一部分，注入即可。

### 上下文继承策略

#### 默认剥离

| 路径 | 上下文继承 | 适用 |
|---|---|---|
| Regular subagent | 不继承 | 任务独立（探索 X 模块、对比 A vs B） |
| Fork path | 全部继承 | 父已决策、子需延续 |

cc-10 §五 5.6 的 14×5 上下文继承矩阵明示 Explore / Plan / General / 自定义都不继承 messages 列，只有 Fork Worker 继承。

子 Agent 任务独立时，父对话历史多半是噪声——子 Agent 探索 X 模块，父的"用户说想重构 X"对它无意义。Fork 路径是"父已决策、子需延续"，才是继承的真正场景。

判断口诀：子 Agent 是否需要知道"主 Agent 为何这样决定"？不需要就剥离，需要就继承。

#### Fork 路径的 prompt cache 经济性

Fork worker 维持 byte-identical API request prefixes 才能命中 cache。三件套：

| 措施 | 作用 |
|---|---|
| `useExactTools` | 工具集完全相同 |
| `renderedSystemPrompt` 透传 | 不重算 |
| 占位 `tool_result` | 结构对齐 |

如果 fork worker 各自的 prompt 有差异，cache 全 miss、账单翻 10 倍。fork worker 数量超过 3 个且长跑时，prompt cache 是经济性瓶颈。

### 物理隔离 vs Prompt 警告

如何保证 Explore/Plan agent 真的不会写文件？

| 方式 | 约束强度 | 可靠性 |
|---|---|---|
| system prompt 写"不要 Write" | 软约束 | LLM 可能在新会话里忘掉 |
| 工具白名单物理移除 | 硬约束 | 每次调用强制检查 |

cc-10 §七 2 的 Explore Agent 用 `disallowedTools: [Agent, ExitPlanMode, Edit, Write, NotebookEdit]`——从工具列表里物理移除写工具。即便子 Agent 在 prompt 里忽略"不要 Write"的警告，工具调用也会失败。

约束是"LLM 应该这样做"（可失败）还是"LLM 绝不能这样做"（不可失败）？后者必须物理隔离。安全敏感场景用双保险——prompt 警告 + 工具移除。

### 并发模型

同轮并行 + 跨轮串行，不要全局异步任务池。

| 模型 | 适用 |
|---|---|
| 同轮并行（依赖 LLM tool_use 数量） | 默认 |
| 全局异步任务池（Temporal 类） | 跨轮并发 + 崩溃恢复 + 确定性重放 |

cc-10 §五 5.9 明示"最大并发子 Agent 取决于 LLM 同轮 tool_use 数量"。子 Agent 作为 tool_use 跑，主 Agent 等待同轮所有 tool_use 返回后再继续。

LLM 同轮发 N 个 `tool_use` 时框架会并行跑，N 通常是 1-10，正好匹配"个人 3-5、团队 5-10"的合理并发区间。写自己的调度器是过度工程。

任务是否需要"跨轮并发 + 崩溃恢复 + 确定性重放"？需要才上工作流引擎，否则同轮并行就够。

### Handoff 层次

| 层次 | 适用 |
|---|---|
| 前序注入（preamble） | 链式依赖，下游需要知道上游结论 |
| 共享工作区（文件 / Redis） | 任务间需要共享大量数据 |
| P2P Mailbox | 协商通信 |

链式依赖也上"共享工作区"是反模式。能用浅层（前序注入）就不用深层（工作区 / P2P）。传数据是单向数据流，协商才是 P2P 协议——传数据也上 P2P Mailbox 是反模式。

### 失败处理

#### 检测 + 重试 + 告警

一个子 Agent 跑挂了（rate limit / 工具错 / 超时）整图怎么办？

| 做法 | 后果 |
|---|---|
| 让单 Agent 串行重试 | 慢，掩盖根因 |
| 检测到失败就让 Lead 决定继续 / 重试 / 降级 | 失败暴露成数据让编排器决策 |
| 无限重试堆出 99.9% | 根因没找到，账单先翻倍 |

cc-10 §五 5.9 列了 4 种退出条件（end_turn / maxTurns / abort/error / 后台超时）。主 Agent 看到 `is_error: true` 决定下一步。整体机制是"失败可观测 + 显式决策"，不靠重试掩盖。

失败是因为"临时问题"（网络抖动、限流）还是"任务问题"（prompt 错、工具缺）？前者重试，后者改路径。

#### 结果综合

直接拼接 5 个 Agent 的输出是反模式——信息重复、信息矛盾、没有洞察。必须 LLM 整合：

```
1. 去重：消除多 Agent 输出重复
2. 过滤：剔除无意义 / 错误结果
3. LLM 整合：综合 prompt 显式要求"标注矛盾、生成洞察"
```

只处理 `success=True` 的结果，失败的被静默丢弃是反模式——综合报告看似完整实则漏掉关键来源。

### Token 预算分配

简单任务和复杂任务同等 Token 预算是反模式。复杂任务半途截断，简单任务烧太多。

按复杂度分配：任务依赖图、预估 LLM 调用次数、预估输出长度，算出每个子 Agent 的合理预算。

## 四、编排图的编写与维护工程技巧

### 图类型选型：DAG / Swarm / Hybrid

多 Agent 拓扑不是"画一张图"那么简单——三种范式各有适用场景。

| 范式 | 形态 | 适用 | 不适用 |
|---|---|---|---|
| **DAG** | 静态依赖图，节点显式 | 任务依赖清晰可画图（如 ETL / 流水线） | 运行时路径需要协商、动态调整 |
| **Swarm** | 去中心化，Agent 间 P2P 通信 | 多 Agent 协商、动态派活 | 全局协调任务（撞 ABI） |
| **Hybrid** | DAG 骨架 + 局部 Swarm 协商 | 大图中部分环节需要协作（如 RAG 多查询协同） | 整个图都要协商（直接 Swarm）|

**选型硬标准**：

- 任务依赖图能否在运行前画完？ 能 → DAG
- 任务依赖运行时才知道？ → Swarm 或 Hybrid
- Swarm 撞 ABI bug：每个 Agent 独立工作无 Lead，遇到全局协调任务会互相覆盖——这是 Swarm 的硬边界

cc-10 子 Agent 隔离作为 DAG 范式的工具层实现：主 Agent 是 Lead，子 Agent 是节点，工具调用是边。如果未来需要 Swarm 范式，那是更高一层的运行时（OpenAI Swarm SDK / 自建 mailbox）。

### 状态外部化

子 Agent 的状态有三层归属：

| 状态归属 | 形态 | 适用 |
|---|---|---|
| 子 Agent 上下文 | in-memory | 子 Agent 内部 reasoning / 工具调用 |
| 主 Agent 可见 | tool_result 回流 | 需要父决策的关键节点 |
| 全图共享 | Redis / 文件 / 数据库 | 跨子图共用数据（如 RAG 中间产物）|

**选型要点**：

- 共享数据量小（< 1MB）+ 不持久 → 子 Agent 上下文
- 共享数据量中 + 跨进程 → Redis
- 共享数据需要跨崩溃恢复 + 长生命周期 → 数据库 / S3
- 共享数据仅在单次跑里用 → 临时文件（运行时清理）

**反模式**：把所有状态塞主 Agent 上下文（主 Agent 被淹没）、把共享状态放文件而不锁（并发写覆盖）、用 Redis 但忘了过期（内存堆积）。

### 节点配置三件套

每个节点（子 Agent）必须有三个明确配置：

| 配置 | 作用 | 缺失后果 |
|---|---|---|
| **工具白名单** | 限定可调用工具范围（与 Tool 篇"权限层"联动）| 子 Agent 误调用工具 |
| **角色 prompt** | 明确职责、能力边界、输出格式 | 输出不稳定 |
| **退出条件** | end_turn / maxTurns / abort/error | 子 Agent 跑挂主 Agent 等不到 |

cc-10 §七 6 的子 Agent prompt 共同模式：角色重置（消除主 Agent 上下文影响）+ 能力边界（做什么不做什么）+ 工具物理隔离（`disallowedTools`）+ 结构化输出（便于下游解析）。

节点的"角色 prompt"与 Skill 篇 §四 `frontmatter description` 同源——只是粒度不同：Skill 是场景化专家封装，节点角色是任务化角色定义。

### 可观测性三层

| 层 | 观测对象 | 工具 |
|---|---|---|
| **节点级** | 单子 Agent 的输入 / 输出 / 工具调用 / token | LangSmith / Langfuse span |
| **整图级** | 边、并发度、节点耗时分布、Handoff 频率 | DAG 监控面板 / span 聚合 |
| **跨图级** | 跨任务的 trace 关联、失败率、SLA 达成 | 跨任务 trace 后端 |

**最低要求**：节点级 trace 必须开——出问题能跳到具体节点。整图级监控是工程化的下一步。跨图级观测看业务价值。

可观测性缺位等于多 Agent 盲调——配合 [Agent 评测篇](./agent-evaluation.md) 一起落地。

### 可重放性

任务可不可重放决定图能不能上线：

| 任务类型 | 重放要求 | 实现 |
|---|---|---|
| 短跑（< 1 分钟，无外部副作用）| 不需要重放（重跑即可） | trace 日志 |
| 中跑（5-60 分钟，有部分副作用）| 部分重放 | Temporal / event sourcing |
| 长跑（小时级，强事务 / SLA） | 完全确定性重放 | Temporal 工作流引擎 |

LLM 节点的不可重放性是核心挑战——同一 prompt 两次调用不会得到完全相同的输出。能做的就是"接受不可重放 + 用 LLM Judge 验证重放结果是否合理"。

OpenAI Agents SDK、LangGraph、Temporal 这三个是当代多 Agent 编排的三种主流落地形态：

- **OpenAI Agents SDK**：轻量 Swarm 范式实现，handoff 是其核心抽象
- **LangGraph**：生产级 DAG 调度，StateGraph 是状态外部化的代表
- **Temporal**：确定性重放与状态外部化，适合长跑 SLA 场景

### 图的迭代

跟 Skill / Tool 一样，多 Agent 的图也需要评测驱动迭代：

| 动作 | 适用 | 做法 |
|---|---|---|
| **新增节点** | 当前图漏掉某类任务 | 加节点 + 接评测用例回归 |
| **合并节点** | 两个节点频繁 Handoff 但分工不清 | 合并 + 重新拆评测用例边界 |
| **废弃节点** | 节点长期未被触发 | 移到 `archive/` + 加 `deprecated: true` |
| **拓扑变更** | 依赖关系变了 | 重新画 DAG + 评测用例覆盖新路径 |

**评测用例三件套**：

- **输入**：真实跨任务场景（从生产 trace 抽）
- **预期**：节点级预期（每个子 Agent 输出应包含什么）+ 整图预期（最终结果应满足什么）
- **回归触发**：每次拓扑变更都跑全套

迭代失败的图往往缺这一层——图变成"第一次画就对"的赌博，缺持续改进的工程纪律。

## 五、反模式

### 编排机制侧反模式

- "查个天气"拆成 3 个 Agent 跑——协调开销 > 并行收益，单 Agent 一行工具调用搞定
- `MaxConcurrency=100` 拉满——LLM API 回一堆 429，反而比串行慢几倍
- 综合阶段直接拼接 5 个 Agent 的输出，信息重复、矛盾、无洞察
- 只处理 `success=True` 的结果，失败的被静默丢弃
- 简单任务和复杂任务同等 Token 预算
- 链式依赖也上"共享工作区"，能用浅层就不用深层
- 传数据也上 P2P Mailbox
- 纯去中心化 Swarm（每个 Agent 独立工作、无 Lead），遇到全局协调任务会撞 ABI bug 互相覆盖
- 把"子 Agent 失败"靠无限重试掩盖，根因没找到账单先翻倍
- 忘了"生产者集合校验"，运行时等"无人 produces 这个 topic"直到超时
- Fork worker 各自 prompt 略差异 → cache 全 miss、账单翻 10 倍
- 把"为何这样做"塞进 prompt 让子 Agent 决定 → 子 Agent 推断错就全错，前序注入或 Fork 继承才能延续父决策

### 编排图编写与维护侧反模式

- 三个 Agent 拆完但只跑一次——建图成本远超收益
- 所有状态塞主 Agent 上下文，子 Agent 输出被淹没
- 共享状态放临时文件不锁 → 并发写覆盖
- Redis 共享状态忘了过期 → 内存堆积
- 节点没设 `disallowedTools` → 子 Agent 误调用（Explore 写了文件）
- 节点角色 prompt 没定输出格式 → 综合阶段无法解析
- 节点缺退出条件 → 子 Agent 跑挂主 Agent 等不到
- 跨图观测缺失 → 出问题只能看日志盲调
- 拓扑变更不跑回归 → 优化的拓扑常常破坏原有场景
- 长期没触发的节点不治理 → 节点膨胀、调度成本陡升
- 跨任务 trace 后端没接 → 失败 root cause 难定位
- "重跑就行"思维覆盖长跑事务——长跑场景必须有 Temporal 类引擎兜底

## 六、何时不该用

> 总原则：不属于"多 Agent 协作能带来并行 / 协商 / 跨子图共享"价值范畴的，硬拆多 Agent 都比单 Agent 差。

多 Agent 编排不是"放之四海而皆准"的工程层，遇到这些场景**别用**：

| 我要做的是… | 应该用 |
|---|---|
| 单循环能搞定的（任务串行 + 工具 + LLM） | 单 Agent + 工具 |
| 工具调用后等异步回调，单 Agent 串行即可 | 单 Agent + 异步工具 |
| 强事务 / 重放 / SLA 兜底（节点必须是确定函数） | Temporal / Airflow 类工作流引擎 |
| 角色化经验封装（场景化 SOP） | Skill（Skill 内部可调白名单 Tool / 调子 Agent）|
| 永久生效的规范 | CLAUDE.md |
| 中长跑需要持久状态 + 跨崩溃恢复 | Temporal / 状态外部化数据库 |

边界判定口诀：

- **单循环能搞定** → 单 Agent + 工具
- **场景化 SOP** → Skill
- **多循环并行 / 协商** → 多 Agent
- **强事务 / 重放** → Workflow / DAG 引擎
- **永久规范** → CLAUDE.md

**硬约束**：

- 协调开销 > 并行收益时，硬拆多 Agent 比不拆更糟——这是反模式的根因
- 任务依赖图能在运行前画完优先 DAG，运行时路径未定才 Swarm / Hybrid
- 多 Agent 节点自身是 LLM（非确定）——不能像 Temporal 那样追求完全确定性重放

不属于"多循环并行 / 协商"价值范畴的，硬拆成多 Agent 都会变成协调灾难。

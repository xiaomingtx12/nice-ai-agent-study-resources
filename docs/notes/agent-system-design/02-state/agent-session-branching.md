# 会话续接与分支：让历史经验留在正确的任务里

旧会话能保存调查过程，也可能把过期的架构、根因和待办带进新任务。复用历史时，需要同时决定继承哪些内容、从哪里开始成为独立工作，以及哪些现场事实必须重新获取。

例如，同一团队维护新旧两套支付系统。新系统采用灰度发布，旧系统使用独立脚本。即使切换了代码目录，沿用新系统的长会话仍可能让 Agent 按灰度实例和服务网格查找故障。文件位置变了，会话里的系统认识却没有随之清空。

## 一、按任务关系选择续接方式

会话是任务历史的容器，不宜把一个用户、一个服务甚至一个团队的全部工作永久装在同一条时间线里。

| 方式 | 适合什么关系 | 需要保留什么 | 主要风险 |
| --- | --- | --- | --- |
| Resume，继续原会话 | 同一事故尚未结束，等待补充材料后继续 | 原目标、进度、有效证据与未决项 | 把等待前的环境当成当前环境 |
| Fork，从历史建立分支 | 新任务需要一段已有背景，并应独立记录 | 选定历史边界及来源关系 | 一并继承旧结论和旧动作 |
| 新建会话 | 对象变化大、旧历史不相关，或方法已整理完整 | 当前任务与适用规则、Skill | 缺少必要背景时重复探索 |

Fork 的价值是建立独立任务，同时利用选定历史。它并不自动判断什么是通用知识，也不能保证历史中的错误假设被清除。若已有可靠的模块文档和 Skill，新建会话并按需加载，通常更容易控制输入。

## 二、分支点应落在背景与现场结论之间

假设一场旧调查留下六段记录：

| 历史阶段 | 主要内容 | 新事故怎样使用 |
| --- | --- | --- |
| 认识系统 | 部署方式、日志入口、监控口径 | 可作为背景，但需要核对有效性 |
| 获取现场 | 当时的发布、错误时间和实例版本 | 只作为旧事故证据 |
| 形成假设 | 连接等待与错误率同时上升 | 可作历史线索，不能直接沿用判断 |
| 确认原因 | 当时的连接池配置发生变化 | 留在旧事故结论中 |
| 执行处置 | 恢复配置并观察效果 | 留在旧动作记录中，不能重新执行 |
| 整理报告 | 收束证据与遗留问题 | 按需回查，不自动成为新任务待办 |

如果系统支持指定历史边界，可以选择“认识系统”完成后的位置。这样继承的主要是查找入口，后续现场观察留在父会话中。选择接口时还要确认边界是否包含指定记录、是否要求对应运行已结束，以及压缩后的上下文如何参与继承。

历史未必划分得这么整齐。背景、事故事实和错误假设可能已经混在同一轮里，摘要也可能同时覆盖多个阶段。遇到这种情况，可以新建会话，整理经过核对的交接材料，并保留旧记录引用，不必为了使用 Fork 而接受整段污染。

## 三、历史有来源，新事实有自己的时间

新任务开始时，应明确当前对象、独立目标和继承内容的用途。针对旧支付系统，新任务的交接要求可以写成：

> 当前调查针对本次支付超时。继承记录用于定位部署、日志、监控和配置入口。先确认这些入口仍然有效，再读取本次时间窗内的现场数据。旧事故结论只作待核对线索，不继承其处置动作和未完成事项。

建议在新任务中保留父会话标识、历史边界、继承目的和创建时间。通过这些信息，后来审查结论时能够区分：这是旧调查提供的背景，还是本次工具查询得到的证据。

对于会变化的事实，要按用途决定重新读取的内容：

- 日志与监控入口可能迁移，需要确认当前仍可访问且属于正确系统。
- 当前版本、实例、配置、依赖地址必须以本次现场为准。
- 指标定义较稳定，但单位、聚合窗口和标签也可能改变。
- 旧事故中的因果判断不能靠相似现象自动晋升为当前根因。

新事故即使同样出现连接等待，也可能由请求路径没有释放连接造成，与旧事故的配置上限无关。验收新分支时，应检查它是否会接受这种与旧结论不同的解释。

## 四、会话分支与环境隔离需要分别建立

复制或引用一段历史，不代表代码、文件和生产环境也回到当时。旧会话里记录的某个文件内容，可能已与当前磁盘不同；两个独立会话也可能写入同一个目录。

因此，应分别确认三项边界：

| 边界 | 要决定的问题 |
| --- | --- |
| 历史边界 | 子会话继承到哪里，父记录是否保持可追查 |
| 工作环境 | 读取哪个代码版本，写入独立副本还是共享目录 |
| 行动授权 | 新任务当前允许哪些动作，旧批准是否仍有适用依据 |

需要并行修改时，为各分支准备独立工作副本，或明确共享资源的写入顺序。旧会话中的“已批准恢复配置”不能直接授权今天修改生产。更完整的环境设计见[工作区与沙箱](../05-action/agent-workspace-sandbox.md)。

## 五、把反复继承的背景整理成长期入口

如果每次处理告警都要搜索旧会话、挑选分支点，说明常用知识仍埋在任务历史里。可以按内容拆出更稳定的入口：

- 系统边界和指标口径进入模块文档。
- 团队确认的长期要求进入[项目规则](../03-view/agent-project-rules.md)。
- 有效期明确的环境事实进入[记忆](../03-view/agent-memory-design.md)。
- 查询顺序、证据关联和验收方法进入[Skill](../03-view/agent-skill-design.md)。

旧会话仍保存方法形成的过程，包括无效尝试和人工纠正；日常新任务则直接从已整理的入口开始。方法需要修订时，再回到历史证据核对。

## 六、用相似现象、不同原因检验继承边界

可以准备两份同模块的事故材料：第一份由配置变化导致异常，第二份配置正常但代码路径有缺陷。将第一份调查中“认识系统”的记录用于第二份任务，检查以下结果：

- 新任务有独立身份，产物和后续记录不会写回父任务。
- 当前日志、配置与版本被重新读取，证据时间可区分。
- 旧处置动作和旧待办没有被再次执行。
- 当前证据与旧结论冲突时，Agent 会修改调查方向。
- 追问某项背景来源时，能够找到继承位置或对应文档。

另设一份完全不同系统的任务作为负例，检查系统是否选择新建会话。继承带来的收益应表现为更少的背景探索，同时不增加旧假设误用。

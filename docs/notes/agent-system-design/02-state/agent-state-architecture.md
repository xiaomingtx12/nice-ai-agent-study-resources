# Agent 状态：事实、进度与共享变量

> **模块本质：** 为每次继续执行提供可核对的起点。模型输入会裁剪，进程会退出，外部动作又可能先于本地记录生效；状态层必须保存任务事实及其版本，并在恢复时核对哪些工作已经发生、哪些条件仍然成立。

沿用[工具执行](../05-action/agent-tool-calling.md)的设计案例：任务 `T17` 准备通过动作 `A903` 将页面 `doc-42` 的 `v7` 更新为草稿 `r18`。发布服务已经生成 `v8`，Agent 进程却在保存发布结果前退出。恢复出来的图还停在“准备发布”，页面已经改变，两边都如实记录了各自最后确认的事实。

恢复要合并这两份证据。只看检查点会重复执行，只看当前页面又可能无法证明变化来自本任务。本文重点说明保存位置、恢复顺序与执行权；工具参数、请求幂等协议与单次动作校验由工具执行篇负责。案例用于设计推演，不代表已实现或测试通过的发布系统。

状态层关注当前任务的事实连续性：

```text
任务目标
→ 已确认事实
→ 当前进度
→ 共享变量
→ 下一轮继续使用
```

## 一、状态解决什么问题 {/* #状态解决什么问题 */}

### 1. 保持事实连续 {/* #保持事实连续 */}

保存已经确认或验证过的信息：

- 当前任务目标和约束；
- 用户确认的参数和决定；
- 已验证的外部结果；
- 当前有效的配置和运行选项；
- 仍然适用的限制条件。

每条事实都需要来源、版本或有效时间。模型的临时猜测不直接成为状态事实。

### 2. 保持进度连续 {/* #保持进度连续 */}

记录任务进行到哪一步、已经完成什么、还缺少什么：

```text
未开始 → 进行中 → 等待输入 → 继续进行 → 已完成
                         ↘ 已取消
                         ↘ 已失败
```

进度字段让下一轮模型知道当前工作位置，也让系统能够判断任务是否仍然需要继续。

### 3. 保持共享变量一致 {/* #保持共享变量一致 */}

模型调用、用户交互和后台运行可能共同使用目标、配置、阶段和临时决定。状态层为这些变量确定唯一事实来源，避免不同模块各自保存一份互相冲突的值。

### 4. 保持状态规模可控 {/* #保持状态规模可控 */}

核心业务状态只保存会影响后续判断的字段。框架可以另外保留消息历史，诊断系统可以保存调用日志，大产物放到文件或对象存储；核心状态记录它们的稳定引用与版本。将这些内容全部追加进同一个字段，会同时增加检查点体积、恢复读取和迁移成本。

## 二、状态应该记录什么 {/* #状态应该记录什么 */}

状态内容可以收敛为五组：

| 状态组 | 典型内容 | 作用 |
|---|---|---|
| 任务事实 | 目标、参数、约束、确认结果 | 提供后续判断依据 |
| 任务进度 | 当前阶段、已完成事项、待处理事项 | 维持任务连续 |
| 共享变量 | 当前配置、用户选择、运行模式 | 保持多方读取一致 |
| 有效性信息 | 来源、版本、生效时间、失效时间 | 判断内容是否仍可使用 |
| 变更信息 | 修改者、修改原因、更新时间 | 解释状态为什么变化 |

字段从实际任务失败中倒推。目标、已确认事实和待办用于构建模型视图；动作身份、预算账本和待审批记录用于运行时恢复。后一类字段未必需要全部暴露给模型，但必须有可靠的保存位置。单次展示内容和可重算的临时结果可以留在核心状态之外。

## 三、状态的范围 {/* #状态的范围 */}

状态按共享范围分成三类：

| 范围 | 保存内容 | 生命周期 |
|---|---|---|
| 调用范围 | 当前调用的临时参数、阶段标记和中间变量 | 当前调用 |
| 任务范围 | 目标、事实、进度和待处理事项 | 当前任务 |
| 共享范围 | 项目约定、当前配置和多方共用变量 | 按项目或会话保留 |

跨任务长期复用的偏好、经历和经验进入记忆系统；当前任务的目标、进度和临时变量留在状态中。

状态范围越大，写入权限、版本管理和冲突处理越重要。全局共享字段需要明确使用方和失效条件。

## 四、状态所有权 {/* #状态所有权 */}

每个字段都要回答：

```text
谁创建？
谁可以修改？
谁可以读取？
修改后通知谁？
什么时候失效？
```

状态所有权遵循三条规则：

1. 一个事实只有一个权威来源；
2. 调用方通过明确的更新接口修改状态；
3. 同一字段的同步方向集中在一个入口。

例如，用户选择的模型和当前实际使用的模型可以分别记录：

```text
selected_model  用户最后选择的值
active_model    当前运行采用的值
```

两者产生差异时，状态中记录原因和生效条件。

## 五、状态如何更新 {/* #状态如何更新 */}

状态更新基于旧版本生成新版本：

```text
next_state = update(previous_state, change)
```

更新接口应表达具体意图，例如确认事实、推进阶段、使旧证据失效。确认事实时检查来源与当前版本；推进阶段时检查该阶段的验收结果；目标变化时使依赖旧目标的计划和审批失效。这样可以在写入边界检查字段关系，也便于追踪状态为什么变化。

在 LangGraph 中，节点返回更新，reducer（字段合并函数）决定如何把更新合入已有状态。reducer 解决图内的字段归并，业务数据库的并发版本检查仍需由写入端完成。框架不会仅凭一个字段叫 `approved`，就自动知道它必须绑定 `r18`。

以并行收集引用为例，直接追加列表可能在重复提交时留下两份相同证据；按来源 ID 与版本合并可以去重，但也要保留同一来源不同版本的差异。草稿当前版本适合由一个负责推进阶段的节点更新，避免多个子任务争相覆盖。字段的合并方式应依据业务语义选择，不能统一设成“后来的覆盖”或“全部追加”。

## 六、版本、来源与有效期 {/* #版本来源与有效期 */}

状态事实需要附带最小元数据：

```text
source
confidence
confirmed_by
valid_from
valid_until
version
updated_at
```

这些字段是候选元数据，不要求每条记录机械地全部保存。版本与来源服务于事实核对；`confidence` 若来自模型自报，不能当作事实正确的概率。发布记录应以服务端确认的结果为依据，审批应以对应决定和内容版本为依据。

过期事实标记为失效并触发重新确认，旧版本保留变更关系，避免新旧内容静默混用。

## 七、状态存储方式 {/* #状态存储方式 */}

先决定允许丢失什么、需要恢复到哪里，再选择存储。下面按需求逐步增加能力，后面的方案不需要成为所有 Agent 的默认配置。

| 需求 | 可以从什么开始 | 升级信号 | 新增成本 |
| --- | --- | --- | --- |
| 短暂的只读任务，失败后允许重做 | 进程内状态 | 重算成本过高，或需要跨请求继续 | 增加持久存储与清理策略 |
| 多轮会话，需要保存同一执行线 | 图状态与持久 checkpointer（检查点保存器） | 需要人工暂停、进程重启后继续 | 序列化、恢复与版本兼容 |
| 存在发布等外部写入 | 检查点加业务动作账本 | 出现未知结果、重复投递或跨服务操作 | 对账任务、记录保留与异常处理 |
| 多 worker 可能接管同一任务 | 执行权管理加条件写入 | 旧 worker 迟到回写，单任务发生竞争 | 租约续期、冲突处理与执行端配合 |
| 需要审计历史及重建旧状态 | 评估事件溯源或专项审计记录 | 快照已无法回答业务必须追溯的问题 | 事件模式演进、回放兼容与存储增长 |

LangGraph 的 Store 是跨执行线数据接口，区别于 checkpointer；它并不保证所有实现都具备持久性或订阅能力。关系数据库可以同时承载业务表和检查点表，但“使用同一个数据库”不自动让图保存与外部发布处于同一事务。

## 八、恢复现场需要保存到哪一步 {/* #恢复现场需要保存到哪一步 */}

任务 `T17` 在发布前可以保存以下三类记录。它们的职责不同，即使物理上存放在同一个数据库，也应能分别查询。

| 记录 | 发布前 | 服务已提交、进程尚未确认时 |
| --- | --- | --- |
| 图检查点 | 目标 `doc-42`、期望 `v7`、草稿 `r18`、动作 `A903`、阶段待发布 | 可能仍然停在原检查点 |
| 业务动作账本 | `A903` 的操作意图、内容摘要与执行状态 | 可能只有已登记或已尝试发送，不能据此宣称外部失败 |
| 发布服务记录 | 尚无已确认结果 | `A903` 已生成 `v8`，可按动作身份查询 |

“已登记”只能证明意图已保存。程序若在发出请求之后、标记已发送之前退出，账本仍可能是已登记；除非发送协议提供额外证据，恢复者不能据此认定请求肯定没发出。

需要恢复的对象应按责任分别保存，不必塞进同一个大 JSON：

| 对象 | 恢复时需要回答的问题 |
| --- | --- |
| 任务与计划版本 | 这次运行仍在处理哪个目标，哪些步骤有效 |
| 检查点及未合并结果 | 哪些状态已提交，哪些任务结果已保存但尚未汇合 |
| 动作登记与外部身份 | 哪些动作未发送、已提交、已确认或结果未知 |
| 预算与失败计数 | 已消耗多少，哪些重试已经用完 |
| 待审批动作 | 等待谁决定什么，批准的是哪一份参数 |
| 执行所有者 | 当前由哪个 worker 推进，旧 worker 是否仍可能返回结果 |

Checkpoint（检查点）保存某个执行边界的状态。增量事件记录之后发生的变化，需要事件身份、顺序和去重规则；不能把普通日志任意重放成业务状态。已保存的模型输出与工具结果应在框架恢复协议允许时复用；未保存的步骤可能重新执行，因此执行代码仍需处理重复进入。重新调用模型会产生一次新决策，不能用它证明故障前发生了什么。

可以从任务边界上的快照和动作登记起步。只有确实需要细粒度重放或审计时，再承担完整事件溯源的存储、模式升级与清理成本。

### 1. 保存完成与生成检查点是两个时点 {/* #保存完成与生成检查点是两个时点 */}

LangGraph 1.2.10 源码快照中的 `Pregel.stream()` 是推进图任务并输出事件的运行入口。轮次结束时，同步持久化模式会等待检查点写入任务完成。快照 commit 未知，文件指纹与版本范围见 [LangGraph 导读](../../../application-notes/engineering/langchain-series/langgraph/index.md)。

源码：`libs/langgraph/langgraph/pregel/main.py` → `Pregel.stream()`（第 2984–2988 行节选，其他逻辑省略，原注释已翻译）。

```python
loop.after_tick()
emit_graph_lifecycle_events(loop)
# 等待检查点保存。
if durability_ == "sync":
    loop._put_checkpoint_fut.result()
```

这里能够证明同步路径存在等待点；保存成功究竟意味着写入内存、写入本机磁盘还是完成数据库事务，还取决于保存器。该等待也不会把之前的外部 API 调用纳入同一事务。

同步保存增加执行延迟，异步保存允许继续推进但需要接受未落盘窗口。选择时分别声明 RPO（可容忍的数据丢失范围）和 RTO（期望恢复时间），并用故障试验验证。仅保存器返回成功，不能证明外部副作用可以无损恢复。保存协议与任务结果的细节见[检查点、恢复与分叉](../../../application-notes/engineering/langchain-series/langgraph/06-checkpoints-store-and-recovery.md)。

## 九、外部动作未知时，先查账再决定是否重试 {/* #外部动作未知时先查账再决定是否重试 */}

业务动作 ID 表示一次已经确定的操作意图，例如对某个交付版本发起一次发布。它应在发送前可靠登记，同一动作的网络重试与恢复复用该身份。用户再次明确要求发布另一版本时，应形成新动作；不能只用工具名和参数相同来判定所有调用都是重复。

| 崩溃位置 | 恢复时可用的证据 | 建议处理 |
| --- | --- | --- |
| 有可靠证据确认尚未发送 | 未消费的发送任务等协议证据与参数版本 | 重新校验授权后发送；不能只依据普通“已登记”标志 |
| 请求可能已发出，没有响应 | 动作身份，效果未知 | 按外部业务身份查询或用服务端幂等协议重试 |
| 外部已成功，本地确认未落盘 | 可查询的外部结果 | 对账并补记结果，避免重新产生效果 |
| 本地已提交结果，确认消息丢失 | 已持久化的动作结果 | 重复投递返回已有结果 |
| 外部只完成部分操作 | 可核实的生效范围 | 保留已完成部分，重排或补偿剩余部分 |

本地去重记录不能单独保证跨系统副作用只发生一次。需要核对服务端幂等键的作用域、保留期、相同键不同参数的处理，以及去重与业务写入是否原子完成。既无可用幂等保证、又无法查询真实状态时，应保持未知并转入人工对账，不能继续承诺“精确一次”。

### 1. 将外部证据合入恢复状态 {/* #将外部证据合入恢复状态 */}

对 `T17`，恢复者读到旧检查点后，用 `A903` 查询发布服务。若结果确认 `r18` 已生成 `v8`，就补记动作结果，再将图中的发布步骤推进为已确认，继续后置验收。这个过程没有重新生成发布提案，也没有再次调用发布接口。

补记动作结果后、图状态更新前仍可能再次退出，因此这两个写入也必须允许重复执行：已确认的动作结果按同一身份复用，图更新检查当前版本及是否已经处理过该结果。不能修复了“外部重复发布”，却在恢复时重复追加产物或扣减预算。

若服务返回查询暂不可用，任务进入待对账并受截止时间限制；若明确确认动作被拒绝，记录失败原因，再判断是否允许创建新提案。动作账本、图检查点和发布服务可以短暂不同步，但每次推进都要能说明采用了哪份证据。

补偿也需要业务规则。删除尚未使用的临时资源与撤回已经发送给外部用户的通知，恢复能力完全不同。设计时要声明哪些效果可撤销，哪些只能记录并人工处理。工具侧的执行合同见[工具执行](../05-action/agent-tool-calling.md)。

## 十、恢复前重新取得执行权并检查外部事实 {/* #恢复前重新取得执行权并检查外部事实 */}

从检查点恢复后，不应立即执行其中保存的下一步。推荐按以下顺序处理：

1. 取得该任务的执行权，防止两个 worker 同时恢复同一条状态流。
2. 加载已提交状态与动作记录，确认版本兼容，保留已用预算和失败计数。
3. 对账结果未知的外部动作，识别已经生效的部分。
4. 重新检查任务是否取消、审批是否过期、权限与目标资源是否变化。
5. 根据新事实生成当前视图，只推进仍然成立的剩余工作。

执行权可以用租约管理，但租约到期不代表旧 worker 已停止。对共享状态使用版本条件写入；必要时引入递增的 fencing token（隔离令牌），由写入端拒绝旧持有者。外部工具如果不检查令牌，租约本身无法防止旧 worker 继续产生副作用，仍要依靠外部幂等与执行端限制。

审批等待期间也会发生业务变化。例如等待批准的任务原本准备覆盖草稿，恢复时草稿已经发布。即使审批令牌尚未过期，也应重新检查目标版本；不满足前置条件时使旧提案失效，进入重排或再次确认。

## 十一、用故障位置验证恢复能力 {/* #用故障位置验证恢复能力 */}

以下为故障注入方案，不是已经执行的实验报告。隔离环境需要能在指定写入前后退出进程、暂停 worker，并独立查询发布记录与检查点。

| 故障位置或竞争条件 | 恢复后应该发生什么 | 必须检查的证据 |
| --- | --- | --- |
| 登记 `A903` 后、发送状态更新前退出 | 先消除是否已发送的不确定性，或按服务幂等协议恢复 | 动作身份未变化，未无条件创建新发布 |
| 服务生成 `v8`，本地未收到响应 | 查询 `A903` 并补记结果 | 发布版本只有一份，图最终引用 `v8` |
| 动作账本补记成功，图更新前再次退出 | 重复合入同一结果，不重复扣费或追加产物 | 动作表、产物列表、预算账本与检查点相互对应 |
| 审批等待时草稿变为 `r19` | 旧批准不能授权发布新草稿 | 审批仍绑定 `r18`，新提案经过重新确认 |
| 两个 worker 同时恢复，旧 worker 延迟返回 | 只有当前有效执行者可以推进受保护状态 | 条件写入或隔离令牌的拒绝记录 |
| 幂等保留期已过，外部结果无法查询 | 保持未知或转人工，不能按原保证自动重发 | 自动写入次数与任务终态 |
| 加载旧字段结构的检查点 | 通过明确迁移继续，或在执行前拒绝 | 模式版本、迁移记录、没有发生新副作用 |

分别记录恢复等待、对账耗时与重新执行耗时。同步检查点可能降低未保存状态的范围，同时增加正常运行延迟；仅在正常路径测吞吐或仅测一次重启，都不足以决定保存模式。

## 十二、用框架保存执行现场，用业务记录确认外部事实 {/* #框架接入与状态定制 */}

### 1. 按生命周期选择接口 {/* #1-按生命周期选择接口 */}

LangChain 的 `create_agent()` 用于装配模型与工具循环，`state_schema` 声明循环中的状态字段，`context_schema` 声明单次运行注入的上下文类型。LangGraph 的 checkpointer 是执行现场保存器；Store 是跨执行线读写业务数据的存储接口。它们解决的持久化问题不同。

| 业务数据 | 框架接入位置 | 定制时的判断 |
| --- | --- | --- |
| 已选资料、草稿版本、待审批动作 | `state_schema` 与 `checkpointer` | 定义字段所有者、更新方式与恢复后的有效性检查 |
| 当前请求的身份、租户和服务依赖 | `context_schema`，调用时传入 `context` | 从可信服务端注入；恢复请求要重新鉴权并注入，不能当作已保存的授权 |
| 跨任务的项目约定、用户偏好 | `store` | 定义命名空间、来源、有效期和删除规则 |
| 发布请求及真实结果 | 业务动作表与外部系统 | 用稳定动作 ID 对账，不能只依赖消息或图状态 |

这里按 LangChain 1.3.7 的 `libs/langchain_v1/langchain/agents/factory.py` → `create_agent()`，以及 LangGraph 1.2.10 的检查点实现核对接口。`context_schema` 只声明接口，不会自动完成身份验证。

### 2. 固定执行身份，明确字段合并规则 {/* #2-固定执行身份明确字段合并规则 */}

调用配置中的 `configurable.thread_id` 应由服务端映射到有访问权限的业务任务。恢复同一任务使用原 ID；新任务使用新 ID。不能把用户 ID 直接当作所有任务共享的执行线，也不能允许客户端仅凭猜中的 ID 读取或恢复别人的任务。

字段合并规则在[状态更新](#状态如何更新)中确定，再落实到 `state_schema`。本例让 State 持有草稿版本、动作 ID 和结果引用，完整发布记录由业务服务维护。先确定事实由谁确认，再决定字段放在哪里，可以避免两个存储同时成为“发布是否成功”的独立裁决者。

演示时可用 `InMemorySaver`，它只在进程内保存检查点。需要跨进程恢复时，换成持久保存器并验证实际部署的事务、并发和保留策略。将 `durability` 设为 `sync` 可等待本轮检查点保存，但仍不能把发布接口与检查点合成一个事务。

### 3. 把发布业务接在恢复边界上 {/* #3-把发布业务接在恢复边界上 */}

需要固定恢复顺序时，可以用 LangGraph 的 `StateGraph` 构建器把核对动作、重新校验与继续执行组织成明确节点。恢复入口及可能重执行的发布节点，都必须经过动作检查；只有入口检查一次，无法覆盖节点内部重试。已有标准 Agent 循环也可以把这项检查封装在业务工具适配层，前提是所有发布路径都经过它。

是否补记成功由服务证据决定，是否继续执行还需重新核对取消、授权、草稿与预算。`get_state()` 用于读取图快照，`update_state()` 按图的更新规则修改状态；它们都不能验证远端发布结果，也不能单独充当任务锁。业务核验后才能选择恢复或更新状态的入口。实现细节见[检查点、恢复与分叉](../../../application-notes/engineering/langchain-series/langgraph/06-checkpoints-store-and-recovery.md)和[状态字段与 reducer](../../../application-notes/engineering/langchain-series/langgraph/01-state-schema-channels-and-reducers.md)。

## 十三、常见状态失败 {/* #常见状态失败 */}

| 失败现象 | 原因 | 调整方式 |
|---|---|---|
| 不同模块保存不同事实 | 缺少唯一所有者 | 指定权威字段和同步入口 |
| 模型猜测被长期保存 | 缺少确认等级 | 区分候选、推断和确认事实 |
| 旧配置覆盖当前选择 | 缺少版本和生效条件 | 保存版本、来源和更新时间 |
| 状态不断追加导致读取膨胀 | 把过程材料当核心事实 | 只保留影响后续判断的字段 |
| 跨项目读取到错误变量 | 共享范围过大 | 增加用户、租户和项目作用域 |
| 过期事实继续影响任务 | 缺少有效期 | 失效标记和重新确认 |
| 多方同时修改产生覆盖 | 更新接口没有版本检查 | 使用版本号和冲突处理 |

## 十四、状态层的验收 {/* #状态层的验收 */}

### 1. 事实一致 {/* #事实一致 */}

下一轮模型能够读取已确认的目标、参数和关键结果，旧版本不会静默覆盖当前事实。

### 2. 进度准确 {/* #进度准确 */}

状态能够说明当前阶段、已完成事项和待处理事项。

### 3. 恢复一致 {/* #恢复一致 */}

已确认动作不重复执行，未知结果进入对账；重试计数和已用预算不会清零，失效审批与过期事实不能继续授权。旧 worker 的迟到结果不能覆盖新所有者已经提交的版本。

### 4. 所有权清晰 {/* #所有权清晰 */}

每个关键字段都有唯一事实来源，修改路径和通知范围可以追踪。

### 5. 版本有效 {/* #版本有效 */}

过期、冲突和推断内容带有明确标记，新旧内容可以解释。

### 6. 规模稳定 {/* #规模稳定 */}

状态不会随着每轮对话和临时输出无限增长，核心字段保持可读和可维护。

对发布业务，优先跟踪重复副作用数、未知动作积压时长、恢复失败原因、检查点大小与保存延迟。任务只有少量字段时，不必一次实现事件溯源和分布式接管；但只要产生外部写入，就必须明确响应丢失时依据什么确认效果。

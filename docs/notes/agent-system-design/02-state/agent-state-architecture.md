# Agent 状态：事实、进度与共享变量

> 状态层的核心本质，是把模型下一轮继续工作所需的当前任务事实、进度和共享变量外置保存，并为这些内容提供明确的所有权、版本和更新规则。

模型每轮调用都只看到一段有限输入。上一轮确认过的参数、当前任务进行到哪一步、用户刚刚修改的要求，都需要由系统持续保存，才能在下一轮继续使用。

状态层关注当前任务的事实连续性：

```text
任务目标
→ 已确认事实
→ 当前进度
→ 共享变量
→ 下一轮继续使用
```

## 一、状态解决什么问题

### 保持事实连续

保存已经确认或验证过的信息：

- 当前任务目标和约束；
- 用户确认的参数和决定；
- 已验证的外部结果；
- 当前有效的配置和运行选项；
- 仍然适用的限制条件。

每条事实都需要来源、版本或有效时间。模型的临时猜测不直接成为状态事实。

### 保持进度连续

记录任务进行到哪一步、已经完成什么、还缺少什么：

```text
未开始 → 进行中 → 等待输入 → 继续进行 → 已完成
                         ↘ 已取消
                         ↘ 已失败
```

进度字段让下一轮模型知道当前工作位置，也让系统能够判断任务是否仍然需要继续。

### 保持共享变量一致

模型调用、用户交互和后台运行可能共同使用目标、配置、阶段和临时决定。状态层为这些变量确定唯一事实来源，避免不同模块各自保存一份互相冲突的值。

### 保持状态规模可控

状态保存会影响后续任务判断的事实和变量。原始消息、临时日志和无关过程不进入核心状态，避免状态无限增长。

## 二、状态应该记录什么

状态内容可以收敛为五组：

| 状态组 | 典型内容 | 作用 |
|---|---|---|
| 任务事实 | 目标、参数、约束、确认结果 | 提供后续判断依据 |
| 任务进度 | 当前阶段、已完成事项、待处理事项 | 维持任务连续 |
| 共享变量 | 当前配置、用户选择、运行模式 | 保持多方读取一致 |
| 有效性信息 | 来源、版本、生效时间、失效时间 | 判断内容是否仍可使用 |
| 变更信息 | 修改者、修改原因、更新时间 | 解释状态为什么变化 |

一个最小状态对象可以是：

```text
AgentState {
  goal
  constraints
  confirmed_facts
  current_phase
  completed_items
  pending_items
  shared_variables
  sources
  version
  updated_at
}
```

字段从实际任务失败中倒推。下一轮模型必须使用的内容优先进入状态，单次展示内容和临时计算结果保持在状态之外。

## 三、状态的范围

状态按共享范围分成三类：

| 范围 | 保存内容 | 生命周期 |
|---|---|---|
| 调用范围 | 当前调用的临时参数、阶段标记和中间变量 | 当前调用 |
| 任务范围 | 目标、事实、进度和待处理事项 | 当前任务 |
| 共享范围 | 项目约定、当前配置和多方共用变量 | 按项目或会话保留 |

跨任务长期复用的偏好、经历和经验进入记忆系统；当前任务的目标、进度和临时变量留在状态中。

状态范围越大，写入权限、版本管理和冲突处理越重要。全局共享字段需要明确使用方和失效条件。

## 四、状态所有权

每个字段都要回答：

```text
谁创建？
谁可以修改？
谁可以读取？
修改后通知谁？
什么时候失效？
```

状态所有权遵循三条规则：

1. 一个事实只有一个权威来源；
2. 调用方通过明确的更新接口修改状态；
3. 同一字段的同步方向集中在一个入口。

例如，用户选择的模型和当前实际使用的模型可以分别记录：

```text
selected_model  用户最后选择的值
active_model    当前运行采用的值
```

两者产生差异时，状态中记录原因和生效条件。

## 五、状态如何更新

状态更新基于旧版本生成新版本：

```text
next_state = update(previous_state, change)
```

统一更新入口集中处理：

- 字段校验；
- 版本递增；
- 并发冲突；
- 来源和更新时间；
- 失效条件；
- 变更通知。

更新操作使用带语义的命令：

```text
set_goal(...)
confirm_fact(...)
advance_phase(...)
replace_shared_variable(...)
invalidate_fact(...)
```

带语义的更新可以在写入边界检查字段关系和业务约束，也便于追踪状态为什么发生变化。

## 六、版本、来源与有效期

状态事实需要附带最小元数据：

```text
source
confidence
confirmed_by
valid_from
valid_until
version
updated_at
```

这些字段支持四类判断：

- 内容从哪里来；
- 内容由谁确认；
- 内容现在是否有效；
- 新旧内容如何合并。

过期事实标记为失效并触发重新确认，旧版本保留变更关系，避免新旧内容静默混用。

## 七、状态存储方式

存储方式根据规模、共享范围和一致性要求选择：

| 方式 | 适用场景 | 主要特点 |
|---|---|---|
| 局部对象 | 单次调用、短任务 | 成本最低，进程结束即释放 |
| 会话 Store | 多轮交互、界面同步 | 支持订阅和局部更新 |
| 键值或文档存储 | 跨请求任务 | 读取简单，字段演化灵活 |
| 关系数据库 | 多实体、多约束状态 | 事务和查询能力强 |
| 共享状态服务 | 多进程、多执行单元 | 需要版本和并发控制 |

状态存储需要与状态所有权保持一致。存储系统负责保存和读取，业务代码负责定义字段、更新规则和失效条件。

## 八、常见状态失败

| 失败现象 | 原因 | 调整方式 |
|---|---|---|
| 不同模块保存不同事实 | 缺少唯一所有者 | 指定权威字段和同步入口 |
| 模型猜测被长期保存 | 缺少确认等级 | 区分候选、推断和确认事实 |
| 旧配置覆盖当前选择 | 缺少版本和生效条件 | 保存版本、来源和更新时间 |
| 状态不断追加导致读取膨胀 | 把过程材料当核心事实 | 只保留影响后续判断的字段 |
| 跨项目读取到错误变量 | 共享范围过大 | 增加用户、租户和项目作用域 |
| 过期事实继续影响任务 | 缺少有效期 | 失效标记和重新确认 |
| 多方同时修改产生覆盖 | 更新接口没有版本检查 | 使用版本号和冲突处理 |

## 九、状态层的验收

### 事实一致

下一轮模型能够读取已确认的目标、参数和关键结果，旧版本不会静默覆盖当前事实。

### 进度准确

状态能够说明当前阶段、已完成事项和待处理事项。

### 所有权清晰

每个关键字段都有唯一事实来源，修改路径和通知范围可以追踪。

### 版本有效

过期、冲突和推断内容带有明确标记，新旧内容可以解释。

### 规模稳定

状态不会随着每轮对话和临时输出无限增长，核心字段保持可读和可维护。

建议跟踪：

```text
状态冲突率
过期事实命中率
用户重复确认次数
状态读取规模
字段更新失败率
状态对任务完成率的影响
```

状态层的质量，取决于模型每次继续工作时能否获得一致、有效、来源明确的当前任务事实和共享变量。

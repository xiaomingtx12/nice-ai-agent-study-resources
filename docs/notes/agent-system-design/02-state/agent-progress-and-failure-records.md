# 长任务的进度与失败经验：怎样保存、恢复和复用

长任务需要两种连续性：当前执行者知道正在完成什么，接手的执行者知道哪些动作已经发生。任务结束以后，还需要判断哪些经历值得影响下一次工作。这三件事使用不同的记录，不能全部交给一段不断更新的聊天摘要。

以批量整理知识库为例，“已经处理大部分文章”能够帮助人理解进展，却不能告诉恢复程序哪些文件已经验收、哪份结果基于旧版本、哪个远端请求仍未确认。恢复要依赖明确的文件身份、版本与结果。

## 一、把目标解释、业务事实和调度状态分开

| 记录 | 主要内容 | 谁可以更新 |
| --- | --- | --- |
| 目标与进展说明 | 要完成什么、范围、里程碑、当前缺口 | 模型可以提出更新，目标变更受任务规则约束 |
| 精确业务事实 | 对象 ID、路径、版本、金额、回执及来源 | 由受控接口读取、解析与确认 |
| 调度状态 | 步骤身份、依赖、执行尝试、阻塞、验收状态 | 由调度器依据事件与检查结果推进 |

模型可以解释业务事实，提出变更，也可以建议重排步骤。解释文本不应直接改写已确认事实。例如“链接应该已经替换”不能把文件检查结果改为通过；“下一步重新提交”也不能绕过外部请求的对账。

恢复时分别读取这三类记录：目标说明帮助理解任务，业务事实确定现场，调度状态决定下一步是否具备条件。三者存在冲突时，保留冲突并核验，不能让最近生成的摘要自动获胜。

## 二、进度账围绕目标、里程碑和当前工作集组织

### 1、目标记录给长期任务提供基准

目标记录保存任务身份、目标版本、范围、限制、预算和完成证据。任务从“修复失效链接”变成“重写整个目录”时，应形成明确变更，而不是通过新增待办悄悄扩展。旧里程碑仍保留，但要标明哪些已不适用于新目标。

完成标准尽量能落到产物或外部结果。例如“指定文件全部检查，未修复项都有原因”，比“内容看起来更好”更容易判断。开放性质量仍可由人或量表审查，同时保留客观检查项。

### 2、里程碑记录已经确认的推进

每个里程碑记录对应范围、输入版本、产物引用、验收依据、完成时间和未决事项。待办勾选只表示执行者的状态提案；真正完成需要匹配的验收证据。

一个远端更新请求超时后，应保存“结果未知”及原请求身份。它既不能作为已完成里程碑，也不能被当成从未执行。外部状态确认后，再补写结果。流程恢复与副作用恢复的区别见[状态与恢复](./agent-state-architecture.md)。

### 3、当前工作集只装下一步需要的内容

当前工作集应短而具体：正在处理的对象、最新有效结论、待验证假设、下一步动作及理由、阻塞项和可展开引用。历史全文放在持久记录里，必要时回查。

压缩工作集时，保留结论强度。“候选替代页面，尚未验证内容”不能压成“替代页面已找到”。也要保留下一步理由，否则接手者只看到一个动作名，容易重复已经走过的路径。

## 三、用状态变化判断是否真的有进展

任务运行次数、输出长度和计划版本数都只能描述活动量。判断进展，要看是否新增有效证据、完成一个验收项、消除一个阻塞，或缩小一项未决问题。

例如搜索词连续变化，返回的却是相同页面，而且没有新增核验结果，属于无证据增量。此时应改查其他来源、缩小问题或停止；再生成一份更长的计划并不能改变现场。

恢复入口需要核对目标版本和当前资源。文件已被其他人修改时，旧检查结果只证明旧版本通过，应重新核验受影响部分。已经确认的外部效果则保留历史身份，通过新动作修正，不能删除旧记录后重新解释成“尚未开始”。

## 四、失败日记把事实与教训分成两层

错误日志记录一次事件，失败日记则连接“发生了什么”和“类似任务下次应检查什么”。为了避免把猜测变成长期规则，两层内容要分开保存。

| 层次 | 应保留的内容 | 示例 |
| --- | --- | --- |
| 失败事实 | 任务、版本、症状、预期与实际、工具结果、外部效果、证据位置 | 链接检查只验证了状态码，替代页内容与原主题不符 |
| 候选教训 | 适用条件、建议检查、例外、证据、验证状态 | 替换知识链接时，除可访问性外还要核对主题与适用版本 |

根因尚未查明时，事实层直接保留“未知”。时间上相邻的两个动作不自动构成因果关系；一次成功重试也不能证明某个无关步骤是必要条件。

候选教训在进入正式召回前，需要检查是否过度概括、是否混入当前对象的临时值、是否与现行规则冲突。比如“文件 A 的新地址是 B”属于带版本的对象事实，“替换前核对标题和内容范围”才可能成为跨任务方法。

## 五、经验要在相关动作前被召回

把失败存下来以后，还要选择使用位置。任务启动时可召回任务族的常见缺口；规划时可召回流程陷阱；执行相关工具之前，可提示该工具与对象的已知失败条件。

召回先按租户、权限、环境、工具和有效期过滤，再判断语义相关性。当前任务只加载必要教训与证据引用；完整轨迹留待追查。旧经验可以提醒查什么，当前对象的值仍由权威接口提供。

需要把三类事件分别记账：

- **召回：** 哪条经验进入了哪次输入，依据什么条件。
- **采用：** 哪个计划或动作使用了这条建议，有无可观察的对应检查。
- **结果：** 独立验收发现了什么，是否避免了原类错误，付出了多少额外成本。

同一任务加载五条经验并最终成功，不能给五条经验都记一次有效。采用记录可以说明相关性；要判断收益，仍需在隔离评测中比较有无该经验或不同版本的结果。线上成功受其他条件影响，只能提供有限证据。

## 六、经过验证的经验有不同去向

经验库负责保留待检验的方法，不必永久承担所有知识。

| 已确认的内容 | 更合适的去向 |
| --- | --- |
| 可检查的前置条件，例如对象版本必须匹配 | 执行器或确定性守卫 |
| 稳定的多步做法，有激活条件和验收办法 | 版本化 Skill |
| 可查询的业务事实，有更新和引用要求 | 知识库或业务接口 |
| 只适用于某个项目的长期约束 | 项目规则 |
| 已失效、无收益或造成误导的教训 | 撤回或归档，保留历史依据 |

比如“执行前检查目标文件版本”一旦可以程序化，就应由提交入口保证。让模型每次从失败日记里想起它，会留下绕过空间。转成硬规则以后，仍需验证误拦、兼容性与正常任务效果。

验证进度与经验体系时，可以安排一次中断恢复、一项过期事实和一条错误教训：恢复后不得重做已确认效果；过期事实不得覆盖当前值；错误教训应能被拒绝或撤回。重复失败率按同类任务的暴露次数计算，不能因为任务量减少就认定系统学会了。

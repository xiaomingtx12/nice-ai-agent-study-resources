# 意图识别篇

意图识别是 Agent 入口分路的关键。读这篇之前你应该已经了解 Agent 大脑（详见 [Agent 大脑篇](./agent-brain.md)）——本篇聚焦入口分路、分类粒度设计、模糊 query 兜底、路由分发。

意图识别是"入口"，解决"用户说的是哪类问题、要哪些参数、信不信"。大脑是"中枢"，解决"拿到意图后怎么一步步办完"。两者边界详见 [易混淆的两个工程技巧](./index.md)。

工程化的核心拉扯：语义模糊 ↔ 分类粒度。粒度太粗（粗分类到任务）路由错误，工具选错；粒度太细（细分类到动作）维护成本爆炸，边界模糊。

本篇按"工程化背景 → 最基本问题 → 演化叠加复杂度"展开：

- **§三 基本做法**：从最朴素的"调一次大模型"出发，定义意图识别是什么、什么时候做、为什么必须有
- **§四 分类粒度**：粒度由路由需要决定，不是由"语义精确"决定
- **§五 模糊 query 与兜底**：按代价风险分流、双出口（拒识/澄清）、可量化问题
- **§六 多轮意图累积**：指代消解、上下文继承、跨轮评估信号、词汇表机制
- **§七 Slot Filling 与约束**：参数抽取 + 软硬约束贯穿对话
- **§八 三层意图识别架构**：单次 LLM 撑不住时怎么叠加重型与轻量
- **§九 意图识别层的位置**：独立层优于塞进大脑循环
- **§十 评测体系**：指标 + 测试集 + 准确率目标值的选取
- **§十一 降级路径**：崩溃 / 超时 / 置信度过低时怎么办
- **§十二 与权限的配合**：按意图路由最小工具白名单

> 与 [Context 篇](./agent-context-management.md) 的边界：Context 篇展开"每轮上下文怎么装 / 跨 session 记忆怎么管"；本篇展开"用户输入规范化作为意图识别的前置环节"以及"指代消解 / 关键事实累积"的工程化做法。

## 一、动机

意图识别不是必须有的层。简单任务可以让大脑直接吃 query，复杂任务才需要单独建层。

本篇聚焦：
- 什么时候该单独建意图识别层
- 分类粒度怎么定
- 模糊 query 怎么兜底
- 多轮意图怎么累积
- 意图识别与权限怎么配合

### 为什么需要有这一层

很多系统在回答意图识别时只有一句话："我们就是调用一次大模型，让大模型判断用户意图。"这种回答毫无工程化特色。一旦评审或追问展开："大模型判断错了怎么办？候选意图很多怎么办？用户输入很模糊怎么办？用户少说了参数怎么办？怎么评估意图识别准不准？"——整套设计就暴露缺口。

站在工程化视角，意图识别至少承担三件事：

1. **决定后续加载哪一套业务规范（Prompt / Spec）**。电商售前和售后两套流程的思考点完全不同，意图不同则 Prompt 不同。
2. **决定上下文窗口里装什么、不装什么**。售前塞用户画像和商品偏好，售后塞订单和退款记录，混搭就是浪费窗口。
3. **决定工具选择**。商品推荐调商品检索工具，订单查询调订单系统，退款申请调售后系统。意图错了工具调用大概率也会错。

借用一句话总结：**意图识别不是为了给用户输入贴标签，而是为了决定 Agent 后面应该怎么想、加载什么上下文、调用什么工具、进入哪个业务流程。**

### 与"用户输入规范化"的边界

意图识别前还有一道前置工序：**用户输入规范化（User Input Normalization）**——把用户的口语化、跳跃、代词、病句、黑话处理成结构化表达。两件事的边界：

| 工序 | 输入 | 输出 | 时机 |
|---|---|---|---|
| 用户输入规范化 | 原始 query + 历史 | 指代消解后的完整 query | 每次 query 进入时 |
| 意图识别 | 规范化后的 query | intent + slots + confidence | 规范化之后 |

两件事可以合二为一（小型 / 领域专属 Agent），也可以拆开（通用 / ToC Agent）。但合并时**必须给规范化层画职责边界**——让它"只做规范化，不做意图识别；不执行工具；不直接回答用户问题；不擅自补充事实"，否则大模型会"过于自主"地把后续活也抢了。

## 二、关键判断速览

- 路由决策复杂度 > 3 个分支才建意图识别层，否则大脑直接吃 query
- 分类粒度按路由需要决定，粗分类起步按需细化
- 分类标签互斥优先，可重叠次之，层级最复杂，默认互斥起步
- 模糊 query 按代价风险分流，高风险反问 + 转人工，低风险默认分支
- 多轮意图累积 = 槽位填充 + 指代消解 + 上下文继承
- 默认 LLM 单次分类，高频简单意图可缓存；表达复杂 / 强依赖上下文 / 多意图时才升级到三层架构
- 意图识别层独立于大脑循环，不塞进每轮循环
- 意图识别失败让大脑兜底，不直接拒答
- Slot Filling 必填项缺失必须反问，不"先猜再答"
- 软硬约束分开抽取，约束贯穿本轮对话影响后续推理
- 离线评估集 + 在线分布监控 + 边界 case 专项三类评测
- 跨轮评估：上一轮是否识别错，下一轮的"我不是这个意思"就是评估信号
- 按意图路由最小工具白名单，与权限配合
- "有性价比"这种主观形容词必须显式可量化，不能粗暴解释成"价格低"
- 黑话 / 缩写 / 行业术语用迭代式词汇表沉淀，不靠每次提示词里塞

## 三、什么时候建意图识别层

| 系统复杂度 | 是否建层 |
|---|---|
| 简单任务（单一工具 / 单一知识库） | 不建，大脑直接吃 query |
| 中等复杂（多工具 / 多知识库 / 不同意图走不同路径） | 建一个轻量意图识别层 |
| 高复杂度（多业务线 / 跨系统 / 跨 Agent 派发） | 建意图识别层 + 子 Agent 路由 |

不建意图识别层的代价：路由决策分散在大脑里，每次都要重新判断，浪费 token。

建层的代价：每次查询多一次 LLM 调用（成本 + 延迟）。但大多数意图都是明确的（电商场景下 80% 都是商品推荐），用轻量模型识别一次的速度远低于让大脑多跑一轮推理的代价。

### 意图识别承担的三件事

意图识别不只为"贴标签"，更承担三件事：

| 作用 | 说明 |
|---|---|
| 决定业务规范 | 不同意图加载不同 Prompt / Spec |
| 决定上下文 | 不同意图窗口里装不同内容 |
| 决定工具 | 不同意图暴露不同工具集 |

最极端的形态是意图识别后**分发到不同的"子 Agent"**——子意图内部可进一步做子意图识别、再分发。这种递归分发适合业务线多且每线动作复杂的场景。

## 四、分类粒度设计

### 粗分类 vs 细分类

| 粒度 | 适用 | 例子 |
|---|---|---|
| 粗分类（任务级） | 不同任务走不同大流程 | 客服 / 技术支持 / 销售 |
| 细分类（动作级） | 同一任务内的不同动作走不同工具 | 查订单 / 改地址 / 退款 |

粒度由"路由需要"决定，不是由"语义精确"决定。分类标签数 ≤ 10 个优先粗分类，> 10 个用层级分类（粗 + 细两层）。

### 标签关系

| 设计 | 适用 | 代价 |
|---|---|---|
| 互斥（一对一） | 默认起步 | 实现简单，丢失"多意图组合" |
| 可重叠（一对多） | 多意图组合 query > 20% | 按置信度排序执行 |
| 层级分类（粗 → 细） | 业务线多 + 每线动作多 | 维护成本高 |

互斥是默认起点，必要时升级到可重叠或层级。上来就用可重叠 + 层级组合，维护成本爆炸。

### 候选意图必须显式定义

提示词中最容易踩的坑是只写"请判断用户意图"，然后让模型自由发挥。意图识别提示词的核心是让模型**在一个受控的业务意图空间里完成分类和结构化输出**——用人话来说就是给定几个选项让大模型输出。

候选意图的撰写要点：

1. **定义候选意图**：明确告诉模型当前系统支持哪些意图，**不要让模型自己发明意图，不允许无中生有**。可在意图识别后用代码校验兜底。
2. **定义意图边界**：意图名称之间容易混淆时（比如 `product_recommendation` / `product_comparison` / `product_query`），必须用正反例子明确边界。

```text
当用户希望系统根据预算、用途、偏好推荐一个或多个商品时，选择 product_recommendation。

当用户明确提到两个或多个商品、品牌或型号，并希望比较优劣或做选择时，选择 product_comparison。

当用户只是询问某个商品、品牌、型号、参数、价格、库存等信息时，选择 product_query。
```

3. **加入 few-shot**：覆盖容易混淆的边界。意图特别容易混的，正反两方面的例子都要给。
4. **意图特别多时用层级意图 / 决策树**：把全部意图塞提示词会撞窗口，分层识别是工程化做法。

## 五、模糊 query 与兜底

### 按代价和风险分流

| 意图风险 | 处理方式 |
|---|---|
| 低风险 + 低成本（信息查询） | 默认分支兜底（"我没太懂，请再说一遍"） |
| 高风险（付款 / 删除 / 权限变更） | 反问用户确认 + 必要时转人工 |
| 多次反问仍模糊 | 转人工兜底 |

不能假装识别对了。置信度 < 阈值必须显式标记，让大脑知道"这是兜底"。

### 双出口：拒识 vs 澄清

不要什么输入都强行识别到某个业务意图上。真实的输入经常是不完整、不清楚、超出能力范围的，必须给两个出口：

- **unsupported（拒识）**：意图完全不在候选意图中，超出系统能力范围。例：用户问"帮我生成一个奥特曼动画"，而当前是电商 Agent。
- **unclear（澄清）**：意图之间有混淆，或者参数不够。例：用户说"帮我推荐一条裤子"，缺价格。

澄清的写法（示例）：

```json
{
  "intent": "product_recommendation",
  "slots": { "category": "衣服" },
  "missing_slots": ["price"],
  "need_clarification": true,
  "clarification_question": "你想让我推荐多少钱的商品呢？"
}
```

澄清优先于猜测。**好的回答比快的回答用户体验更好**——不要急着"先猜再答"。

### 可量化：主观形容词的处理

形容词、极值、主观判断词（"有性价比""更高级""最划算"）是 Agent 经常翻车的地方。一看到"性价比高"就粗暴理解成"价格低"，忽略质量 / 性能 / 品牌 / 售后，是用户觉得"Agent 很蠢"的重要原因。

可量化处理的关键点：

1. **形容词必须在 Prompt 里详细描述如何判定**。例如"性价比"在电商场景下应优先围绕"同等价格下，质量 / 配置 / 服务或体验更好"展开，而不是"价格低"。
2. **落地到工具参数**。"有性价比的牛仔裤" → 第二轮调用推荐商品工具时，价格限定为 [150, 200]，作为硬约束传入。
3. **词汇多了就上词汇表**。如果有很多这种需要告知大模型如何解释的词，整合到 §六 的词汇表机制里。

可量化的反面例：用户说"再高级一点"，Agent 直接调出更贵的方案，但"高级"在用户语境里可能指材质 / 工艺 / 设计，不一定指价格。

### 典型例子：主语缺失

为了感受输入规范性 / 兜底处理不当的弊端，看一个真实例子：

> 用户问 1：良信互联这家公司产品如何？
>
> 用户问 2：全屋智能市场占有率如何？

用户在问 2 时其实想表达的是"良信互联的全屋智能市场占有率如何"——主语缺失。而 Agent 把问 2 当成"整个市场的占有率"理解，且没有结合上下文告诉用户良信互联的市占率数据。这是**主语缺失 + 上下文召回失败**的典型案例。

## 六、多轮意图累积

### 三件套

| 组件 | 作用 |
|---|---|---|
| 槽位填充 | 每个意图需要的关键参数（订单号 / 地址 / 退款原因）从历史累积 |
| 指代消解 | 把"改成新地址"中的"新"解析为上下文提到的地址 |
| 上下文继承 | 分类器要把历史 query 一起喂进去，不只是当前 query |

工程化要点：槽位填充满才能执行动作；缺关键槽位必须反问。

### 指代消解的工程做法

指代消解不能只靠模型自由发挥，需要结构化约束：

| 做法 | 说明 |
|---|---|
| 输出指代消解表 | Prompt 要求最终输出"代词 / 代称 → 实体"映射表 |
| 关键事实贯穿全流程 | 指代消解结果作为本轮对话的关键事实，影响后续轮 |
| 命名要稳定 | Agent 输出"方案一"用户后续用"方案一"引用，输出"TCC 方案"用户用"TCC 方案"引用；按名索引能规避大模型引用错误 |
| 低置信度不瞎猜 | 推断不出来人 / 物 / 地点时，触发澄清机制，不要强行猜 |

### 深度结合上下文的三件套

简单指代（"刚才那个项目"）可以靠短期记忆 + 当前 query 解决；复杂指代要靠更深的上下文工程：

| 维度 | 工程做法 |
|---|---|
| 用户画像 | 用户反复讨论《三国演义》电视剧 → 后续《三国演义》应优先解释为电视剧 |
| 关键事实 | 用户喜好 / 观点 / 态度 / 前几轮已被认可的要点 |
| 对话历史召回 | 跨多 session 的指代要靠召回，召回后用大模型基于召回内容做二次推断 |

跨 session 的指代（"你上次推荐的那个看樱花的地方"）有两层难点：

1. **时间跨度长**：短期记忆没了，session 之间穿插大量对话，召回困难。
2. **属性指代**：比"这个""那个"还多一层属性匹配（"看樱花的"是属性，"鸡鸣寺"是实体）。

工程化做法是两步 + 一道补偿：

```
步骤 1：根据用户输入去历史对话召回细节（"樱花、旅游"）
步骤 2：大模型基于召回内容推断，完成指代消解（"看樱花的那个地方" → "鸡鸣寺"）
补偿：大模型基于属性推断失败 → 提取相关属性作为参数发起工具调用 → 大模型再次基于历史对话细节推理
```

### 行业 / 领域词汇表机制

同样的词在不同行业、领域、上下文里有不同含义：

- CRM：IT 行业 = Customer Relationship Management；医疗行业 = Clinical Research Management
- 抓手 / 不够 P8：阿里系黑话
- RAG / 检索增强 / 知识库：同一概念的不同叫法

最朴素的做法是在 Prompt 里带行业信息和强调结合行业解释。更工程化的做法是**自迭代演进的词汇表**：

| 组件 | 说明 |
|---|---|
| 存储 | MySQL 或向量数据库 |
| 触发时机 | 输入规范化处理之前检索，检索结果注入窗口 |
| 公共 vs 个人 | 公共词汇表 + 用户个人词汇表两层 |
| 沉淀路径 | 离线分析多轮对话 → 标记疑似词汇 → 记录次数和含义 → 频繁出现则升级放入词汇表 |

升级阈值举例（系统设计文档里可以展开成更详细的判定逻辑）：

- 总次数 > 100
- 讨论的人数 > 3（升级为公共词汇）
- 连续讨论 10 次

词汇表的核心目的是把"每次都要 Prompt 里提醒"变成"系统自动检索注入"——避免每次写新场景都要改 Prompt。

### 跨轮评估信号

意图识别效果可以在下一轮对话被隐式评估：

- 用户输入"不是，我不是这个意思" → 上一轮意图识别失败
- 用户输入"你理解错了" → 上一轮意图识别失败

可以在下一轮对话开始时**先评估上一轮意图识别是否准确**，而不是只看当前轮的 Top-K Accuracy。

## 七、Slot Filling 与约束

### 意图识别 = 分类 + 参数抽取

意图识别的输出是两件事：

1. **intent classification**：用户要进入哪个业务流程（枚举值）
2. **slot filling**：该流程需要哪些关键参数

举例：用户说"帮我推荐一台笔记本，主要是写代码，最好轻一点"：

```json
{
  "intent": "product_recommendation",
  "slots": {
    "category": "笔记本电脑",
    "usage_scenario": "写代码",
    "soft_preferences": ["轻一点"]
  },
  "missing_slots": ["budget_max"],
  "need_clarification": false
}
```

字段约定：

- `slots` 已抽取出的参数
- `missing_slots` 还缺的参数（用于决定是否触发澄清）
- `need_clarification` 是否需要反问
- `clarification_question` 反问的具体问题

### 通用参数 schema

除了业务专属参数，还可以预设一组通用参数让模型抽取：

| 参数 | 含义 |
|---|---|
| `must_have_features` | 必须满足的特性 |
| `nice_to_have_features` | 加分项 |
| `hard_constraints` | 硬约束 |
| `soft_preferences` | 软偏好 |

国内大模型在这一块普遍做得不好——用户明确说不要推荐某品牌，结果还是推荐了，根本原因是这些通用参数没被识别和注入。

### 软硬约束的工程化做法

| 约束类型 | 含义 | 处理 |
|---|---|---|
| 硬约束 | 模型无论如何都要满足 | 强校验，违反则重试或拒绝执行 |
| 软约束 | 模型要努力满足，必要时可放弃 | 没满足时明确告知用户 |

工程化要点：

1. **约束贯穿本轮对话**——不要在第二轮就忘了第一轮的硬约束（"不要修改 A 接口"）
2. **违反硬约束要重试或拒绝**——而不是默认放过
3. **没满足软约束要显式告知**——提升用户体验而不是默默吞掉

举例：用户输入"帮我推荐一条裤子，不超过 100 块，最好是牛仔裤"：

```json
{
  "intent": "product_recommendation",
  "category": "服装",
  "hard_constraints": ["price < 100"],
  "soft_constraints": ["type = 牛仔裤"],
  "missing_slots": ["subcategory"]
}
```

### 在 ReAct 循环中补全槽位

Slot Filling 不一定要在第一轮就做完。高级做法是**在 ReAct / TAO 循环中补全所有槽位**：

```
第一轮：识别出 intent 和部分 slots，missing_slots 不空
第二轮 / 第三轮：进入 ReAct 循环，借助工具调用、历史检索补全剩余 slots
最后一轮：missing_slots 为空，启动业务流程
```

这种形态下意图识别不仅是找出枚举值，还要"找全所有参数"。

## 八、三层意图识别架构

单次 LLM 调用撑不住复杂场景（表达复杂、强依赖上下文、多轮意图切换、多意图输入），需要**三层意图识别机制**：

| 层 | 实现 | 适用 | 特点 |
|---|---|---|---|
| 第一层 | 代码层（关键字 / 正则 / 规则引擎 / 按钮引导） | "继续""下一步"等强规则输入 | 快、准、便宜、稳定 |
| 第二层 | 轻量级 LLM（Flash / Mini） | 不需要深度推理的常规输入 | 快、省 |
| 第三层 | 深度推理 LLM | 表达复杂 / 强依赖上下文 / 多轮意图切换 / 多意图 | 慢、贵、准 |

调用顺序：第一层没识别出来 → 第二层；第二层没识别出来 → 第三层。

### 第一层：代码层

包括但不限于：

- **页面引导**：用户点击"下一步"按钮，直接跳到下一步意图
- **关键字提取 / 正则匹配**：用户输入"继续"→ 延续上一个意图
- **规则引擎**：用户输入符合某规则 → 直接归类
- **状态机**：上下文中的状态符合某规则 → 直接归类

特点：快、准、便宜、稳定。日常的"继续""下一步"用这一层效果奇好。

### 第二层 vs 第三层：为什么不跳过第二层直接用深度模型

大多数时候用户的输入和意图都是非常明确的，轻量级模型就能高准确率 + 快速响应。跳过第二层直接上深度模型只会让"明确的输入"白白多花时间。

实际中常见的误区是纠结意图识别的性能，**效果 > 效率**——用户能接受多等几秒得到一个好结果，但不能接受快了几秒收到一个坏结果。

### 第二层的置信度分档

第二层怎么才算"没识别出来"？常规解法是**让模型输出置信度**，按分档走不同路径：

```json
{ "intent": "product_recommendation", "confidence": 0.87 }
```

| 置信度区间 | 处理 |
|---|---|
| > 0.85 | 直接接受 |
| 0.60 ~ 0.85 | 进入仲裁或澄清 |
| < 0.60 | 交给下一层深度推理模型 |

阈值不是拍脑袋定的，要根据测试集和线上效果调出来。

**注意**：大模型输出的 confidence 不一定是真正的概率，更像一个"自我判断分数"。实践中最好结合规则命中、向量相似度、历史准确率等信号一起判断。

## 九、意图识别层的位置

| 位置 | 优劣 |
|---|---|
| 独立层（在 query 解析后、改写前） | 意图分类一次，结果喂给大脑；省 token，省延迟 |
| 塞进大脑循环（每轮重新识别） | 每轮重新识别浪费 token；让大脑在"意图"和"行动"之间混乱 |
| 完全去掉 | 简单任务可以，路由决策复杂度高时需要 |

独立层优于塞进大脑循环。

但意图识别**不一定全在入口完成**——复杂场景的某些处理要放到 ReAct 循环里：

| 时机 | 适用 |
|---|---|
| 入口（在 ReAct 之前） | 通用 Agent / ToC Agent / 大多数场景；推荐独立 |
| 和意图识别合并 | 用户不多、领域专属的 Agent；输入比较规范 |
| 在 ReAct 循环中 | 涉及严重依赖上下文 / 工具调用的形容词 / 复杂属性指代 |

实际中 1 和 2 可以结合——入口先初步处理，循环里再做深度处理。

## 十、评测体系

### 基础指标：Top-K Accuracy

| 指标 | 含义 |
|---|---|
| Top-1 Accuracy | 系统输出的第一个意图是否就是标准答案 |
| Top-3 Accuracy | 标准答案是否在前 3 个候选意图里 |

实践中主要看 Top-1，只在特殊业务里看 Top-K。

### 分意图准确率

假设系统 80% 请求都是商品推荐，模型全部猜商品推荐也可能有不错整体准确率，但退款、投诉、订单查询这些**低频但重要**的意图可能识别得很差。

做法：拆开看每个意图的准确率，对低频高风险意图重点盯。

### 拒识与澄清指标

| 指标 | 含义 |
|---|---|
| 拒识准确率 | 应该拒识的时候系统是否拒识 |
| 误拒率 | 本来能处理却被错误拒识 |
| 漏拒率 | 本来应该拒识却被强行归类 |
| 澄清触发准确率 | 缺关键信息时是否正确追问 |
| 澄清后收敛率 | 追问之后用户任务是否顺利推进 |

意图识别不永远追求"猜中"，拒识或追问在很多场景是更优解。

### Slot Filling 指标

| 指标 | 含义 |
|---|---|
| 槽位准确率 | 抽出来的槽位值是否正确 |
| 槽位召回率 | 用户提供的信息有没有被抽出来 |
| 必填槽位完整率 | 启动流程必须的槽位是否齐备 |
| 槽位更新准确率 | 多轮对话中新信息是否正确覆盖旧信息 |
| **约束识别准确率** | 硬约束和软偏好是否识别正确（当下 Agent 普遍最差） |

约束识别准确率低是 Agent 翻车的核心原因——用户明确说"不要修改 A 接口"结果改了，怒气值爆表。

### 跨轮评估信号

下一轮对话开头可以用上一轮的隐式反馈评估：

- 用户说"不是，我不是这个意思" → 上一轮意图识别失败
- 用户说"你理解错了" → 上一轮意图识别失败

用这些信号构建**上一轮评估器**，比单纯离线评估更能反映真实用户体验。

### 测试集设计

设计测试集时覆盖的场景：

| 场景 | 必选 |
|---|---|
| 标准表达 | 用户明确说出系统支持的意图，测基础识别能力 |
| 口语化表达 | 病句 / 缺省 / 指代，结合用户输入规范化一起测 |
| 槽位缺失输入 | 用户输入中少了一部分参数 |
| 拒识 | 会被意图识别明确拒绝的输入 |
| 容易混淆的样本 | 两个相近输入但意图差别大 |
| 跨轮补充 | 多轮合并才能得出所有参数值 |
| 识别约束 | 带硬约束 / 软约束的输入 |
| 意图切换 | 多轮里从一个意图跳到另一个意图 |
| 多意图输入 | 用户一次性想干多件事 |

传统软件工程的测试用例设计技巧一样可以用在这里。

### 准确率目标值：多少算合理

设计意图识别层时，目标准确率定多少是常见争论。给出几个参考区间：

| Agent 类型 | 准确率参考 |
|---|---|
| 专属领域（输入规范、意图数少） | ≥ 99% |
| 通用 Agent | Top-1 80%-90%（声称更高的水分大） |

不管报多高都可能被质疑太高或太低，关键是**为两种情况都准备好解释口径**：

- **数字偏高**：解释为"Agent 是专属领域，候选意图就那么几个"+"用户输入比较规范，没有五花八门的口语"。这两点是支撑高准确率的必要条件，缺一个都站不住脚。
- **数字偏低**：解释为"意图识别做得比较简单，目前是 LLM 单次分类 + 关键词兜底"，然后讲下一步优化方向（三层架构 / Slot Filling / 跨轮评估 / 词汇表沉淀）。承认问题 + 给出改进路径比硬撑可信。

## 十一、降级路径

意图识别层崩溃 / 超时 / 置信度过低时怎么办？

1. 让 Agent 大脑兜底，不要直接拒答
2. 大脑收到"意图未知"标记后，尝试理解 + 执行
3. 执行失败再走人工

拒答太硬：用户问"查订单"，意图识别失败拒答，体验极差。意图识别是辅助层不是必需层，没有意图识别大脑也能工作。

Dify 的实现参考：question-classifier 节点支持设置默认分支，置信度低时直接走兜底分支（默认节点）；分类器失败时静默跳过走通用 LLM 节点。

## 十二、与权限的配合

### 按意图路由工具集

| 意图 | 暴露的工具 |
|---|---|
| 查订单 | 订单查询 API |
| 退款申请 | 退款 API + 订单查询 API |
| 投诉 | 工单 API + 订单查询 API |

每个意图对应一个最小工具集。高敏感工具（删 / 改）只在特定意图下暴露。

### 工程化要点

- 过滤时机：意图识别后、schema 注入 LLM 前（不要等 LLM 选了再拒绝）
- 减少 LLM 选错工具的可能
- 提升 Prompt Cache 命中（不同意图的 schema 不同）

详见 [Tool 篇 §用户可见的权限](./agent-tool-calling.md)。

## 十三、何时不该用

意图识别是辅助层不是必需层，**以下场景要慎重**：

| 场景 | 处理 |
|---|---|
| 单一工具 / 单一知识库 | 不建意图识别层，大脑直接吃 query |
| 路由决策 < 3 个分支 | 不建意图识别层 |
| 上来就用可重叠 + 层级组合 | 维护成本爆炸，回退到互斥起步 |
| 上来就用规则覆盖全部 | 覆盖不全，回退到 LLM 单次分类 |
| Embedding 单一策略 | 语义模糊时不靠谱，回退到 LLM |
| 把意图识别塞进大脑每轮循环 | 浪费 token，意图识别层独立 |
| 意图识别失败就拒答 | 让大脑兜底 |

判断标准：**意图识别层存在是为了让后续决策更准**，不是为了存在而存在。如果建层后没有显著提升（路由更准 / 工具选择更准 / 上下文更聚焦），那这一层就该撤掉。

## 十四、反模式

### 阶段判断

- 简单任务硬建意图识别层，大脑直接吃 query 更省 token
- 上来就用可重叠 + 层级组合，维护成本爆炸
- 上来就用规则覆盖全部，覆盖不全

### 标签设计

- 分类标签没有下游路由，分完不知道干嘛
- 标签互不覆盖，留空白区
- 标签粒度追求"语义精确"，粒度由路由需要决定
- 可重叠占比 < 20% 还硬上
- 让模型自己发明意图，不给候选清单

### 模糊 query

- 置信度低假装识别对了，大脑基于错误意图执行产生幻觉
- 高风险意图走默认分支，猜错了代价不可逆
- 拒答代替兜底
- 没有置信度阈值
- 缺关键参数也强行执行动作
- 主观形容词粗暴解释（"性价比" → "价格低"）

### 多轮意图

- 每轮独立分类丢掉历史
- 只填当前 query 不填历史
- 缺关键槽位也执行动作
- 不做指代消解
- 指代消解结果不贯穿后续轮
- 跨 session 指代靠短期记忆硬撑（应该走召回 + 二次推断）

### Slot Filling / 约束

- 不抽通用参数（must_have / nice_to_have / hard_constraints / soft_preferences）
- 软硬约束混在一起不加区分
- 第二轮就忘了第一轮的硬约束（约束不贯穿全流程）
- 违反硬约束默默放过
- 软约束没满足也不告知用户

### 实现方式

- Embedding 单一策略，语义模糊时不靠谱
- 塞进大脑循环浪费 token
- 三层架构里跳过第二层直接用深度模型（响应慢且大多数输入不需要深度）
- 置信度只看模型输出不结合规则命中 / 历史准确率

### 评测

- 只用离线评估集，在线分布漂移无人发现
- 不覆盖边界 case
- 没有跨意图组合评测
- 不分意图看准确率（高频意图掩盖低频高风险意图的问题）
- 漏掉跨轮评估信号
- 报准确率时不能解释"为什么这么高"或"为什么这么低"

### 与权限配合

- 所有意图暴露所有工具，违反最小权限原则
- 过滤在 LLM 选择之后，浪费一次循环
- 高敏感工具在所有意图下可见

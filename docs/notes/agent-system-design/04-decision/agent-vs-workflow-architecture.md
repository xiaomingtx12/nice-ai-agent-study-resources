# Workflow 与 Agent Loop：把控制权放在合适的位置

> Workflow 与 Agent Loop 的核心区别，不在于有没有使用模型，而在于下一步由谁决定：代码负责固定路径，模型负责依赖现场信息的局部判断。

很多任务同时包含两种步骤：

- 顺序、条件和验收规则可以提前确定；
- 下一步需要根据用户输入、工具结果或外部变化临时判断。

把所有步骤都写成 Workflow，会让变化被硬编码成脆弱分支；把所有步骤都交给 Agent Loop，则会损失可预测性、审计能力和成本控制。工程设计要先找出不确定性出现的位置，再把模型放进最窄的决策节点。

## 三种控制形态

| 形态 | 下一步主要由谁决定 | 适合的任务 |
| --- | --- | --- |
| Workflow | 代码和预定义规则 | 顺序固定、规则稳定、结果需要严格审计 |
| Agent Loop | 模型根据观察结果决定 | 路径无法提前枚举、需要探索和调整 |
| 混合编排 | 代码控制外框，模型负责局部节点 | 主流程稳定，局部存在语义不确定性 |

混合编排通常是生产系统的默认选择：

```text
固定入口
→ 数据准备
→ Agent 判断节点
→ 固定动作或分支
→ 结果验证
→ 固定出口
```

模型只在真正需要判断的节点获得决策权，流程的预算、失败出口和终态仍由代码掌握。

## 先定位任务中的不确定性

将任务拆成步骤后，逐项判断：

| 步骤特征 | 控制方式 |
| --- | --- |
| 输入格式校验、字段转换、固定计算 | Workflow |
| 顺序固定但可能重试 | Workflow + 明确重试策略 |
| 从多个已知分支中选择 | Router 或条件节点 |
| 需要理解自然语言、判断意图或评估证据 | Agent 节点 |
| 根据现场结果选择未知的下一步 | Agent Loop |
| 结果必须满足固定规则 | Workflow 验收节点 |
| 任务需要多个独立角色共同完成 | 进入多 Agent 协作设计 |

划分依据是“下一步是否依赖无法提前枚举的观察结果”，不是“这一步能不能调用模型”。

## Workflow 负责固定什么

Workflow 适合承载可以明确表达的控制规则：

- 节点顺序和分支条件；
- 必经的校验、审批和结果检查；
- 重试次数、超时和取消出口；
- 并行任务的汇合条件；
- 失败如何传播到上游；
- 哪些节点可以重复，哪些动作只能执行一次；
- 任务达到什么终态才算完成。

这些规则放在代码或声明式流程中，能够获得稳定的执行顺序、可回放记录和明确的失败位置。

## Agent Loop 负责判断什么

Agent 节点适合处理语义和现场信息：

- 从用户目标中识别当前要解决的问题；
- 在多个工具或策略中选择下一步；
- 根据观察结果调整假设；
- 生成计划或重新规划剩余步骤；
- 判断证据是否足以形成回答；
- 发现信息不足并提出澄清问题。

Agent 节点不应拥有无限范围。它需要明确输入范围、可见能力、输出格式、预算和退出条件，输出经过运行时检查后才能进入下一个 Workflow 节点。

## Agent 节点的窄合同

一个可控的 Agent 节点至少要定义：

| 合同字段 | 说明 |
| --- | --- |
| 输入范围 | 模型可以读取哪些任务事实和证据 |
| 决策目标 | 这一节点需要做出什么判断 |
| 可用能力 | 可以调用哪些工具或产生哪些动作 |
| 输出格式 | 下一节点可以直接消费的结构化结果 |
| 预算 | 模型调用、工具调用、Token 和时间限制 |
| 失败出口 | 信息不足、判断失败、权限拒绝和超时如何处理 |
| 完成条件 | 什么结果允许离开该节点 |

例如“选择资料来源”的 Agent 节点只负责判断需要哪些来源并输出来源选择，不应顺便修改文件、发布结果或自行宣布整个任务完成。

## 常见混合结构

### 固定流程中的局部判断

```text
接收请求
→ Workflow 校验输入
→ Agent 判断请求类型
→ Workflow 路由到固定处理链
→ Workflow 验证输出
```

模型负责语义分类，代码负责真正的分支和后续执行。

### 固定流程中的探索循环

```text
准备任务
→ Agent Loop 探索与行动
→ Workflow 检查阶段目标
→ 未达成：回到 Agent Loop
→ 达成：进入固定收尾
```

循环只能在预先划定的范围内运行。阶段目标、预算和终止条件由外层流程控制。

### 多个模型节点的顺序连接

```text
研究节点
→ Workflow 校验研究结果
→ 生成节点
→ Workflow 执行格式和事实检查
→ 输出
```

每个 Agent 节点只交付下一节点需要的结果，不把完整对话历史作为默认输入。

## Workflow 与 Agent 的失败边界

不同失败需要回到不同层处理：

| 失败类型 | 更合适的处理 |
| --- | --- |
| 输入格式错误 | Workflow 拒绝或要求补充 |
| 固定节点执行失败 | 按节点策略重试或终止 |
| Agent 参数选择错误 | 修正当前决策后重试 |
| Agent 的假设不成立 | 让 Agent 重新规划 |
| 节点输出不符合合同 | 运行时拦截，不交给下游 |
| 全局目标已经变化 | 返回入口重新建立任务 |
| 终态校验失败 | 进入修复节点或明确失败出口 |

所有失败都交给模型重试，会让流程失去边界；所有失败都由代码硬编码，也会把需要判断的问题变成脆弱分支。

## 如何选择控制形态

可以用四个问题做判断：

1. 下一步是否能由有限规则提前枚举？
2. 结果是否必须经过固定校验才能继续？
3. 现场观察是否可能改变后续路径？
4. 出错时是否需要模型理解原因并调整假设？

前三个问题偏向 Workflow，后两个问题偏向 Agent Loop。一个任务通常会同时得到两种答案，因此混合编排比二选一更常见。

## 什么时候不该引入 Agent Loop

以下任务优先使用普通函数或 Workflow：

- 固定的 CRUD 和数据转换；
- 规则可以完整表达的判断；
- 必须严格按顺序执行的审批流程；
- 没有探索价值的单次模型调用；
- 失败后只能按固定补偿动作处理的流程；
- 结果可以由确定性校验器完全判断的步骤。

使用模型的理由应来自语义不确定性或路径不确定性，而不是为了让固定流程看起来更智能。

## 如何验收控制平面

重点检查控制权是否放在了正确位置：

- 固定步骤是否始终经过必要节点；
- Agent 输出不符合合同是否会被拦截；
- Agent 节点是否只能访问授权输入和能力；
- Workflow 是否能限制模型调用、工具调用和总预算；
- 节点失败是否只影响允许的范围；
- 计划重排是否不会跳过固定验收；
- 取消、超时和恢复是否有明确出口；
- 相同输入下，确定性部分是否保持稳定；
- 引入 Agent 后，任务成功率是否提升且成本可接受。

Workflow 的价值是把可确定的部分固定下来，Agent Loop 的价值是处理无法提前写死的判断。好的控制平面不会让二者互相替代，而是让模型只在真正需要决策的地方获得控制权。

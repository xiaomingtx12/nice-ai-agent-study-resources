# 多 Agent 协作：分工、交接与合并

> 多 Agent 的核心本质，是让多个独立的决策循环围绕同一个任务合同分工工作，并用明确的交接和合并规则把局部结果变成全局结果。

多 Agent 的价值来自责任分工、并行执行和相互验证。增加模型调用次数本身不会带来协作收益；只有当子任务可以独立推进、结果能够验证合并、协调成本能够被控制时，拆分才有意义。

## 什么时候需要多 Agent

可以从四个问题开始判断：

- 子任务是否具有相对独立的目标；
- 子任务是否可以使用不同的工具、资料或工作方法；
- 子任务结果是否能通过结构化产物交接；
- 并行或专业分工带来的收益是否大于协调成本。

适合拆分的任务包括：

```text
研究多个方案
→ 分别验证
→ 汇总比较
```

```text
资料整理
→ 内容生成
→ 事实检查
→ 发布审核
```

一个 Agent 只需要多调用几次工具时，继续使用单个 Agent Loop 更简单。拆分后如果所有子 Agent 都依赖同一段上下文、频繁互相等待，说明任务边界还没有形成。

## 先确定责任边界

每个子 Agent 都应该拥有一个窄任务：

| 内容 | 要说明的问题 |
| --- | --- |
| 任务目标 | 这个 Agent 要交付什么结果 |
| 输入范围 | 它可以读取哪些事实、资料和产物 |
| 能力范围 | 它可以使用哪些工具和执行权限 |
| 完成条件 | 什么结果可以标记为完成 |
| 输出产物 | 下游需要消费什么结构化结果 |
| 失败出口 | 无法完成时如何报告、重试或交回上游 |
| 责任人 | 谁拥有该结果的修改和确认权 |

任务拆分的单位应该是“可独立验收的产物”，而不是“让几个模型分别思考一下”。例如，研究 Agent 交付带来源的候选方案，验证 Agent 交付问题清单和证据，协调 Agent 负责比较和裁决。

## 三种常见协作结构

### 主控—子 Agent

主控拥有全局任务目标、终态和最终合并权，子 Agent 在授权范围内完成一个子任务：

```text
主控拆分任务
→ 子 Agent 执行
→ 返回结构化产物
→ 主控验证并合并
```

这种结构适合任务边界清晰、结果需要集中汇总的场景。

### 顺序协作

上游产物成为下游输入：

```text
研究
→ 实现
→ 验证
→ 发布判断
```

顺序协作适合下游强依赖上游结果的任务。每一步都要绑定输入版本，避免下游消费已经过期的产物。

### 并行分工与汇合

多个 Agent 分别处理互不依赖的子任务，最后由合并节点汇总：

```text
任务拆分
→ Agent A
→ Agent B
→ Agent C
→ 结果验证与合并
```

并行只适合子任务之间低耦合、结果可以独立验证、汇合规则明确的情况。没有稳定的合并规则时，并行只会增加冲突。

## 交接包是协作的基本接口

子 Agent 完成后交付结构化交接包，而不是把完整聊天记录复制给下游：

```text
Handoff
├── task_id
├── producer_run_id
├── input_version
├── status
├── summary
├── claims
├── evidence_refs
├── artifact_refs
├── unresolved_questions
└── recommended_next_step
```

其中：

- `claims` 区分已验证结论、候选结论和失败假设；
- `evidence_refs` 指向来源、工具结果或文件版本；
- `artifact_refs` 让下游按需读取完整产物；
- `unresolved_questions` 防止未完成事项被当成结论；
- `input_version` 让协调者发现结果是否基于过期任务信息。

下游先读取摘要和元数据，再根据当前决策需要打开具体产物。这种交接方式减少上下文复制，也让结果可以被审查和回放。

## 共享事实与私有工作

协作需要共享事实，但不需要共享所有消息历史。

### 共享内容

适合进入共享任务板的内容包括：

- 任务合同和硬约束；
- 已确认事实及其来源；
- Artifact 索引和版本；
- 全局任务状态；
- 已裁决的决策记录。

共享字段需要有所有者、版本和写入规则。候选事实应标记为候选，不能由任意 Agent 直接升级为全局事实。

### 私有内容

中间推理、局部工具输出、失败尝试和角色专属资料保留在 Agent 的私有工作区。只有会影响其他 Agent 决策的内容，才通过 Handoff 或版本化产物公开。

```text
共享任务事实
        ↓
Agent A 私有工作区 → 结构化交接包
        ↓                    ↓
Agent B 私有工作区 ← 合并与裁决
```

全量共享上下文会放大错误假设、增加 Token 成本，也会让角色边界失效。

## 同步还是异步

| 模式 | 交接方式 | 适合场景 |
| --- | --- | --- |
| 同步 | 主控等待子 Agent 返回结果 | 子任务短、下一步强依赖结果 |
| 异步 | 任务快照入队，结果通过事件或产物返回 | 任务较长、可以并行、主控无需阻塞 |

同步模式需要处理超时和取消。父任务在结果返回前，不能把子任务当作已完成。

异步模式需要保存：

```text
child_run_id
input_version
artifact_ref
status
deadline
retry_policy
cancel_policy
```

结果回到主控时，先检查任务版本、权限和有效期，再决定是否合并。父任务已经改过目标时，旧结果只能作为历史产物，不能直接覆盖当前任务。

## 结果如何合并

合并规则应在拆分任务时确定。常见方式包括：

- 字段级合并；
- 按优先级选择；
- 规则校验后通过；
- 独立验证器确认；
- 由协调 Agent 解释并提交人工裁决。

协调 Agent 可以组织和解释结果，但不能无依据地拼接冲突结论。冲突结果需要保留来源、版本和裁决理由：

```text
冲突结论
→ 比较来源和有效期
→ 执行确定性规则
→ 无法消解时升级
→ 记录最终裁决
```

一个 Agent 负责产出，另一个 Agent 负责验证时，验证结果不能被产出 Agent 自己覆盖。

## 失败、取消与恢复

| 情况 | 处理方式 |
| --- | --- |
| 子任务参数错误 | 修正当前子任务后重试 |
| 子任务假设错误 | 返回主控重新拆分或改写任务 |
| 子任务权限不足 | 停止该子任务，等待授权或更换路径 |
| 子任务超时 | 按策略等待、重试、降级或取消 |
| 一个子任务失败，其他任务独立 | 其他任务继续，合并阶段标记缺失结果 |
| 关键子任务失败 | 主控暂停全局合并，重新规划或终止 |
| 父任务取消 | 取消排队任务，处理执行中的未知副作用 |
| 异步结果过期 | 拒绝直接合并，要求基于新版本重算 |

取消和重试需要绑定运行 ID 和幂等键，避免恢复时重复产生外部副作用。

## 如何验收多 Agent 协作

重点验证协作行为，而不是 Agent 数量：

- 每个子任务是否有清晰的输入、输出和责任人；
- 子 Agent 是否只能访问授权的资料和能力；
- Handoff 是否能区分结论、证据和未决问题；
- 下游是否会校验输入版本和产物有效期；
- 并行任务是否真的缩短总时间或提升质量；
- 子任务失败后，其他任务和全局任务是否按策略继续或停止；
- 取消和恢复是否不会产生重复副作用；
- 冲突结论是否保留来源并经过明确裁决；
- 最终结果是否能回溯到参与的 Agent、产物和输入版本。

多 Agent 的成熟度体现在责任边界、交接协议和失败处理上，而不是同时运行了多少个模型。

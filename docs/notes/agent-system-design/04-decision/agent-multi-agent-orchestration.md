# 多 Agent 协作：分工、交接与合并

> **模块本质：** 将复杂任务拆成有责任边界、可独立验收的工作，通过明确的交接与合并规则组织多个决策循环，并统一控制共享资源、权限和失败传播。

多 Agent 的价值来自责任分工、并行执行和相互验证。增加模型调用次数本身不会带来协作收益；只有当子任务可以独立推进、结果能够验证合并、协调成本能够被控制时，拆分才有意义。

## 一、什么时候需要多 Agent {/* #什么时候需要多-agent */}

可以从四个问题开始判断：

- 子任务是否具有相对独立的目标；
- 子任务是否可以使用不同的工具、资料或工作方法；
- 子任务结果是否能通过结构化产物交接；
- 并行或专业分工带来的收益是否大于协调成本。

适合拆分的任务包括：

```text
研究多个方案
→ 分别验证
→ 汇总比较
```

```text
资料整理
→ 内容生成
→ 事实检查
→ 发布审核
```

一个 Agent 只需要多调用几次工具时，继续使用单个 Agent Loop 更简单。拆分后如果所有子 Agent 都依赖同一段上下文、频繁互相等待，说明任务边界还没有形成。

## 二、先确定责任边界 {/* #先确定责任边界 */}

每个子 Agent 都应该拥有一个窄任务：

| 内容 | 要说明的问题 |
| --- | --- |
| 任务目标 | 这个 Agent 要交付什么结果 |
| 输入范围 | 它可以读取哪些事实、资料和产物 |
| 能力范围 | 它可以使用哪些工具和执行权限 |
| 完成条件 | 什么结果可以标记为完成 |
| 输出产物 | 下游需要消费什么结构化结果 |
| 失败出口 | 无法完成时如何报告、重试或交回上游 |
| 责任人 | 谁拥有该结果的修改和确认权 |

任务拆分的单位应该是“可独立验收的产物”，而不是“让几个模型分别思考一下”。例如，研究 Agent 交付带来源的候选方案，验证 Agent 交付问题清单和证据，协调 Agent 负责比较和裁决。

## 三、三种常见协作结构 {/* #三种常见协作结构 */}

### 1. 主控—子 Agent {/* #主控子-agent */}

主控拥有全局任务目标、终态和最终合并权，子 Agent 在授权范围内完成一个子任务：

```text
主控拆分任务
→ 子 Agent 执行
→ 返回结构化产物
→ 主控验证并合并
```

这种结构适合任务边界清晰、结果需要集中汇总的场景。

### 2. 顺序协作 {/* #顺序协作 */}

上游产物成为下游输入：

```text
研究
→ 实现
→ 验证
→ 发布判断
```

顺序协作适合下游强依赖上游结果的任务。每一步都要绑定输入版本，避免下游消费已经过期的产物。

### 3. 并行分工与汇合 {/* #并行分工与汇合 */}

多个 Agent 分别处理互不依赖的子任务，最后由合并节点汇总：

```text
任务拆分
→ Agent A
→ Agent B
→ Agent C
→ 结果验证与合并
```

并行只适合子任务之间低耦合、结果可以独立验证、汇合规则明确的情况。没有稳定的合并规则时，并行只会增加冲突。

## 四、交接包是协作的基本接口 {/* #交接包是协作的基本接口 */}

子 Agent 完成后交付结构化交接包，而不是把完整聊天记录复制给下游：

```text
Handoff
├── task_id
├── producer_run_id
├── input_version
├── status
├── summary
├── claims
├── evidence_refs
├── artifact_refs
├── unresolved_questions
└── recommended_next_step
```

其中：

- `claims` 区分已验证结论、候选结论和失败假设；
- `evidence_refs` 指向来源、工具结果或文件版本；
- `artifact_refs` 让下游按需读取完整产物；
- `unresolved_questions` 防止未完成事项被当成结论；
- `input_version` 让协调者发现结果是否基于过期任务信息。

下游先读取摘要和元数据，再根据当前决策需要打开具体产物。这种交接方式减少上下文复制，也让结果可以被审查和回放。

### 1. 接收方校验交接内容，不直接相信成功声明 {/* #接收方校验交接内容不直接相信成功声明 */}

派发给子 Agent 的任务需要绑定任务身份、目标、输入版本、资源范围和交付条件。返回时再检查结果是否对应这份任务，字段合法只是第一步。

例如子 Agent 返回合法的文档 ID 和“更新成功”，主控还应核对文档所属项目、内容版本与实际写入结果。子 Agent 的结论不能自动升级为全局事实，它返回的后续操作建议也不能授予新的工具权限。

校验失败时区分缺字段、证据不可读取、实体错误和结果过期。缺字段可以有限补交；越界资源或错误实体应拒绝合并；仅凭完整 JSON 无法判断业务结果可靠。交接重复投递时，按产物身份与版本去重，避免同一结果被重复累计。

## 五、共享事实与私有工作 {/* #共享事实与私有工作 */}

协作需要共享事实，但不需要共享所有消息历史。

### 1. 共享内容 {/* #共享内容 */}

适合进入共享任务板的内容包括：

- 任务合同和硬约束；
- 已确认事实及其来源；
- Artifact 索引和版本；
- 全局任务状态；
- 已裁决的决策记录。

共享字段需要有所有者、版本和写入规则。候选事实应标记为候选，不能由任意 Agent 直接升级为全局事实。

### 2. 私有内容 {/* #私有内容 */}

中间推理、局部工具输出、失败尝试和角色专属资料保留在 Agent 的私有工作区。只有会影响其他 Agent 决策的内容，才通过 Handoff 或版本化产物公开。

```text
共享任务事实
        ↓
Agent A 私有工作区 → 结构化交接包
        ↓                    ↓
Agent B 私有工作区 ← 合并与裁决
```

全量共享上下文会放大错误假设、增加 Token 成本，也会让角色边界失效。

### 3. 消息隔离之外，还要检查共享资源 {/* #消息隔离之外还要检查共享资源 */}

两个 Agent 使用不同的消息历史，仍可能共用同一个文件目录、数据库记录或外部账号。判断隔离是否成立，需要实际检查资源访问范围，不能只看 State 是否复制成了新对象。

| 协作方式 | 适合的任务 | 需要付出的代价 |
| --- | --- | --- |
| 各自读取同一不可变快照 | 调研、分析、并行审查 | 合并前检查快照是否仍有效 |
| 各自写独立工作区 | 生成文件、修改代码、制作候选产物 | 汇合时处理内容冲突并重新验收 |
| 单一写入者接收修改提案 | 多方修改同一业务实体 | 增加排队与裁决步骤 |
| 带版本条件的共享写入 | 确实需要共享可变资源 | 冲突重试、事务和外部副作用处理更复杂 |

不要让 Agent 持有数据库锁等待模型推理或人工审批。可以先读取版本，完成分析后在短事务中检查版本并提交；版本变化时重新判断，不能静默覆盖。独立 Git 工作区也只隔离文件，不能自动隔离共享数据库与凭据。

源码中的字段筛选与资源隔离差异见 [Deep Agents 故障路径与边界验证](../../../application-notes/engineering/langchain-series/deepagents/21-production-failure-validation.md)。其中的场景用于定位特定调用路径，不能据此假定所有共用存储的应用都已经越权。

## 六、同步还是异步 {/* #同步还是异步 */}

| 模式 | 交接方式 | 适合场景 |
| --- | --- | --- |
| 同步 | 主控等待子 Agent 返回结果 | 子任务短、下一步强依赖结果 |
| 异步 | 任务快照入队，结果通过事件或产物返回 | 任务较长、可以并行、主控无需阻塞 |

同步模式需要处理超时和取消。父任务在结果返回前，不能把子任务当作已完成。

异步模式需要保存：

```text
child_run_id
input_version
artifact_ref
status
deadline
retry_policy
cancel_policy
```

结果回到主控时，先检查任务版本、权限和有效期，再决定是否合并。父任务已经改过目标时，旧结果只能作为历史产物，不能直接覆盖当前任务。

## 七、结果如何合并 {/* #结果如何合并 */}

合并规则应在拆分任务时确定。常见方式包括：

- 字段级合并；
- 按优先级选择；
- 规则校验后通过；
- 独立验证器确认；
- 由协调 Agent 解释并提交人工裁决。

协调 Agent 可以组织和解释结果，但不能无依据地拼接冲突结论。冲突结果需要保留来源、版本和裁决理由：

```text
冲突结论
→ 比较来源和有效期
→ 执行确定性规则
→ 无法消解时升级
→ 记录最终裁决
```

一个 Agent 负责产出，另一个 Agent 负责验证时，验证结果不能被产出 Agent 自己覆盖。

## 八、失败、取消与恢复 {/* #失败取消与恢复 */}

| 情况 | 处理方式 |
| --- | --- |
| 子任务参数错误 | 修正当前子任务后重试 |
| 子任务假设错误 | 返回主控重新拆分或改写任务 |
| 子任务权限不足 | 停止该子任务，等待授权或更换路径 |
| 子任务超时 | 按策略等待、重试、降级或取消 |
| 一个子任务失败，其他任务独立 | 其他任务继续，合并阶段标记缺失结果 |
| 关键子任务失败 | 主控暂停全局合并，重新规划或终止 |
| 父任务取消 | 取消排队任务，处理执行中的未知副作用 |
| 异步结果过期 | 拒绝直接合并，要求基于新版本重算 |

取消和重试需要绑定运行 ID 和幂等键，避免恢复时重复产生外部副作用。

父任务还要统一限制派生深度、同时运行数、累计子任务数和总预算。子任务局部限额用于约束单个分支，不能替代全树限额。主控等待期间，应能看见尚未结束的分支及其费用归属。

汇合前明确哪些结果是必需的，哪些可以缺失。必要分支失败时不能用其他分支的成功数量掩盖缺口；允许部分交付时，最终结果标明未覆盖范围。取消请求发出后仍需跟踪执行端状态，不能立即把所有子任务记为已停止。

## 九、用子代理配置表达分工，用业务协议控制交接 {/* #框架中的多代理定制 */}

### 1. 选择声明式子代理还是预编译子图 {/* #1-选择声明式子代理还是预编译子图 */}

Deep Agents 的 `SubAgent` 是子代理配置，声明名称、用途、模型、工具和提示词等内容；`CompiledSubAgent` 则接入已经构建好的可运行对象，适合内部有固定步骤或独立状态设计的执行单元。它们通过 `create_deep_agent(subagents=[...])` 装配，主代理使用 `task` 工具委派任务。

| 业务分工 | 框架配置重点 | 交接需要补什么 |
| --- | --- | --- |
| 资料查找 | 明确 `description`、只读工具与检索范围 | 来源、版本、证据片段和未解决问题 |
| 引用审校 | 独立提示词、所需 `skills` 与读取能力 | 按引用逐项返回依据，不能只说“审校通过” |
| 固定质量检查 | 接入预编译图或普通确定性工具 | 机器可校验的检查结果与失败项 |
| 长时间外部处理 | 采用异步任务管理接口 | 远端任务 ID、状态查询、取消和结果归属 |

如果检查只需要运行一个确定性脚本，直接作为工具或节点即可，不必为它再创建一个会自主规划的 Agent。

### 2. 核对权限继承和真实资源共享 {/* #2-核对权限继承和真实资源共享 */}

本文核对的 Deep Agents 0.6.12 源码快照中，`libs/deepagents/deepagents/graph.py` → `create_deep_agent()` 第 759–760 行按以下方式选择声明式子代理权限；其他装配逻辑省略。

```python
# 子代理显式配置的规则优先，否则继承父代理规则。
subagent_permissions = spec.get("permissions", permissions)
```

因此，子代理的 `permissions` 会替换父规则，不是追加规则；空列表也会改变继承结果。为审校代理补规则时，应把需要保留的限制一起带上，再验证实际权限。预编译子代理则需要检查其自身的装配，不能假设顶层会替它补齐所有约束。

子代理的独立消息状态只隔离对话。父子可能仍使用同一个 Backend、文件目录、凭证或外部服务账号。资料查找代理应只有读取能力；草稿修改代理应写入自己的工作区，再由父流程验证并合并。

### 3. 在汇合处校验交付，而不直接相信摘要 {/* #3-在汇合处校验交付而不直接相信摘要 */}

标准 `task` 委派可以返回文本或结构化结果，但“返回成功”不代表交接包满足业务要求。父流程应验证来源版本、产物位置和必填字段，区分可重试失败、缺少输入与真正完成。需要固定的并行汇合和失败传播时，可用 LangGraph 的 `Send` 表达动态分发；它为目标节点提供一次执行输入，汇总字段仍需设计 reducer。

文档维护可以让资料代理和引用审校代理并行工作，但发布者只有一个。用一个子任务失败、另一个已产生草稿的场景检查汇合逻辑，确认不会丢弃有效产物，也不会带着缺失的审校结果发布。委派、状态回写及版本范围见[同步子代理](../../../application-notes/engineering/langchain-series/deepagents/09-subagent-sync.md)、[异步子代理](../../../application-notes/engineering/langchain-series/deepagents/12-async-subagent.md)和[动态分发](../../../application-notes/engineering/langchain-series/langgraph/05-dynamic-routing-and-send.md)。

## 十、如何验收多 Agent 协作 {/* #如何验收多-agent-协作 */}

重点验证协作行为，而不是 Agent 数量：

- 每个子任务是否有清晰的输入、输出和责任人；
- 子 Agent 是否只能访问授权的资料和能力；
- Handoff 是否能区分结论、证据和未决问题；
- 下游是否会校验输入版本和产物有效期；
- 并行任务是否真的缩短总时间或提升质量；
- 子任务失败后，其他任务和全局任务是否按策略继续或停止；
- 取消和恢复是否不会产生重复副作用；
- 冲突结论是否保留来源并经过明确裁决；
- 最终结果是否能回溯到参与的 Agent、产物和输入版本。

多 Agent 的成熟度体现在责任边界、交接协议和失败处理上，而不是同时运行了多少个模型。

# 运行中干预：排队、转向、中断与停止

长任务执行期间，用户会补充要求，外部系统会发来告警，已经采用的证据也可能失效。运行时需要把这些变化送到正确的任务，在可控的位置改变后续行动，并保留仍然有效的进展。

以巡检服务为例：Agent 正在读取一台机器的部署记录，告警系统突然报告该机器延迟升高。部署记录仍然有用，后续工作却应优先调查告警。这个问题涉及消息路由、输入装配和执行控制，不能只靠给模型追加一句“优先处理”。

## 一、消息到达和模型看见是两个时刻

Harness 是组织模型调用、工具执行与任务状态的运行时。一项连续任务通常经历多次模型调用，工具结果在调用之间返回，下一轮输入也在这个边界重新准备。

假设工具正在查询部署记录，此时告警到达。已经发出的工具请求使用的是旧参数；告警需要先由运行时接收，再进入后续某轮模型输入，才能改变模型接下来的判断。对于很快结束的只读查询，可以让它返回后，将查询结果和告警一起交给模型。

排查干预是否生效，应区分三个证据：

| 阶段 | 能证明什么 | 不能直接推出什么 |
| --- | --- | --- |
| 消息已接收 | 服务接受了输入，能够找到目标任务 | 模型已经读取消息 |
| 消息已进入调用 | 某次模型输入包含这条消息 | 所有运行中的工具都已停止 |
| 后续行动已调整 | 新计划、工具参数或任务状态响应了变化 | 已经产生的外部效果被撤销 |

客户端只显示“发送成功”，无法解释告警究竟影响了哪一步。设计观测记录时，应把消息 ID、目标运行和首次纳入输入的位置关联起来；若接口不能暴露完整输入，至少保留可观察的事件边界，并核对后续动作。

## 二、先选择控制意图，再调用具体接口

Thread 可以理解为保存一项工作历史的会话；Turn 表示一次由输入启动的运行，其中可能包含多轮模型调用和工具执行。不同系统的对象名称并不一致，接入时要映射到自己的任务与执行身份。

下面四类是设计上的控制意图，不是一套所有框架都实现的标准 API。

| 意图 | 适用情形 | 后续工作怎样变化 |
| --- | --- | --- |
| queue，排队 | 巡检结束后再整理早报 | 当前运行继续，新要求等待调度 |
| steer，转向 | 巡检期间出现相关告警 | 沿用有效背景，改变后续优先级或方向 |
| interrupt，中断 | 调查依赖的时间戳被确认有误 | 请求终止当前运行，保留历史供重新启动 |
| stop，停止调度 | 暂停整项自动巡检服务 | 阻止后续运行继续启动，并处理在途工作 |

同一句“先停一下”，可能指中断当前推理，也可能指暂停整项服务。产品入口应让调用方表达控制范围，并返回实际执行状态。不能把某个产品中名为 `stop` 的操作直接理解成停止所有后台调度。

转向请求还要绑定目标运行。消息生成时任务可能仍在执行，消息到达时任务已经结束。此时应按预先约定进入后续队列或返回目标已结束，不能悄悄把它注入后来启动的另一项工作。

## 三、转向时只重做已经失效的部分

有效的干预需要说明新事实、它影响的范围，以及原任务还剩什么。只写“改查告警”，可能让巡检清单和恢复条件一起丢失。

一次从巡检切换到调查的交接，可以保留这些信息：

- 新告警对应哪台机器、哪个服务、哪个时间窗。
- 已取得的部署记录来自什么时刻，哪些仍可使用。
- 原巡检已经完成哪些对象，还有哪些待处理。
- 调查完成、转人工或达到预算后，是否继续巡检。

如果新证据只推翻某个假设，就使依赖该假设的计划失效；已核实的日志入口和服务身份仍可保留。如果告警归属另一套系统，原背景可能大部分不再适用，应考虑[独立会话与历史分支](../02-state/agent-session-branching.md)。

任务目标改变后，还要核对已准备的动作。例如旧计划准备修改配置，新要求改为只调查，尚未执行的修改提案应失效。将新文字加入上下文只是其中一步，工具执行前仍须检查当前任务约束。

## 四、取消请求之后，还要确认执行端发生了什么

模型生成、工具进程、远端请求和任务调度可能有不同的生命周期。中断模型不会天然终止已经启动的命令；终止命令也无法撤回远端服务已经接受的写入。

设计取消收尾时，应分别处理：

| 对象 | 需要确认的状态 |
| --- | --- |
| 后续模型调用 | 是否已经禁止继续启动 |
| 等待执行的工具 | 是否已从调度队列撤下 |
| 运行中的工具 | 是否支持取消，取消是否被确认 |
| 已提交的外部写入 | 已成功、已失败，还是结果未知 |
| 后台与子任务 | 是否属于本次取消范围，是否仍持有执行权 |

“已请求取消”与“已停止”应是不同状态。配置写入已经完成时，需要独立的恢复动作；远端响应丢失时，需要查询实际结果。副作用核对见[状态与恢复](../02-state/agent-state-architecture.md)，执行端约束见[工具调用](../05-action/agent-tool-calling.md)。

## 五、用事件位置验收运行干预

可以在隔离环境中分别安排以下情形。这是一组验收方案，不能用界面出现一句“收到”替代结果检查。

| 场景 | 预期行为 | 检查证据 |
| --- | --- | --- |
| 短只读查询期间收到相关告警 | 保留查询结果，在后续判断中提高告警优先级 | 告警纳入位置、下一步工具选择 |
| 当前工作期间收到早报要求 | 当前任务完成后才开始早报 | 两项工作的启动和结束顺序 |
| 目标运行刚结束，转向消息才到达 | 明确拒绝或排入后续任务 | 目标运行 ID、消息处理结果 |
| 慢工具期间请求中断 | 记录取消请求，继续确认工具状态 | 进程或服务的实际终态 |
| 写入完成后收到取消 | 不再发起后续动作，保留已发生效果 | 外部版本、动作记录与恢复安排 |
| 调查结束后恢复巡检 | 从未完成位置继续，重新检查过期事实 | 待办列表、事实时间与新查询结果 |

衡量干预能力时，同时观察消息等待时间、方向调整是否正确、有效进展是否保留，以及取消后是否还有未解释的外部动作。

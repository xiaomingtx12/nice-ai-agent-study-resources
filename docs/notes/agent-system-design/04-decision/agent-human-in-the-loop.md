# 人机协作：把控制权交给人，再安全地交回来

> **模块本质：** 在需要澄清、审批、复核或接管时，将控制权连同具体问题和证据交给人，再把人的决定绑定到明确的任务或动作，经过重新校验后恢复执行。

人在环路（Human-in-the-Loop，HITL）不是给模型追加一句“请询问用户”，而是一次运行时控制权转移。系统要知道为什么暂停、希望人决定什么、等待期间能否继续、恢复时哪些条件必须重新检查。

## 一、什么时候需要人介入 {/* #什么时候需要人介入 */}

人介入应由任务条件触发，而不是由模型的主观感觉触发。常见信号包括：

- 用户目标、资源范围或成功条件缺失；
- 多个解释都会导致不同的执行路径；
- 动作不可逆、影响范围大或包含敏感资源；
- 权限、业务策略或发布责任要求确认；
- 外部状态无法确认，继续执行可能重复产生副作用；
- 自动验收失败，系统无法判断结果是否可接受；
- 多个 Agent 产生冲突结论，确定性规则无法裁决。

低风险、可撤销且验收规则完整的动作，可以继续自动执行。人工介入的价值在于解决真正影响路径、风险或终态的问题。

## 二、让审批人能看清这次决定 {/* #让审批人能看清这次决定 */}

审批规则应结合目标环境、数据敏感度、影响范围和可撤销性。仅给工具贴上“高风险”标签，会把大量性质不同的请求推给同一批人。模型可以提示异常线索，实际分级以可审计的业务规则和已验证事实为依据。

一份审批证据包应展示：

| 内容 | 应呈现的信息 |
| --- | --- |
| 要批准的动作 | 目标资源、环境、修改前后差异或待发送内容 |
| 与任务的关系 | 为什么需要这个动作，属于哪一步 |
| 已验证影响 | 涉及资源数量、访问范围、不可逆效果与未知项 |
| 授权范围 | 准确参数、资源版本、策略版本和有效期 |
| 拒绝后的路径 | 修改、停止、换方案或升级处理 |

例如审批覆盖文档时，展示文档身份、当前版本和具体差异，比展示一整段工具调用 JSON 更便于判断。影响数量应来自可信查询，模型生成的风险摘要要与已验证字段分开展示；未知影响直接标为未知。

重复通知可以合并，但不能静默扩大授权。批量审批应冻结明确的动作集合，每项动作仍有独立身份；等待期间新增的动作不自动加入已经批准的集合。每个请求还应有明确负责人和转交规则，避免所有人都收到通知却无人负责。

## 三、四种介入方式 {/* #四种介入方式 */}

### 1. 澄清 {/* #澄清 */}

任务合同中缺少关键信息时，向用户提出一个可以直接改变后续路径的问题。问题应说明：

- 缺少哪个字段；
- 为什么这个字段会影响执行；
- 用户可以选择哪些值；
- 不回答时任务如何处理。

用户的回答只更新对应的任务事实，不能被解释成对所有后续动作的长期授权。

### 2. 审批 {/* #审批 */}

审批针对一次具体动作，而不是一句自然语言计划。展示内容至少包括：

- 动作和参数摘要；
- 目标资源和影响范围；
- 风险和不可逆后果；
- 使用的策略版本；
- 预计产生的副作用；
- 通过、拒绝和修改后的出口。

审批通过后，执行前仍要重新检查动作参数、资源范围、权限和有效期。参数发生变化时，应生成新的审批请求。

### 3. 结果复核 {/* #结果复核 */}

工具返回成功、模型生成结果或多个 Agent 汇总完成后，系统仍可能无法自动判断结果是否可接受。复核界面应展示：

- 结果本身；
- 使用的证据；
- 未通过的检查；
- 尚未解决的风险；
- 可选择的后续动作。

人工可以接受结果、要求修复、补充信息或终止任务。人工接受不能跳过系统仍然必需的安全和格式检查。

### 4. 接管 {/* #接管 */}

用户或操作人员可以暂停模型，直接修改目标、取消动作或接管后续执行。接管改变的是运行时控制权，不是向模型追加一条普通消息。

## 四、暂停和恢复是一条状态流 {/* #暂停和恢复是一条状态流 */}

人机协作需要显式表示等待和恢复：

```text
running
→ waiting_for_human
→ approved / clarified / rejected / expired
→ resumed / replanned / stopped
```

暂停时要冻结尚未执行的副作用，保存当前决策提案、证据、任务版本和等待原因。已经发出的动作如果状态未知，应标记为未知，不能因为等待人工而自动重复。

恢复时重新检查：

- 用户目标和任务事实是否变化；
- 决策提案和动作参数是否仍然一致；
- 权限、策略版本和审批是否仍然有效；
- 工作区、凭据和外部资源是否仍然可用；
- 等待期间是否已经发生外部变化。

恢复不是从旧 Prompt 继续生成，而是用新的任务事实重新进入 Agent Loop。

等待审批时先持久化暂停现场，再释放执行资源，通过之后的事件恢复任务。短交互可以等待用户响应，但不能让一个进程内的等待对象成为唯一审批记录。是否采用消息队列取决于规模，持久化状态、可靠投递和去重才是需要验证的性质。

审批创建后、通知发出前崩溃，应能补发通知；响应收到后、恢复前崩溃，应能继续消费已经确认的决定。通知投递和执行恢复都要处理重复，不能把重复点击解释成再次执行。

## 五、人工请求要绑定具体决策 {/* #人工请求要绑定具体决策 */}

一次人工请求至少需要关联：

```text
run_id
gate_id
reason
decision_or_action
evidence_refs
allowed_responses
policy_version
expires_at
status
```

`decision_or_action` 表示人正在批准或修改的具体对象；`evidence_refs` 让人可以检查依据；`expires_at` 防止过期请求被长期使用；`status` 区分等待、批准、拒绝、过期和已替代。

请求中不应只放“模型建议执行某操作”这样的描述，而应展示运行时已经解析出的动作、参数和资源范围。

人工响应还要验证审批人身份、其对目标资源的审批权限和请求当前状态。批准、拒绝、撤销与过期可能竞争，状态更新需要原子检查；已经消费或被替代的请求不能再次授权。审计记录保留实际决定者，不能只记录一个没有身份的 `approved`。

## 六、人工决定如何回到循环 {/* #人工决定如何回到循环 */}

人工响应需要转成结构化任务事实，再决定下一步：

```text
人工响应
→ 校验响应范围
→ 更新任务事实或动作授权
→ 重新装配当前输入
→ continue / replan / stop
```

不同响应有不同含义：

| 人工响应 | 下一步 |
| --- | --- |
| 补充参数 | 更新任务事实，继续决策 |
| 选择方案 | 固定对应分支，继续执行 |
| 批准动作 | 在有效期内进入执行门 |
| 要求修改 | 生成新的决策提案 |
| 拒绝动作 | 终止该动作或重新规划 |
| 取消任务 | 停止后续循环和排队动作 |
| 接受部分结果 | 标记已接受范围，保留未完成事项 |

人工选择应写入运行记录，成为后续决策和离线回归的依据。

## 七、多 Agent 场景中的控制权 {/* #多-agent-场景中的控制权 */}

子 Agent 通常没有独立的用户会话和审批界面。需要人工介入时，应将请求上浮到拥有全局任务和用户关系的协调者：

```text
子 Agent 提出结构化请求
→ 协调者检查任务和权限
→ 用户审批或补充信息
→ 协调者更新共享任务事实
→ 子 Agent 继续或停止
```

协调者不能把一次审批泛化给其他子任务。每个动作仍然需要绑定自己的参数、资源范围和任务版本。

还需要提前确定：

- 人工等待时其他子 Agent 是否继续；
- 一个子任务被拒绝后是局部重排还是整体停止；
- 哪个角色拥有最终暂停和恢复权；
- 异步结果返回时是否仍然需要重新确认。

## 八、等待、超时和过期 {/* #等待超时和过期 */}

人工等待不能无限悬挂。系统应为每个等待节点定义：

- 等待期限；
- 期限到达后的默认处理；
- 是否允许转交其他审批人；
- 等待期间哪些低风险任务可以继续；
- 任务目标变化后是否自动使请求失效。

高风险动作在审批超时后默认保持停止状态。低风险动作是否自动降级，需要由任务规则明确允许。

紧急通道是另一个有责任主体和审计要求的授权流程，不能把“超时”直接解释成自动批准。恢复执行时还要复查前置条件：即使参数未变，目标资源的版本、状态或归属也可能已经变化。

除了等待时长，还应观察重复请求比例、请求过期率、批准后参数失效率和人工修改率。单看批准率无法判断审批质量；几乎全部通过可能是规则合理，也可能是证据展示不足或审批疲劳，需要抽查具体请求。

## 九、接入中断协议，再实现业务审批 {/* #框架中的审批接入 */}

### 1. 按暂停位置选择接口 {/* #1-按暂停位置选择接口 */}

LangChain 的 `HumanInTheLoopMiddleware` 用于在工具执行前暂停，让外部返回批准、修改或拒绝等决定。LangGraph 的 `interrupt()` 用于在图节点内发出可恢复的中断；`Command(resume=...)` 是将外部决定送回暂停执行的恢复指令。前者适合工具审批，后者也能表达补充资料、人工校验等流程节点。

接入中断需要配置 checkpointer，并保留原执行线的 `thread_id`。正式服务应使用持久保存器，审批页面只显示中断请求，恢复接口负责检查审批者身份、请求版本和有效期。

LangChain 1.3.7 的 `libs/langchain_v1/tests/unit_tests/agents/middleware/implementations/test_human_in_the_loop.py` → `test_human_in_the_loop_middleware_no_interrupts_needed()` 使用以下配置；省略测试状态与断言。

```python
middleware = HumanInTheLoopMiddleware(
    interrupt_on={"test_tool": {"allowed_decisions": ["approve", "edit", "reject"]}}
)
```

`test_tool` 是测试工具名，业务中对应真实注册名称。未列入 `interrupt_on` 的工具不会因此暂停；它不是默认拒绝的权限表。发布工具若不允许改参数，可以只开放批准与拒绝，参数修改则回到生成候选和重新审批流程。

### 2. 恢复时校验审批对象，而不只解析决定 {/* #2-恢复时校验审批对象而不只解析决定 */}

该中间件的恢复值包含 `decisions` 列表，其中每项描述一种决定。一次中断包含多个动作时，要按中断请求的动作列表逐项匹配；多个图中断还需要核对具体中断身份。前端不能仅传一个“同意”就授权当前所有待执行动作。

业务审批记录应绑定草稿版本、发布目标、规范化参数摘要与有效期。恢复服务核对这些字段后才构造 `Command`。如果允许 `edit`，修改后的动作仍要通过参数、权限和业务约束检查；原审批不能覆盖新增资源或更大的影响范围。

### 3. 避免把副作用放在会重执行的位置 {/* #3-避免把副作用放在会重执行的位置 */}

LangGraph 恢复包含 `interrupt()` 的节点时，会从节点开头重新执行。中断前若已经发送通知、创建发布单或写入外部系统，应拆成已完成的前置节点，或通过稳定动作 ID 去重。不要把暂停理解成 Python 调用栈原地冻结。

文档发布验收至少覆盖：审批期间草稿改变、重复点击批准、审批者失去权限、恢复时服务重启。前两种应拒绝旧授权或复用已有处理结果，不能发布错误版本或产生两次发布。源码细节见[人工审批中间件](../../../application-notes/engineering/langchain-series/langchain/08-human-in-the-loop.md)和[中断与恢复协议](../../../application-notes/engineering/langchain-series/langgraph/07-interrupts-and-command.md)。

## 十、常见错误 {/* #常见错误 */}

| 错误 | 后果 | 调整方式 |
| --- | --- | --- |
| 把“用户说可以”当成长期权限 | 后续动作越过审批 | 授权绑定具体动作、参数和有效期 |
| 审批只显示在界面，不写入运行状态 | 无法恢复和审计 | 保存审批结果、版本和证据 |
| 审批后重新生成参数 | 实际执行内容未经批准 | 执行前校验参数摘要，变化后重新审批 |
| 暂停后继续执行排队动作 | 产生未授权副作用 | 暂停时冻结队列并重新检查 |
| 恢复时复用旧权限和资源 | 使用过期执行环境 | 恢复前重新检查策略、凭据和工作区 |
| 让模型自行判断何时必须问人 | 高风险场景可能被跳过 | 用任务规则和运行时硬门触发 |
| 人工接受结果后直接结束 | 终态仍可能不满足 | 保留必要的自动验收 |
| 子 Agent 各自等待用户 | 多个悬挂请求和重复确认 | 由协调者统一汇总和上浮 |

## 十一、如何验收人机协作 {/* #如何验收人机协作 */}

重点检查控制权是否真的发生了安全转移：

- 缺少关键信息时，系统是否提出具体问题；
- 审批是否绑定准确的动作、参数和资源；
- 审批等待超时后是否不会自动放行高风险动作；
- 用户取消后，排队和并发动作是否按策略停止；
- 恢复时是否重新检查任务版本、权限和外部状态；
- 人工修改目标后，旧计划和旧审批是否失效；
- 子 Agent 的请求是否能够上浮到正确的协调者；
- 人工决定是否会进入任务事实和运行记录；
- 结果复核是否保留证据、风险和未完成事项；
- 每次暂停、恢复、拒绝和接管是否能在记录中重建。

人机协作的质量，不在于系统向人弹出了多少确认框，而在于它只在真正需要人判断的节点暂停，并且让每一次人工决定都能被准确约束、记录和恢复。

# 人机协作：把控制权交给人，再安全地交回来

> 人机协作的核心本质，是在模型无法独立完成、风险不适合自动承担或结果无法可靠验证时暂停决策循环，把一个明确的问题交给人，再将人的决定作为新的任务事实继续执行。

人在环路（Human-in-the-Loop，HITL）不是给模型追加一句“请询问用户”，而是一次运行时控制权转移。系统要知道为什么暂停、希望人决定什么、等待期间能否继续、恢复时哪些条件必须重新检查。

## 什么时候需要人介入

人介入应由任务条件触发，而不是由模型的主观感觉触发。常见信号包括：

- 用户目标、资源范围或成功条件缺失；
- 多个解释都会导致不同的执行路径；
- 动作不可逆、影响范围大或包含敏感资源；
- 权限、业务策略或发布责任要求确认；
- 外部状态无法确认，继续执行可能重复产生副作用；
- 自动验收失败，系统无法判断结果是否可接受；
- 多个 Agent 产生冲突结论，确定性规则无法裁决。

低风险、可撤销且验收规则完整的动作，可以继续自动执行。人工介入的价值在于解决真正影响路径、风险或终态的问题。

## 四种介入方式

### 澄清

任务合同中缺少关键信息时，向用户提出一个可以直接改变后续路径的问题。问题应说明：

- 缺少哪个字段；
- 为什么这个字段会影响执行；
- 用户可以选择哪些值；
- 不回答时任务如何处理。

用户的回答只更新对应的任务事实，不能被解释成对所有后续动作的长期授权。

### 审批

审批针对一次具体动作，而不是一句自然语言计划。展示内容至少包括：

- 动作和参数摘要；
- 目标资源和影响范围；
- 风险和不可逆后果；
- 使用的策略版本；
- 预计产生的副作用；
- 通过、拒绝和修改后的出口。

审批通过后，执行前仍要重新检查动作参数、资源范围、权限和有效期。参数发生变化时，应生成新的审批请求。

### 结果复核

工具返回成功、模型生成结果或多个 Agent 汇总完成后，系统仍可能无法自动判断结果是否可接受。复核界面应展示：

- 结果本身；
- 使用的证据；
- 未通过的检查；
- 尚未解决的风险；
- 可选择的后续动作。

人工可以接受结果、要求修复、补充信息或终止任务。人工接受不能跳过系统仍然必需的安全和格式检查。

### 接管

用户或操作人员可以暂停模型，直接修改目标、取消动作或接管后续执行。接管改变的是运行时控制权，不是向模型追加一条普通消息。

## 暂停和恢复是一条状态流

人机协作需要显式表示等待和恢复：

```text
running
→ waiting_for_human
→ approved / clarified / rejected / expired
→ resumed / replanned / stopped
```

暂停时要冻结尚未执行的副作用，保存当前决策提案、证据、任务版本和等待原因。已经发出的动作如果状态未知，应标记为未知，不能因为等待人工而自动重复。

恢复时重新检查：

- 用户目标和任务事实是否变化；
- 决策提案和动作参数是否仍然一致；
- 权限、策略版本和审批是否仍然有效；
- 工作区、凭据和外部资源是否仍然可用；
- 等待期间是否已经发生外部变化。

恢复不是从旧 Prompt 继续生成，而是用新的任务事实重新进入 Agent Loop。

## 人工请求要绑定具体决策

一次人工请求至少需要关联：

```text
run_id
gate_id
reason
decision_or_action
evidence_refs
allowed_responses
policy_version
expires_at
status
```

`decision_or_action` 表示人正在批准或修改的具体对象；`evidence_refs` 让人可以检查依据；`expires_at` 防止过期请求被长期使用；`status` 区分等待、批准、拒绝、过期和已替代。

请求中不应只放“模型建议执行某操作”这样的描述，而应展示运行时已经解析出的动作、参数和资源范围。

## 人工决定如何回到循环

人工响应需要转成结构化任务事实，再决定下一步：

```text
人工响应
→ 校验响应范围
→ 更新任务事实或动作授权
→ 重新装配当前输入
→ continue / replan / stop
```

不同响应有不同含义：

| 人工响应 | 下一步 |
| --- | --- |
| 补充参数 | 更新任务事实，继续决策 |
| 选择方案 | 固定对应分支，继续执行 |
| 批准动作 | 在有效期内进入执行门 |
| 要求修改 | 生成新的决策提案 |
| 拒绝动作 | 终止该动作或重新规划 |
| 取消任务 | 停止后续循环和排队动作 |
| 接受部分结果 | 标记已接受范围，保留未完成事项 |

人工选择应写入运行记录，成为后续决策和离线回归的依据。

## 多 Agent 场景中的控制权

子 Agent 通常没有独立的用户会话和审批界面。需要人工介入时，应将请求上浮到拥有全局任务和用户关系的协调者：

```text
子 Agent 提出结构化请求
→ 协调者检查任务和权限
→ 用户审批或补充信息
→ 协调者更新共享任务事实
→ 子 Agent 继续或停止
```

协调者不能把一次审批泛化给其他子任务。每个动作仍然需要绑定自己的参数、资源范围和任务版本。

还需要提前确定：

- 人工等待时其他子 Agent 是否继续；
- 一个子任务被拒绝后是局部重排还是整体停止；
- 哪个角色拥有最终暂停和恢复权；
- 异步结果返回时是否仍然需要重新确认。

## 等待、超时和过期

人工等待不能无限悬挂。系统应为每个等待节点定义：

- 等待期限；
- 期限到达后的默认处理；
- 是否允许转交其他审批人；
- 等待期间哪些低风险任务可以继续；
- 任务目标变化后是否自动使请求失效。

高风险动作在审批超时后默认保持停止状态。低风险动作是否自动降级，需要由任务规则明确允许。

## 常见错误

| 错误 | 后果 | 调整方式 |
| --- | --- | --- |
| 把“用户说可以”当成长期权限 | 后续动作越过审批 | 授权绑定具体动作、参数和有效期 |
| 审批只显示在界面，不写入运行状态 | 无法恢复和审计 | 保存审批结果、版本和证据 |
| 审批后重新生成参数 | 实际执行内容未经批准 | 执行前校验参数摘要，变化后重新审批 |
| 暂停后继续执行排队动作 | 产生未授权副作用 | 暂停时冻结队列并重新检查 |
| 恢复时复用旧权限和资源 | 使用过期执行环境 | 恢复前重新检查策略、凭据和工作区 |
| 让模型自行判断何时必须问人 | 高风险场景可能被跳过 | 用任务规则和运行时硬门触发 |
| 人工接受结果后直接结束 | 终态仍可能不满足 | 保留必要的自动验收 |
| 子 Agent 各自等待用户 | 多个悬挂请求和重复确认 | 由协调者统一汇总和上浮 |

## 如何验收人机协作

重点检查控制权是否真的发生了安全转移：

- 缺少关键信息时，系统是否提出具体问题；
- 审批是否绑定准确的动作、参数和资源；
- 审批等待超时后是否不会自动放行高风险动作；
- 用户取消后，排队和并发动作是否按策略停止；
- 恢复时是否重新检查任务版本、权限和外部状态；
- 人工修改目标后，旧计划和旧审批是否失效；
- 子 Agent 的请求是否能够上浮到正确的协调者；
- 人工决定是否会进入任务事实和运行记录；
- 结果复核是否保留证据、风险和未完成事项；
- 每次暂停、恢复、拒绝和接管是否能在记录中重建。

人机协作的质量，不在于系统向人弹出了多少确认框，而在于它只在真正需要人判断的节点暂停，并且让每一次人工决定都能被准确约束、记录和恢复。

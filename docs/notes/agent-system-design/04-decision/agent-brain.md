# Agent Loop：模型驱动的决策闭环

> Agent Loop 的核心，是让模型根据当前可见信息提出下一步决策，通过行动获得真实结果，再根据新的观察继续、修正、重新规划或结束任务。

模型每次调用只看到一次输入，无法天然记住已经做过什么，也无法保证自己提出的计划一定可执行。Agent Loop 把模型放进一个受运行时约束的循环，让任务从一次生成扩展为连续的决策过程。

```text
任务目标
→ 模型查看当前输入
→ 提出下一步决策
→ 运行时检查并执行
→ 获得观察结果
→ 更新当前任务事实
→ 继续、修正、重排或停止
```

## 一轮循环如何运行

一轮循环由多个有明确边界的动作组成：

1. **准备输入**：提供当前任务目标、已确认事实、待处理事项、可用能力和预算；
2. **生成决策提案**：模型选择行动、追问、计划更新、直接回复或结束；
3. **解释并检查提案**：运行时解析结构化输出，检查参数、权限、预算和当前阶段；
4. **执行或等待**：执行允许的动作，或者等待用户、外部系统和人工决定；
5. **形成观察结果**：把动作结果、错误、外部变化和新事实整理成下一轮可读取的结果；
6. **判断循环出口**：验证终态，决定继续、修正、重新规划、暂停或终止。

模型的自然语言不能直接改变运行时状态。模型提出的是决策提案，运行时负责将提案转换成受约束的状态转移。

### 每轮调用都要重新装配

模型 API 通常是无状态的。下一轮调用不会自动记住上一轮的系统规则、用户任务、模型决策和工具结果，运行时需要根据当前状态重新生成本轮输入。

因此，一轮循环保存的不是“模型已经记住的内容”，而是下一轮必须重新装配的事实：

```text
当前任务
+ 已确认事实
+ 历史决策摘要
+ 工具结果
+ 当前可用能力
+ 预算和停止条件
```

上下文过长时优先保留会影响下一步的事实、动作和结果；被压缩的原始材料要保留来源和重新读取路径。

## 模型输出应该表达什么

Agent Loop 需要让模型明确区分几类决策：

| 决策类型 | 典型含义 |
| --- | --- |
| `act` | 调用工具或执行一项外部动作 |
| `ask` | 缺少会改变路径的关键信息，需要追问 |
| `replan` | 当前假设或步骤无法继续，需要调整剩余计划 |
| `respond` | 已有足够依据，可以向用户返回结果 |
| `stop` | 满足终态，或已经进入明确的失败、取消和等待状态 |

初始系统提示词应说明任务目标和成功条件从哪里读取、当前阶段允许哪些动作、哪些事实必须验证、何时需要追问，以及模型输出必须遵循的决策协议。

思考协议可以要求模型整理计划、假设、依据和下一步，但这些内容服务于决策，不等同于运行时保证。循环上限、权限、预算和终态检查都由运行时强制执行。

一次模型响应可以提出多个工具调用。运行时需要先判断它们之间是否存在数据依赖：相互独立的调用可以并行执行；后一个调用需要前一个结果时必须串行执行。并行调用的数量、资源预算和失败合并规则由运行时控制，不能只根据模型同时返回了几个调用就直接并发。

## 观察结果决定下一轮

动作执行后，运行时需要把结果整理成模型可以使用的观察：

- 动作是否真正执行；
- 外部系统返回了什么；
- 结果是否改变了任务事实；
- 是否产生新的错误或约束；
- 原计划中的哪些步骤已经完成；
- 是否还有待验证的内容。

观察结果应带有来源、时间和状态。工具返回“请求已接受”时，模型不能直接把它理解为业务目标已经完成；只有后续观察或终态检查确认结果，循环才可以结束。

## 继续、修正和重新规划

下一轮不应只有“继续调用模型”这一条路径：

| 当前情况 | 循环动作 |
| --- | --- |
| 当前动作成功，仍有待办 | 继续执行下一步 |
| 参数错误但动作可修正 | 修正参数后重试 |
| 当前步骤假设不成立 | 替换当前步骤 |
| 计划无法覆盖新信息 | 重新规划剩余任务 |
| 关键信息缺失 | 追问或等待人工 |
| 外部状态未知 | 暂停并确认状态 |
| 目标已经验证完成 | 进入成功终态 |
| 权限、预算或安全条件不满足 | 停止或转入明确的失败状态 |

重试应绑定失败类型和动作状态。已经产生未知副作用的动作不能当作普通网络错误重复执行。

## 循环停止策略

停止策略是 Agent Loop 的核心组成。模型说“完成了”只能产生一个停止提案，不能直接成为成功信号。

### 成功终止

运行时需要验证目标、必要动作、结果证据和剩余待办。验证通过后才进入 `complete`。

### 人工或用户终止

用户取消、人工接管、审批拒绝和等待澄清都应成为显式状态，例如：

```text
waiting_for_human
cancelled
rejected
taken_over
```

### 预算终止

同时限制模型调用次数、工具调用次数、Token、成本、墙钟时间和并发任务数。`max_iterations` 只是预算的一部分。

### 无进展终止

检测以下信号：

- 状态快照连续不变；
- 相同工具和参数重复调用；
- 相同错误连续出现；
- 计划反复重写但没有新的产出；
- 多轮调用没有减少待办事项。

达到阈值后，进入重新规划、人工确认或失败状态，避免模型无限循环。

### 不可恢复和安全终止

权限拒绝、必要资源不存在、外部状态无法确认、关键输入始终缺失、终态校验多次失败以及安全策略阻断，都需要停止当前循环并保留退出原因。

停止状态至少应区分：

```text
complete
continue
replan
waiting_for_human
blocked
failed
cancelled
budget_exhausted
```

每个停止结果都应记录原因、证据、最后动作、任务版本和允许的下一步，保证任务可以解释、恢复或安全结束。

## 常见循环模式

模式的区别在于决策出现的时机和控制路径：

| 模式 | 循环特点 | 适合场景 |
| --- | --- | --- |
| ReAct | 观察和行动交替发生 | 路径未知、需要现场探索 |
| Plan-and-Execute | 先形成计划，再按步骤执行 | 任务可拆分、进度需要可见 |
| Reflection / Verify | 生成结果后增加独立检查 | 结果可验证、错误代价较高 |
| Router | 先选择专用路径，再进入局部循环 | 领域或工具集合差异明显 |
| Supervisor-Worker | 一个循环负责拆分和合并，多个循环负责执行 | 子任务独立、结果可合并 |

这些模式都必须共享同一套终态、预算、取消和失败出口。改变循环形态，不会改变停止责任。

## 如何验收 Agent Loop

重点观察循环行为：

- 模型提出完成时，终态检查是否真正执行；
- 工具结果和下一轮决策是否正确关联；
- 相同错误是否会触发无限重试；
- 计划重排是否保留原计划和触发原因；
- 用户取消后是否停止后续动作；
- 预算耗尽后是否进入明确状态；
- 外部状态未知时是否避免重复副作用；
- 重启或恢复后是否从正确的任务版本继续；
- 每次退出是否能解释原因并提供证据。

Agent Loop 的质量不取决于模型调用了多少轮，而取决于它能否在有限预算内持续利用观察修正行为，并在成功、失败、不确定和人工接管之间做出可验证的选择。

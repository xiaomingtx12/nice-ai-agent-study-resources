# Agent Loop：模型驱动的决策闭环

> **模块本质：** 将模型提出的下一步决策接入受控循环，由运行时检查、执行并观察结果，在有限预算内持续推进任务，并依据验收结果决定继续、重排、暂停或结束。

模型每次调用只看到一次输入，无法天然记住已经做过什么，也无法保证自己提出的计划一定可执行。Agent Loop 把模型放进一个受运行时约束的循环，让任务从一次生成扩展为连续的决策过程。

```text
任务目标
→ 模型查看当前输入
→ 提出下一步决策
→ 运行时检查并执行
→ 获得观察结果
→ 更新当前任务事实
→ 继续、修正、重排或停止
```

## 一、一轮循环如何运行 {/* #一轮循环如何运行 */}

一轮循环由多个有明确边界的动作组成：

1. **准备输入**：提供当前任务目标、已确认事实、待处理事项、可用能力和预算；
2. **生成决策提案**：模型选择行动、追问、计划更新、直接回复或结束；
3. **解释并检查提案**：运行时解析结构化输出，检查参数、权限、预算和当前阶段；
4. **执行或等待**：执行允许的动作，或者等待用户、外部系统和人工决定；
5. **形成观察结果**：把动作结果、错误、外部变化和新事实整理成下一轮可读取的结果；
6. **判断循环出口**：验证终态，决定继续、修正、重新规划、暂停或终止。

模型的自然语言不能直接改变运行时状态。模型提出的是决策提案，运行时负责将提案转换成受约束的状态转移。

### 1. 每轮调用都要重新装配 {/* #每轮调用都要重新装配 */}

模型 API 通常是无状态的。下一轮调用不会自动记住上一轮的系统规则、用户任务、模型决策和工具结果，运行时需要根据当前状态重新生成本轮输入。

因此，一轮循环保存的不是“模型已经记住的内容”，而是下一轮必须重新装配的事实：

```text
当前任务
+ 已确认事实
+ 历史决策摘要
+ 工具结果
+ 当前可用能力
+ 预算和停止条件
```

上下文过长时优先保留会影响下一步的事实、动作和结果；被压缩的原始材料要保留来源和重新读取路径。

## 二、模型输出应该表达什么 {/* #模型输出应该表达什么 */}

Agent Loop 需要让模型明确区分几类决策：

| 决策类型 | 典型含义 |
| --- | --- |
| `act` | 调用工具或执行一项外部动作 |
| `ask` | 缺少会改变路径的关键信息，需要追问 |
| `replan` | 当前假设或步骤无法继续，需要调整剩余计划 |
| `respond` | 已有足够依据，可以向用户返回结果 |
| `stop` | 满足终态，或已经进入明确的失败、取消和等待状态 |

初始系统提示词应说明任务目标和成功条件从哪里读取、当前阶段允许哪些动作、哪些事实必须验证、何时需要追问，以及模型输出必须遵循的决策协议。

思考协议可以要求模型整理计划、假设、依据和下一步，但这些内容服务于决策，不等同于运行时保证。循环上限、权限、预算和终态检查都由运行时强制执行。

一次模型响应可以提出多个工具调用。运行时需要先判断它们之间是否存在数据依赖：相互独立的调用可以并行执行；后一个调用需要前一个结果时必须串行执行。并行调用的数量、资源预算和失败合并规则由运行时控制，不能只根据模型同时返回了几个调用就直接并发。

## 三、观察结果决定下一轮 {/* #观察结果决定下一轮 */}

动作执行后，运行时需要把结果整理成模型可以使用的观察：

- 动作是否真正执行；
- 外部系统返回了什么；
- 结果是否改变了任务事实；
- 是否产生新的错误或约束；
- 原计划中的哪些步骤已经完成；
- 是否还有待验证的内容。

观察结果应带有来源、时间和状态。工具返回“请求已接受”时，模型不能直接把它理解为业务目标已经完成；只有后续观察或终态检查确认结果，循环才可以结束。

## 四、继续、修正和重新规划 {/* #继续修正和重新规划 */}

下一轮不应只有“继续调用模型”这一条路径：

| 当前情况 | 循环动作 |
| --- | --- |
| 当前动作成功，仍有待办 | 继续执行下一步 |
| 参数错误但动作可修正 | 修正参数后重试 |
| 当前步骤假设不成立 | 替换当前步骤 |
| 计划无法覆盖新信息 | 重新规划剩余任务 |
| 关键信息缺失 | 追问或等待人工 |
| 外部状态未知 | 暂停并确认状态 |
| 目标已经验证完成 | 进入成功终态 |
| 权限、预算或安全条件不满足 | 停止或转入明确的失败状态 |

重试应绑定失败类型和动作状态。已经产生未知副作用的动作不能当作普通网络错误重复执行。

## 五、长任务用计划管理依赖与失效范围 {/* #长任务用计划管理依赖与失效范围 */}

短任务可以直接按观察与动作交替推进。任务包含多个产物、并发步骤或不可逆操作时，再把计划存成可检查的数据。每步至少关联目标、输入版本、依赖、完成证据和副作用范围。自然语言待办清单便于展示，但单独靠勾选无法判断依赖是否成立。

例如“读取资料 → 生成报告 → 审核 → 发布”，审核应绑定报告版本。用户补充资料后，重新生成的报告需要重新审核；已经读取且仍有效的旧资料可以保留，旧审核不能直接继承。重排时标记受影响步骤及其下游失效，保留不受影响的完成记录。

计划执行前检查依赖是否成环、输入是否存在、必要授权能否取得、预计资源是否超出预算。DAG（有向无环图）适合表达没有循环的步骤依赖；需要反复修订时，可以把修订循环封装在一个有次数上限的步骤中，避免计划本身无限展开。

计划越长，交接、失效和恢复点越多。可以将确定性的连续数据处理收进代码步骤，减少模型参与的中间决策；合并时仍要保留授权、校验和可恢复边界。不能为了减少步数，把校验与不可逆执行合成一个无法中断的黑盒。

并行优化还要分别计算总工作量与关键路径。关键路径是决定最早完成时间的依赖链；缩短它可能降低延迟，但所有必要分支的正确性与成本仍影响最终交付。一个任务很快地跑完失败分支，不代表可靠性提高。

## 六、循环停止策略 {/* #循环停止策略 */}

停止策略是 Agent Loop 的核心组成。模型说“完成了”只能产生一个停止提案，不能直接成为成功信号。

### 1. 成功终止 {/* #成功终止 */}

运行时需要验证目标、必要动作、结果证据和剩余待办。验证通过后才进入 `complete`。

### 2. 人工或用户终止 {/* #人工或用户终止 */}

用户取消、人工接管、审批拒绝和等待澄清都应成为显式状态，例如：

```text
waiting_for_human
cancelled
rejected
taken_over
```

### 3. 预算终止 {/* #预算终止 */}

同时限制模型调用次数、工具调用次数、token、成本、墙钟时间和并发任务数。`max_iterations` 只是预算的一部分。循环步数少，也可能有一次长时间阻塞的工具；主 Agent 调用少，也可能派生了大量子任务。

### 4. 无进展终止 {/* #无进展终止 */}

检测以下信号：

- 状态快照连续不变；
- 相同工具和参数重复调用；
- 相同错误连续出现；
- 计划反复重写但没有新的产出；
- 多轮调用没有减少待办事项。

达到阈值后，进入重新规划、人工确认或失败状态，避免模型无限循环。

动作重复只是一种信号。模型不断变换搜索关键词，可能让工具签名每次都不同，却没有得到新证据。进度应落到经验证的变化，例如排除了一个候选原因、产生了新的可用产物、解决了一个验收失败项。计划文本改写次数和模型自报完成百分比都不能单独换取更多预算。

正常的异步任务轮询可能暂时没有进展。它应有单独的等待状态、轮询间隔和期限，不必每次都重新调用模型；到期后再决定继续等待还是交回用户。

### 5. 不可恢复和安全终止 {/* #不可恢复和安全终止 */}

权限拒绝、必要资源不存在、外部状态无法确认、关键输入始终缺失、终态校验多次失败以及安全策略阻断，都需要停止当前循环并保留退出原因。

运行状态至少应区分继续、重排、等待和各类终态：

```text
complete
continue
replan
waiting_for_human
blocked
failed
cancelled
budget_exhausted
```

每个停止结果都应记录原因、证据、最后动作、任务版本和允许的下一步，保证任务可以解释、恢复或安全结束。

## 七、预算在调用前预留，调用后结算 {/* #预算在调用前预留调用后结算 */}

仅在每轮结束后检查总用量，会允许正在进行的调用继续超支。并发时更明显：两个子任务都看见同一份剩余额度，各自判断够用，实际消费却超过父任务上限。

建议由任务级账本统一管理已结算、已预留和待核对的消耗。调用前按输入规模、输出上限与工具配额申请额度；成功预留后才派发；返回后按实际用量结算并释放余额。预留必须通过同一存储中的原子更新或等效并发控制完成，不能让各 worker 只读余额后自行扣减。

| 时点 | 预算处理 | 失败出口 |
| --- | --- | --- |
| 模型、工具或子任务派发前 | 检查父任务剩余额度并预留 | 拒绝新工作、降低范围或等待追加 |
| 正常返回 | 记录实际用量，结算预留 | 用量异常进入核对，不静默归零 |
| 超时或连接中断 | 保留待核对记录 | 查询外部状态与用量，避免立刻释放全部额度 |
| 任务恢复 | 加载已有账本与未结算调用 | 不重新分配一份完整初始预算 |
| 父任务终止 | 停止新派发，处理仍在运行的调用 | 保留可能继续计费的任务清单 |

预算覆盖主模型、子 Agent、摘要、评分和重试。子任务可以有更小的局部上限，但它消费的是父任务总预算的一部分。需要避免局部账本各自合规、任务树总体超支。

金额预留依赖计价与用量上限。外部服务计费不透明、取消不保证立即生效时，应明确预算控制的误差和在途上界；不能因为本地已发取消就宣称费用停止。报表与计价版本的维护见[证据与反馈](../06-observation/agent-observability.md)。

### 1. 追加预算与降级都要保留任务约束 {/* #追加预算与降级都要保留任务约束 */}

追加额度应绑定已经验证的阶段成果、剩余工作和总上限，不能由模型自行批准。预算不足时，可以交付已完成部分、缩小探索范围或减少非必要候选；权限检查、必需证据和终态验收不能作为省成本的可选项。

更换模型也是需要评测的策略。便宜模型增加重试后，成功交付成本可能更高。涉及关键动作时，如果降级后的能力不足以完成必要判断，应暂停该动作并说明未完成范围。

### 2. 源码中的循环限制需要核对计量范围 {/* #源码中的循环限制需要核对计量范围 */}

Deep Agents 声明版本 0.6.12 的源码快照中，`create_deep_agent()` 是组装模型、工具和中间件并返回可运行图的工厂函数。其返回配置包含 `recursion_limit`，用于限制底层图的执行步数。commit 未锁定，版本边界见[源码版本与路径约定](../../../application-notes/engineering/langchain-series/deepagents/source-baseline.md)。

源码：`libs/deepagents/deepagents/graph.py` → `create_deep_agent()` 的返回配置（第 1044–1051 行；以下为原配置字典，外围工厂调用省略）。

```python
{
    "recursion_limit": 9_999,
    "metadata": {
        "ls_integration": "deepagents",
        "lc_versions": {"deepagents": __version__},
        "lc_agent_name": name,
    },
}
```

这段配置没有时间、token 或金额字段。框架其他扩展是否提供预算能力，需要另查相应实现；不能把这个图步数值换算成任务费用上限。各类守卫的实际范围见[循环预算与终止控制](../../../application-notes/engineering/langchain-series/deepagents/19-loop-budget-and-termination.md)。

## 八、停止循环后，处理尚未结束的工作 {/* #停止循环后处理尚未结束的工作 */}

停止继续调用模型，只关闭了一个入口。队列里的写操作、已提交的远端任务和正在运行的子 Agent，需要各自的取消或收尾策略。

取消时先阻止新派发，使排队动作失效，再向执行中的操作传递取消请求。能够确认未生效的动作可以记为取消；已经生效的部分保留结果；效果未知的操作继续对账。任务退出记录应列出未完成项和仍需追踪的外部任务。

这一规则同样适用于预算终止和人工接管。用户接管之前，需要知道 Agent 是否仍可能写入同一资源，避免人和旧执行流同时修改。

## 九、常见循环模式 {/* #常见循环模式 */}

模式的区别在于决策出现的时机和控制路径：

| 模式 | 循环特点 | 适合场景 |
| --- | --- | --- |
| ReAct | 观察和行动交替发生 | 路径未知、需要现场探索 |
| Plan-and-Execute | 先形成计划，再按步骤执行 | 任务可拆分、进度需要可见 |
| Reflection / Verify | 生成结果后增加独立检查 | 结果可验证、错误代价较高 |
| Router | 先选择专用路径，再进入局部循环 | 领域或工具集合差异明显 |
| Supervisor-Worker | 一个循环负责拆分和合并，多个循环负责执行 | 子任务独立、结果可合并 |

这些模式都必须共享同一套终态、预算、取消和失败出口。改变循环形态，不会改变停止责任。

## 十、在框架循环之外补上业务推进条件 {/* #框架中的循环定制 */}

### 1. 按流程约束选择编排入口 {/* #1-按流程约束选择编排入口 */}

LangChain 的 `create_agent()` 已提供模型与工具之间的循环，适合模型根据结果选择下一步。LangGraph 的 `StateGraph` 是显式声明状态、节点和边的图构建器，适合固定“检索、编辑、校验、审批、发布”等必经阶段；开放式 Agent 可以作为其中一个节点。Deep Agents 的 `create_deep_agent()` 在循环上装配计划、文件和委派能力，适合长任务中的资料处理与子任务执行。

文档维护业务可以让 Agent 自行选择如何搜集资料和修改草稿，但把独立校验、审批与发布顺序写入图。模型提出完成只表示准备进入校验节点；只有引用、版本和变更范围通过检查，流程才能进入发布阶段。

### 2. 用内置限次控制循环，用业务账本控制费用 {/* #2-用内置限次控制循环用业务账本控制费用 */}

`ModelCallLimitMiddleware` 是 LangChain 统计并限制模型节点调用次数的中间件。以下为 LangChain 1.3.7 的 `libs/langchain_v1/langchain/agents/middleware/model_call_limit.py` 类文档中的配置原文，省略导入和 Agent 装配。

```python
call_tracker = ModelCallLimitMiddleware(thread_limit=10, run_limit=5, exit_behavior="end")
```

通过 `create_agent()` 的 `middleware` 接入后，`run_limit` 限制一次运行，`thread_limit` 限制执行线累计次数；跨调用保存执行线计数需要配置 checkpointer。示例中的次数用于演示，实际值应按任务评测确定。

源码的单次运行计数使用 `UntrackedValue`，即不写入检查点的状态通道，不能拿它做跨恢复的持久预算。一次模型节点运行内部也可能因重试或回退发起多次供应商请求。`exit_behavior="end"` 会结束循环并给出限次提示，业务层需要将终态记成预算或次数终止，而不是任务成功。

如果需要控制费用，在实际模型请求边界记录每次尝试的预算预留与用量，在工具调用边界记录工具费用，并让子任务共享父任务额度。包装器的先后顺序要让重试中的每次实际调用经过计量；外层只记一次入口调用，会漏掉内部重试。

### 3. 将无进展、取消和失败接成明确出口 {/* #3-将无进展取消和失败接成明确出口 */}

图状态可以保存已确认的证据版本、草稿版本和待办数量；控制节点比较阶段前后的变化，决定继续、补充输入或结束。待办被模型改成完成，只是计划更新，不能替代实际产物校验。

达到截止时间或收到取消后，要阻止新的模型和工具请求，并登记已经发出的写操作和子任务，继续处理其结果。验收时分别模拟单轮限次、跨恢复累计限次、重试消耗和父任务取消，确认它们走到不同且可解释的终态。实现定位见[调用治理](../../../application-notes/engineering/langchain-series/langchain/07-call-governance.md)与[循环预算和终止](../../../application-notes/engineering/langchain-series/deepagents/19-loop-budget-and-termination.md)。

## 十一、如何验收 Agent Loop {/* #如何验收-agent-loop */}

重点观察循环行为：

- 模型提出完成时，终态检查是否真正执行；
- 工具结果和下一轮决策是否正确关联；
- 相同错误是否会触发无限重试；
- 计划重排是否保留原计划和触发原因；
- 用户取消后是否停止后续动作；
- 预算耗尽后是否进入明确状态；
- 外部状态未知时是否避免重复副作用；
- 重启或恢复后是否从正确的任务版本继续；
- 每次退出是否能解释原因并提供证据。

Agent Loop 的质量不取决于模型调用了多少轮，而取决于它能否在有限预算内持续利用观察修正行为，并在成功、失败、不确定和人工接管之间做出可验证的选择。

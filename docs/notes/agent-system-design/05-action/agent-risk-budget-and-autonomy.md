# Agent 影响范围与渐进授权：限制累计效果，按证据放权

允许调用一个工具，还需要明确它能作用于哪些对象、产生多少效果、持续多久。一次只改十条记录的 Agent，如果不断重试或派生执行者，仍可能改完整个数据库。控制应覆盖所有消费同一份授权和额度的执行路径。

这类设计有两个时间尺度：当前任务最多影响多大范围，以及某项能力在长期运行后可以获得多大自治范围。一次小范围任务通过验收，不会自动扩大长期权限。

## 一、按具体后果定义边界

| 边界 | 限制内容 | 例子 |
| --- | --- | --- |
| 能力与身份 | 工具、凭据、租户、对象与字段 | 文档整理者能编辑指定目录，没有发布凭据 |
| 执行环境 | 文件、网络、进程、算力和运行时间 | 只能写隔离工作区，不能连接生产数据库 |
| 业务效果 | 修改数量、外发人数、资金、频率和总量 | 本批只处理已确认的对象集合，数量有上限 |

环境隔离无法代替业务效果控制。一个合法 API 可以在允许的网络范围内修改大量记录；一个只读工具也可能导出过多敏感信息。边界应由实际后果决定，不能只依据工具名或自述的“只读”标签。

当前执行范围取各层约束的交集。对象必须同时属于身份、任务和本次动作允许的集合；数量与费用服从各层有效上限；任一层拒绝，都不能依靠另一层的允许覆盖。

正在执行的 Agent 不应持有修改自身硬上限、关闭计量或跳过提交入口的能力。策略可以调整，但调整走独立管理路径并保留版本与责任。

## 二、子任务分配额度，不能复制额度

假设一项任务最多允许更新 100 条记录，拆成四个子任务后，每个子任务都配置“最多 100 条”，就扩大了整个任务的影响范围。应使用共同的父级账本，子任务从中预留自己的份额。

在一个额度池内，应持续满足：已消费量、已预留未结算量与可用量之和等于总量。父级分配给子级的份额视为父级的占用；汇总时不能再把子级已消费量重复加到同一份占用上。

预留必须原子化。剩余 10 条额度时，两个执行者同时各申请 8 条，不能都在读取余额后放行。数据库事务或等效的并发控制应把“检查和占用”作为一次操作完成。

数量之外，还可按任务需要约束运行时间、外发速率、并发数、子任务总数和递归深度。不要只限制单个 worker，却遗漏恢复进程、回调处理器和人工补单也在消费相同业务额度。

## 三、未知结果继续占用额度

效果提交前建立动作身份与额度预留，成功确认后转为已消费；明确未生效时才释放。请求超时后保持“结果未知”，继续占住相关额度，直到独立查询或对账给出结果。

例如一次远端批量更新没有返回，立即释放额度并再次提交，可能让旧请求和新请求都生效。恢复应沿用原业务幂等键，并检查请求摘要一致；重试是否安全还取决于下游的去重和查询能力。

子任务结束也不能立即返还全部剩余额度。还要确认没有在途请求、未知效果或尚未结算的子任务。控制面发出取消，只代表取消请求已发送，不能据此认定外部动作已经停止。

停止开关应位于模型之外，能阻止新的提交。已发出的请求继续核实，已发生的效果进入修正或补偿流程。停止与恢复承担不同责任。

## 四、批准绑定可审查的具体提案

审批材料应先做到对象明确、证据充分、差异突出、影响可说明。能通过工具核对的事实，由系统先核对；事实缺失时标明需要补证，不能只抛给人一句“是否继续”。

一份提案应让审批者看清当前动作、对象与参数、相较之前的变化、证据引用、外部效果、可逆性、未决事项，以及授权范围和有效期。批准结果绑定这份提案的版本或摘要，并记录批准者身份与策略版本。

执行前重新核对提案、批准、当前权限和业务前置条件。等待期间对象版本变化，旧批准可能失效；余额或剩余额度也可能变化，必须在提交时重新检查，并通过事务或版本条件避免检查后的竞态。

审批范围要覆盖用户已经明确授权的工作，避免对同一范围重复索取确认；范围扩大或提案关键条件变化时，再依据策略判断是否需要新的批准。

放宽“哪些动作可以免审批”的规则本身也是变更。应记录提出者、修改原因、批准者、生效范围和策略版本，不能让执行者因一项动作被拒绝，就自行放宽规则再提交。

暂停与恢复的运行机制见[人机协作](../04-decision/agent-human-in-the-loop.md)。这里关注的是批准内容与实际效果怎样保持一致。

## 五、单次扩大范围与长期放权分别管理

### 1、当前任务逐步提交

在既定授权内，可以先预演、再小批执行、核验后继续。知识库维护先生成差异，再处理少量文件并检查引用，确认没有系统性问题后处理剩余文件。每一阶段仍受同一任务总量约束。

预演需要真实表达其限制：不写生产数据的检查，尚未验证真实写入时的并发、超时和重复提交；一个小样本通过，也不代表它覆盖了全部异常输入。

### 2、长期权限按能力与范围积累证据

长期放权可以从只读观察、形成建议、影子运行，逐步进入受限执行，再到约定范围内的自主执行。等级名称和数量按业务确定，关键是每次扩大了什么、用什么证据支持。

信任对象应具体到能力版本、环境与业务范围。例如“该版本能在指定目录自动修复已确认的链接”，不能外推成“可以自行发布网站或重写全部内容”。

晋级证据保存运行身份、外部结果、任务切片、策略与能力版本、发生时间和验证者。重复提交同一次成功不增加样本量；只选简单任务也不能证明更宽范围可靠。

证据窗口确定后再形成授权提案。等待批准期间出现足以改变判断的失败，应重新评估提案。一次放权完成后，还需观察人工纠正、回滚和事故是否增加。

## 六、降权要能即时生效，并留出恢复路径

严重失败可以触发独立控制面冻结对应能力、撤销旧凭证或收窄范围。撤销结果必须在实际提交入口生效，不能只更新管理界面的等级。降权入口自身也要有身份与权限控制。

重新放权时，核对修复后的版本、策略和新证据；旧版本积累的好成绩不能直接抵消新问题。对局部能力的故障，可以精确收回对应范围，避免无关能力一起停止。

每个业务还应保留明确的重大例外边界，由具备责任的主体裁决。自动化程度提高后，人的工作可以集中在标准、困难样本和事故处理上，普通范围内的动作继续按既定规则完成。

## 七、用并发、重放与撤权验证控制

| 场景 | 应观察到的行为 |
| --- | --- |
| 两个 worker 同时争取最后一份额度 | 合计占用不超限，拒绝有明确原因 |
| 将一个批次拆成多个小批次 | 累计效果仍受根任务限制 |
| 外部请求结果未知 | 额度不提前释放，保留对账任务 |
| 相同动作身份携带不同参数 | 拒绝重放并保存不匹配证据 |
| 批准后对象或策略变化 | 执行前发现变化，按失效规则重新判断 |
| 降权后继续使用旧凭证 | 新提交被阻止，在途效果继续核实 |
| 用重复成功申请升权 | 证据去重，不增加有效样本 |

这些检查可在隔离环境使用受控外部接口完成。额度、批准和权限事件通过共同的任务与动作身份连接，完整记录方法见[可观测性](../06-observation/agent-observability.md)。

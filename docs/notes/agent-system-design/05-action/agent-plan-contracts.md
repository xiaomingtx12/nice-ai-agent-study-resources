# 计划与工件契约：让 Agent 按依赖执行、在局部恢复

一份计划要参与执行，就必须能回答：哪一步现在可以开始，依据哪份输入，做完用什么确认，失败会影响哪里。仅有“查询、整理、提交”三项清单，恢复程序仍然不知道哪些结果可用、哪些副作用已经发生。

计划控制任务之间的依赖，工件契约控制相邻步骤之间的数据。两者结合，才能在中途失败后保留有效结果，并阻止错误继续传向下游。

## 一、将计划写成运行时可以检查的对象

每个步骤需要稳定身份、允许调用的处理入口、依赖、输入引用、输出要求、状态和验收条件。执行器只调度前置条件满足的步骤，并记录每次尝试。

以知识库批量更新为例，读取资料后产生核验工件，修改阶段消费核验工件，检查阶段消费修改结果。发布是否属于任务范围，由目标合同与授权决定。修改已经完成，不能因为后续检查失败就重跑所有文件。

依赖可以表示为有向无环图，即步骤有方向且不存在循环依赖。模型提出图，程序检查缺失节点、循环、非法处理入口和输入绑定。调查需要反复补证时，可在一个步骤内部运行有界循环，再把验收后的产物交给外层计划。

步骤状态要分清等待、就绪、执行中、等待验收、完成、失败、阻塞和结果未知。函数正常返回只能证明调用结束；任务要求的后置条件满足以后，才能进入已验收的完成状态。

## 二、局部重排保留已经发生的事实

失败后，规划器提交针对受影响范围的计划补丁。校验器检查它是否仍符合原目标、范围、预算与业务不变量，再决定是否接受。

| 补丁约束 | 要避免的问题 |
| --- | --- |
| 范围限于失败步骤及其受影响后继 | 一个局部错误引发全任务无差别重启 |
| 不改写已确认外部效果的历史记录 | 已经提交的动作被伪装成从未执行 |
| 保留对范围外有效事实的依赖 | 重排后跳过原来的核验或对象绑定 |
| 新节点仍受权限、数量和预算约束 | 恢复过程无限扩展任务 |
| 新计划有版本，旧批准按绑定范围重新判断 | 修改后的动作借用旧批准 |

保留完成记录不等于产物永久有效。上游资料变更后，可以追加“旧产物失效”的事件并重新计算受影响部分；已经产生的外部效果，则通过有身份、有授权的修正或补偿动作处理。

例如某篇文章基于旧资料完成编辑，后来资料更新。系统应保留旧稿与旧检查记录，生成新的编辑任务；不能直接删除历史状态后宣称这是第一次处理。

## 三、每段交付具名工件，下一段按契约签收

提示链把一个任务分为顺序明确的处理段。每段正式交付一份工件，下一段在检查通过后才能消费。单纯拆成多次模型调用，尚未建立这种边界。

工件契约需要说明类型、结构版本、业务对象、输入版本、关键字段、来源引用、生成者和内容摘要。全文可放入工件存储，下一段读取引用和完成本职工作所需的字段。

例如“替代链接核验”工件不只返回“可以替换”，还要绑定原文件、原链接、候选地址、内容对应关系和核验时间。修改阶段使用这些已经验收的字段，避免从自由文本里重新推测地址。

段间检查分四层：

| 层次 | 检查内容 | 能发现的错误 |
| --- | --- | --- |
| 语法 | 内容能否解析 | 不完整 JSON 等格式错误 |
| 结构 | 字段、类型、枚举和版本是否兼容 | 缺少文件身份或字段类型不符 |
| 业务语义 | 必须成立的关系和状态条件 | 替代项遗漏、对象重复、流程跳步 |
| 事实与来源 | 关键值能否独立核实 | 工件声称已写入，实际文件仍是旧内容 |

后两层需要业务规则和独立证据。工件自己声明“已校验”不能证明其内容正确；总条数一致，也不能证明逐项对应关系正确。检查应覆盖真正不能错的字段与关系。

检查失败时返回原因、证据和允许的恢复方式。格式错误可以重新生成；版本过期需要刷新事实；对象不匹配需要核对身份；权限不足不能通过反复重试解决。

## 四、在实际执行前核对当前状态

计划可能早于执行生成，工件也可能在等待期间失效。步骤最好保存业务对象引用和预期版本，在真正提交前读取当前状态并进行版本条件检查。

工具调度先根据身份、任务和阶段限定可用工具，再核对本次调用的对象、参数、状态与批准。工具在可见集合里，只表示它可能被使用；每一次实际动作仍须符合执行条件。隐藏工具也不足以构成权限保证，真实执行入口必须无法被旁路绕过。

前置检查阻止不合格请求产生副作用，受控执行记录实际尝试，后置检查确认结果并决定是否供下游使用。后置检查失败时，副作用可能已经发生，必须记录待核实或待补偿状态。

例如文件已写入，但检查发现引用错误，可以停止发布并修正文件；若通知已经发出，事后拒绝“成功”输出并不能撤回通知。不同效果需要不同恢复办法。

## 五、检查点与动作账共同支持恢复

检查点保存流程确认到哪里，动作账保存外部动作是否提交、采用什么请求、取得什么回执。二者之间可能存在崩溃窗口，需要对账。

| 观察到的情况 | 恢复动作 |
| --- | --- |
| 执行入口拒绝，尚未提交 | 修正前置条件后重新申请 |
| 外部确认完成，本地状态未更新 | 补记结果，保留原动作身份 |
| 请求超时，外部结果不明 | 保持未知，用原身份查询 |
| 外部确认未生效 | 在当前条件仍允许时重试 |
| 效果已发生，后置验收失败 | 阻止依赖步骤，创建修正或补偿任务 |

重试沿用稳定的业务幂等键，并绑定请求内容摘要。同一个键出现不同对象或参数时，应拒绝。幂等键不能只由每次网络尝试随机生成，否则系统仍会把重试当成新动作。

本地唯一约束能防止本地重复登记，无法单独保证外部系统只执行一次。下游支持幂等或结果查询时，恢复可以据此确认；下游两者都不支持时，未知结果可能需要人工核实，不能宣称“自动恢复即可保证一次”。

## 六、重试、补偿和整链成本分别验收

业务工件不合格的重试，应补充失败原因、刷新证据或调整方法。相同条件下再次生成只是重新抽样，需要计入有限预算。基础设施短暂不可用可以按退避策略重试，但要满足幂等与次数限制。

补偿记录保持到外部结果确认，不能在“发起补偿”后立即清除。补偿失败需要保留责任人、下一次核查与剩余预算；不能用一个“已标记回滚”的字段代表世界已经恢复。

验收这条链，可以使用三类隔离测试：

- 中间工件字段齐全但事实错误，确认下游动作没有开始。
- 外部动作成功、本地写回前崩溃，确认恢复不会重复提交。
- 补丁试图覆盖已完成步骤或删除必要依赖，确认计划校验拒绝。

同时统计端到端通过率、等待时间、重复读取、重试和恢复成本。拆分的每一段都增加交接代价；字段转换和确定性检查优先由程序完成，需要语言理解或生成的部分再交给模型。

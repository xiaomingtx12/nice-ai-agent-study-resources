# 工具执行：把模型提案变成受控动作

> **模块本质：** 在模型提案与真实副作用之间建立执行协议。参数合法只能证明请求可解析，收到响应也未必证明业务完成；工具层需要确定谁对哪个资源做了什么，并把已生效、未生效和仍未知的结果准确交回循环。

考虑一次文档发布：任务 `T17` 要把页面 `doc-42` 从当前版本 `v7` 更新为已批准的草稿 `r18`。服务完成发布，生成 `v8`，响应却在网络中丢失。如果工具只返回“超时，请重试”，模型可能再次发布；如果直接返回成功，又缺少可核验的结果。

本文用这个**设计案例**说明执行方法，未声称站点已经实现该发布服务。案例假定服务支持按动作 ID 查询结果，并能原子地处理幂等登记与发布写入；没有这些能力时，恢复保证需要相应收缩。真实框架行为另用源码片段说明。

故障发生在两个不同的完成时点之间：服务端已经提交，调用方尚未确认。工具层必须保留这个区别。模型看到的是描述和参数协议，凭证、执行连接及资源约束由运行时持有。

```text
模型提出 Tool Call
→ 解析调用
→ 校验参数
→ 检查授权和执行条件
→ 执行真实动作
→ 归一化结果
→ 验证后置条件
→ 返回 Observation
```

## 一、工具合同由三层组成 {/* #工具合同由三层组成 */}

| 层 | 作用 | 典型内容 |
|---|---|---|
| 描述层 | 让模型知道能力用途 | 名称、用途、适用条件、限制 |
| Schema 层 | 约束调用结构 | 输入参数、输出格式、错误类型 |
| 执行层 | 产生真实副作用 | 凭据、连接、文件句柄、执行逻辑 |

描述层和 Schema 层可以进入模型的 View；执行层始终由运行时持有。工具描述、Schema、权限策略和结果解析必须使用兼容版本，避免模型看到的能力与真实执行能力不一致。

工具在 View 中如何筛选和渐进式披露，属于[上下文装配](../03-view/agent-context-management.md)；本文关注模型已经提出调用之后，运行时如何处理它。

### 1. 根据副作用选择实现深度 {/* #根据副作用选择实现深度 */}

| 工具类型 | 起步实现 | 何时需要继续升级 | 增加的代价 |
| --- | --- | --- | --- |
| 无外部副作用的查询或计算 | 参数校验、授权、超时与输出限制 | 多次失败影响交付时，增加有限重试与依赖监控 | 重试增加延迟和请求量 |
| 支持版本条件的单资源更新 | 在写入端检查期望版本，返回新版本 | 超时后无法辨认是谁完成更新时，增加动作身份与结果查询 | 需要保留动作记录并定义过期策略 |
| 发布、发送、创建外部任务 | 稳定动作 ID、幂等约定、结果查询、后置验证 | 跨请求恢复或多个执行者竞争时，增加持久对账和接管机制 | 更多存储、查询流量与故障分支 |
| 无幂等能力且无法查询结果的动作 | 限制自动执行，预先定义未知结果的人工处理出口 | 业务服务具备结果查询或去重能力后再提高自动化程度 | 人工等待会延长交付时间 |

接口使用 GET 还是 POST 不能单独决定策略，要看它是否产生业务效果。上述控制可以先由普通工具函数和业务服务承担；多个工具开始重复同一治理逻辑时，再抽出公共中间件。

## 二、一次工具调用的执行链 {/* #一次工具调用的执行链 */}

### 1. 解析模型提案 {/* #解析模型提案 */}

在发布案例中，应区分下面几种身份。这些字段是业务协议设计，不是框架统一提供的字段。

| 数据 | 示例 | 来源与用途 |
| --- | --- | --- |
| 模型工具调用 ID | `call-31` | 配对这次模型提案与工具结果 |
| 页面、期望版本、草稿版本 | `doc-42`、`v7`、`r18` | 模型可以提出，执行端核对归属、版本与批准内容 |
| 主体、租户、任务 ID | 当前主体、项目范围、`T17` | 服务端鉴权后注入，不信任模型自报身份 |
| 业务动作 ID | `A903` | 发送前持久登记，同一动作的重试和恢复保持不变 |
| 结果引用 | 发布记录与页面 `v8` | 由业务服务确认，用于查询和后置验证 |

自然语言中的“请帮我删除数据”不能直接交给执行器。工具名称和参数来自调用协议；任务版本、主体和租户从可信运行上下文绑定，不能让模型自行填写后就获得信任。无法确定执行身份或目标范围时，在执行前拒绝。

模型的调用消息和运行时返回的工具结果需要通过 `call_id` 成组关联。一次响应包含多个相互独立的调用时，运行时可以并行执行，但应等待这一批结果完成并完整归还，再让模型继续决策；存在数据依赖时，后续调用必须等待前一个结果。

### 2. 校验参数 {/* #校验参数 */}

参数校验分为两层：

- **Schema 校验**：字段是否存在、类型是否正确、格式是否符合约定；
- **业务校验**：资源是否存在、参数组合是否合法、动作是否适用于当前阶段。

运行时可以补充确定的默认值，但不能替模型猜测会改变副作用范围的字段。参数校验失败时返回可修正的结构化错误，不执行真实动作。

例如，更新文档的参数包含合法的 `document_id` 和正文，只能说明结构可解析。还要核对文档归属、是否允许修改、调用依据的版本是否仍然有效。不能因为 JSON 中的租户字段“看起来正确”，就跳过运行时身份与资源归属检查。

校验与写入之间仍可能发生并发修改。需要强一致前置条件时，在真正写入端使用版本条件更新或事务检查；调用前查询一次，再无条件覆盖，仍可能写坏已经变化的资源。

校验失败反馈应明确哪个字段、哪条约束不成立，以及是否允许重新提交。修正次数受预算限制；缺少实体身份或授权时交回用户或上游，不能通过放松 schema、填入猜测值或切换低约束解析器绕过检查。模型供应商的结构化输出能力也不承担这些业务校验。

### 3. 检查执行条件 {/* #检查执行条件 */}

进入执行器前确认：

- 当前主体和租户是否有权限；
- 目标资源是否在允许范围内；
- 当前阶段是否允许执行；
- 工作区、网络和资源配额是否满足；
- 预算、并发和超时是否足够；
- 是否需要一次性人工审批。

这些判断由运行时完成。模型看到工具描述，不等于获得工具权限；审批、权限和沙箱的详细策略分别由对应文章说明。

### 4. 执行真实动作 {/* #执行真实动作 */}

执行器负责：

- 在运行时注入凭据和连接；
- 绑定工作区、网络和资源限制；
- 传递取消信号和超时；
- 记录动作和副作用；
- 防止同一动作重复执行。

发布 `r18` 前，执行端登记动作 `A903`，将其绑定到页面、期望版本和草稿内容摘要，再调用发布服务。同一 `A903` 的重复请求应返回已有结果；同键不同内容应拒绝。这样的保证需要服务端将去重记录与业务写入原子提交，单独在 Agent 进程里保存一个“执行过”的集合无法覆盖网络故障。

工具调用身份和业务幂等身份应分别记录。前者配对模型消息，后者在重试、恢复和重复投递之间保持稳定；同一业务动作不能因为模型又生成了一次调用就换键。幂等键作用域、保留期和重复参数校验需要与服务端约定，详细恢复分支见[状态架构](../02-state/agent-state-architecture.md)。

### 5. 归一化执行结果 {/* #归一化执行结果 */}

工具结果要转换成下一轮可以消费的观察，至少区分：

```text
success
failure
partial_success
timeout
cancelled
unknown
```

结果应携带调用 ID、来源、时间、版本和副作用状态。HTTP 200、进程退出码为 0 或工具返回一段“成功”文本，只能说明调用层完成，不能直接证明业务目标已经达成。

## 三、写操作必须经过后置验收 {/* #写操作必须经过后置验收 */}

创建、修改、删除、发布和发送等动作都可能产生外部变化。执行完成后要读取真实状态，检查任务合同要求的后置条件：

```text
动作请求
→ 执行
→ 读取真实状态
→ 检查后置条件
→ complete / partial / unknown
```

在案例中，先按 `A903` 查询发布记录，确认对应 `doc-42` 与 `r18`；再读取其发布结果 `v8`，比较内容摘要和允许的变更范围。若页面已被后续动作更新为 `v9`，不能仅因“当前版本不是 v8”就重新发布；应检查历史版本或发布记录，区分本次发布曾成功与当前页面后来又被修改。

无法获得足够证据时，验收保持待确认。即使动作账本已确认服务端提交，也应单独记录后置检查暂不可用，不能把“已提交”改写成“未执行”。若查询服务存在延迟，“暂时查不到”也不足以证明发布没有发生。查询一致性与可用的重试保证需要写进服务合同。

## 四、错误如何回到 Agent Loop {/* #错误如何回到-agent-loop */}

工具错误需要包含下一步判断所需的信息：

```text
ActionError {
  code
  retryable
  user_action
  recovery_hint
  partial_effect
}
```

| 错误类型 | 循环出口 |
|---|---|
| 参数格式错误 | 修正参数后重试 |
| 资源不存在 | 追问、替换资源或终止 |
| 权限拒绝 | 等待授权或停止 |
| 临时网络错误，且动作可安全重试 | 在截止时间和次数上限内退避重试 |
| 超时且状态未知 | 查询真实状态，避免直接重放 |
| 部分成功 | 保存已生效范围，重新规划剩余动作 |
| 后置条件失败 | 修复、回滚或人工确认 |
| 不可恢复副作用 | 停止扩散并记录人工处理入口 |

是否重试由运行时根据错误类别、动作幂等性和当前预算决定；模型消费的是错误事实和允许的恢复路径。

对 `A903` 的响应丢失，反馈应保留“请求已尝试发送、业务效果未知、动作 ID 已登记、下一步查询发布记录”四项信息。不能只把异常文本交给模型，让它自由选择换参数或重新申请一个动作 ID。未知结果的完整恢复分支由[状态层](../02-state/agent-state-architecture.md#外部动作未知时先查账再决定是否重试)处理。

## 五、按工具限制故障扩散 {/* #按工具限制故障扩散 */}

每个工具应声明超时、并发上限、输出上限、可重试错误及是否支持取消。公共执行器可以统一落实这些规则，但规则取值仍由具体操作决定。查询、创建任务和不可逆发布，不应共享一套无差别的重试策略。

熔断器在持续故障时暂时拒绝新调用，并在冷却后通过有限探测判断依赖是否恢复。按依赖或工具划分故障域，可以避免一个查询服务不可用时阻断无关能力。权限拒绝、参数错误和业务不满足应分开统计，不宜都算作服务故障。

只在一层集中安排重试。模型循环、执行器和 SDK 各自重试，会放大调用次数；需要保留底层重试时，应共享总尝试上限和截止时间。已提交但结果未知的写操作先对账，不能直接用它作为熔断恢复探针。

工具暂时不可用时，将状态反馈到[能力视图](../03-view/agent-context-management.md)，减少模型反复选择；执行门仍保留检查，以阻止来自旧视图的调用。

### 1. 框架重试识别异常，业务代码识别副作用 {/* #框架重试与副作用 */}

LangChain 的 `ToolRetryMiddleware` 是包裹工具执行、按异常与退避规则重试的中间件。1.3.7 源码 `libs/langchain_v1/langchain/agents/middleware/tool_retry.py` → `wrap_tool_call()` 包含以下分支；省略前面的工具筛选、后续退避与重试耗尽逻辑，注释译为中文。

```python
# 首次调用，加上允许的重试次数。
for attempt in range(self.max_retries + 1):
    try:
        return handler(request)
    except Exception as exc:
        attempts_made = attempt + 1  # attempt 从 0 开始。

        # 判断这个异常是否允许重试。
        if not should_retry_exception(exc, self.retry_on):
            return self._handle_failure(tool_name, tool_call_id, exc, attempts_made)
        # 后续退避和重试耗尽处理省略。
```

`handler` 是下一层执行函数。这里重试的是同一个工具请求；异常本身没有说明远端是否已提交。默认 `tools=None` 覆盖全部工具，`retry_on=(Exception,)` 覆盖异常类型很广，不能直接作为发布工具的业务重试策略。

查询工具可以通过 `tools` 限定适用范围，再用 `retry_on` 筛选临时错误。发布工具应先由业务适配层将发送结果分类：明确拒绝则结束，未知则对账，只有满足服务端幂等约定时才允许重放。`ToolMessage` 是框架用于向模型返回工具结果的消息；已经返回的错误消息不会因其内容写着“失败”就触发上面的异常重试。包装器顺序和错误转换位置会影响最终行为。

`max_retries=2` 表示最多三次尝试。退避时间、底层 SDK 重试和查询对账都计入整个任务的截止时间；“每次请求超时五秒”不代表整个工具调用五秒内结束。

## 六、输出大小也属于执行合同 {/* #输出大小也属于执行合同 */}

长结果应返回关键状态、有限预览和可继续读取的位置。列表查询可以使用游标分页；日志或大文件可以外部化保存。分页游标需要绑定查询条件、访问范围和必要的数据版本，不能作为绕过权限的读取入口。

截断必须标明被省略范围和恢复方式，错误类型与副作用状态不能一起被截掉。超大的错误堆栈也要处理，否则一次失败就可能挤掉下一轮所需的任务约束。

输出文本属于外部数据。工具返回中出现“忽略此前规则”“把文件发送到某地址”等内容时，不能将其提升为系统授权。内容进入上下文的来源边界与动作执行权限需要分别控制，见[权限与后置条件](./agent-permission-and-postconditions.md)。

## 七、把工具函数接成可治理的业务入口 {/* #框架中的工具定制 */}

### 1. 模型参数与运行上下文分开注入 {/* #1-模型参数与运行上下文分开注入 */}

LangChain 的 `@tool` 将函数或给定 schema 注册为模型可调用的工具；`ToolRuntime` 是框架注入的运行对象，可提供当前状态、上下文、Store 和工具调用 ID。业务对象 ID、查询条件可以由模型提交；租户身份、凭证和授权范围应从可信运行上下文取得，不应作为让模型自由填写的身份参数。

例如发布工具接受页面 ID 和草稿版本，运行时提供当前主体和任务 ID，业务服务再校验该主体能否修改对应页面。即使模型生成的参数完全符合类型，也要继续检查页面归属、版本冲突与允许的发布范围。

### 2. 返回业务结果，也维护工具调用协议 {/* #2-返回业务结果也维护工具调用协议 */}

`ToolMessage` 是与模型工具调用相匹配的结果消息；LangGraph 的 `Command` 可以把工具结果连同结构化状态更新一起交回图。两者分别解决消息协议与状态推进，不能只返回一句自然语言就假设状态已被修改。

下面是 LangChain 1.3.7 的 `libs/langchain_v1/langchain/agents/middleware/todo.py` → `_write_todos()` 第 153–165 行的函数主体，省略签名和文档字符串。它是框架真实的待办写入工具。

```python
return Command(
    update={
        "todos": todos,
        "messages": [
            ToolMessage(f"Updated todo list to {todos}", tool_call_id=runtime.tool_call_id)
        ],
    }
)
```

`todos` 更新结构化状态，`tool_call_id` 把结果关联到本次调用。业务发布工具可以采用同类返回方式，在确认外部发布成功后写回页面版本和结果引用；但这段框架代码只写待办，不包含外部事务、发布校验或幂等保证。未知结果应写成待对账，不能提前标记完成。

### 3. 通过中间件治理调用，通过业务服务保证动作语义 {/* #3-通过中间件治理调用通过业务服务保证动作语义 */}

`wrap_tool_call` 是包裹工具执行的中间件入口，适合接入统一审计、超时分类、调用计量和错误归一化。异步运行路径需要对应的 `awrap_tool_call` 实现，避免仅在同步测试中验证过控制逻辑。

| 约束 | 适合放置的位置 | 原因 |
| --- | --- | --- |
| 参数类型和基本范围 | 工具 schema 与入口校验 | 及早拒绝无法执行的输入 |
| 当前主体与资源权限 | 工具入口和业务服务 | 资源归属与权限可能在执行前改变 |
| 幂等、并发版本与原子变更 | 业务服务或数据库 | 所有调用入口都需要遵守 |
| 限流、尝试次数和观测 | 执行包装器 | 多工具共用治理规则 |
| 发布后读取验证 | 业务验收步骤 | 工具响应与真实终态需要分别确认 |

将本例接入框架时，按以下顺序拆开责任：工具入口解析页面与草稿参数，通过 `ToolRuntime` 获取可信上下文；业务服务绑定或复用 `A903` 并处理发布；工具将已知结果包装成 `ToolMessage`，需要更新图状态时通过 `Command` 返回结果引用。外围中间件记录尝试与耗时，但不替发布服务定义事务。接口详见[工具运行时注入](../../../application-notes/engineering/langchain-series/langchain/10-tool-injection.md)和[工具执行层](../../../application-notes/engineering/langchain-series/langgraph/11-prebuilt-tool-layer.md)。

## 八、常见失败 {/* #常见失败 */}

| 现象 | 原因 | 调整方式 |
|---|---|---|
| 模型参数直接传给执行器 | 只有格式解析，没有业务校验 | 增加资源、阶段和副作用检查 |
| 工具描述和真实能力不一致 | Schema、权限或实现版本不同步 | 绑定兼容版本并执行回归 |
| 凭据出现在 Prompt 或日志 | 描述与执行句柄混在一起 | 在运行时注入敏感信息 |
| 非幂等工具重复执行 | 把未知状态当成失败 | 增加幂等键和状态查询 |
| 工具成功被当成业务完成 | 缺少后置条件 | 执行后读取真实状态 |
| 结果过长挤满上下文 | 原始输出直接回传 | 外部化保存，返回摘要和引用 |
| 错误被吞掉 | 主循环无法判断失败类型 | 结构化错误并保留原始证据 |
| 多个工具共享模糊名称 | 模型无法稳定选择 | 使用稳定命名、明确用途和适用边界 |

## 九、如何验收工具执行 {/* #如何验收工具执行 */}

以下是发布工具的验收设计，需在隔离服务或可检查的模拟环境中执行；它们不是本文已经跑出的测试结果。固定模型提案可以稳定触发故障分支，真实模型评测再检查它能否理解错误并选择允许的后续操作。

| 注入条件 | 预期处理 | 应读取的证据 |
| --- | --- | --- |
| 模型提交另一个租户的页面 | 执行前拒绝 | 发布服务调用数为零，目标页面未变化 |
| 提案依据 `v7`，执行前页面已变成 `v8` | 版本冲突，不覆盖新内容 | 写入端的条件更新结果、当前页面内容 |
| 发布生成 `v8`，丢弃响应 | 保留 `A903`，查询后补记结果 | 该动作只生成一个版本，最终结果指向 `v8` |
| 使用 `A903` 重发不同草稿 | 拒绝同键不同参数 | 原动作绑定与原发布版本未变 |
| 查询暂不可用或结果延迟可见 | 保持待确认并限时查询 | 没有换动作 ID 重发，没有误报成功 |
| 重试中间件外层提前将异常转为消息 | 检查实际尝试次数符合配置意图 | 包装顺序、执行次数与模型收到的错误 |

比较改动前后时，同时记录重复发布次数、未知结果持续时间、查询次数与任务总耗时。对账通常增加请求和等待，但可以减少盲目重放；只有真实测量后才能判断这项代价是否满足业务要求。进程退出和多个 worker 接管的测试放在[状态恢复验收](../02-state/agent-state-architecture.md#用故障位置验证恢复能力)，本篇聚焦一次动作的协议与真实效果。

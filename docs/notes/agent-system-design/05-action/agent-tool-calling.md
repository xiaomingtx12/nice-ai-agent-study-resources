# 工具执行：把模型提案变成受控动作

> 工具执行的核心本质，是让模型只能提出结构化的动作请求，再由运行时完成参数校验、权限判断、真实执行和结果验证。

模型可以看到工具的用途和调用格式，但它不直接拥有文件句柄、数据库连接、网络凭据或外部服务状态。工具调用必须经过执行边界，才能产生真实副作用。

```text
模型提出 Tool Call
→ 解析调用
→ 校验参数
→ 检查授权和执行条件
→ 执行真实动作
→ 归一化结果
→ 验证后置条件
→ 返回 Observation
```

## 工具合同由三层组成

| 层 | 作用 | 典型内容 |
|---|---|---|
| 描述层 | 让模型知道能力用途 | 名称、用途、适用条件、限制 |
| Schema 层 | 约束调用结构 | 输入参数、输出格式、错误类型 |
| 执行层 | 产生真实副作用 | 凭据、连接、文件句柄、执行逻辑 |

描述层和 Schema 层可以进入模型的 View；执行层始终由运行时持有。工具描述、Schema、权限策略和结果解析必须使用兼容版本，避免模型看到的能力与真实执行能力不一致。

工具在 View 中如何筛选和渐进式披露，属于[上下文装配](../03-view/agent-context-management.md)；本文关注模型已经提出调用之后，运行时如何处理它。

## 一次工具调用的执行链

### 解析模型提案

运行时先将模型输出解析为结构化调用，至少保存：

```text
tool_name
arguments
call_id
task_version
```

自然语言中的“请帮我删除数据”不能直接交给执行器。工具名称、参数和任务版本缺失时，调用应在执行前被拒绝。

模型的调用消息和运行时返回的工具结果需要通过 `call_id` 成组关联。一次响应包含多个相互独立的调用时，运行时可以并行执行，但应等待这一批结果完成并完整归还，再让模型继续决策；存在数据依赖时，后续调用必须等待前一个结果。

### 校验参数

参数校验分为两层：

- **Schema 校验**：字段是否存在、类型是否正确、格式是否符合约定；
- **业务校验**：资源是否存在、参数组合是否合法、动作是否适用于当前阶段。

运行时可以补充确定的默认值，但不能替模型猜测会改变副作用范围的字段。参数校验失败时返回可修正的结构化错误，不执行真实动作。

### 检查执行条件

进入执行器前确认：

- 当前主体和租户是否有权限；
- 目标资源是否在允许范围内；
- 当前阶段是否允许执行；
- 工作区、网络和资源配额是否满足；
- 预算、并发和超时是否足够；
- 是否需要一次性人工审批。

这些判断由运行时完成。模型看到工具描述，不等于获得工具权限；审批、权限和沙箱的详细策略分别由对应文章说明。

### 执行真实动作

执行器负责：

- 在运行时注入凭据和连接；
- 绑定工作区、网络和资源限制；
- 传递取消信号和超时；
- 记录动作和副作用；
- 防止同一动作重复执行。

对于非幂等动作，应使用幂等键、去重记录或补偿方案。调用超时后先查询真实状态，再决定是否重试，不能把“没有收到响应”直接当成“动作没有发生”。

### 归一化执行结果

工具结果要转换成下一轮可以消费的观察，至少区分：

```text
success
failure
partial_success
timeout
cancelled
unknown
```

结果应携带调用 ID、来源、时间、版本和副作用状态。HTTP 200、进程退出码为 0 或工具返回一段“成功”文本，只能说明调用层完成，不能直接证明业务目标已经达成。

## 写操作必须经过后置验收

创建、修改、删除、发布和发送等动作都可能产生外部变化。执行完成后要读取真实状态，检查任务合同要求的后置条件：

```text
动作请求
→ 执行
→ 读取真实状态
→ 检查后置条件
→ complete / partial / unknown
```

后置条件可以检查资源是否存在、字段是否更新、状态是否变化、数量是否符合预期、版本是否一致或外部系统是否返回业务确认。

无法读取真实状态时，结果应保持 `unknown`。下一轮可以选择查询、等待、补偿或人工确认，但不能直接向用户报告完成。

## 错误如何回到 Agent Loop

工具错误需要包含下一步判断所需的信息：

```text
ActionError {
  code
  retryable
  user_action
  recovery_hint
  partial_effect
}
```

| 错误类型 | 循环出口 |
|---|---|
| 参数格式错误 | 修正参数后重试 |
| 资源不存在 | 追问、替换资源或终止 |
| 权限拒绝 | 等待授权或停止 |
| 临时网络错误 | 有限退避重试 |
| 超时且状态未知 | 查询真实状态，避免直接重放 |
| 部分成功 | 保存已生效范围，重新规划剩余动作 |
| 后置条件失败 | 修复、回滚或人工确认 |
| 不可恢复副作用 | 停止扩散并记录人工处理入口 |

是否重试由运行时根据错误类别、动作幂等性和当前预算决定；模型消费的是错误事实和允许的恢复路径。

## 常见失败

| 现象 | 原因 | 调整方式 |
|---|---|---|
| 模型参数直接传给执行器 | 只有格式解析，没有业务校验 | 增加资源、阶段和副作用检查 |
| 工具描述和真实能力不一致 | Schema、权限或实现版本不同步 | 绑定兼容版本并执行回归 |
| 凭据出现在 Prompt 或日志 | 描述与执行句柄混在一起 | 在运行时注入敏感信息 |
| 非幂等工具重复执行 | 把未知状态当成失败 | 增加幂等键和状态查询 |
| 工具成功被当成业务完成 | 缺少后置条件 | 执行后读取真实状态 |
| 结果过长挤满上下文 | 原始输出直接回传 | 外部化保存，返回摘要和引用 |
| 错误被吞掉 | 主循环无法判断失败类型 | 结构化错误并保留原始证据 |
| 多个工具共享模糊名称 | 模型无法稳定选择 | 使用稳定命名、明确用途和适用边界 |

## 如何验收工具执行

重点检查执行边界：

- 模型只能调用当前 View 允许的工具；
- 工具参数经过 Schema 和业务校验；
- 权限、工作区、网络和资源限制在执行前生效；
- 凭据和真实执行句柄从未进入模型上下文；
- 写操作具有幂等、取消、超时和未知状态处理；
- 工具结果能区分调用成功和业务目标完成；
- 后置条件失败不会被标记为成功；
- 错误能够回到 Agent Loop 的正确恢复路径；
- 动作、授权、结果和副作用可以被完整回放。

工具执行的边界可以归纳为一句话：**View 决定模型能请求什么，Action 决定请求是否能安全发生，Observation 记录真实发生了什么。**

# 权限与后置条件：动作能否执行，以及是否真的完成

> **模块本质：** 在动作发生前校验执行主体、资源范围和授权，在动作发生后用外部真实状态检查目标是否达成，让“允许执行”和“确认完成”都有可核验的依据。

模型提出“要做什么”，不代表系统允许执行；工具返回“调用成功”，也不代表业务目标已经完成。权限、审批、执行保护和后置条件共同组成动作的确定性边界。

```text
动作提案
→ 授权判断
→ 一次性审批
→ 执行保护
→ 读取真实状态
→ 后置条件验收
→ 完成 / 部分完成 / 未知 / 失败
```

## 一、权限判断 {/* #权限判断 */}

权限是运行时对主体、资源和动作的判断，不能依靠模型看到的一句规则。一个可执行的权限判断至少需要考虑：

```text
subject × tenant × resource × action × stage
```

例如，“允许当前用户修改当前任务工作区中的 Markdown 文件”比“允许写文件”更接近可执行策略。

权限策略需要说明：

- 谁在执行；
- 代表哪个用户或租户；
- 要访问什么资源；
- 执行什么动作；
- 当前任务处于什么阶段；
- 使用哪个策略版本；
- 是否需要额外审批。

未声明的组合默认拒绝。权限判断结果、策略版本和实际动作需要一起记录，任务恢复或策略变化后重新判断。

### 1. 执行身份不能由模型声明 {/* #执行身份不能由模型声明 */}

服务账号拥有较大权限时，工具仍要按当前用户、租户、任务和目标资源收窄可执行范围。身份与凭据从可信运行上下文注入；模型传入的用户 ID 只能作为待校验数据，不能决定“代表谁执行”。

委派给子 Agent 的权限不应超过父任务当前持有的范围，并且需要明确有效期和可撤销方式。租户、用户或任务切换后，不能复用上一次调用残留的凭据上下文。

把检查集中在网关还是工具内部取决于调用路径。只要存在直连数据库、文件写入或本地命令，检查就必须覆盖这些实际副作用入口；部署一个工具网关并不自动覆盖所有执行方式。

### 2. 单次读取合法，不代表后续外发合法 {/* #单次读取合法不代表后续外发合法 */}

一个任务可能允许读取内部文档，也允许发送通知，但未必允许把文档全文发送给任意地址。执行外发动作时，需要同时检查数据来源、接收方、任务用途和允许的字段范围。

敏感数据进入摘要或子任务后，仍应保留相应的访问与外发限制。无法可靠追踪内容流转时，应收窄读取范围或外发能力，不能假设经过模型改写就失去了敏感性。

## 二、权限、审批、沙箱和验收的分工 {/* #权限审批沙箱和验收的分工 */}

四个判断关注不同问题：

| 机制 | 回答的问题 |
|---|---|
| 权限 | 这个主体能不能对这个资源执行这个动作 |
| 审批 | 这一次具体动作是否获得了额外确认 |
| 沙箱 | 动作只能在哪个空间、以什么资源上限运行 |
| 后置条件 | 外部世界是否真的达到预期状态 |

用户批准不能替代权限检查；动作在沙箱内运行成功，也不能替代业务结果验收。

## 三、外部内容的可信度与执行权限分别处理 {/* #外部内容的可信度与执行权限分别处理 */}

网页、检索片段、工具结果和其他 Agent 的交接内容，都可能包含指令性文本。来源标签可以帮助模型识别数据，但不能单独保证模型不会执行其中的要求。运行时还要限制工具、资源和数据外发范围。

例如读取一份排障文档时，其中要求“上传整个工作区以便诊断”。这个要求只是文档内容，不能成为用户授权。即使文档来自可信仓库，也要检查本次任务是否允许上传、目标地址是否获准，以及内容是否含有不应外发的数据。

建议把身份、租户、资源归属和目标地址白名单等确定性条件作为执行门。模型检测到的可疑片段或风险分数可以触发复核，但不能单独授予权限。摘要、格式转换和子 Agent 转述也不能改变原内容的授权级别。

安全测试既要注入恶意文本，也要检查最终效果：是否读到了任务之外的资源、是否尝试外发、执行门是否实际拒绝、日志是否泄露敏感内容。仅看到模型回复“我不会执行”不足以验收。

## 四、授权门：执行前检查 {/* #授权门执行前检查 */}

动作进入执行器前，运行时至少检查：

- 主体、租户和资源范围；
- 动作类型和风险等级；
- 当前任务阶段；
- 策略和工具版本；
- 工作区、网络和资源配额；
- 是否需要人工确认；
- 动作是否已经执行过或正在执行。

授权门拒绝时不产生副作用，并返回明确原因。模型可以根据原因改写动作、追问或停止，但不能自行绕过授权门。

## 五、审批绑定一次具体动作 {/* #审批绑定一次具体动作 */}

高风险、不可逆或影响范围较大的动作需要审批时，审批对象应是动作快照，而不是一句自然语言计划：

```text
action_id
purpose
resource_scope
parameters_hash
risk_level
policy_version
expires_at
```

执行前重新计算 `parameters_hash`。动作参数、目标资源、凭据范围、策略版本或风险等级发生变化时，原审批立即失效。

审批只解决“这一项动作是否允许继续”，不改变权限矩阵，也不替代沙箱限制。审批的交互、等待和人工响应见[人机协作](../04-decision/agent-human-in-the-loop.md)；本文关注审批结果如何成为执行门的一部分。

## 六、保护门：执行过程中继续约束 {/* #保护门执行过程中继续约束 */}

动作获准执行后，运行时仍要处理：

- 用户取消；
- 超时；
- 资源配额耗尽；
- 并发限制；
- 权限或策略变更；
- 外部状态已经变化；
- 幂等键冲突；
- 沙箱或连接失效。

保护门触发后，结果需要区分“未执行”“部分生效”和“状态未知”。不能把中断统一转换成失败，再让模型直接重试。

## 七、后置条件：确认真实状态 {/* #后置条件确认真实状态 */}

后置条件描述动作完成后外部世界必须满足的事实。它应该来自任务目标或业务规则，而不是工具返回的成功文本。

```text
动作执行
→ 读取真实状态
→ 比较预期和实际
→ 通过：完成
→ 不一致：修复、补偿或失败
→ 无法读取：未知
```

常见后置条件包括：

- 文件已经生成且内容符合格式；
- 数据记录已经创建或更新；
- 状态字段已经切换到目标值；
- 版本、数量或引用关系符合要求；
- 发布系统返回业务确认；
- 外部任务已经进入可追踪状态。

工具返回 HTTP 200、进程退出码为 0 或 API 返回 `ok`，只能说明调用层成功。没有读取真实状态或业务确认时，动作仍然处于未验收状态。

## 八、结果状态要能驱动下一步 {/* #结果状态要能驱动下一步 */}

动作结果至少区分：

| 状态 | 含义 | 允许的下一步 |
|---|---|---|
| `completed` | 后置条件全部满足 | 进入下一个任务步骤 |
| `partial` | 部分副作用已经发生 | 保存已生效范围，重新规划剩余动作 |
| `unknown` | 无法确认真实状态 | 查询、等待或人工确认 |
| `rejected` | 授权或审批未通过 | 修改动作、等待授权或终止 |
| `failed` | 确认没有达到目标 | 修复、补偿或报告失败 |
| `cancelled` | 动作被用户或运行时取消 | 保留取消原因和未完成范围 |

状态必须带有动作 ID、策略版本、结果证据和时间。下一轮模型只能消费这些结构化事实。

## 九、失败出口 {/* #失败出口 */}

不同失败进入不同处理路径：

| 失败 | 处理 |
|---|---|
| 未授权 | 拒绝执行，说明资源或权限范围 |
| 审批过期 | 重新申请审批 |
| 参数不合法 | 返回可修正字段，不产生副作用 |
| 执行超时且状态未知 | 查询真实状态，避免直接重放 |
| 部分成功 | 记录已生效范围，执行补偿或重排 |
| 后置条件失败 | 修复、回滚或人工确认 |
| 权限版本变化 | 重新授权，不能复用旧许可 |
| 不可逆动作失败 | 停止扩散，保留人工处理入口 |

是否可以重试，取决于动作是否幂等、状态是否明确和预算是否足够。统一重试所有错误会放大副作用。

## 十、证据与审计 {/* #证据与审计 */}

每次授权和验收都应保留：

```text
action_id
task_version
policy_version
approval_ref
resource_scope
parameters_hash
execution_result
postcondition_result
evidence_refs
```

这些记录用于回答：

- 谁批准了什么；
- 实际执行的参数是否与批准一致；
- 动作在哪个资源范围内运行；
- 外部状态是否真的发生变化；
- 任务恢复时为什么允许或拒绝继续。

敏感凭据不写入记录，但动作身份、范围、版本和结果证据必须可以回放。

## 十一、把框架权限规则与业务授权连接起来 {/* #框架中的权限定制 */}

### 1. 明确权限规则实际覆盖的调用路径 {/* #1-明确权限规则实际覆盖的调用路径 */}

Deep Agents 的 `FilesystemPermission` 用于声明文件操作的路径、操作类型和处理模式，通过 `create_deep_agent(permissions=[...])` 接入。本文核对的 0.6.12 源码快照支持允许、拒绝与中断审批三种模式，规则按声明顺序匹配，普通调用采用首个匹配结果；没有命中规则时默认允许。

这要求业务显式设计兜底规则。若目标是“只允许修改草稿目录”，仅写一条草稿允许规则并不够；还要限制其他写入路径，并检查父目录删除等特殊操作。规则效果需要覆盖读取、列举、搜索、编辑和删除各入口，不能只测试 `write_file`。

权限在 `FilesystemMiddleware` 的工具层检查，不自动包住所有 Backend 直接调用，更不自动限制自定义 HTTP 工具或任意 shell 命令。自定义工具绕过文件工具时，需要自己的授权检查；执行环境仍需限制进程、网络与凭证。

### 2. 配置继承和审批时避免扩大能力 {/* #2-配置继承和审批时避免扩大能力 */}

| 框架入口 | 可承担的职责 | 业务定制注意点 |
| --- | --- | --- |
| `permissions` | 内置文件工具的路径规则 | 子代理显式规则替换父规则，发布前检查完整有效规则 |
| `interrupt_on` | 按工具暂停并收集决定 | 未配置工具不会自动暂停；审批不是访问控制 |
| `wrap_tool_call` | 在工具执行路径统一检查 | 核对实际资源与主体，并覆盖同步和异步入口 |
| Backend 与执行环境 | 文件映射、存储和进程能力 | 路径映射不等于完整沙箱；需要验证真实资源边界 |

`create_deep_agent()` 会从中断模式的文件规则生成审批配置，再与显式 `interrupt_on` 合并；本快照中显式工具配置优先。覆盖配置时要验证原本要求审批的操作仍会暂停。版本与依赖要求见[文件工具与权限](../../../application-notes/engineering/langchain-series/deepagents/08-filesystem-middleware-and-permissions.md)。

### 3. 从真实测试学习验收粒度 {/* #3-从真实测试学习验收粒度 */}

`libs/deepagents/tests/unit_tests/test_permissions.py` → `TestRecursiveDeletePermissions.test_recursive_delete_refused_when_descendant_denied()` 检查：某个子目录禁止写入时，对其父目录的递归删除必须整体拒绝。以下节选拒绝后的断言，前面的后端、规则和调用构造省略。

```python
assert "permission denied for write" in result
assert "/work/secrets" in result
# 整体拒绝：允许访问的兄弟文件也没有被提前删除。
assert (tmp_path / "work" / "a.txt").exists()
assert (tmp_path / "work" / "secrets" / "key.txt").exists()
```

关键是既检查拒绝消息，也检查真实文件仍然存在。业务发布同样需要在拒绝后查实际页面与发布记录：目标未被修改、没有生成额外版本，才证明控制生效。成功路径则读取已发布页面，比较版本、正文与允许的变更范围，不能只验收模型说“发布完成”。

本节规则基于已核对的源码快照，不能仅凭分发包版本推断行为一致，具体范围见[源码版本约定](../../../application-notes/engineering/langchain-series/deepagents/source-baseline.md)。

## 十二、常见失败 {/* #常见失败 */}

| 现象 | 原因 | 调整方式 |
|---|---|---|
| “用户同意过”被当成长期权限 | 审批没有绑定动作 | 绑定参数、资源、版本和有效期 |
| 参数改变后仍使用旧审批 | 执行前没有重新计算摘要 | 变化后重新审批 |
| 工具成功被报告成业务完成 | 没有后置条件 | 读取真实状态并验收 |
| 超时后直接重试写操作 | 不知道上一次是否已生效 | 查询状态、使用幂等或人工确认 |
| 权限通过但访问了错误目录 | 权限和操作空间没有同时检查 | 授权门和沙箱门共同校验 |
| 部分成功被当成整体失败 | 没有记录副作用范围 | 保存已生效部分，重新规划剩余动作 |
| 策略更新后恢复旧任务 | 复用了旧授权 | 恢复时重新授权 |

## 十三、如何验收 {/* #如何验收 */}

重点验证三个确定性门：

- 未授权动作不会产生副作用；
- 参数、资源或策略变化会使旧审批失效；
- 权限通过但超出工作空间时仍然会被拒绝；
- 执行超时不会自动重复未知状态的写操作；
- 工具调用成功但后置条件失败时不会报告完成；
- 部分成功能够被准确记录并进入补偿或重排；
- 权限、审批、执行和验收证据可以回放；
- 任务恢复时会根据当前策略和真实状态重新判断。

Action 的完成标准不是“模型提出了动作”或“工具返回了成功”，而是**动作在允许的范围内执行，并且外部世界通过后置条件验证达到了目标**。

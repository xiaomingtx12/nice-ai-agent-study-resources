# Agent 工程的第一性原理：用确定性外框管理不确定性模型

Agent 工程技巧不应被理解成一组需要全部装入产品的组件。**工程技巧栏要尽量完整地总结各类问题和应对方法，具体产品则根据任务、风险和模型真实失败选择必要部分。** 图谱追求持续完整，产品实现保持克制。

这些技巧共同处理一个基础问题：模型根据上下文生成概率性结果，业务系统却需要明确的身份、权限、参数、状态和责任。Agent 工程是在两者之间建立一层系统，让模型能够理解人类任务、使用软件能力，并把不确定性控制在产品可以接受的范围内。

## 一、Agent 工程服务于产品任务

技术组件本身不产生产品价值。意图识别、Agent 大脑、记忆、RAG、多 Agent 和评测只有进入具体用户任务，解决了可观察的问题，才有引入价值。

需要区分两个层次：

### 知识沉淀层：尽量总结完整

Agent 工程技巧栏需要持续记录：

- 有哪些结构性组件和专项工程
- 每个组件处理什么不确定性
- 它在什么条件下有效
- 常见反模式和适用边界
- 模型能力变化后，哪些实现需要调整
- 真实项目采用了哪些方案

完整的图谱用于理解和选型，不能因为某个当前项目用不到就停止研究。

### 产品应用层：按需选择

单个产品不应为了架构完整而集齐组件。选择路径应该是：

```text
产品任务
→ 观察模型和系统的真实失败
→ 判断失败属于哪类不确定性
→ 选择最小必要工程技巧
→ 用评测验证是否改善
→ 模型或产品变化后重新判断
```

例如，三个固定分支的低风险请求未必需要独立意图识别；一次生成任务不需要长程状态；精确数据库查询也不应为了使用 RAG 而先向量化全部数据。

## 二、三套处理方式需要对齐

人在表达任务、模型理解任务、程序执行任务时，使用的是三套不同机制。

| 人 | AI 模型 | 程序系统 |
|---|---|---|
| 依赖场景、常识、关系和省略 | 依赖当前上下文和训练所得模式 | 依赖字段、类型、协议和规则 |
| 目标可能模糊 | 能补全，也可能误解或编造 | 不能自行解释模糊目标 |
| 能处理价值取舍和例外 | 能生成判断与候选路径 | 只能执行编码后的确定动作 |
| 会默认共享大量背景 | 只看到被放进上下文的信息 | 只接收明确参数和状态 |

Agent 系统实际在做两次转换：

```text
人的业务语言
    ↓ 意图识别、上下文补全、任务表示
模型可以处理的目标与环境
    ↓ 工具选择、参数构造、权限检查
程序可以执行的结构化动作
```

执行结果再回到模型，成为下一轮判断的观察。Agent 大脑负责维持这条往返链路，直到任务完成、失败或转人工。

这也是 [Agent 产品功能形态图谱](../agent-product-method/agent-product-functional-form-atlas.md) 与工程技巧图谱的连接点：产品侧描述用户任务如何变化，工程侧解释这条转换链怎样可靠运行。

## 三、确定性外框与不确定性内核

“给模型模板、划定范围，再允许它发挥”可以进一步拆成两部分：

### 适合工程确定化的部分

- 用户和组织身份
- 可访问的数据范围
- 工具名称、参数类型和返回协议
- 不允许猜测的事实
- 必须遵守的业务规则
- 高风险动作的审批点
- 事务、幂等、超时和资源上限
- 日志、审计和责任归属

### 适合模型判断的部分

- 用户真实意图和省略信息
- 当前任务需要哪些资料
- 哪些历史信息相关
- 多个合理路径中哪条更合适
- 如何组织说明、建议和候选方案
- 中间结果是否要求调整计划

可以压成一句：

> **确定性外框由工程提供，不确定性内核由模型处理。**

边界不是固定的。任务风险越高、结果越难验证，外框越需要明确；任务越开放、模型能力越强，语义判断空间可以越大。

外框也不是越厚越好。大量固定分支、模板和强制流程会限制模型本可完成的工作，增加维护成本。只给一句目标、不提供事实和权限边界，又会让模型在不该自由发挥的地方做推断。

## 四、工程技巧从哪些不确定性中产生

Agent 组件不是凭空设计出来的，每一类都对应任务链上的一种不确定性。

| 工程技巧 | 主要处理的问题 | 典型产品信号 |
|---|---|---|
| 意图识别 | 用户到底要做什么、缺哪些参数 | 同一句话可能进入不同流程 |
| Agent 大脑 | 下一步做什么、何时继续或结束 | 任务需要根据中间结果推进 |
| Context | 当前决策应该看到哪些信息 | 模型知道能力但缺少现场信息 |
| Tool | 模型意图如何变成可靠动作 | 结果需要进入真实业务系统 |
| Skill | 某类任务应复用什么经验和边界 | 处理方法稳定、重复且可迁移 |
| RAG | 外部知识中哪些内容与任务相关 | 知识无法全部放进上下文 |
| GraphRAG | 多跳关系如何被发现和解释 | 问题跨实体、链路和时间关系 |
| 多 Agent | 是否要拆分角色、上下文或并行任务 | 单一上下文过载或任务可独立并行 |
| 可观测性 | 失败发生在哪里、过程是否可解释 | 端到端结果无法定位具体故障 |
| RAG 评测 | 检索和生成是否满足知识任务 | 召回正确但回答仍错误，或反之 |
| Agent 评测 | 决策链、节点和工具调用是否正确 | 最终答案无法反映过程风险 |
| 权限与审批 | 哪些不确定动作不能直接执行 | 动作会改变真实数据或外部关系 |

理解一项技巧时，先问：

1. 它替模型补什么能力？
2. 它约束哪类不确定性？
3. 产品是否真的出现了这种失败？
4. 有没有更简单的产品或工程方案？

如果回答不了，引入组件通常只是架构堆叠。

## 五、Agent 大脑是当前模型能力的工程外骨骼

模型一次调用本身不负责长期状态、工具执行、失败恢复和任务问责。当前的 [Agent 大脑](./agent-brain.md) 因此提供：

- 循环和退出条件
- 状态保存
- 工具结果回传
- 计划、重规划和反思
- 步数、时间和成本限制
- 重试、回退和人工接管
- 跨进程续做

这些机制让模型能完成多步任务，但也在控制它如何思考和行动。Agent 大脑不是永久固定的架构真理，而是当前模型能力与产品要求之间的工程外骨骼。

同样，独立意图分类、强制工具路由、固定规划模板和大量 Prompt 脚手架，也可能是阶段性能力补偿。强模型能够稳定承担后，相关结构可以收缩。

但“放松 Agent 大脑”不是删除运行时。真正变化的是**对模型认知过程的控制强度**：

| 阶段 | 模型承担 | 工程承担 |
|---|---|---|
| 强控制 | 局部语义判断和单步生成 | 规定流程、路由、格式、重试和结束 |
| 边界控制 | 自主规划路径和选择工具 | 提供环境、状态、权限、成本和异常处理 |
| 环境治理 | 大部分理解、规划和执行 | 系统契约、安全、责任、可观测与问责 |

约束变松，不等于工程消失。认知控制会减少，真实系统的确定性边界仍然存在。

## 六、模型变强后，哪些代码应该删除

工程代码默认不是资产，而是复杂度成本。模型能可靠承担某项工作后，能力补偿代码应该被重新评估。

### 可能逐步减少：能力补偿

- 独立的简单意图分类器
- 大量固定路由和关键词分支
- 过度细化的规划模板
- 为防模型忘记而重复注入的 Prompt 脚手架
- 强制每一步输出固定思考结构
- 模型已经能够稳定完成的手工纠错规则

### 长期存在：系统契约

- API Schema 和参数校验
- 身份认证与权限检查
- 事务、幂等和数据一致性
- 状态持久化和资源限制
- 成本、超时和并发控制
- 日志、审计和故障恢复

这些结构不是为了教模型思考，而是为了让动作安全进入真实系统。

### 持续存在：价值与责任边界

- 高风险操作审批
- 隐私和数据使用边界
- 法律、合规和组织规则
- 用户知情与控制权
- 公平性和价值取舍
- 最终责任归属

模型能力再强，也不会自动获得替组织和用户决定价值边界的权利。

因此，更准确的演化是：

```text
能力补偿逐渐减少
系统契约长期存在
安全、价值与责任边界持续存在
```

## 七、删除约束必须基于评测

不能因为模型版本更新或宣传中的能力提升，就直接移除工程控制。每次放松约束需要走完整验证：

1. 明确当前代码在防止什么失败。
2. 收集触发该失败的真实任务样本。
3. 让新模型直接承担这一部分工作。
4. 对比任务成功率、错误类型、成本和延迟。
5. 检查权限、责任和极端情况是否仍被覆盖。
6. 删除或缩减约束后持续观察线上分布。

如果没有评测，既无法证明工程技巧有效，也无法证明它已经可以删除。评测不仅是发布前验收，也是架构减法的依据。

这也是 [Agent 评测](./agent-evaluation.md) 和 [可观测性](./agent-observability.md) 的上游意义：前者判断任务链是否达到产品要求，后者提供失败位置和运行事实。

## 八、工程技巧如何持续进化

完整图谱不是静态组件目录。每项技巧都应持续记录四种变化：

### 新问题

新的产品形态是否带来了此前没有的不确定性。例如多模态交付会增加生成耗时、媒介核验和内容审核问题。

### 新能力

模型是否已经能直接承担过去需要代码补偿的工作。例如工具选择稳定后，是否仍需要大量硬编码路由。

### 新边界

产品进入真实业务后，是否出现权限、责任、审计或成本问题。这些通常不会仅靠模型升级解决。

### 新证据

真实项目采用了什么结构，在哪些任务上有效，在哪些条件下失败。没有样本支撑的技巧保留为待验证判断，不写成通用结论。

因此，工程技巧图谱的维护方式是：

```text
观察产品形态和真实项目
→ 提取新的工程问题
→ 更新组件方法和边界
→ 用评测验证
→ 模型增强后删除失效补偿
→ 保留新的经验与证据
```

## 九、行动前检查

准备引入一项 Agent 工程技巧时，先检查：

### 产品问题

- 它服务哪个用户任务？
- 当前失败能否被用户感知？
- 不处理会造成时间、质量、风险还是责任问题？

### 不确定性

- 失败来自意图、上下文、规划、工具、知识还是权限？
- 应该确定化的是事实和协议，还是本可交给模型的语义判断？
- 模板是在稳定边界，还是压缩模型能力？

### 工程选择

- 最小可行约束是什么？
- 能否通过产品交互解决，而不是增加组件？
- 新组件增加了哪些状态、成本和故障点？

### 演进与删除

- 这段代码属于能力补偿、系统契约还是责任边界？
- 什么评测结果出现后可以缩减它？
- 模型升级时是否会重新验证必要性？

## 十、反模式

- 工程技巧图谱不完整，就误以为产品也只需要研究当前用到的组件。
- 为了显得架构完整，把所有组件装进单个产品。
- 用大量固定流程约束模型，却没有对应的真实失败证据。
- 把权限、事务和审计当成模型变强后可以删除的脚手架。
- 模型更新后只增加新能力，不清理过时的补偿代码。
- 删除约束只看演示效果，不跑真实任务评测。
- 把“自由发挥”放在事实、权限和不可逆动作上。
- 把所有语义判断写成程序分支，让模型退化成模板填充器。

## 十一、何时不该增加工程约束

以下情况优先保持简单：

- 单次调用已经稳定完成任务
- 失败容易识别和重试
- 任务不涉及真实系统写入
- 用户可以低成本纠正结果
- 新组件增加的状态和故障点大于收益
- 产品需求仍未验证，尚不知道真正失败在哪里

此时可以先保留最短任务链，通过日志和样本观察真实问题，再决定是否引入意图层、长循环、记忆、RAG 或多 Agent。

## 结论

Agent 工程的第一性原理不是“用代码控制模型”，也不是“尽量把控制权交给模型”，而是根据产品任务划分确定性与不确定性的边界：

- 工程提供事实、协议、权限、状态和责任等确定性外框。
- 模型承担语义理解、相关性判断、路径选择和表达等不确定性内核。
- 工程技巧图谱持续总结各类组件、边界和真实样本。
- 单个产品从实际任务和失败出发选择必要组件。
- 模型增强后，以评测为依据删除失去必要性的能力补偿。
- 系统契约、安全、价值与责任边界不会因为模型变强而自动消失。

Agent 大脑会逐步放松对模型认知过程的约束，但工程仍要为真实世界提供运行环境和治理边界。技术最终服务产品，产品问题也会持续推动工程技巧演化。

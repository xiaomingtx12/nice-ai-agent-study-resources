# RAG 工程篇

RAG 不等于"上完整管线"。知识总量小（< 50 段）时直接塞 Prompt 比动态检索更稳；问法高度集中在少量主题时 Summary Index 比 BM25 更有效。

工程化的核心拉扯是召回率、精度、成本、延迟、可解释性五项。

---

## 一、动机

RAG（检索增强生成）是 Agent 接入私域知识的标配，冲着大模型的三个硬伤去：**幻觉**（不知道也编得理直气壮）、**知识时效**（训练截止后一无所知）、**私域盲区**（自家保单、理赔指南完全没见过）。检索把实时的、私域的、带出处的资料喂进去，一次补上这三样。读这篇之前你应该已经有 RAG 的基本认知，这里聚焦的是工程化层面的判断：

- 什么场景该上 RAG、什么场景直接塞 Prompt 反而更对
- 切分、embedding、Query 理解、检索、重排各环节的策略怎么选
- 多轮对话的记忆怎么和检索并行工作
- 在线 RAG 的缓存与失效怎么设计
- 引用与归属怎么抑制幻觉
- 上线前怎么评测、上线后怎么监控

有个反直觉的判断先摆出来：**做 RAG，大模型反而是最省心的部分，90% 的功夫在解析、切分、检索、重排这些"喂资料"的环节**——答案质量的上限由知识库质量决定，库里有且准模型才答得对，库里没有再强的模型也只能编。

另一点要摆正：**RAG 不等于零幻觉**。它只是把幻觉的来源从"模型凭空瞎编"迁移成"检索喂错了料"——检索给了错误段落，模型会"有依据地答错"，这种错更隐蔽。所以防幻觉必须两层都做：检索层保证喂对料，生成层用 Prompt 硬约束 + 输出校验兜底。这条贯穿全文。

## 二、关键判断速览

- **该不该上 RAG**：知识 100+ 段、问法多变、需要引用支撑、内容更新频繁 → 该上。知识 < 50 段且静态、主题高度集中、强实时性、强成本敏感 → 不该上。
- **RAG / 微调 / 长上下文**：知识对不对用 RAG，话说得顺不顺用微调，文档就三五篇塞得下用长上下文，三者可组合
- **R0-R3 选哪级**：知识 < 100 段 → R0；100-10K → R1；10K+ → R2；高复杂度任务 → R3
- **切分默认**：paragraph + chunk_size 512 + overlap 100；overlap 要对齐到完整句子，100 token 是性价比拐点；结构感知按"章→节→段→句"逐级降级
- **Embedding 选型**：中文 / 中英 → BGE，多语言 → GTE-multilingual，省事 → OpenAI API，长文 ≥8K → Jina v2；维度 768 / 1024 是中文甜点
- **ANN 选型**：读多写少、低延迟 → HNSW；超大规模、能调参换召回 → IVF；取舍本质是内存-召回-写入三角
- **优化优先级**：先切分 → 混合检索 → 重排，微调是最后的杀手锏不是必选项，顺序搞反花大力气收效甚微
- **Query 理解**：检索的上限从用户按下回车那刻就定了；重写求准（1 句）、扩写求全（多句，只对核心业务开）；意图识别先钉输出格式再谈准确率
- **检索默认**：专有名词 / 错误码 / 数字 ID 占比 > 1/3 必须 Hybrid，否则纯向量够用；多路融合用 RRF（k=60）；BM25 vs TF-IDF 的两点改进是词频饱和 + 长度归一（k1≈1.2~2.0、b≈0.75）
- **召回旋钮**：候选池 N（召回上限，放宽）、top-k（喂 3-10）、元数据过滤（零成本缩范围）；调权先固定 + RRF 跑通再据评估集改动态
- **HYBRID 阈值**：必须推迟到 Rerank 之后，向量相似度和 BM25 分数基线不可比
- **Rerank 模型**：本地优先（如 BGE-reranker-base），跨太平洋 Cohere 是延迟大头；reranker 和 Embedding 不必同源；召回池 Top-N 几十到一两百、喂 LLM Top-K 3-10
- **多轮记忆**：记忆是与检索并行的第二个上下文来源，滑动窗口 + 语义检索历史 + 关键事实单独提醒组合；长期记忆要管"忘"，记太多反而更笨
- **引用与归属**：强制引用 + 一致性校验 + 低置信度兜底；Prompt 硬约束"仅依据资料"；LLM 自标引用漏标率约 15%，必须后处理兜底
- **评测**：见 [RAG 评测篇](./rag-evaluation.md) —— 上线前 30 条最小评估集 + 4 项指标（Context Precision / Recall / Faithfulness / Answer Relevancy），ground truth 标到 chunk 级；先看检索段 Recall 再排查生成；只盯准确率不看 P95/P99 必翻车

## 三、RAG 工程化要点

先立一个贯穿全章的判断：**RAG 不是"写个检索"就完事，得拆成几个各管一摊的模块一个个治，大模型反而是最省心的部分**。整套系统拆开是两条链路、四大模块：

- **离线索引链路**（文档解析 → 切分 → embedding → 入库）像后厨提前备菜，慢一点没关系，一天或文档更新时才跑一次，追求质量；
- **在线问答链路**（Query 理解 → 检索 → 重排 → 生成 → 引用）像客人点单后现炒，每个提问都从头跑一遍，每一毫秒都被用户盯着，追求速度。

两条链路靠"知识库/索引"这一个交汇点连起来——把解析、切分、向量化这些重活全挪到离线提前备好，在线只做"查 + 拼 + 答"的轻活，这就是拆两条的根本原因。四大模块（解析切分入库 / Query 理解 / 检索召回重排 / 上下文生成）分别坐在这两条链路上，下面按离线、在线的顺序走一遍。

**模块之间是联动的，一处劣化会沿链路放大**：一份「本保险承保……但以下情况除外：核辐射」的条款，切分把它从"除外："劈开，前半块看起来像"全都承保"，检索召回的就是这半块残片，模型顺势答"在保障范围内"——一句要赔钱的错，根子在切分。所以排查时盯 recall@5/10 顺着埋点往回查是切分、检索还是 Query 理解出了岔，别一上来就换模型。

### R0 到 R3 的演化

RAG 不是一蹴而就的工程。从能用到好用分四个阶段：

```
R0 朴素 RAG → R1 高级 RAG → R2 模块化 RAG → R3 Agentic RAG
  ↓            ↓             ↓              ↓
单次检索     多路召回      检索前后置      Agent 工具化
单次生成     重排 + 引用   路由分发        多次反思
1-2 天       1-2 周        1-2 月         2-3 月
```

**R0 朴素 RAG**：单次检索加单次生成。`query → embedding → top-K → Prompt 拼接 → LLM`。适用知识 < 100 段、问法单一的场景。

**R1 高级 RAG**：每一步都做工程化优化（切分、embedding、检索、重排策略池），加引用标注。适用知识 100-10K 段、问法多变的真实业务。

**R2 模块化 RAG**：检索前后都加预处理（Query 改写、HyDE、Step-back，加去重、压缩、上下文窗口适配），配合多模块路由。适用知识 10K+ 段、多库多源的复杂场景。

**R3 Agentic RAG**：检索成为 Agent 工具之一，Agent 自主决定何时检索、是否多轮、是否反思。适用高复杂度任务（研究、报告、跨库综合）。代价是 token 消耗翻倍。

从 R0 跑通开始，按真实信号（召回率、精度、成本）逐级升级。

在升级 RAG 之前先确认 RAG 是不是对的工具。RAG、微调、长上下文解决的是三件不同的事，可组合：

| 方案 | 解决什么 | 什么时候用 |
|---|---|---|
| RAG | 外部 / 私域 / 会变 + 要溯源的知识 | 知识量大、会更新、要出处 |
| 微调 | 风格 / 格式 / 领域语感 | 想固定输出格式、统一话术口吻 |
| 长上下文 | 一次性少量文档 | 文档就三五篇、塞得下 |

组合用法：RAG 管"知识对不对"，微调管"话说得顺不顺"——保险客服用 RAG 查实时条款保证答得对，微调统一话术保证答得像客服。

下面按离线索引、在线问答两条链路的顺序展开各模块的策略池。

### 离线索引链路

一次建好、反复被查，追求质量。四步顺次做：**文档解析 → 切分 → embedding → 入库**，任一步劣化都会静默传导到线上。

#### 文档解析

离线链路的第一步不是切分，是解析——把 PDF / Word / PPT / 扫描件 / 音视频变成干净、带结构的文本。它不是"读取文本"一个动作，而是一条 pipeline：**版面分析 → 元素分类 → 针对性解析 → 结构化输出**。这一步的错误会静默传导到下游，比切分本身更致命。四类真实文档各有坑：

| 坑 | 现象与后果 | 应对 |
|---|---|---|
| 多栏排版 | 双栏理赔指南按行从左读到右，"流程"和"材料"逐句交错，模型分不清谁是谁 | 用带版面分析的工具（Deepdoc / MinerU），按版面结构而非文本行顺序解析 |
| 无边框表格 | 靠空格对齐没有边框线，行列错乱——费率表"30 岁"费率错配到"60 岁"，金额差 3 倍；识别率从有边框的八九成掉到五六成 | 对无边框 / 半结构化表格切换更强的表格识别模型 |
| 印章 / 签名压字 | 红章盖在金额、日期上，OCR 糊成一团——"理赔限额 100 万"被压住"0"读成 10 万 | 先做遮挡检测把印章层和文字层分离，再对文字层单独 OCR |
| 扫描件模糊 | 低分辨率老合同字迹发虚，OCR 识别率只有七成多，错字污染知识库 | 图像增强（去噪 / 锐化 / 超分）+ 按模糊程度分档，能拉到九成以上 |

音视频类知识（录播培训、客服录音）要先过 ASR 转字幕再进后续流程，RAG 的"知识"远不止 PDF。

工程上不要"所有文档都上最贵的解析模型"，而是**分类器前置 + 动态调度**：先判断这份文档是不是无边框表、是不是模糊扫描件，普通文档走轻量快速通道，难 case 才调重型方案。既保住准确率，又不让平均延迟爆掉，也更好维护。

#### 切分策略

切分策略从 paragraph 起步，按召回率和精度信号再升级。

召回率低（漏检）就升 `chunk_size` 或加 `overlap`，让 chunk 包含更多上下文。precision 低（噪声多）就降 `chunk_size` 或开 Rerank，让 chunk 更聚焦。

dify 在 `_get_splitter()` 里按 `processing_rule_mode` 分两路，自定义模式用 `FixedRecursiveCharacterTextSplitter`，自动模式用 `EnhanceRecursiveCharacterTextSplitter`。`IndexStructureType` 上提供 paragraph、parent_child、qa_model 三种正交模式，附录 C 给出 512 / 100 的经验甜点。

##### 切分策略池

| 策略 | chunk_size | overlap | 召回率 | 精度 | 适用场景 |
|---|---|---|---|---|---|
| FixedRecursiveCharacterTextSplitter | 256-1024 | 50-200 | 中 | 中 | 通用起步点，文本结构化弱 |
| 按段落 | 段落自然长度 | 段落边界 | 高 | 中 | 内容天然分段（FAQ / 文档） |
| 按 Markdown 标题 | 章节自然长度 | 标题边界 | 中 | 高 | 结构化文档（README / 手册） |
| 语义切分（embedding 距离突变） | 动态 | 动态 | 高 | 高 | 长文 + 主题切换明显 |
| parent_child 双层 | child 256-512 | 100 | 最高 | 高 | 检索精准 + 回答用大段上下文 |
| qa_model 改写 | N/A | N/A | 中 | 最高 | 文档知识稀缺场景（LLM 成本是段落模式几十倍） |

##### 结构感知切分的递归骨架

固定长度切分会把句子拦腰截断，开篇那类"核辐射被从'除外：'切开"的事故就是这么来的。结构感知不是玄学，核心是一句口诀：**按"章 → 节 → 段 → 句"逐级降级，每级先判断超没超 max_size，超了才往下拆，永远先保住更大的语义单元**。两个配套动作：

- **识别层级**靠编号，但中文文档编号特别杂（`1.1.1` / `第一条` / `（一）` / 纯字号加粗，还跳号重号）。实测某批保险文档约 **25% 的编号不规范**，纯正则只能认出六成，所以要正则 + 样式（字号 / 加粗 / 缩进）+ 轻量分类器多策略融合，正则救不回来的交给分类器。
- **表格按行切后每块都要复制表头**。一个 50 行的费率表只把第 30-40 行喂给模型、不带表头，它根本不知道每列是什么，答不出"30 岁男性费率是多少"。

##### 智能 overlap 与 chunk 元数据

固定长度的 overlap 会在句子中间截断，带进来半句话反而是噪音。改进是**取上一块结尾一段、裁到最近的句号再带过去**，而不是硬切在第 512 个 token——语义被切断的比例能从两成多降到个位数。overlap 从 0 加到 100 召回提升明显，加到 200 / 300 只多涨一丁点、存储和成本却线性上升，**100 token 是性价比拐点**。

切分时给每个 chunk 带上元数据，检索和引用阶段都用得上：

- `section_path`：章节层级路径（用于引用溯源，见后文）
- `content_type`：正文 / 表格 / 标题
- `is_key_clause`：是否关键条款（可用于加权）
- `prev_next_chunk_id`：前后 chunk 指针（回答需要相邻上下文时回查）

切分方案的好坏不能拍脑袋。某保险项目 5000 文档 + 200 道人工标注题实测：固定长度 67% → 句子级 74% → 结构感知（识别层级 + 表格单独处理 + 智能 overlap + 元数据）91%。**没有评估集的切分优化都是自嗨。**

#### Embedding 策略

工程化要点：

- embedding 模型与切分大小要匹配，chunk_size 512 配 1024 维 embedding 是经验甜点
- embedding 缓存，相同 chunk 不重复算，索引阶段用 hash 去重
- embedding 版本管理，升级必须重建索引（无法增量）
- 多语言 embedding，CJK 选 BGE-multilingual，不要用纯英文模型

**为什么 embedding 检索能到毫秒级**：用的是双塔（Bi-Encoder）结构——query 和 document 各自独立编码，document 向量在索引阶段离线预存好，线上只算 query 一次再做向量比对。这和后面重排用的 Cross-Encoder（query 和 document 拼在一起过一遍模型）形成"快 vs 准"的分工。相似度用余弦而非欧氏距离，因为余弦只看方向不看长短，对长短不一的文本更鲁棒。

判断口诀：用户问法里专有名词、错误码、数字 ID 占比 > 1/3 必须混合，否则稠密够用。

选型别迷信榜单。MTEB / C-MTEB 是通用语料，换到保险 / 法律 / 医疗，排名会变，务必在自己的评估集上实测。选型口诀：

- **中文 / 中英**：BGE
- **多语言**：GTE-multilingual
- **省事、能接受外发**：OpenAI text-embedding API
- **长文 ≥8K**：Jina v2
- **资源紧张**：E5-small / MiniLM

维度上 **768 / 1024 是中文 RAG 的性价比拐点**，维度翻倍存储和延迟线性翻倍、精度只微涨。预算紧可以用 MRL（套娃式可截断维度）：1024 维模型截成 512 用，精度损失可控。

> 踩坑案例：某项目直接上 OpenAI text-embedding，每天几十万 query + 全量重建，账单肉疼，还撞上保险条款不能合规外发。切回本地 BGE 后成本降下来、效果不降反升——"榜单第一"不等于"适合你"。

向量库的 ANN 索引（HNSW / IVF）也是一组取舍。**ANN 的 A 是 approximate（近似）**——它不死磕"绝对最近的那条"，用一点点召回损失换百倍提速，理解了这点就不会再问"为什么不暴力扫全库"。HNSW 召回高、查询快，但内存占用大、写入慢；IVF 省内存、写入快，但召回和延迟要靠 `nprobe` 调。判断口诀：**读多写少、追求低延迟 → HNSW；超大规模、能接受调参换召回 → IVF**，取舍的本质是内存、召回、写入速度的三角。调参盯 HNSW 的 `efSearch` 和 IVF 的 `nprobe`，在召回-延迟曲线上找拐点。

##### Embedding 策略池

| 策略 | 索引大小 | 语义能力 | 成本 | 适用场景 |
|---|---|---|---|---|
| 稠密 embedding（BGE / OpenAI text-embedding-3） | 大 | 高 | 高 | 通用语义检索 |
| 稀疏 embedding（BM25 / SPLADE） | 小 | 低（关键词级） | 低 | 专有名词 / 错误码 / 数字 ID 占比高 |
| 混合 embedding（稠密 + 稀疏加权） | 大 | 高 | 高 | 客户问法多变的真实业务 |
| 多模态 embedding（CLIP / BGE-VL） | 很大 | 高 | 很高 | 图文混排内容 |

> 微调 embedding 是把知识注入向量的杀手锏，但**不是必选项**。优先级永远是先切分 → 混合检索 → 重排，这三步榨干了再考虑微调，顺序搞反会花大力气收效甚微。真要做，具体路径是用"问题 — 正确 chunk"当正样本、不相关 chunk 当负样本，用对比学习（`MultipleNegativesRankingLoss`）在通用 BGE 上继续训，而不是从零训。

#### 入库与增量索引

离线链路的最后一步是入库，写入是个状态机：`pending → splitting → embedding → completed / failed`。

读时只查 `enabled == True and status == "completed"` 的段，吸收部分写失败段。双写一致性：向量库、文档库、段关系库三者必须原子更新。**embedding 模型升级必须全量重建，不支持增量**——向量空间变了，新旧向量不可比。

### 在线问答链路

每个提问都从头跑一遍，每一毫秒都被用户盯着，追求速度。重活已在离线备好，这里只做"查 + 拼 + 答"：**Query 理解 → 检索 → 重排 → 生成 → 引用**。

#### Query 理解与改写

在线链路的第一步不是检索，是理解用户到底问了什么。**检索的上限，从用户按下回车那一刻就定了**——问题理不顺，后面切分再好、模型再强也救不回来。既有的 Multi-Query / HyDE / Step-back 只是 Query 改造的一部分，完整的 Query 理解是一个独立在线模块，包含意图识别、重写、扩写、指代消解四件事。

**意图识别**：先判断这个 query 属于哪类（查保额 / 查理赔 / 闲聊），再决定走哪条检索路径、调哪个库。三条技术路线：

- **规则**：关键词匹配，冷启动够用，维护成本高
- **BERT 分类器**：攒够标注数据后训一个，快且稳
- **LLM**：零样本能力强，但延迟和成本高

实务组合是冷启动用 LLM 兜底，攒够真实数据后训 BERT 接管主流量，怎么选按"意图数量、有没有标注数据、延迟/成本预算"三条来定。**意图识别最坑的不是"分不准"，而是输出不可控**——模型今天回"理赔咨询"，明天回"这应该属于理赔相关咨询～"，下游根本没法用。所以先用 Prompt 三件套把输出钉死再谈准确率：枚举候选意图 + 强制输出格式（"只输出编号"或 JSON）+ few-shot，再留一个"其他"兜底类。

意图数量到 **300-500 类**时，简单分类扛不住，两个高阶方案：

- **检索式**：把每个意图当成一份"文档"建向量库，来了 query 先召回 top-10 个候选意图，再让 LLM 从里面选——本质是把检索能力复用到意图识别上
- **两级分类**：先粗分大类，再在大类内细分

前者是面试高频题：很多人卡在"prompt 塞不下几百个意图"就答不下去，能说出"把意图当文档去检索、先召回再判断"，把前面学的检索能力迁移过来，立刻显出体系化思维。

**重写 vs 扩写**：重写是把一句话改准（消歧、补全、规范化），求准，输出 1 句；扩写是从多个角度展开成多个 query 并行检索，求全，输出多句。三者的召回差别很直观——原始 query "请问保险理赔呢？"可能一条都召不回，重写成"保险理赔"召回 1 条，扩写成"保险理赔 / 保险索赔"召回 2 条。扩写代价是查询数翻几倍、延迟和成本同步翻，**只对核心业务场景扩，简单 FAQ 不扩**。重写有改错风险，降险手法是"原始 query + 改写 query 都查，结果合并"，宁可多查一次也别把用户本意改歪。HyDE 的假设文档就算事实错了也没关系，它只借"语义丰满度"去检索，最终回答仍基于真实召回的文档；代价是多一次 LLM 调用，一般只在"短查询召回不佳"时才上。

**指代消解**本质是 Query 重写的特例，只是补全信息的来源换成对话历史——"它过期了还能退吗"里的"它"要靠上一轮补全，详见后面的多轮记忆一节。

#### 检索策略

HYBRID 是默认推荐：专有名词、错误码、数字 ID 占比 > 1/3 必须 Hybrid，否则纯向量够用。**召回率是天花板**——排序只能在召回回来的候选里腾挪，召回阶段漏掉的段，后面再强的重排也救不回来。所以召回宁可放宽（候选池 N 开大），把精度交给重排。

两类查询各有克星：精确型（专有名词、错误码）用 BM25 靠字面命中，语义型用向量靠语义相似，单一检索必然漏一类。BM25 有两个可调参数：`k1`（≈1.2~2.0，控词频饱和速度）、`b`（≈0.75，控长度归一强度）。但 BM25 也会被字面蹭分坑到——"推销保险"可能靠"保""险"两个字把不相关段排到第一，这正是要靠向量和重排补位的原因。

**多路召回怎么合并**：向量相似度（0-1）和 BM25 分数（无界）基线不可比，不能直接相加。两条路线——**归一化加权**（各自拉到 0-1 再按权重相加，可调但要处理量纲）和 **RRF（Reciprocal Rank Fusion，倒数排序融合）**（每个文档在每一路里按排名贡献 `1/(k + rank)`，各路加总，`k` 常取 60，只看排名不看原始分，天然规避量纲问题）。工程上别一上来就追求动态权重：**先用固定权重 + RRF 跑通，再拿评估集看哪类查询拉胯，才有依据调成动态**，权重永远实测出来、不拍脑袋。

**召回旋钮三件套**，调这三个比一上来微调 embedding 见效快得多：

- **候选池 N**：每条腿先召回多少，是召回率的上限——正确 chunk 没进候选池，后面重排再准也救不回来，所以 N 先放宽，把精度交给重排
- **top-k**：最终喂给下游几条，常用 3-10，太小漏信息、太大喂噪声
- **元数据过滤**：检索前用 `content_type` / 时间 / 部门等标签先把候选集缩小，既提精度又降延迟，几乎零成本，是被低估的一招

HYBRID 模式下 score_threshold 必须推迟到 Rerank 之后。向量相似度（0-1）和 BM25 分数（无界）的基线不可比，在向量召回阶段下推阈值会把 BM25 高分但向量分低的段误杀。

dify 的工程化处理是把 `embedding_score_threshold` 在召回阶段重写为 0.0，把 `score_threshold` 推迟到 `DataPostProcessor.invoke()` 末尾。没有 Rerank runner 时走兜底路径，用原始向量分数。

##### 检索策略池

| 策略 | 召回率 | 精度 | 延迟 | 成本 | 适用场景 |
|---|---|---|---|---|---|
| 纯向量（SEMANTIC） | 中 | 中 | 低 | 低 | 问法单一 / 语义相似即可 |
| 纯关键词（FULL_TEXT / BM25） | 中 | 高 | 极低 | 极低 | 错误码 / 数字 ID / 专有名词 |
| Hybrid（向量 + BM25 加权） | 高 | 中 | 中 | 中 | 客户问法多变时默认选这个 |
| Multi-Query（多角度 query 改写后并行检索） | 很高 | 中 | 高 | 高 | 模糊问法 / 需要召回多角度 |
| HyDE（生成假设文档再检索） | 高 | 中 | 很高 | 高 | 短 query / 缺关键词 |
| Step-back（抽象 query 后检索） | 中 | 高 | 高 | 高 | 复杂问题需要先抽象 |

##### 检索路径设计

- 单库场景：query → embedding → 检索 → Rerank → top-N → LLM
- 多库场景（SINGLE）：合并多个库的检索结果，统一 Rerank
- 多库场景（MULTIPLE）：每个库独立检索 + Rerank，分别 LLM 生成，再合并
- 路由场景：先意图识别，按意图选库（不同库用不同 embedding / 不同切分策略）

#### 重排策略

**召回决定"对的段在不在候选里"，重排决定"对的段在不在前面"，两件事缺一不可**。混合检索上线后常有一类投诉：评估集 recall 很漂亮，用户却抱怨"答反了"——问"孩子摔伤住院意外险能赔吗"，召回里"保险责任"和"责任免除"都在，但字面更近的"责任免除"被排到第一，LLM 顺着答"不赔"。问题不在召回，在排序。召回用的双塔模型 query 和 document 分开编码，读不出"责任免除"和用户问题是反义关系；重排用 Cross-Encoder 把 query 和 document 拼在一起过一遍模型，能捕捉这种细粒度交互——代价是每个候选都要现算一遍，所以只能对召回后的 top-N 小批量做，扫全库不可行。工程数字上，召回池 Top-N 常取几十到一两百，最终喂 LLM 的 Top-K 常取 3-10。

Rerank 优先用本地模型而非云端 Cohere。Cohere 跨太平洋调用是常见延迟大头，能本地化就本地化。多语言混合、top-3 明显不相关时上 Rerank，短段密集时不上。

判断口诀：top-3 已经有 ≥ 1 段明显不相关就上 Rerank；用户延迟敏感就优先本地 BGE 而不是 Cohere。

两个容易忽略的工程点：**reranker 和 Embedding 不必同源**，各挑各的最优即可；**reranker 的最大输入长度要和 chunk 对齐**，否则超长 chunk 尾部被截断，精排等于白做。

重排完还有个摆放技巧：LLM 对上下文中间段的注意力会衰减（Lost in the Middle），把最相关的段放最前、次相关的放最后、**首尾交替摆放**，让最该被读到的段避开中间盲区。

Rerank 慢时按这个顺序提速：**批量推理**（把候选打包一次推理，是最大的浪费点、收益最大——新手常用 for 循环逐条 predict，GPU 一直空等，改成一次 batch 延迟直接掉一个数量级）→ 减少候选数 → INT8 量化。

若嫌 Cross-Encoder 太慢又不想丢精度，ColBERT 这类 late-interaction（迟交互）模型是双塔和交叉编码之间的折中：token 级表示部分预存，精度接近 Cross-Encoder、速度更好，长文档场景可作中庸选项。

##### 重排策略池

| 策略 | 精度提升 | 延迟 | 成本 | 适用场景 |
|---|---|---|---|---|
| 无重排 | 基准 | 0 | 0 | top-3 已经够准的简单场景 |
| cross-encoder 本地模型（BGE-reranker-base） | +20-40% | 中 | 中 | 默认推荐，本地化免跨网调用 |
| LLM 重排（GPT-4 / Claude 重排） | +30-50% | 很高 | 很高 | 关键路径小批量 |
| Cohere Rerank API | +20-40% | 中高（跨太平洋） | 中高 | 多语言场景（但延迟是大头） |
| WEIGHTED_SCORE 线性加权 | +10-20% | 低 | 低 | 极简场景，不需要模型 |

#### 多轮对话与记忆管理

单轮 RAG 看检索，多轮 RAG 还要看记忆。**记忆是与检索并行的第二个上下文来源**——不是检索的附庸。用户问"重疾险犹豫期多久"，下一句追问"那它过了还能退吗"，单独拿这句去检索，"它"什么都匹配不到（业内戏称"金鱼记忆"）；用户说"我给孩子买的"，几轮后这句被挤出窗口，机器人就会反复追问投保对象。记忆没做好，再聪明的模型也会前言不搭后语。

记忆分两层：

- **短期记忆**：本次会话内，存 Redis + TTL，管的是"刚才聊了什么"——小项目先把这层做好就够用
- **长期记忆**：跨会话的用户画像 / 历史事实，存向量库 + 文档库，本质就是**"对用户过去的一次 RAG"**——需要时检索出来拼进上下文

历史怎么选进上下文，靠组合拳（业内叫 Selective Context），别以为要二选一：

1. **滑动窗口**：保最近 N 轮，保时效
2. **语义检索历史**：从更早的历史里按当前 query 检索相关轮次，防止关键信息被窗口挤掉
3. **关键事实单独提醒**：投保人、金额这类关键事实单独留底，不进裁剪逻辑
4. **主题 + 重要度**：给历史轮次标注关键事实 / 决策点，当前问题同主题时才取用——最准，但要预处理标注

上下文裁剪守四条原则：**最近几轮原样保**（权重最高）、**远处用摘要压缩而不是硬砍**、**跑题闲聊直接删**、**关键事实单独留底**别被压没。长期记忆可以引入类似艾宾浩斯遗忘曲线的机制——给每条记忆记访问次数和时间戳，常用的巩固加权、长期没用的衰减淘汰，配合去重和层次化摘要。这里最容易翻车的不是存不下，而是**记太多反而更笨**：一堆陈旧、重复、不相关的记忆被检索出来污染当前回答，所以遗忘 + 去重 + 重要度截断和"能存"同样重要。

指代消解是多轮的入口动作：把当前 query 里的"它 / 这个 / 上面说的"用最近提到的实体替换掉，再送进检索。这一步接在 Query 理解之后、检索之前。

框架层面，LangChain 提供 Buffer / BufferWindow / Summary / VectorStoreRetriever 四种 Memory，接口统一在 `load_memory_variables` / `save_context`；LlamaIndex 用 `ChatMemoryBuffer` 设 `token_limit`，超限自动转长期 Block（Static 画像 / FactExtraction 事实 / Vector 语义）。要灵活自己拼选 LangChain，要长期对话开箱即用选 LlamaIndex——但**底层都是 buffer / window / summary / vector 这几招，框架只是封装**，看透这层比背 API 更顶用。

#### 缓存与失效

在线链路的重复计算靠四层缓存兜底：

| 缓存层 | 命中对象 | 失效策略 |
|---|---|---|
| Query embedding 缓存 | 相同 query 不重复算 embedding | query hash TTL |
| 检索结果缓存 | 相同 query 不重复检索 | 文档更新即失效 |
| Rerank 结果缓存 | top-K rerank 分数 | 文档更新即失效 |
| LLM 生成缓存 | 相同 query + 检索结果不重复生成 | 文档更新即失效 |

#### 生成与引用溯源

到这一步资料已经检索、重排好，剩下的是怎么让 LLM 只依据资料作答、并把出处交代清楚。LLM 在无证据情况下会自由发挥，这就是幻觉。强制引用是抑制幻觉最直接的手段。

段级引用是最常见的形式，每个检索段落标注 `source_doc_id` + `chunk_id` + `score`，LLM 生成答案时附引用编号 `[1][2]`。句级引用更精细，每个生成的句子标注来自哪些段落，幻觉检测精度更高但成本翻倍。

生成 Prompt 有个稳定骨架，五件套：**角色 + 硬约束开头**（一句"仅依据提供的资料回答，资料中没有就明确说没有"同时干两件事——奠定可溯源、挡住一部分幻觉）、**检索片段带编号 `[1][2]`**、**输出要求**（每个事实必须标编号、找不到就说"资料中没有"）、**few-shot（可选）**、**长度 / 语气控制**。

引用溯源有两条路线，别只用第一条：让 LLM 在生成时自标引用，快、简单，但**自标引用的漏标率约 15%**，还挡不住幻觉；生成后用 NLI 模型做归因校验，慢、要多一道模型，但更可靠。**NLI 既是归因校验也是幻觉检测**：逐句验证"原文是否蕴含这句"，找不到支撑就是幻觉嫌疑，处理动作有四种——删掉 / 标"存疑" / 触发拒答 / 回退重新检索。

所以防幻觉是**两道闸**，缺一不可：只靠生成前 Prompt 约束挡不住（模型偶尔会自信越界），只靠生成后处理也挡不住（有些幻觉长得很像真的），必须前约束 + 后校验一起上。除了引用，回答控制还有配套的三件事：**拒答**（没依据就别给）、**防越权**（敏感问题拦截给安全话术）、**多段融合**（片段相互矛盾时倾向更可信那条）。

幻觉抑制三层兜底：

1. 强制引用，Prompt 要求 LLM "每个事实必须标注引用编号，否则不能写"
2. 引用一致性校验，生成后用 NLI 或 LLM-as-judge 校验每个句子是否被引用段落支撑
3. 低置信度兜底，Rerank 分数低于阈值时直接拒答"知识库无相关信息"

引用能不能落到"点开看原文"，取决于全链路有没有收口：切分时给 chunk 打的 `section_path` 元数据 → 检索时带着走 → 生成时映射成可点击的出处。这条链断在哪一环，引用就退化成一个没法核对的编号。

## 四、反模式

### 切分与索引

- 默认上完整管线，知识 < 100 段也硬上 R2/R3，过度工程化
- 跳过解析质检直接切分，无边框表 / 印章遮挡的错误静默传导到下游
- chunk_size 过大（如 2048+），召回率暴跌，LLM 注意力分散
- chunk_size 过小（如 128），上下文碎片化，答案不完整
- overlap = 0 或硬切在 token 边界，段边界句子被拦腰截断
- CJK 用纯英文 embedding，召回率惨不忍睹
- 迷信 MTEB 榜单选 embedding，通用榜第一到垂域可能排名翻车
- 没榨干切分 / 检索 / 重排就先上微调，花大力气收效甚微
- embedding 模型升级用增量会丢段，必须全量重建

### Query 理解与检索

- 拿到 query 直接检索，不做意图识别和指代消解，多轮场景"它"指代失败
- 用 LLM 做意图识别不约束输出格式，返回结果五花八门没法用
- 全场景无脑扩写 query，简单 FAQ 也翻几倍查询数，延迟和成本爆炸
- 重写 query 不做降险，直接拿改写结果去查，把用户本意改歪也没有"原始 + 改写都查"兜底
- 多路召回的分数直接相加，向量分和 BM25 分量纲不可比，该用 RRF
- 纯向量检索全部场景，专有名词、错误码、数字 ID 召回率极低
- HYBRID 模式下推 score_threshold，向量相似度和 Rerank 分数基线不可比，误杀良段

### 重排与多轮

- 用 Cohere 跨太平洋调用当默认，延迟大头，本地 BGE 替代
- Rerank 全量上，短段密集场景 Rerank 浪费 token
- reranker 最大输入长度没和 chunk 对齐，超长 chunk 尾部被截断，精排白做
- Rerank 慢就先减候选，忘了批量推理才是最大浪费点
- 多轮把全部历史硬塞进上下文，token 爆炸还触发 Lost in the Middle
- 关键事实（投保人 / 金额）不单独留底，被滑动窗口挤掉后反复追问
- 长期记忆只管"存"不管"忘"，陈旧重复记忆越攒越多，反而污染当前回答
- Economy 库没向量，HYBRID 实际只跑 2 路，别误判为 bug

### 缓存与索引

- 缓存粒度太粗，query 全文缓存 → 拼写差异不命中
- 缓存不过期，文档更新后用户看到旧答案
- 文档状态机没读时过滤，写失败的段直接暴露给用户
- embedding 模型升级用增量索引，新旧向量不可比，必须全量重建

### 引用与归属

- 只让 LLM 自标引用不做后处理，约 15% 漏标 + 挡不住幻觉
- 只引用不校验，LLM 引用不相关段落，幻觉率反而更高
- 引用编号藏在脚注，用户看不到等于没引用，必须 inline 标注
- 过度引用，每句话都强行引用让答案可读性崩溃，应该只在"事实性陈述"处引用

### 评测

> 详见 [RAG 评测篇 §反模式](./rag-evaluation.md#反模式)

## 五、何时不该用 RAG

- **知识 < 50 段且相对静态**：直接塞 Prompt 比动态检索更稳
- **主题高度集中**（如客服 80% 问题集中在少量主题）：Summary Index 比 BM25 兜底更有效
- **强实时性场景**（毫秒级响应）：RAG 检索 + 重排延迟通常 0.5-2s，Prompt 直塞或预生成模板更合适
- **强成本敏感**：RAG 全套管线的索引成本远高于 Prompt 直塞，且每次查询都有额外 token 消耗

# 任务合同与意图识别

## 结论

意图识别不是给输入贴一个 `intent` 标签，而是为下游确定四件事：

- 进入哪个任务流程；
- 需要哪些参数和上下文；
- 哪些约束必须持续生效；
- 当前应该执行、澄清、拒绝还是转人工。

因此，意图识别的产物不应只有一个枚举值，而应是带有槽位、约束、缺失信息、置信度和证据的 `TaskContract`。例如“帮我推荐一条裤子，不超过 100 元，最好是牛仔裤”至少要被拆成商品推荐、服装/裤子、价格硬约束和牛仔裤软偏好；只识别成 `product_recommendation`，后续工具仍然可能返回不符合预算的商品。

```text
原始输入
  -> 初步输入规范化
  -> 代码规则路由
  -> 轻量模型识别
  -> 深度模型处理复杂上下文
  -> 槽位、约束与风险校验
  -> 澄清 / 确认 / 拒绝
  -> TaskContract
  -> 初始化 State、上下文和可见能力
```

这条链路不要求每个系统都部署三个模型。单一任务或只有一个执行路径的系统，可以直接使用类型校验和业务规则；只有当意图会改变工具集、权限、Workflow 或成本时，才需要把识别独立成一层。

## 组件边界

Task 是逻辑合同，不等于一个独立的 Intent Classifier 服务。不同 Agent 可以用不同方式形成它：

| 形成方式 | 典型场景 | Task 在哪里完成 |
| --- | --- | --- |
| 显式路由 | 多产品入口、多个 Workflow、不同权限域 | Agent Loop 之前的分类器或路由器 |
| 首轮理解 | Coding Agent、通用助手、开放式研究 | 首轮 View 中由模型解释目标，必要时追问 |
| 结构化入口 | SDK、表单、固定 API、后台任务 | 调用方直接提交 `TaskContract` |
| 固定流程 | 单一用途 Workflow、定时任务 | 代码和配置预先确定，不需要模型分类 |

输入路由负责：

- 绑定用户、租户、会话、语言和入口来源；
- 把随意表达规范化为可判断的任务描述；
- 识别会改变执行路径的任务级意图；
- 抽取资源范围、时间范围、输出格式、预算和禁止事项；
- 区分硬约束、软偏好和需要用户确认的动作；
- 判断信息不足、意图冲突或超出能力范围；
- 输出执行、澄清、拒绝或人工接管；
- 为任务创建初始运行状态。

它不负责：

- 在入口阶段直接回答用户问题；
- 执行工具或修改外部状态；
- 用意图标签替代权限检查；
- 把模型猜测的字段当作已确认事实；
- 覆盖已经确认的参数和审批结果。

## 先做输入规范化

用户不会总是用完整、标准的句子描述任务。至少要处理以下几类输入：

| 类型 | 处理目标 | 示例 |
| --- | --- | --- |
| 指代 | 找到“这个、那个、第一个、刚才那个”对应的对象 | “第二个适合生产吗？” |
| 省略 | 补出缺失的主语、宾语或动作对象 | “市场占有率多少？” |
| 表达混乱 | 处理口语、病句、倒装、临时改口 | “不是，我说的是另一个。” |
| 术语多义 | 结合行业和上下文统一缩写、黑话、内部代号 | `CRM`、项目代号、团队内部简称 |
| 主观判断 | 把“高级”“便宜”“性价比高”等词转成可检查的标准 | “换个更有性价比的方案” |
| 外部事实 | 标记需要检索或工具确认的内容 | “现在最便宜的是哪个？” |

### 两个规范化阶段

初步规范化放在意图识别之前，处理当前输入本身就能解决的错别字、明显指代、术语和句式问题。它的职责边界要写进 Prompt 或 Spec：

- 可以做指代消解、省略句补全、病句修正、术语标准化和多义词消歧；
- 可以标记需要澄清、历史检索或外部搜索的情况；
- 不直接回答用户问题；
- 不执行工具；
- 不做最终推荐；
- 不擅自补充业务事实；
- 不强行猜测低置信内容。

深度规范化放在任务执行过程中。当输入依赖很久以前的对话、工具结果或执行中间事实时，入口阶段没有足够信息完成消解。例如用户几天后说“你上次推荐的看樱花的那个地方”，系统需要先检索历史细节，再判断它对应哪个地点。

```text
当前输入
  -> 用“樱花、旅游、推荐”等属性召回历史细节
  -> 把候选对话放入当前上下文
  -> 推断“看樱花的那个地方”对应的实体
  -> 无法唯一确定时追问，而不是选择一个候选直接执行
```

短期记忆不足时，检索结果可以由大模型再次根据属性判断；检索不理想时，可以让模型提取更具体的属性作为下一次检索参数。这里的补偿机制只负责扩大证据范围，不能把检索不到的对象伪造出来。

### 让名称成为稳定索引

模型输出“方案一”“第二个”会诱导用户在后续对话中继续使用位置性指代。输出时应给对象赋予稳定、可复用的名称，例如把“第一个方案”命名为“TCC 方案”。后续用户说“调整 TCC 方案”时，系统可以按名称查找，而不是依赖模型重新猜测列表位置。

规范化结果应作为关键事实贯穿当前任务，至少记录：

```json
{
  "normalized_query": "评估 TCC 方案是否适合生产环境",
  "references": {
    "第二个": {
      "resolved_to": "TCC 方案",
      "source": "assistant_previous_turn",
      "confidence": 0.94
    }
  },
  "term_mapping": {},
  "needs_clarification": false,
  "needs_retrieval": false
}
```

`references`、术语解释和用户确认过的事实不能只存在于一次 Prompt 中。它们需要进入当前任务的状态或事实存储，否则下一轮又会退回到原始的模糊表达。

## 意图识别只识别执行路径

候选意图按执行需要定义，不要为了覆盖所有语言差异建立细粒度标签树。电商 Agent 中，下面三个意图的边界已经足够决定后续路径：

| 意图 | 判断标准 | 示例 |
| --- | --- | --- |
| `product_recommendation` | 根据预算、用途或偏好推荐一个或多个商品 | “3000 元以内有什么手机推荐？” |
| `product_comparison` | 明确提到两个或多个对象，并要求比较或选择 | “iPhone 16 和小米 15 哪个更适合拍视频？” |
| `product_query` | 查询某个对象的参数、价格、库存或事实 | “iPhone 16 的电池容量是多少？” |

意图定义至少包含名称、适用条件、排除条件、必需槽位、可选槽位、成功条件和确认条件。相近意图必须配正反例，避免只给模型一组名称，让它自行发明边界。

候选意图太多时，先识别粗粒度任务域，再在域内识别子意图。例如先判断“售前”或“售后”，再在售后域内区分订单查询、退货申请和投诉。这样可以缩短 Prompt，也能让每一层只面对当前可执行的候选集合。

意图识别至少要保留两个出口：

- `unclear`：候选意图之间有混淆，或关键槽位不足，需要澄清；
- `unsupported`：请求不在系统能力范围内，应拒绝或转人工。

不能把“帮我生成一个奥特曼动画”强行归到电商商品推荐。拒识本身是正确路由，错误路由才是风险。

## 三层识别机制

三层机制的价值在于把确定性、常见请求和复杂请求分开处理。实际系统可以按成本和风险裁剪层级，但每一层都要有明确的“识别成功”条件。

### 第一层：代码规则

代码层适合处理确定性强、重复频率高的输入：

- 页面按钮、表单提交和显式 API 参数；
- “继续”“下一步”“取消”等固定操作；
- 当前 State 已经满足条件时的状态转移；
- 规则引擎能明确判断的命令或权限前置条件。

这一层应直接输出结构化路由和证据，例如 `source=ui_action`、`rule_id=continue_current_plan`。它的特点是快、稳定、可回放，不能覆盖所有自然语言。

### 第二层：轻量模型

代码层没有命中时，使用轻量模型处理常见且不需要深度推理的表达，例如“帮我推荐一个手机”。输出候选意图、槽位、置信度和缺失信息，不要只输出一个标签。

轻量模型的结果不能仅凭自报的 `confidence` 接受。这个分数更接近模型的自我判断，不一定是真实概率。更稳妥的做法是结合：

- 规则是否命中；
- 输入与候选意图描述的相似度；
- 槽位是否满足该意图的最低要求；
- 历史测试集和线上样本中的意图级准确率；
- 是否存在相近候选或约束冲突。

阈值应从验证集和线上回流样本中校准。高分可以接受，中间区间进入澄清或仲裁，低分交给深度模型；不应把固定的 `0.85`、`0.6` 当作通用标准。

### 第三层：深度模型

深度模型处理以下情况：

- 句子复杂、多个动作混在一起；
- 强依赖跨轮上下文或历史事实；
- 用户在多轮对话中切换任务；
- 一次输入包含多个意图；
- 需要根据上下文补全隐含参数；
- 轻量模型给出相近候选或发现硬约束冲突。

它可以在入口阶段运行，也可以嵌入 ReAct / Workflow 循环，在召回历史、读取工具结果后继续补全槽位。深度模型仍然要受候选意图、输出 Schema 和拒识出口约束，不能因为推理能力更强就绕过权限和确认边界。

## 槽位、约束与可量化表达

意图枚举只决定进入哪条流程，槽位填充（Slot Filling）负责收集这条流程真正需要的参数。以商品推荐为例，槽位可以包括：

```text
category
sub_category
budget_min
budget_max
usage_scenario
brand_preference
must_have_features
nice_to_have_features
hard_constraints
soft_preferences
```

每条意图都要声明必填槽位、可选槽位、默认值来源和校验规则。用户说“帮我推荐一台笔记本，主要写代码，最好轻一点”时，系统可以得到品类、场景和软偏好，但如果预算会影响检索范围，就必须把 `budget_max` 标记为缺失，而不是静默猜一个数字。

约束要区分强度和来源：

| 类型 | 行为 | 示例 |
| --- | --- | --- |
| 硬约束 | 必须满足，无法满足时停止、换方案或明确告知 | “价格不超过 100 元”“不要修改 A 接口” |
| 软偏好 | 尽量满足，无法满足时说明取舍 | “最好是牛仔裤”“希望更轻一点” |
| 待确认条件 | 需要用户确认后才能执行 | 发送邮件、退款、修改生产配置 |

每个字段都记录 `source`、`confidence` 和 `validation_status`。`source` 至少区分用户原话、历史事实、模型推断和系统校验；高风险字段不能因为模型给出高置信度就视为用户确认。

“更便宜”“更高级”“最有性价比”不能直接作为可执行参数。系统应根据领域规则、用户偏好或进一步澄清把它们转换成可比较的条件。例如“性价比”可能表示同等价格下质量、配置、服务或体验更好，也可能表示同等质量下价格更低。只有确定比较维度后，才能把价格区间、质量等级、功能要求等条件传给检索或推荐工具。

这类解释规则可以写入意图 Spec，也可以沉淀到领域词汇表。不要让每次调用都临时猜测同一个词的含义。

## 领域词汇表与上下文检索

缩写、黑话和内部代号需要结合行业、用户和会话解释。同一个 `CRM` 在不同领域可能指客户关系管理系统，也可能指临床研究管理；一个团队反复讨论的“大黄蜂”也可能是项目名称。

可以维护三类词汇：

- 公共词汇表：行业术语、通用缩写和组织级项目名；
- 用户词汇表：某个用户长期使用的简称、偏好表达和对象别名；
- 会话词汇表：当前对话中新出现、尚未沉淀的临时称呼。

输入规范化前先按行业、租户、用户和当前对话检索相关词条，把定义作为证据注入上下文。新词不要一次出现就自动写入公共词汇表，可以离线分析多轮对话，统计出现次数、讨论人数、连续出现情况和基本含义，再进入审核或升级流程。这样既能减少漏收，也能避免把一次误识别固化成系统事实。

跨较长时间线寻找对象时，优先按用户输入中的属性检索历史细节，再让模型在候选证据中完成指代消解。检索结果不足时扩大属性或改写查询；仍不能唯一确定时澄清，不要从多个候选中随意选择一个。

## Prompt 与输出约束

意图识别 Prompt 的重点是收窄模型的决策空间：

1. 列出当前路由允许的候选意图，禁止模型创造新标签。
2. 写清相近意图的适用边界、排除条件和正反例。
3. 为每个意图声明槽位、必填条件、默认值来源和校验规则。
4. 明确硬约束、软偏好、确认条件、`unclear` 和 `unsupported` 的处理。
5. 要求输出固定 Schema，并在代码层校验枚举、字段类型和必填字段。
6. 用线上失败样本维护 few-shot；样本过多时，按当前领域和混淆边界检索少量示例注入。
7. 明确入口识别不能回答问题、执行工具或伪造外部事实。

可用的最小输出结构如下：

```json
{
  "intent": "product_recommendation",
  "slots": {
    "category": "服装",
    "sub_category": "裤子",
    "budget_max": 100
  },
  "hard_constraints": [
    {
      "field": "price",
      "operator": "<=",
      "value": 100,
      "source": "user"
    }
  ],
  "soft_preferences": ["牛仔裤"],
  "missing_slots": [],
  "ambiguous_fields": [],
  "need_clarification": false,
  "confidence": 0.91
}
```

解析失败、枚举非法、槽位互相冲突或证据不足时，应进入澄清或下一层处理，不能把不完整的 JSON 当作完整合同。

## 澄清、拒绝与合同冻结

澄清问题要针对具体缺失字段，避免让用户重新描述整个任务。例如“帮我推荐一条裤子”如果预算会改变检索范围，就问“预算上限是多少”，不要直接随机推荐。

澄清回答只能更新对应字段，不能被解释成对后续所有动作的授权。用户补充“预算 100 元”只更新预算，不代表用户同意购买、下单或使用此前未确认的收货地址。

多个意图都合理时，让用户选择或拆分任务；超出能力范围时返回 `unsupported`，说明可处理的边界；高风险动作在低置信度、参数缺失或确认状态不明时默认停在入口，不走高风险路径。

合同冻结后再初始化 `State`、选择 Workflow 或 Agent 模式、组织首轮上下文并计算最小可见能力集合。合同改变任务目标时递增版本，旧的动作计划、审批和风险判断不能自动沿用。

```text
TaskContract {
  task_id
  version
  normalized_query
  goal
  intent
  route
  slots
  constraints
  success_conditions
  refusal_conditions
  risk
  required_confirmation
  confidence
  evidence
  missing
  ambiguous_fields
  fallback
}
```

合同中的参数必须带来源、置信度和校验状态，不能把模型生成的值直接当成已确认事实。`success_conditions` 和 `refusal_conditions` 要在进入 Agent Loop 前确定，否则 Decision 无法判断何时停止、澄清或拒绝。

## 评估与回归集

不能只看一个总体准确率。推荐至少建立覆盖以下场景的测试集：

- 标准且完整的输入；
- 口语化、病句、指代和主语省略；
- 缺少一个关键槽位；
- 两个相近意图的混淆样本；
- 超出能力范围的请求；
- 跨轮补充参数；
- 硬约束、软偏好和确认要求；
- 多轮意图切换；
- 多意图输入；
- 检索不到历史事实或词汇解释的输入。

核心指标包括：

| 指标 | 观察内容 |
| --- | --- |
| Top1 / TopK 准确率 | 第一候选是否正确，或正确意图是否在候选集合中 |
| 分意图准确率 | 低频、高风险意图是否被多数类掩盖 |
| 拒识准确率、误拒率、漏拒率 | 该拒绝的是否拒绝，可处理请求是否被误拒 |
| 澄清触发准确率、澄清后收敛率 | 是否问对了字段，追问后任务能否继续 |
| 槽位准确率、召回率 | 参数值是否正确，用户已表达的信息是否被抽出 |
| 必填槽位完整率 | 启动流程前必需参数是否齐备 |
| 槽位更新准确率 | 多轮新信息是否正确覆盖旧值 |
| 约束识别准确率 | 硬约束和软偏好是否被正确区分并持续生效 |
| 任务成功率与副作用率 | 正确路由是否带来完成结果，错误路由是否造成错误工具调用或状态修改 |

线上用户说“不是这个意思”“你理解错了”时，可以把它作为上一轮规范化或意图识别失败的弱信号，回写到错误样本和 few-shot 候选中。用户纠正后的最终意图、槽位和约束还应保留，作为回归测试的标准答案。

阈值、候选数量和路由层级都应由这组数据驱动。一个系统即使总体 Top1 很高，也可能把低频退款、投诉或生产修改请求路由错；这些意图需要单独看准确率、漏拒率和副作用。

## 最小实现

1. 先定义少量会改变执行路径的任务级意图，写清相近意图边界。
2. 在识别前做初步规范化，保留指代映射、术语解释和需要检索的标记。
3. 用代码处理按钮、固定命令和明确状态转移。
4. 用轻量模型处理常见请求，输出意图、槽位、约束、置信度和缺失字段。
5. 只在复杂上下文、低置信度、候选冲突或多意图时启用深度模型。
6. 为每条路由声明必填槽位、硬约束、软偏好、成功条件和确认条件。
7. 将解析失败、缺槽位、低置信度和拒识交给澄清、拒绝或下一层，不要默认执行。
8. 合同冻结后再初始化 State、上下文和工具权限。
9. 用标准、口语、指代、缺参、混淆、拒识、跨轮和意图切换样本持续回归。

## 失败模式

| 失败行为 | 正确处理 |
| --- | --- |
| 缺参数却直接执行 | 标记 `missing`，针对字段澄清 |
| 入口阶段无法消解长时段指代却硬猜 | 检索历史细节，仍不确定则澄清 |
| 低置信度默认走高风险路径 | 拒绝、确认或转人工 |
| 标签很多但路径不变 | 合并标签，减少维护面 |
| 把意图标签当权限 | 在执行边界重新鉴权 |
| 把硬约束当软偏好 | 在工具参数和结果校验中强制检查 |
| 把软偏好当硬约束 | 无法满足时说明取舍，不伪造满足 |
| 多轮重复覆盖已确认参数 | 保存参数来源、版本和确认状态 |
| 词汇出现一次就写入公共词汇表 | 先离线聚合、验证和审核 |
| 把模型 `confidence` 当真实概率 | 结合规则、相似度、历史准确率和槽位完整度 |
| Task 合同和 Agent 状态混在一起 | 合同保存任务目标与约束，State 保存运行事实和过程版本 |

## 不该引入

固定表单、固定 API、只有一个执行路径的任务，不需要额外的意图识别层。直接使用类型校验和业务规则更简单。

如果只是改变页面文案或提示语，也不必为此建立复杂分类器；如果会改变工具、Workflow、权限或高风险动作，才值得把意图和任务合同独立出来。

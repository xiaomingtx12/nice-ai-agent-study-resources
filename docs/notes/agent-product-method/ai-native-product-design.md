# AI Native 产品怎么设计：执行杠杆、人的决策与不确定性管理

AI Native 产品不是把所有工作交给 AI，而是重新分配操作与决策：**AI 承担信息处理、路径组织和可控执行，人保留目标、取舍与高影响决策。** 产品价值来自执行杠杆，不来自无人参与。

[理解 + AI 与 AI Native](./plus-ai-and-ai-native.md) 讨论两种产品形态的边界。本文继续回答：确定要围绕 AI 重构任务后，怎么处理模型不准确、人机分工、个性化和系统接入。

## 一、操作学习成本消失后，判断成本会上升

传统软件要求人同时掌握业务和工具：既要知道自己想完成什么，也要知道菜单位置、字段含义和操作顺序。AI Native 产品把第二部分交给系统。用户表达业务目标，AI 将目标转成查询、填写、调用和流程推进。

但成本没有完全消失，而是发生了转移：

| 传统软件中的主要成本 | AI Native 产品中的主要成本 |
|---|---|
| 学习功能入口和操作顺序 | 判断 AI 是否理解正确 |
| 手动查找和搬运信息 | 判断依据是否充分 |
| 按固定步骤完成流程 | 处理执行中的歧义和异常 |
| 自己保证字段和动作正确 | 确认高影响动作能否执行 |

因此，AI Native 产品不能只缩短操作路径，还要降低判断成本。系统需要提供足够的依据、预览和状态，但不能把完整推理过程和所有中间数据都丢给人检查。

## 二、人机分工：AI 执行，人做取舍

“副驾驶”不等于只提供建议。AI 可以承担大量连续工作：

- 读取当前页面、历史记录和业务规则
- 检索相关信息，发现冲突与遗漏
- 把目标拆成步骤，选择可用工具
- 执行低风险操作，跟踪中间状态
- 生成候选方案，并说明关键依据
- 在责任边界前请求确认

人保留的不是所有操作，而是几类机器不能代替的责任：

- 定义目标和优先级
- 在多个合理方案之间做价值取舍
- 批准高风险或不可逆动作
- 处理证据不足、规则冲突的情况
- 承担最终业务责任

衡量 AI Native 程度时，不必追求自动执行比例。更直接的问题是：**人是否还在承担本可机械化的查找、搬运、组合和系统操作。**

## 三、不准确无法消除，只能按风险管理

模型输出具有不确定性。这不是等待模型升级后就会消失的临时缺陷，而是产品设计的长期约束。

任务可以按风险和可验证性划分：

| 任务特征 | 产品机制 |
|---|---|
| 低风险、易验证 | 自动执行，保留结果和操作记录 |
| 低风险、难验证 | 给出依据、候选结果或置信信号 |
| 高风险、可撤销 | 执行前预览确认，执行后支持回滚 |
| 高风险、不可撤销 | AI 准备材料，人明确批准 |
| 关键信息不足 | 追问，不自行补全事实 |
| 超出能力或权限 | 停止执行，说明缺口并转人工 |

### 确认点放在责任变化处

每一步都确认会把 AI 变成更慢的操作界面。完全不确认又会失去控制。确认点应该放在责任发生变化的地方，例如：

- 对外发送消息、文件或承诺
- 修改核心业务数据
- 付款、签署和提交审批
- 删除、覆盖或批量变更
- 提升权限或扩大数据范围
- 采用无法自动核验的专业结论

查询、整理、格式转换和可撤销的草稿生成可以连续执行。产品需要减少无意义确认，而不是减少所有确认。

### 失败处理是主流程，不是异常页

AI Native 任务通常包含多个步骤。任一步失败，都可能改变后续路径。产品至少要区分：

- **重试**：外部服务暂时失败，参数和目标不变
- **换路径**：原工具不可用，改用其他来源或步骤
- **回退**：撤销已完成但不再适用的动作
- **补信息**：缺少关键条件，请人提供
- **人工接管**：风险或歧义超过系统边界

只在最后显示“执行失败”，无法支撑真实任务。

## 四、AI 应用负责三种语言之间的转换

做 AI 应用需要先区分三种表达：

1. **人的业务语言**：依赖常识、场景、关系和大量省略。
2. **模型的任务表示**：需要目标、上下文、约束、可用能力和输出要求。
3. **软件的执行语言**：需要确定的字段、类型、参数、权限和动作。

转换链如下：

```text
人的业务语言
    ↓ 意图识别、指代解析、上下文补全
模型可处理的任务表示
    ↓ 工具选择、参数构造、权限检查
软件可执行的结构化动作
```

例如用户说“把这个客户跟进一下”，其中省略了当前客户、跟进目的、渠道、历史关系和执行时间。系统不能要求用户先学习字段，也不能让模型直接猜完。合理过程是：

1. 从当前页面和历史记录补充可确定的信息。
2. 对影响结果的歧义进行追问。
3. 生成结构化动作和内容草稿。
4. 对外发送前展示人能快速判断的预览。
5. 执行后读取系统结果，核验是否落库或送达。

这条转换链是 AI 应用的核心产品能力。模型只是其中一个环节。

## 五、通用 Agent 能做，专用系统还有什么价值

通用 Agent 已能读取文件、调用工具、组织步骤。专用 AI 应用的意义不是再造一个聊天框，也不是拥有一个更聪明的模型，而是预先提供稳定的业务条件：

| 专用系统提供的内容 | 解决的问题 |
|---|---|
| 组织、用户和任务上下文 | 当前在为谁处理什么事 |
| 业务概念和字段语义 | 系统数据在业务上代表什么 |
| 真实工具和系统连接 | 结果如何进入业务流程 |
| 身份、权限和数据边界 | 哪些信息和动作可以使用 |
| 流程、确认点和安全规则 | 哪些步骤能自动推进 |
| 业务评测标准 | 什么结果才算正确完成 |
| 状态、审计和责任记录 | 出错后如何追踪和处理 |

通用 Agent 提供通用执行引擎，专用系统提供业务上下文与治理边界。二者可以组合，而不是互相替代：

```text
通用 Agent 运行时
+ 企业业务上下文
+ 专用工具与 Skill
+ 权限、审计和评测
= 可进入业务流程的 AI 应用
```

判断是否值得做专用系统，可以问：每次使用通用 Agent 时，需要临时补充的上下文、工具、规则和权限是否稳定、重复且多人共用。如果答案是肯定的，这些内容就值得产品化。

## 六、把历史记录“变活”

传统企业软件已经保存了大量客户、工单、会议、审批和操作记录，但主要用途是展示、搜索和审计。AI Native 产品可以让历史进入当前任务：

- 根据历史客户互动判断下一步动作
- 从相似工单中提取有效处理方法
- 从会议记录中找到未完成事项
- 从审批记录中识别实际决策条件
- 根据个人工作习惯调整输出和确认方式

“变活”不等于把全部历史塞进上下文。系统要检索当前任务相关的记录，区分事实、偏好和推断：

| 信息类型 | 例子 | 产品要求 |
|---|---|---|
| 事实记录 | 用户发送过某封邮件 | 保留来源和时间，可核验 |
| 稳定偏好 | 常用中文表格输出 | 可查看、修改和删除 |
| 系统推断 | 用户可能偏好某类客户 | 明确标识为推断，不当成事实 |

个性化的风险是错误累积。一次临时要求不能自动变成长期规则，模型推断也不能悄悄固化为用户画像。记忆机制需要显式的来源、作用范围和清除方式。

## 七、CLI、MCP 和 Skills 在产品层是什么

CLI、MCP 和 Skills 不是 AI Native 产品本身。它们构成的是**Agent 可操作面**：让 AI 能发现、理解并使用软件能力。

### CLI：可执行动作面

CLI 把页面操作变成参数明确、结果可读的命令。它适合 Agent 调用，因为动作容易组合、重试、记录和测试，也比模拟点击界面更稳定。

它回答：**AI 怎么操作系统。**

### MCP：标准化能力接入面

MCP 用统一协议暴露工具和资源，使不同 Agent 能发现并调用同一套系统能力。它降低接入成本，也减少业务系统与具体 Agent 客户端的绑定。

它回答：**AI 怎么发现和连接系统能力。**

MCP 只解决接入协议，不自动解决业务语义、权限、流程和结果正确性。

### Skills：业务方法与经验层

Skill 封装的不只是工具清单，还包括触发条件、操作顺序、业务规则、安全边界和输出要求。它把“系统能做什么”组织成“面对这类任务应该怎么做”。

它回答：**AI 应该怎样使用系统。**

三者的关系可以压成一条链：

```text
CLI：系统能做什么
MCP：Agent 如何接入这些能力
Skill：面对具体任务时应该怎么使用
```

企业软件提供 CLI、MCP 和 Skills，说明它开始同时服务人的操作界面和 Agent 的操作界面。这是 AI Native 的基础设施，但不代表产品已经完成 AI Native 转型。只有当这些能力进入目标理解、任务执行、风险控制和结果反馈的完整链路，产品形态才真正改变。

## 八、设计时检查什么

一个 AI Native 功能进入实现前，可以检查以下问题：

### 任务与价值

- 用户交付的是目标，还是仍要逐步操作功能？
- AI 是否减少了查找、搬运、组合和协调工作？
- 个性化是否改变了任务结果，而不只是语气？

### 人机分工

- 哪些步骤可以自动执行？
- 哪些位置涉及价值取舍或责任转移？
- 人工确认是否只保留在关键节点？

### 不确定性

- 结果依据是否可追溯？
- 操作能否预览、撤销、重试和回退？
- 信息不足时会追问还是猜测？
- 超出边界时如何转人工？

### 系统接入

- 人类语言如何转成结构化动作？
- 工具是否继承真实身份与权限？
- 执行结果是否会读回核验？
- CLI、MCP 和 Skills 分别承担什么职责？

### 记忆与评测

- 事实、偏好和推断是否分开？
- 用户能否查看、修改和删除长期信息？
- 指标是否覆盖任务完成率、人工介入率、恢复率、时间和成本？

## 结论

AI Native 产品的核心不是全自动，而是建立一条可控的任务执行链：

- 人用业务语言给出目标和约束。
- AI 利用上下文组织步骤，调用系统能力执行。
- 产品管理依据、权限、确认、回退和人工接管。
- 历史记录参与当前决策，但事实、偏好和推断保持边界。
- 人保留价值取舍和高影响决策，AI 尽量承担其余可验证工作。

模型不准确不会因为界面变成对话框而消失。好的 AI Native 产品不掩盖这种不确定性，也不把全部判断压力还给用户，而是把不确定性限制在可观察、可控制、可恢复的范围内。

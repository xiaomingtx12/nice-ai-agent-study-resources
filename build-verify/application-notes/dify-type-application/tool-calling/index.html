类Dify 平台的工具调用设计

如果说 Agent 层负责“想什么、下一步做什么”，那工具调用层负责的就是“怎么把动作真的执行出去”。

这个项目里，工具平台不是一个简单的插件列表，而是一个统一的工具体系：Builtin Tool、API Tool、MCP Tool 三类统一治理，支持 OpenAPI Schema 导入、MCP Server 配置与工具发现、参数校验、调试运行，并通过 LangChain BaseTool 抽象实现 App / Workflow 统一注入。

工具调用不是一个按钮​

工具调用至少包含四件事：

  • 工具的定义
  • 工具的注册
  • 工具的选择与参数生成
  • 工具的执行与结果回传

只要平台想支持不止一个工具，这四件事就都得系统化。

我会把它拆成六个部分​

1. 工具定义​

每个工具都要能被平台理解，而不是只靠代码约定。

  • 名称
  • 描述
  • 输入参数 schema
  • 输出结果结构
  • 权限要求
  • 是否支持异步

在这个项目里，Builtin Tool、API Tool、MCP Tool 最终都要落到统一的工具元数据和执行协议上。

如果工具定义不标准，Agent 很难稳定选择它，也很难稳定传参。

2. 工具注册与发现​

平台需要知道当前有哪些工具可用。

  • 是手工注册还是自动发现
  • 是按应用隔离还是全局共享
  • 是按角色授权还是按空间授权
  • 是否支持版本管理

API Tool 通过 OpenAPI Schema 导入，MCP Tool 通过 MCP Server 配置与工具发现进入平台；注册后要能给 App 和 Workflow 统一注入。

这一步不只是管理问题，也是平台边界问题。

3. 工具选择与参数生成​

Agent 不只是“会不会调用工具”，而是“什么时候调用哪个工具、怎么构造参数”。

这里通常要处理：

  • 选择策略
  • 置信度不足时的追问
  • 参数缺失时的补全
  • 错误参数时的重试

参数校验和调试运行是平台能力的一部分，不是开发者自己补的脚手架。

这一层做不好，调用会非常脆。

4. 工具执行​

真正执行工具时，平台要面对的就是工程问题了。

  • 超时
  • 重试
  • 幂等
  • 异常捕获
  • 网络失败
  • 第三方限流

这个项目里，工具执行要兼容 App / Workflow 两条链路，不是只服务单一 Agent 对话。

这部分不是附属能力，而是工具系统的底盘。

5. 结果回传与归一化​

工具返回的结果不能原样扔回模型。

平台通常还要做：

  • 结构化整理
  • 结果截断
  • 错误归一化
  • 敏感信息过滤
  • 供下一步推理使用的摘要化

同时还要支持给工作流节点和 Agent 事件流复用。

如果不做归一化，工具越多，Agent 越乱。

6. 审计与可观测​

工具调用一定要能被追踪。

  • 谁调用了什么工具
  • 什么时候调用的
  • 参数是什么
  • 返回了什么
  • 最终是否成功

没有这些记录，平台出了问题根本没法排查。

最容易掉坑的地方​

1. 把工具调用当成纯函数接口​

实际上它是“模型决策 + 平台编排 + 外部执行”的组合问题。

2. 工具越加越多，但没有统一规范​

最后会变成每个工具都能用，真正稳定复用的没有几个。

3. 只关注“能不能调通”，不关注“能不能长期维护”​

平台最贵的不是接通，而是后续的稳定性和治理成本。

我现在的判断​

如果要把工具调用做成这个平台能力，至少要做到：

  1. 工具定义标准化
  2. 调用链路可观测
  3. 执行结果可归一化
  4. 错误和权限可治理

做不到这些，工具调用就只是“演示效果”，不是平台能力。

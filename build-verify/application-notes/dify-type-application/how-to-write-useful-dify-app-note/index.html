怎么把一篇类似 Dify 的 Agent 平台文档写得真正有用

这一页不是在讲 Dify 怎么用，而是在给自己定一套写“类似 Dify 的 Agent 应用开发平台”笔记的标准。

目标很简单：以后写这类文档，不能只停留在“我搭了一个什么流程”，而要让人看完之后知道它为什么值得做、为什么能跑起来、功能是怎么被工程化拆开的、以及一扩展就会遇到什么问题。

先别从“功能清单”开始​

很多类似 Dify 的平台一上来就写：

  • 支持知识库问答
  • 支持工作流编排
  • 支持工具调用
  • 支持多模型切换

这种写法最大的问题不是不对，而是很容易把重点写丢。

因为它没有回答更关键的问题：

  • 它到底是在解决谁的什么任务
  • 哪个体验点才是真正的核心杠杆
  • 这些体验是靠什么组织方式撑住的
  • 它什么时候只是个 demo，什么时候已经开始变成一个要认真维护的系统

我会强迫自己从三个层面去拆​

1. 产品层​

先回答它为什么值得存在。

  • 它服务的是谁
  • 用户在什么场景下会来用它
  • 不用这类平台时，这件事原来怎么做
  • 它真正省掉的是时间、沟通成本，还是集成成本

如果这一层说不清，后面的流程设计大概率也会飘。

2. 体验层​

再去拆它为什么“看起来顺手”。

  • 哪个体验只是表层效果
  • 哪个体验其实来自提示词、上下文、拆步方式、反馈节奏或默认配置
  • 哪个点决定了用户会不会继续用下去

这一层如果只会写“交互顺畅”“结果不错”，基本等于没写。

3. 系统层​

最后才看它为什么“撑得住”。

  • 知识库怎么组织
  • 工作流怎么分层
  • 状态怎么传递
  • 工具调用怎么兜底
  • 运行态怎么保存
  • 失败怎么处理
  • 后续怎么维护和迭代

很多东西在 demo 里可以先不管，但只要你想长期跑，它们迟早都会回来。

每篇文档至少要回答这 5 个问题​

  1. 这个类似 Dify 的平台最核心的问题定义是什么
  2. 它最值钱的体验不是哪个按钮，而是哪一个机制
  3. 如果把模型能力当黑盒，真正决定效果的工程组织点是什么
  4. 它现在还只是 demo，还是已经开始出现平台复杂度
  5. 它最容易被高估的地方在哪里

如果这 5 个问题里有 3 个都答不上来，我宁可先不写正文。

我会优先采用的最小结构​

1. 这是什么应用，解决谁的问题​

一句话说清对象和目标，不绕。

2. 它最关键的体验杠杆是什么​

不要写“功能很多”，要写“哪个体验点让它成立”。

3. 这个体验背后的组织方式是什么​

把它拆回模块边界、数据流、状态、知识库、工作流和工具编排。

4. 它的边界和代价是什么​

别只写优点。要写哪里容易翻车，哪里最烧时间，哪里一扩展就会复杂。

5. 我的判断是什么​

最后必须给结论：

  • 值不值得做
  • 值不值得学
  • 值不值得继续投入

哪些写法我会主动避开​

  • 把 Dify 的功能页换个说法再写一遍
  • 用“大而全”的综述掩盖自己其实没判断
  • 只讲流程，不碰系统约束
  • 通篇都在夸，没有任何保留意见

一句自查​

如果把应用名字抹掉，这篇文档还能成立，那说明我大概率还没抓住它真正的特征。

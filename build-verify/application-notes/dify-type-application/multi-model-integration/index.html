Dify 平台的多模型集成实现

多模型集成不是把几个模型都接上就结束了。

这个项目里是通过 Provider-Model 两级抽象和 YAML 动态配置统一管理模型接入、能力标记和参数注入，同时支持用户级 API Key 隔离和多厂商模型灵活切换。

多模型集成不是一个下拉框​

它至少涉及：

  • 模型接入
  • 模型能力抽象
  • 路由策略
  • 成本控制
  • 失败降级
  • 结果一致性

如果只是让用户手动选模型，那还不算完整的多模型集成。

我会把它拆成六个部分​

1. 模型适配层​

不同模型的接口不一样，平台不能直接把所有调用写死。

  • Chat 接口
  • Completion 接口
  • Embedding 接口
  • Vision 接口
  • 工具调用接口

不同 Provider 的差异需要先收敛到统一适配层。

先做适配层，后面路由和调度才有统一入口。

2. 能力抽象​

平台要知道每个模型擅长什么。

  • 长上下文
  • 低成本
  • 高质量推理
  • 代码生成
  • 多模态

这个项目里模型能力会被标记到 Provider-Model 两级配置里，方便后续动态路由。

能力抽象不清楚，路由策略就没法写。

3. 路由策略​

真正的多模型集成，核心在路由。

  • 按任务类型路由
  • 按上下文长度路由
  • 按成本路由
  • 按失败回退路由
  • 按用户等级路由

路由不仅看效果，也要能配合 YAML 配置和用户级 API Key 做隔离。

这部分决定平台是不是“聪明地选模型”。

4. 成本与配额​

多模型一定会带来成本治理问题。

  • 每个模型的价格
  • 每个空间的预算
  • 每个用户的限额
  • 超额怎么处理

多厂商并存时，成本和配额也要落在统一治理层。

平台不管成本，最后就会变成谁都能用最贵的模型。

5. 失败切换与降级​

模型不是永远可用的。

  • 超时切换
  • 错误切换
  • 降级到更便宜模型
  • 降级到规则策略

这部分决定平台的稳定性。

6. 结果一致性​

不同模型输出风格不同，平台要尽量收敛结果格式。

  • 输出结构化
  • 结果后处理
  • 统一提示模板
  • 统一错误表达

否则用户会觉得平台“今天像一个产品，明天像另一个产品”。

最容易掉坑的地方​

1. 只做模型列表，不做路由​

这只是配置管理，不是集成能力。

2. 只考虑效果，不考虑成本​

平台越用越贵，会很快失控。

3. 只考虑主路径，不考虑失败​

多模型集成真正值钱的地方，往往在降级和兜底。

我现在的判断​

这个项目要把多模型集成做成能力，至少要做到：

  1. 统一适配
  2. 能力抽象
  3. 路由可控
  4. 成本可管
  5. 降级可用

做不到这些，多模型就只是“可以选很多模型”，不是集成能力。

Dify 平台的可视化工作流实现

可视化工作流之所以值得单独拆，是因为它不是“把节点拖一拖”这么简单。

这个项目里的工作流是基于 StateGraph 实现的，支持条件分支、并行汇聚，以及 LLM、检索、工具、HTTP、代码（云函数）、意图分类、模板转换等多类型节点。

工作流不是画图工具​

一个工作流能力至少要解决：

  • 怎么定义节点
  • 怎么连边
  • 怎么分支
  • 怎么运行
  • 怎么恢复
  • 怎么看执行结果

如果只有画布，没有执行语义，那只是流程图，不是工作流。

我会把它拆成六个部分​

1. 节点模型​

每个节点都要有明确的职责。

  • 输入节点
  • 模型节点
  • 工具节点
  • 条件判断节点
  • 变量处理节点
  • 结束节点

这个项目里还包括 HTTP 节点、代码节点（云函数）、模板转换节点、意图分类节点等更贴近实际落地的类型。

节点职责越清楚，工作流越不容易失控。

2. 连线语义​

线不是装饰，它代表控制流或数据流。

  • 顺序流
  • 条件流
  • 并行流
  • 回退流

条件分支和并行汇聚是这个项目里必须跑通的核心语义。

如果连线语义不统一，后面运行时会非常难维护。

3. 执行引擎​

工作流真正跑起来，靠的是执行引擎，不是画布。

  • 节点执行顺序
  • 中间状态保存
  • 失败重试
  • 分支选择
  • 异步节点等待

项目里通过 draft_graph / graph 双态隔离和调试发布门禁保障运行稳定性，因此执行引擎不仅要能跑，还要能区分编辑态和发布态。

引擎设计决定了它能不能稳定跑复杂流程。

4. 变量与上下文传递​

工作流最常见的问题不是“节点不够”，而是“数据传不过去”。

  • 输入怎么传到下游
  • 中间结果怎么引用
  • 哪些变量是局部的
  • 哪些变量是全局的

StateGraph 的状态流设计就是这部分的底座。

变量体系不清楚，工作流就会越画越乱。

5. 可视化编辑体验​

可视化不是炫技，是为了让复杂性可理解。

  • 节点是否好拖
  • 参数是否好配
  • 结果是否好调试
  • 执行路径是否好回放

编辑态和发布态要拆开，才能让调试和正式执行都清楚。

如果用户看不懂执行过程，这个工作流就不够实用。

6. 调试与回放​

工作流平台必须支持排查问题。

  • 看执行日志
  • 看每个节点输入输出
  • 看分支怎么被选中
  • 看失败发生在哪一步

没有调试能力，工作流就只能靠猜。

最容易掉坑的地方​

1. 只做静态编排，不做运行时​

画出来了不代表能跑。

2. 只支持简单串行，不支持复杂分支​

一旦项目复杂一点，能力就不够用。

3. 只追求“好看”，不追求“好排查”​

工作流真正的价值常常在排查和迭代阶段。

我现在的判断​

这个项目里的可视化工作流如果要成为平台能力，至少要做到：

  1. 节点语义明确
  2. 连线语义统一
  3. 执行引擎稳定
  4. 变量传递可控
  5. 调试回放完整

否则它只会是一个“看起来很强”的流程编辑器。

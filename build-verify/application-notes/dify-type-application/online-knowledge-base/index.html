Dify 平台的在线知识库设计

如果平台想把“知识库”做成一个真正可用的能力，而不是只是一个上传文档的入口，那它就不能只停留在检索结果展示。

这个项目里的 RAG 是全链路能力：文档上传、解析、切分、关键词抽取、向量化、召回与融合都要打通，并且检索能力要 Tool 化，能复用到 Agent 与 Workflow 里。

在线知识库不是文档附件​

在线知识库至少要解决四件事：

  • 知识接入
  • 知识处理
  • 知识检索
  • 知识更新

如果只是“能上传文件”，那还不算知识库，只能算内容存储。

我会把它拆成六个部分​

1. 知识接入​

知识是从哪里来的，决定了后面的处理方式。

  • 手动上传
  • URL 抓取
  • 内部文档同步
  • 第三方系统同步
  • API 写入

这个项目里，知识库要同时服务 Agent 和 Workflow，因此接入后的结构化信息要尽量稳定。

不同来源对应不同的增量更新、权限和格式处理策略。

2. 切片与结构化​

原始文档不能直接拿去检索。

平台至少要处理：

  • 分段
  • 标题层级
  • 表格和列表
  • 代码块
  • 元数据保留

后续还要支持关键词抽取，为混合检索做准备。

切得不好，后面的召回和引用都会变脆。

3. 索引与检索​

知识库的核心不是“存了什么”，而是“能不能准确找回来”。

  • 向量检索
  • 关键词检索
  • 混合检索
  • 过滤条件
  • 权限过滤

这个项目里需要同时支持 Weaviate 语义检索、关键词倒排检索与混合检索，并把 Faiss 作为可选向量能力的一部分。

这里要关注的不只是算法选择，还有索引更新、查询延迟和召回稳定性。

4. 结果重排与引用​

检索结果不是查出来就完了。

平台还需要做：

  • 相关性重排
  • 去重
  • 结果摘要
  • 引用来源标记
  • 结果拼装给 Agent

检索结果还要能以 Tool 的方式提供给 Agent 和 Workflow 节点。

如果没有引用链路，用户就很难信任回答。

5. 增量更新​

在线知识库最麻烦的是“会变”。

  • 文档内容更新
  • 旧片段失效
  • 索引重建
  • 版本对齐
  • 缓存刷新

如果增量更新处理不好，平台会慢慢变成“看起来有知识，实际上已经过期”。

6. 权限与隔离​

知识不是公共资源。

  • 谁能看
  • 谁能查
  • 哪些知识只属于某个应用
  • 哪些知识可以跨项目复用

这部分一旦设计差了，平台会直接碰到数据治理问题。

最容易掉坑的地方​

1. 只关注召回，不关注引用​

召回到内容不等于用户能信任内容。

2. 只做一次性导入，不做增量更新​

知识一旦过期，平台就会开始失真。

3. 只解决中文文档，不考虑混合格式​

真实场景里，PDF、表格、网页、代码和 Markdown 往往是混着来的。

我现在的判断​

这个项目要把在线知识库做成能力，至少得做到：

  1. 多来源接入
  2. 可控切片和索引
  3. 可解释检索和引用
  4. 可增量更新
  5. 可权限隔离

做不到这些，知识库就很难成为 Agent 的稳定支撑。

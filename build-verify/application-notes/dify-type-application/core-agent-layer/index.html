平台的核心 Agent 层

这一篇不讲抽象 Agent 概念，只讲这个项目里真正落地的执行层。

项目里 Agent 层是基于 LangGraph 设计的，核心是 Function Calling / ReAct 双模式执行链路：按模型能力自动切换，统一输出推理、工具调用、检索、错误、停止等事件流，并支持会话级中断和前端推理过程可视化。

先把 Agent 层说清楚​

这里的 Agent 层，不是“接一个大模型接口”这么简单。

它更像是平台里的运行中枢，至少要处理下面几类事：

  • 接住用户输入
  • 组织上下文和状态
  • 决定下一步要不要调用工具
  • 调度一次或多次模型推理
  • 统一事件流输出给前端和调试层
  • 管住中间结果、最终结果、停止和失败路径

如果这一层没拆清，后面的工作流、工具调用、知识库和权限控制都会变成散的。

我会把它拆成五个子块​

1. 输入与运行态​

Agent 每次运行都不是孤立的一问一答，而是一个带状态的过程。

  • 当前会话是谁
  • 这次任务的目标是什么
  • 上一轮已经做到了哪里
  • 本轮输入和历史上下文怎么拼接
  • 会话级中断后如何恢复当前执行位置

这一块决定了平台是不是“真的能继续做事”，而不是每次都像重新开始。

2. 决策与调度​

Agent 层最关键的不是“会不会回答”，而是“下一步做什么”。

  • 直接回答
  • 先检索知识
  • 先调用工具
  • 先追问澄清
  • 先进入子任务

项目里这一步由 LangGraph 承接，双模式链路会根据模型工具调用能力自动分流。

这本质上是一个调度问题，不只是生成问题。

3. 计划与执行​

一旦需要多步推理，Agent 层就不能只产出一段文本。

它至少要能表达：

  • 当前计划
  • 已执行步骤
  • 正在等待的外部结果
  • 失败后的回退策略

执行过程中，推理、工具、检索、错误、停止都会被统一封装成事件流，给调试和前端可视化用。

这也是很多平台从 demo 走向可用时最容易欠账的地方。

4. 记忆与上下文​

Agent 层必须明确哪些东西是短期上下文，哪些东西要落成长期记忆。

  • 短期上下文：本次任务内要用的输入和中间结果
  • 长期记忆：用户偏好、项目设定、常驻知识、可复用状态

这个项目里短期侧通过 token 限额裁剪历史上下文，长期侧通过会话摘要增量更新并在推理前注入系统上下文；摘要生成由后台异步执行，避免阻塞主对话链路。

如果这层不清楚，平台很容易出现“看上去像记住了，实际上只是碰巧命中了上下文”的假象。

5. 观测与控制​

只要平台开始支持真实任务，Agent 层就必须可观测。

  • 这次调用了什么模型
  • 中间做了几次推理
  • 哪一步触发了工具
  • 哪一步失败了
  • 为什么最后给出这个结果

这也是前端做推理过程可视化、会话级中断和调试回放的基础。

没有观测，就没有稳定迭代。

这一层最容易被高估的地方​

很多人会以为 Agent 层主要是提示词工程。

实际上更难的是：

  • 状态怎么管
  • 调度怎么定
  • 上下文怎么裁剪
  • 多步执行怎么落地
  • 异常怎么恢复

提示词只是入口，运行时才是核心。

我现在的判断​

如果要手搓这个平台的 Agent 层，至少要做到三件事：

  1. 能跑多步任务
  2. 能保存并恢复运行态
  3. 能把决策过程记录下来

做不到这三件事，平台就很难从“聊天包装器”进化成真正的 Agent 开发平台。
